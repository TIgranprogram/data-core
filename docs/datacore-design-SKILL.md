# Дизайн интерфейса (data-core)

Единственный источник правды по виду — `docs/DESIGN.md`; законы — `docs/CANON.md` §2. Этот скилл — порядок работы.

## 1. Перед правкой
1. Прочитай `docs/DESIGN.md` §1–§4 (характер, токены, раскладка, каталог). Не читай `base.css` целиком — ищи нужный класс grep'ом.
2. Определи: это **значение** (цвет/размер/отступ) → токен из §2; это **элемент** → компонент из §4; нет нужного → расширяй общий компонент (`ui/base.css`, `ui/*.js`), не раздел.
3. Жалоба пользователя «сливается / не отличить» — почти всегда иерархия: проверь, что заголовок отличается размером + жирностью + цветом `--heading` (§2.1), а соседние значения разделены промежутком.

## 2. Правка
- Цвета и размеры — только `var(--…)`. Новый токен → в `tokens.css` в **обе** темы (`:root` и `:root[data-theme='dark']`), контраст ≥ 4.5:1 посчитать и вписать в DESIGN §2.3.
- Заголовки — только `h1`/`h2`/`h3` (размеры задаёт `base.css`).
- Файлы в репо с CRLF — при правке скриптом сохраняй окончания строк (иначе дифф на весь файл).
- Service worker держит оболочку по версии `version.json` (её кладёт выкладка): после выкладки новая версия подтягивается сама, на стенде (без version.json) — «сеть, иначе кэш». Версию кэша вручную менять не нужно.

## 3. Проверка
1. Чек-лист `docs/DESIGN.md` §6 — пункт за пунктом.
2. Снимки (DESIGN §7): ширины 1920 и 390 минимум (лучше 2560/1920/1024/390), обе темы, «Сегодня», «Заявки» (+ открытая карточка, доска), «Остатки», «Операции».
3. Открой png и посмотри глазами — не говорить «готово» без этого (CANON §1, §6).

## 4. После
- Новое решение по виду → строка в `docs/DESIGN.md` §8 «Журнал решений»; новое правило → CANON §2.
- Пользователю — человеческими словами: что стало видно лучше и где посмотреть (CANON §1).
