# Аудит агентной системы проекта (только факты + структура, без правок)

Ты работаешь в этом репозитории. Твоя задача — **обследовать**, как устроены агенты, оркестрация, промпты, память и правила проекта. **Ничего не меняй, не рефакторь, не «улучшай» файлы.** Только анализ и отчёт.

Если чего-то нет — пиши явно: `НЕТ`. Если не уверен — `НЕИЗВЕСТНО` + что нашёл. Не выдумывай агентов и пайплайны.

## Часть A — Найди и перечисли артефакты

Ищи по репо (и типичным местам) всё, что связано с агентами/AI-настройкой, например:
- `.claude/`, `CLAUDE.md`, `.clauderules`, `AGENTS.md`, `.cursorrules`, `.cursor/`, `.github/copilot*`
- `agents/`, `prompts/`, `rules/`, `orchestrat*`, `workflows/`, `playbooks/`
- `*agent*.md`, `*prompt*.md`, `*system*.md`, `*persona*.md`, `*company*`
- MCP/tools конфиги, hooks, scripts, Makefile targets, CI jobs, связанные с AI
- README/docs про «команду агентов», «компанию», роли

Для каждого найденного файла/каталога:
1. Путь
2. Назначение (1 строка)
3. Размер грубо: число строк или «короткий/средний/длинный»
4. Кто его, похоже, читает при старте (всегда / по задаче / вручную)

## Часть B — Карта «компании» агентов

Если есть роли/агенты (как «сотрудники компании»), опиши таблицей:

| ID/имя | Роль | Триггер (когда вызывается) | Входы | Выходы | Инструменты/права | Системный промпт (файл + ~токены/строки) | Кого вызывает дальше |

Отдельно укажи:
- Кто **оркестратор** (единая точка входа)?
- Есть ли жёсткий pipeline (последовательность шагов) или свободная маршрутизация?
- Есть ли параллельный запуск агентов?
- Есть ли critc/reviewer/qa агент и обязателен ли он?
- Есть ли «менеджер», который только декомпозирует и не пишет код?

## Часть C — Оркестрация и маршрутизация

Ответь точно:
1. Как выбирается агент на задачу? (ручной @, keywords, LLM-router, всегда full-company, другое)
2. Тянется ли в контекст **сразу вся компания** или только нужная роль?
3. Есть ли лимит: «на задачу max N агентов»?
4. Передают ли агенты друг другу **полный** диалог/дифф или **сжатый brief** (summary, checklist, paths)?
5. Есть ли stop-условия (DoD): когда pipeline останавливается без лишних кругов?
6. Есть ли циклы «review → fix → review» и ограничение итераций?
7. Дублируют ли агенты одну работу (например, двое пишут код / двое ревьюят одно и то же)?

## Часть D — Контекст, память, токены

1. Что автоматически попадает в контекст каждой сессии/агента? (корневые MD, дерево файлов, git status, lints, тесты, вся docs/)
2. Какие инструкции **дублируются** в нескольких файлах (скопируй пересечения коротко)?
3. Есть ли разделение: always-on rules (короткие) vs on-demand playbooks (длинные)?
4. Есть ли memory/notes между сессиями (project memory, scratchpad, ADR, decision log)? Что туда пишется и не раздувается ли?
5. Есть ли шаблоны **минимального brief** между агентами (цель, constraints, files in scope, out of scope, acceptance)?
6. Оценка: какие 3 вещи сейчас, похоже, **съедают больше всего токенов** и почему?

## Часть E — Качество и границы (без ухудшения продукта)

1. Как зафиксированы: стек, architecture boundaries, style, security, testing, definition of done?
2. Где это лежит и **в каком объёме** (кратко / простыня)?
3. Есть ли запреты: «не трогать X», «не читать monorepo целиком», «минимальный diff»?
4. Как проверяется результат: тесты, lint, typecheck, preview, checklist — человеком или агентом?
5. Есть ли разделение агентов: plan-only / code / test / review / docs (или все в одном)?

## Часть F — Реальные сценарии использования

Опиши 2–3 **типичных** потока «как сейчас реально работают» (не идеал):
- Пример: «фича» → какие агенты → какие файлы контекста → сколько примерно фаз
- Пример: «багфикс»
- Пример: «ревью/рефакторинг»

Для каждого: где вероятны лишние токены (лишний контекст, лишние агенты, повторное чтение одних и тех же docs, длинные статусы).

## Часть G — Инвентаризация промптов

Список всех system/role prompts:
- путь
- ~строк
- must-keep 20% смысла (3–7 буллетов)
- что выглядит redundancy/water

## Часть H — Жёсткие ответы-резюме (кратко)

1. Модель оркестрации одной фразой
2. Главный антипаттерн по токенам
3. Главный риск для качества, если просто «вырезать агентов»
4. Что уже сделано хорошо (не ломать)
5. Список файлов-источников, на которых основан отчёт

## Формат ответа
- Пиши структурировано по разделам A–H
- Без предложений «я могу сейчас всё переписать…»
- Без правок файлов
- В конце: блок `OPEN QUESTIONS` — вопросы ко мне как к владельцу, только если без ответа нельзя понять runtime-поведение (макс 8 вопросов)

Цель аудита: потом по твоему отчёту настроим агентов так, чтобы **минимум токенов на оркестрацию/контекст**, без падения качества кода и сайта.
