# CONTRACT-MATCHING — сопоставление позиций договора с продукцией (analyst, 2026-10-29, XL)

## 1. Как сейчас
- Договор = `salesorders` (`orderNo`, `customer`, `productionNo`, `stage`). Позиции договора = `incomes` (`orderId` → договор; `title` — текст заказчика; `productId` — необязательная ссылка на изделие) — `income.schema.ts:20-33`.
- Договор → заказ производства: «заказ» — это общий `productionNo` у договоров. `POST /production-orders/assign` (`production-orders.service.ts:81`) ставит `productionNo`; проверка только «договор найден / не занят» (`checkAssign`, :85). Позиции не проверяются.
- `productId` заполняется в трёх местах:
  1. при создании позиции в приложении — `productByTitle` (`incomes.service.ts:178`, вызов :244): точное совпадение `shortProductName(title)` с `products.name` без регистра. Любое отличие в слове — связи нет;
  2. кнопка «Из заказов» (`showcase.service.ts:433-481`): создаёт черновики изделий из названий и ставит `productId` позициям без связи;
  3. вручную: `PATCH income {productId}` (менеджеру разрешено даже после формирования заказа, `incomes.service.ts:24`).
  Импорт из Google-таблицы (`sheets-sync.mapping.ts:54`, лист «Заказы») `productId` не ставит вообще: ссылки нет, пока кто-то не нажал «Из заказов».
- Почему «Открыть заказы» даёт 0: пункт меню строки продукции `products.js:373` делает `go('salesorders', { q: row.name })`. Это поиск по ДОГОВОРАМ: `orderNo, customer, title, contractNo, productionNo, notes` (`salesorders.service.ts:80`). Названия изделий в позициях (`incomes.title`) он не смотрит, `productId` тоже. Поэтому не находит даже связанное изделие. Блок «Где в заказах» в карточке изделия (`showcase.service.ts:246-251`) ищет верно (`productId` ИЛИ точное название) — там 0 только если связи нет и название чуть иное.
- Гипотеза пользователя верна для обоих: связь пустая, потому что в договоре другое название. Но кнопка из меню сломана независимо — даже при полной связи.

## 2. Где пользователь прав, где нет
- Прав: сопоставление нужно до заказа; автопредложение + подтверждение; блок «нельзя в заказ без сопоставления»; кнопка «Перейти к сопоставлению».
- Не совсем: «правится только в договоре». Допсоглашения (новые/изменённые позиции) приходят после формирования заказа; правка нужна и там. Решение: править можно, но позиция-новичок или с изменённым названием снова «не сопоставлена» и подсвечивается в заказе; в заказе остаётся только сопоставление, цена/кол-во — по правилам Ф-4 (admin).
- Не нужно: ломать «позиции без изделия» — услуги, доставка, монтаж. Нужен статус «не изделие», иначе блок не пройти (см. п. 3).

## 3. Поля и справочник
Общие с CRM коллекции — только необязательные поля. Для `incomes` (проверить по `UNIFIED-DB-MAP`; в CRM читается как доход) добавляем:
- `matchStatus`: `auto` (предложено системой, не подтверждено) | `confirmed` | `none` («не изделие»: монтаж, доставка);
- `matchedAt`, `matchedBy`. `productId` остаётся как есть (CRM его не знает — безопасно).
«Сопоставлено» = `matchStatus` in (`confirmed`,`none`) и (для confirmed) `productId` есть. Старые позиции с `productId` и без статуса считаются сопоставленными (меньше шума), но показываются в плане п. 6 как «проверить».
Справочник соответствий — ДА, новая коллекция data-core `productaliases` (`key` = нормализованное короткое название из договора, `productId`, `count`, `lastAt`). Нужен, чтобы второй раз та же формулировка предлагалась сразу с высокой уверенностью. Записывается при подтверждении. Не общая с CRM — риска нет.
ТИ-8 (три названия): `incomes.title` остаётся неприкосновенным снимком заказчика («название в договоре»); `products.name` — короткое; `products.orderName` (уже есть, `product.schema.ts:26`) — «как в заказе» — участвует в поиске совпадений наравне с `name`, `fullName`, `sku`. Новых полей названия не нужно. Подтверждённое название можно предложить дописать в `orderName` (кнопка, не автомат).
Нечёткий поиск: токены без регистра/ё/знаков (есть `search-norm`), совпадение артикула (`sku` в тексте) = высшая уверенность, затем пересечение токенов (Jaccard) с порогом; показать топ-3 с процентом словами («почти наверняка / похоже»). Автоподтверждения нет: только `auto` → человек жмёт.

## 4. Где экран
Решение: НЕ отдельный раздел, а вкладка «Без заказа / К сопоставлению» внутри «Заказы производства» (рядом с уже сделанным списком `unassigned`) + плашка в самом договоре. Причины: меню и так перегружено; шаг идёт в одном потоке «договор → сопоставить → в заказ»; данные те же. Если позже вырастет — выделить.
- Список «Без заказа»: у каждой строки бейдж «сопоставлено 3 из 5». Кнопка «В заказ» неактивна для неполных, под ней подсказка «Сначала сопоставьте позиции» + «Перейти к сопоставлению».
- «Сопоставление» — правая панель договора (ввод только справа): строки позиций, у каждой предложения (топ-3, процент), «Подтвердить», «Выбрать вручную» (поиск по продукции), «Это не изделие», «Создать изделие» (черновик, как «Из заказов»). Кнопка «Подтвердить все уверенные».
- Исправить меню продукции: «Заказы с этим изделием» → отбор договоров по `incomes.productId` (новый фильтр `productId` в списке договоров), а не текст `q`.

## 5. Блокировка
Сервер: `assign` в `production-orders.service.ts` перед записью (после :87) собирает позиции выбранных договоров; если есть несопоставленные — 400: «Договор № X: не сопоставлено N из M позиций («Трибуна…», …). Сопоставьте их в разделе Заказы → Без заказа → Сопоставление». Все договоры сразу, до 5 названий на договор. Ответ содержит `unmatched: [{orderId, lines[]}]` для кнопки. Договор без позиций — тоже 400 («нет позиций»)? По умолчанию: да. Добавление существующего договора в заказ идёт тем же `assign`, правило общее. Договоры, уже имеющие `productionNo`, не трогаем (иначе встанет текущая работа).

## 6. Перепривязка старых данных (прод)
Только после «да» пользователя, на копии/плане; скрипт `backend/scripts/` по образцу `fromOrders(apply)`:
1. План (apply=false): для всех позиций без `productId` — предложения, группировка по нормализованному названию (одна группа = одно решение для N позиций), уверенность; позиции с `productId` без статуса — отдельный счётчик. Выгрузка отчёта, ничего не пишется.
2. Пользователь смотрит группы в экране сопоставления (тот же код), подтверждает; автоприменение — только для точных (совпадение ключа/артикула), остальное вручную.
3. apply: пишет `productId` + `matchStatus` позициям только где `productId` пуст (как :481), аудит, количество в отчёт; резервная копия коллекции `incomes` перед запуском (`backup.sh`). Откат: сохранённый список `_id → старое состояние`.
4. Договоры, уже ушедшие в заказ, не блокируются; сопоставление нужно им только для «Открыть заказы».
