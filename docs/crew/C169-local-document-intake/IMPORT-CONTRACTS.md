# C169 — контракты импорта и подтверждения

Исходный аудит до реализации C169; новые устойчивые маршруты описаны в SUPPLIER-IMPORT.md и IMPLEMENTATION.md. Старую цепочку C157 для автоматической загрузки не использовать.

Маршруты ниже под `/api`. Сверены локальный код и контракты C157/C164. Записи требуют разрешённого менеджера с доступом к разделу и денежным данным.
- **Общее.** До записи сохранить SHA-256 оригинала, UID документа и каждого шага, неизменный запрос, ожидаемого владельца. Проверить активные и удалённые совпадения по SHA и ключу «ИНН сторон, тип, полный номер, дата, редакция». ИНН и полный номер сверять после поиска, сохранять суффиксы. Совпавший SHA без подтверждённой связи, удалённый дубль и расхождение → «Сомнительные».
- **Файл.** Загрузить через `POST /photos/upload` с multipart `file`. Доказательство дают `GET /photos/:id` и SHA скачанного оригинала по `storageUrl`. Для C164 сервер дополнительно сверяет байты с `sourceSha256` при привязке. Существующий подтверждённый `fileId` переиспользуется только при доказанной связи с владельцем.
- **Пробел загрузки.** Текущий multipart не даёт чтения результата по UID/SHA. Общий `Idempotency-Key` кеширует ответ асинхронно и не включает multipart-байты в отпечаток. Сохранить полученный `fileId` до привязки. Если ответ потерян и ID невозможно доказать, остановиться в «Разбираются» до сверки. Для автоматического восстановления свежих загрузок нужен устойчивый UID/квитанция с чтением результата.
- **Счёт поставщика.** `POST /supply/requests` создаёт строки (`clientUid`, `title`, `qty`, `unit`, проверенный `supplierId`, `companyName`, `priceHint`). `POST /supply/invoices {requestIds}` создаёт черновик транзакционно и возвращает существующий счёт для того же полного набора. Заголовок через `PATCH /supply/invoices/:id` (`no,date,payerCompanyId,currency,fileIds`, известные НДС/курс), строки через `PATCH …/lines/:lineId` (`version`, исходные цены/суммы и налог по DTO). `issue:true` после сверки номера, даты, плательщика и суммы строк.
- **Пробел C157.** Создание заявки проверяет `clientUid` без уникальности и хеша, шапка не принимает ожидаемую версию, список `/supply/invoices` видит активные счета. Поиск удалённых заявок `/supply/requests?deleted=1&search=…` помогает ручной сверке, покрытие удалённых шапок не гарантирует. Общая атомарность, серверный ключ источника и безопасная запись новой редакции отсутствуют. Автоматический импорт новых счетов по этому пути пропустить. Для доказанного дубля перечитать карточку, строки, файл и суммы.
- **Договор покупателя.** `POST /salesorders` с `companyId,counterpartyId,customer,orderNo,contractDate,intakeUid,productionAssignment:'unassigned',initialLegal`. В исходных строках `POST /incomes` передать `orderId,clientUid,matchingMode:'manual',sourceLine` (`documentUid,rowKey,title,qty` и подтверждённые реквизиты), согласованные `title,qty,unit` и `unitPrice` либо `amountManual`. Не выбирать `new_product`. Для строк валютного договора API требует отдельного рублёвого основания.
- **LegalBundle.** Для исходных договора/КП `state:'draft',origin:{kind:'source_import'},currency,sourceDate,companySnapshot,counterpartySnapshot` с именами и ИНН, `signature:{state:'unknown'},paymentVerification:'unknown',documents,issues,paymentPlan`. У договора обязателен `sourceNumber` как `orderNo`, у КП допустим отсутствующий печатный номер. Основной документ требует `uid,kind,revision,fileId,sourceSha256`. Блокирующие неизвестные поля → «Сомнительные», допустимые пропуски → `issues`.
- **КП.** `POST /offers` с `companyId,customer,date,intakeUid,initialLegal,items`, `counterpartyId` при доказанной связи и `sourceNumber` при наличии. Поля строк `productName,quantity,unit,unitPrice,sourceRowKey,sourceLine`. Сверить исходный `gross`, сумму строк и согласованный состав. `/offers/intake` разбирает текст. Доказанная связь с имеющимся договором через `POST /offers/:id/link-order {orderId,version,clientUid}`.
- **Счёт покупателю и акт.** Добавить в доказанный существующий комплект договора через `PATCH /salesorders/:id/legal {version,clientUid,reason,legal}` запись `kind:'customer_invoice'|'acceptance'`, с UID, редакцией, ID файла и SHA. Сохранить прежние записи. Добавить номер, дату, суммы и ссылки на строки при наличии. Новая редакция с `supersedesUid`. Самостоятельного импорта, глобальной уникальности вложения и отдельного хранения строк счёта/акта здесь нет. Без однозначной связи или существующего комплекта → «Сомнительные».
- **C164 и повторы.** Создание договора/КП и строк защищают уникальные ключи и сравнение хеша. Смена UID при том же бизнес-ключе и содержимом возвращает исходный ID. Удалённое совпадение или новый payload → 409, неподготовленный индекс → 503. Legal PATCH фиксирует версию, историю и квитанцию одной записью. Файл, шапка и строки единой транзакции не имеют, частичный договор остаётся черновиком.
- **Подтверждение C164.** После записи перечитать `GET /salesorders/:id` или `GET /offers/:id`, сверить реквизиты, состав, суммы, UID/версию, связанный файл и SHA. Отдельно проверить отсутствие новых платежей. Перед записью проверять legacy/корзину по доступной выдаче `/salesorders?search=…&deleted=1` и `/offers?q=…&deleted=1` и активным спискам. У старых КП поиск идёт по внутреннему номеру, клиенту и названию, точного lookup по SHA/печатному номеру нет.
- **Граница MVP.** Сквозная запись C164 доступна для подготовленных оригиналов с доказанным `fileId`, проверенными реквизитами и доступными индексами. «Готово» требует перечитанного результата или доказанного неизменного дубля. В обычном импорте исключить маршруты оплат, приёмки, конверсии КП и производства. Подтверждение оплаты без дня — отдельный C165 с доказательством полной RUB-оплаты, `{clientUid,version,reason,fileIds?}` и без проводки.
