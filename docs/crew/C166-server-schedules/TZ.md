## Решение и контракт
Раздельные настройки. Данные: включено/пауза, режим interval или daily; интервал в минутах либо время и дни недели. Версия: включено/пауза, время и дни недели; операция честно называется «Код и данные», поскольку совместимость нового кода со старой схемой отдельно не доказана. Часовой пояс Europe/Moscow явно виден.
Предлагаемый рабочий график после проверки и сохранения: данные15мин, код+данные ежедневно03:00МСК. До явного сохранения сохраняется legacy env/default15мин и ручной код, чтобы обновление backend само не запускало новый опасный сценарий. Текущее поручение разрешает настроить согласованный выше график после готовности; домен при этом не переключается.
GET /api/control/switch/schedule admin:
{revision,timezone:'Europe/Moscow',data:{enabled,mode:'interval'|'daily',intervalMinutes,time:'HH:mm',days:[1..7]},code:{enabled,time:'HH:mm',days:[1..7]},runs:{data:{lastAttemptAt,lastSuccessAt,lastState,lastError,nextRunAt},code:{lastAttemptAt,lastSuccessAt,lastState,lastError,nextRunAt}},canEdit,reason?}.
PUT того же пути принимает {expectedRevision,timezone,data,code}; ожидаемая ревизия обязательна, конфликт409, вложенные DTO whitelist, только администратор главного в normal/idle. days ISO1=понедельник, уникальные1..7, enabled с пустыми days недопустим; interval 5..1440 целое, HH:mm строгий24h. Отключённое enabled:false сохраняется явно. PATCH иных полей запрещён.
Хранение в существующем SwitchDoc: scheduleConfig {revision,timezone,data,code,savedAt}, scheduleRuntime (курсор/ключ/последняя попытка/успех/ошибка/nextRetryAt по data/code). Поля новые, прежний контракт сохранён. Runtime целевого сервера не перезаписывается при restore: мост сохраняет/возвращает только scheduleRuntime, конфигурация переносится с главного.
Существующий GET /control/switch дополняется domain:{owner:'home'|'office'|null,homeHealthy:boolean|null,officeHealthy:boolean|null,checkedAt:string|null} и switchReadiness:{state:ready|blocked|unknown,reasons:string[]} с понятными причинами. runs.lastWarning optional отдельно от lastError; PUT может вернуть GET-view, UI после сохранения повторяет GET. Bridge report принимает optional domain (owner nullable строго enum, датыISO), хранит его только через прежнюю host-secret защиту. Ошибка statusVPS — unknown, старое успешное состояние не выдаётся свежим. Нового публичного shell/proxy endpoint нет.
POST /control/switch/refresh сохраняет confirm:true, optional scope:'data'|'both' (default both), отдельный RefreshSwitchDto; старые клиенты совместимы. job хранит refreshScope и optional schedule keys. kind/request/code=0 совместимы со старым bridge. Ручные кнопки используют те же проверки и общий job.

Владение только backend/src/modules/control/switch/** и backend/test/e2e/control-switch*. Новые небольшие helpers schedule.rules/service допустимы, не раздувать SwitchService. Постоянный CAS: проверяются revision/role/mode/idle/слот одновременно с записью job и захватом расписания; два процесса не стартуют одинаковый слот. Выполнение по Москве, days и времени; interval/daily, выключено, смена настроек, рестарт, skip-busy, один актуальный запуск вместо очереди пропущенных. Ночной слот допускает задержку до30мин, после этого не догоняется днём. Повтор ошибки ограничен/backoff внутри разрешённого окна; незавершённый restore/code/VPS автоматически вслепую не повторять.
Mongo→request разрыв: job queued хранит scope/слот, после рестарта доставка идемпотентна (тот же id); не заменять чужой request/current, нужен reconcile. Ошибка доставки сохраняет failed/error, не стирает след. report/staleReason доводят расписание до результата. Сохраняются warning отдельно от state=done.
POST start повторно проверяет реальную peer health/свежесть checkedAt/возраст копии/известные совпадающие версии/role/mode/idle/bridge/domain owner. UI не является защитой. Неизвестное и устаревшее — отказ с причиной, включая canStart=false. Чужое владение доменом запрещает плановый refresh. Emergency остаётся отдельным ручным подтверждённым путём, не добавлять autofailover.
Тесты реальных гонок/CAS, TZ/дни/late-window/рестарт/ошибки/busy, 400/403/409, legacy env/API и неизвестной готовности. Не использовать production Mongo.
