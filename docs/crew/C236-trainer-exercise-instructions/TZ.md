# C236 — подробные инструкции упражнений в паспортах тренажёров

Дата: 23.11.2026. Статус: **требования подготовлены; заполнение и реализация не начинались**.

Пилоты выбраны владельцем: 1067 «Жим ногами Новый», 1068 «Велосипед Новый», 1069 «Скороход двойной Новый». Выполняется чтение источников и подготовка кандидатов; [состояние трёх карточек](PROD-PILOTS.md). Исполнение «Новый» требуется сверить с исходными папками. Прод и выданные паспорта пока не менялись.

Последующее уточнение владельца: «папки тебе не нужны — бери просто артикулы». Идентификация пилотов — по артикулам 1067–1069 и действующим карточкам; путь к папкам не запрашивать повторно. Недостающие в карточках характеристики нельзя подменять выдуманными числами или особенностями механизма. Черновики готовить на основании типа изделия и проверенных источников, отдельно отмечая непроверенные детали.
Основание: владелец хочет инструкции как на примере — исходное положение, движения и задействованные мышцы — и спрашивает, что заполнить или доработать.

Класс текущего шага: S, анализ требований. Код, данные рабочего сайта и паспортный стандарт не меняются. Потенциальная реализация: сначала существующие тексты; M при небольшой правке выбора/представления, L только при доказанной необходимости межмодульной структуры. Класс и ответственных уточнить после адресной проверки первого эталона; новую сущность заранее не назначать.

## Границы и источники

- [C235 REPORT](../C235-product-usage-texts/REPORT.md): карта существующих полей, справочников и сборки текста. [PROD-SAMPLE](../C235-product-usage-texts/PROD-SAMPLE.md): проверен только «Вело», артикул1068, ID6aff34a8e27fdcbff25a0c9e; остальные изделия не обследованы.
- [PASSPORTS-STANDARD](../../PASSPORTS-STANDARD.md): ПС-05 — применимые подтверждённые источники и приоритет своих текстов; ПС-07 — редакции действующих выпущенных документов; ПС-10 — чтение/печать без миграции старых экземпляров. Стандарт ещё на независимой приёмке; C236 не закрывает C173 и весь раздел паспортов.
- PRODUCT §5а: назначение/тексты из изделия и справочников, ручное значение главнее автоподстановки. Общий принцип: одно место хранения, повторное использование через проекции.
- Скриншот задаёт состав информации, а не достоверное упражнение для другого изделия. Техника и мышцы для конкретной модели не выводятся из внешнего сходства.

**Не входит:** массовое заполнение каталога/прода, новый номер или выпуск паспорта, массовая правка ранее выданных, новая программа тренировок/медицинские рекомендации, отдельная публикация внешнего сайта. Любая будущая запись/выкладка — в согласованном объёме отдельного шага.

## Подтверждённое текущее состояние

Есть `products.description`, `purpose`, признаки изделия `facetValueIds`; типовые фразы назначения по применимым признакам. Есть раздел дерева текстов `use` («Правила пользования») с применимостью по признакам/группам и собственными формулировками; у функциональных элементов — `usageRules` как последовательность строк. Сервер собирает `textSnapshot.purpose`, `rules`, `sections` и отдаёт short/full проекции шаблона. Существование этих полей не означает готовую библиотеку упражнений.

В проверенном «Вело1068» description/purpose пусты, rules=[],readiness=false; в use15общих пунктов безопасности и служебный маркер maxUsers. Материалы, назначение, элементы, установка, maxUsers, площадка, соединения не заполнены. Это неполный пилот, а не готовая инструкция. Слова «Вело» и фотография не доказывают схему движения, мышцы, число пользователей, исходное положение или ограничения.

## Вариант A — заполнение без новой модели данных, предпочтительный

Цель: для одной подтверждённой модели менеджер получает в существующем разделе пользования связную инструкцию и краткое назначение.

1. Установить точную модель/исполнение: изделие, артикул, паспортная категория, вид, применимые функциональные элементы, число рабочих мест. Данные брать из действующей конструкторской/эксплуатационной документации или от ответственного конструктора. Сведения разных исполнений не объединять по похожему названию.
2. Заполнить `purpose` кратким подтверждённым назначением; группы мышц включать только если источник это подтверждает. `description` описывает устройство, а не заменяет технику выполнения упражнения. Не дублировать подробные движения одновременно в purpose и правилах.
3. Для упражнения подготовить утверждённый блок: название упражнения/рабочего места; «Исходное положение»; нумерованная последовательность движений; «Задействованные мышцы». Дополнительные ограничения/ошибки техники включать только из источника. Не задавать произвольно повторы, нагрузку, дыхание, скорость, возрастные и медицинские ограничения.
4. Минимальный путь — собственный текст раздела `use` с подзаголовками упражнения и «Исходное положение / Движения / Мышцы», ограниченный конкретной моделью. `usageRulesFrom` объединяет и дедуплицирует строки всех элементов: для двух упражнений может потеряться группировка. Поэтому отдельные списки usageRules не считать готовым способом сохранить многоместную инструкцию. Правила общего элемента не должны автоматически становиться инструкцией всей группе тренажёров. Если существующий выбор use не умеет изолировать текст моделью — маленькая адресная правка выбора/хранения текста изделия, без новой категории или справочника.
5. Для разных рабочих мест допустим один собственный текст use с явными подзаголовками, если существующая сборка сохраняет порядок и однозначную связь. Общие правила безопасности остаются отдельно, не заменяются инструкцией упражнения. Свои существующие формулировки сохраняются; смена справочника не перетирает ручное значение.
6. Для каждого блока сохранить источник (документ/версия/страница либо зафиксированное подтверждение конструктора), применимую модель/исполнение, автора и дату одобрения. В варианте A достаточно реестра источников в папке задания и ссылки в доступном описании/примечании; новое поле API только ради этого не требуется. Эти метаданные не считать уже существующими полями usageRules.
7. Получить образец short/full без номера/выпуска, проверить содержимое и переносы. Если существующая сборка выводит полный блок корректно, код не менять. Заполнение остальных50моделей — отдельная очередь после одобрения пилота, без автоматического копирования.

Ожидаемый результат A: исходные данные подтверждены; purpose краткий; use/rules содержит все3смысловых части; источник и применимость прослеживаются; PDF воспроизводим. Полного справочника упражнений/мышц или экспорта HTML этот шаг не обещает.

## Вариант B — небольшая структурная доработка только по доказанному пробелу

Переходить к B, если пилот показывает хотя бы одно: нельзя безопасно ограничить текст моделью/исполнением; несколько независимых упражнений/мест смешиваются; требуется отдельно выбирать и повторно использовать упражнения/мышцы; общий абзац не сохраняет нужный порядок/иллюстрации; необходимы управляемое одобрение/источник и версии прямо в интерфейсе. Зафиксировать конкретный не прошедший сценарий A и файл/поле, а не строить новый модуль «на будущее».

Сначала проверить возможность расширения существующего изделия, функционального элемента или дерева текстов. Новая коллекция/CRUD/справочник допускается только с обоснованием переиспользования и жизненного цикла, после решения архитектора. Требование пользователя — содержательная инструкция, не конкретная схема хранения.

Минимальные смысловые данные структурного варианта (названия полей определяет исполнитель после проверки схем):
- модель/исполнение и явная применимость; рабочее место; упражнение и порядок;
- исходное положение; последовательность шагов; подтверждённые мышцы (основные/дополнительные только если источник различает);
- существующий рисунок/ссылка на источник при наличии, без генерации недоказанной механики;
- источник/версия/страницы, автор, состояние черновик/одобрено, кто/когда одобрил;
- сохранение ручных текстов и режима выбора; компоновка в существующий раздел пользования short/full.

Не создавать второй перечень мышц, если уже имеются применимые признаки/значения; не делать глобальную сущность для единичного модельного текста. Разделение мышц на группы, числа пользователей и рабочие места не взаимозаменяемы. Неподтверждённое остаётся пробелом подготовки, а не автозаполнением из общего назначения.

## Критерии приёмки

| Сценарий | Наблюдаемый результат | Доказательство |
|---|---|---|
| Точная модель с одобренным источником | Три части инструкции соответствуют источнику; purpose не противоречит им | Источник/одобрение, JSONдо/после и образец |
| Похожая модель другого исполнения | Чужие движения/мышцы не подставляются автоматически | Пилот+отрицательный пример применимости |
| Нет источника мышц/механики | Система не выдаёт догадку за утверждённую инструкцию; пробел указан менеджеру | Проверка пустого/неодобренного блока |
| Несколько мест/упражнений | Для каждого различимы исходное положение, движения, мышцы; места не смешиваются | Одобренный многоместный пример либо SKIP с причиной вне выбранного пилота |
| Short и full | Для категории TRN блок пользования доступен в обоих вариантах, читаем, без повторов/обрезанных шагов и служебных маркеров | JSONпроекции и просмотр **всех** страниц обоихPDF; если вариант законно исключает раздел, отдельно согласовать до реализации, не менять short инициативно |
| Свои тексты и общая безопасность, ПС-05 | Ручное значение сохранено; общие предостережения не исчезли; неприменимые упражнения не попали в паспорт | Сравнение до/после, проверка отмены автозамены |
| Образец | Получение JSON/PDF не создаёт экземпляр, номер или историю | Счётчики/IDдо/после, штатный read-only путь |
| Уже выданный действующий паспорт, ПС-07 | Заполнение изделия/справочника не переписывает снимок экземпляра само. При отдельном согласованном изменении — редакция, номер прежний, старый текст/PDFисточник сохранён; повтор тех же входов без лишней редакции | Раздельные до/после шаблона и экземпляра, история/старыйPDF |
| Legacy/аннулированный/закрытый/готовый вложенныйPDF, ПС-10 | Чтение и печать не мигрируют/не заменяют документ; массового обновления нет | Проверка сохранности полей/файлов/номера и истории |

Проверенные данные для первой строки таблицы нужны до обещания PASS. «Вело1068» с текущими пустыми полями не использовать как выдуманный эталон. Неготовность unrelated полей не исправлять придуманными значениями ради картинки. Отдельно различать готовность содержательной инструкции и полную паспортную readiness по стандарту.

## Первые шаги без исходных инструкций

1. Подготовить пустую карточку сбора фактов для одного пилота: модель/исполнение, рабочие места, исходное положение, шаги, мышцы, ограничения, источник/страницы, конструктор/одобрение. Поля не заполнять догадками.
2. Адресно проверить существующий выбор use/usageRules и пути их заполнения на одном пилоте по карте C235: может ли действующий механизм ограничить текст моделью и сохранить три подзаголовка. Код пока не менять, продне писать; для наблюдения использовать read-only access.
3. Определить владельца содержимого по полю «Кто проектировал»/имеющейся документации. Составить список недостающих фактов; назначить получение исходника, не заставлять пользователя писать технику упражнения по памяти.
4. По полученному одобренному материалу подготовить **один** вариантAв копии/эталоне и проверить short/full. Лишь воспроизведённый пробел переводить в адресное ТЗвариантаBс владельцем зоны и архитектором при изменении контракта.
5. После одобрения содержания согласовать конкретный набор изделий/действия записи; сохранность выданных проверить отдельно. Текущее поручение не разрешает массовый ввод на прод.

## Передача исполнителям и ограничения чтения

Analyst отвечает за содержание/источник/критерии. Ответственный по данным готовит адресное заполнение после согласования; backend/frontend подключаются только для доказанного пробелаB. Перед кодом — ownership.json, точный scopeи проверка архитектором межзонного контракта; новые сущности не объявлены обязательными. При изменении UI — DESIGN/UI-ACCEPTANCE; после backend/admin — datacore-verify; затронутые документы — docs-sync. Чтение всего каталога, backend/srcи старых паспортов не требуется: один пилот, один отрицательный пример и нужные эталоны ПС.

Открытый внешний факт: отсутствует одобренная техника/список мышц точной модели пилота. По умолчанию не угадывать; никаких массовых записей. Это нехватка исходных данных, а не основание создавать новую сущность.
