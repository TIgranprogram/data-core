# C148 — состав изделия и части в материалах

**Вердикт:** источники физического состава уже разделены правильно, но интерфейс и паспортное описание представляют несколько разных сущностей словом «состав». Объединять коллекции и переносить паспортные названия в реальные детали нельзя. Нужны единый вход для физического состава и понятная зависимая настройка текста паспорта.

Проверка — чтение текущего кода, без записи данных и без браузерной приёмки. Координатор расширил scope до composition, материалов, печати и импортов, отдельное ТЗ C148 ещё готовится.

## 1. Источники и смысл

## 2. Как источники связаны сейчас

1. Книжка «Состав изделия» читает `/showcase/:id`, сохраняет `PUT /showcase/:id/composition`. Чужие типы строк и CRM-поля должны сохраняться. Основание: `book-composition-funnel.js:48–57,78–119`, `showcase-composition.ts:100–126`.
2. «Части у материалов» читает/сохраняет другую таблицу — materialsSpec. Команда «Взять из состава» только предлагает её заполнение, сама ничего не записывает: `showcase-materials.ts:11–50`; подтверждение замены и явное сохранение — `products/form-fields.js:27–38`.
3. Состав раскрывается по цепочке изделие → модуль → деталь → сырьё. Для материалов вложенное изделие не раскрывается: у него собственный паспорт. Имя детали становится кандидатом названия паспортной части: `composition-expand.ts:121–145`, `showcase-materials.ts:16–29`.
4. Кандидат связывается со словарём passportParts по усечённому имени. Совпадения нет — название пропускается, реальная деталь от этого не теряется: `materials-text.ts:122–128,145–156`. Связи по id физической детали здесь нет.
5. Черновик паспорта берёт materialsSpec, текст материалов и умолчания изделия; compositionSheet получает отдельно из дерева: `passport-from-product.ts:39–52`. Правка BOM не обновляет подтверждённую таблицу материалов автоматически.
6. PDF показывает compositionSheet как «Состав изделия», а описание и обслуживание строит из элементов и материалов. Книжка сама загружает live-дерево, включая сырьё детали: `book-composition-tree.js:42–87`; `book-blocks.js:124–132`. Печатное дерево из `composition-expand.ts:93–114` раскрывает модули, но не сырьё каждой детали. Предпросмотр и печать имеют разную подробность.

## 3. Найденные разрывы

- **P1 — комплекс нельзя собрать целиком из книжки.** Сервер и старый редактор допускают `lineType=product` (`showcase-composition.ts:75–89`, `composition.js:80–100`), но новая воронка предлагает только модуль, деталь и покупное (`book-composition-funnel.js:168–182`), а loadCatalog не загружает изделия (`15–31`). Существующие строки изделия сохраняются, добавить новую нельзя. Добавить выбор изделия с исключением самого владельца и серверной проверкой циклов. Не создавать новый тип данных «комплекс» без отдельной потребности.
- **P1 — два описания состава могут расходиться.** Структурное дерево и ручные слова partIds обновляются независимо. Фраза «Состоит из…» создаётся также по функциональным элементам (`passport-compose-parts.ts:81–94`) и по паспортным частям (`materials-text.ts:63–74`). После изменения BOM ни набор слов, ни подтверждённые ручные материалы не синхронизируются автоматически. Показывать вторую таблицу как «Материалы и формулировки для паспорта» внутри общего контекста состава, с источником и явным обновлением предложения.
- **P1 — два списка модулей могут напечататься одновременно.** В PDF независимо печатаются `compositionSheet` и старый `modules[]` (`passport-pdf-v2-layout.ts:271–272`). В книжке при live-дереве старый список скрыт через else (`book-blocks.js:128–132`). Договориться об одном представлении для нового черновика: дерево, старые строки — резерв только при отсутствии дерева. Выпущенные документы и их исторические modules[] не мигрировать.
- **P2 — неполное сопоставление паспортных частей невидимо менеджеру.** Нет точного/морфологического совпадения детали со словарём — часть исчезает из предлагаемой фразы, а ответ сообщает unmatched/hinted о материалах, не о несопоставленных названиях частей (`materials-text.ts:122–128`, `showcase-materials.ts:47–50`). Показывать «Название детали не связано с термином паспорта» с выбором термина, не создавать новую реальную деталь.
- **P2 — книжка и PDF показывают дерево с разной глубиной и правилами раскрытия.** `book-composition-tree.js:47–75` раскрывает модуль и сырьё детали до трёх уровней, `composition-expand.ts:108–114` печатает только вложенность модулей до четырёх. Использовать одну серверную проекцию printable tree для листа и PDF, а производственное раскрытие оформить отдельным действием.

## 4. Импорты: что действительно меняет состав

- Раздаваемое правило Inventor `pwa/ilogic/passport-images.iLogicVb:519–566` загружает три рисунка, затем по согласию размеры, массу и глубину. composition, материалы и паспортные части не импортирует. По выполнению этого правила нельзя ожидать заполненного состава.
- Отдельный загрузчик PDM строит product/module/part/fastener/purchased и пишет физический composition: `pdm-import/pdm-plan.ts:8,38–39,114–125,160–162`, `pdm-write.ts:39–64,92–97`. Конфликт состава требует выбора (`pdm-plan.ts:214–223`). Он не заполняет materialsSpec и не связывает названия с passportParts.
- Модели и ссылки общие с CRM. Удалять, переименовывать типы строк или превращать существующие словарные id в id materials нельзя. Сохранять постоянные id строк состава и поля PDM/цен/габаритов: `showcase-composition.ts:100–126`.

## 5. Минимальная безопасная стратегия

1. **Без миграции данных** дать один понятный вход «Состав изделия»: физическое дерево, ниже «Материалы для текста паспорта». Развести подписи «Деталь с обозначением» / «Название части в тексте» / «Функциональный элемент» / «Комплект поставки».
2. Закрыть отсутствующий выбор вложенного изделия. API и схемы уже поддерживают его, сохранять id строк и серверный контроль циклов. Покупное и старые прямые строки сырья оставить читаемыми и редактируемыми, не вычищать автоматически.
3. Для материалов оставить предложение по реальному дереву с явным подтверждением. Показать связанные/несопоставленные строки, сохранить ручные passportText/techText, покрытия, размеры и уже принятые формулировки. Разовый выбор паспортного термина не переписывает физический BOM.
4. Согласовать правило вывода состава: новая книжка и PDF используют одну проекцию; legacy modules[] — fallback для старого/пустого дерева, комплектность остаётся отдельной. Выпущенные снимки не пересобирать.
5. Только после приёмки на модуле с деталями, детали с сырьём и комплексе из изделий обсуждать автоматическое связывание/обновление материалов. Оно требует отдельного diff-плана и ручного подтверждения, не массового скрипта по именам.

**Граница аудита:** код прочитан по перечисленным путям. Браузер, живые составы, PDM и Inventor не запускались. Количества, единицы, потери при раскрытии и циклы должны войти в критерии ТЗ и тестовые фикстуры. Код и данные не менялись.

## 6. Конкретный безопасный контракт для следующего этапа

**Повторный ввод сейчас действительно навязывается очередью, но не валидатором PDF.** `techsheet-gaps.ts:16–18` создаёт пункт «Части у материалов», если хоть одна строка не имеет partIds, даже при известном composition; required=false. `productTechGaps:36` считает ready по отсутствию любых missing. `product-fill-queue.ts:50–70` помечает все пункты срочными для изделия в заказе или с выданным паспортом, а composition не покрывает parts. Так необязательная словесная роль превращается в ещё одно срочное действие. Исправлять критерий, а не скрывать реальный пробел материала.

- **Готовность:** роль паспортной части необязательна и не уменьшает готовность при известном физическом составе. «Состав изделия» отвечает только за реальные позиции/количества. «Материалы и покрытия» требует материал/размер там, где они нужны для документа; не требует создавать паспортный термин для уже известной детали. Отсутствующий материал остаётся явным пробелом. Комплектность и обязательные функциональные элементы сохраняют собственные проверки.
- **Имена:** реальные названия и обозначения деталей/модулей уже доступны в compositionSheet и могут печататься без записи в passportParts. Для строки материалов с пустой ролью использовать подпись источника из BOM, не принуждать к словарю. Сейчас `common/print/tech-sheet-rows.ts:46` выводит только partIds либо «Материал», поэтому этому месту требуется дополнительный источник названия.
- **Мостик без миграции:** расширить ответ `GET /showcase/:id/materials-spec/from-composition` аддитивной картой источников строк. Для каждой предложенной строки вернуть пути `ownerKind/ownerId/lineId/refId/name` к исходной позиции. Для несопоставленной позиции вернуть тот же источник и причину отсутствия материала. Слова, не совпавшие с passportParts, сохранять в этой карте как реальные имена, не пропускать. Текущий `StockRef {id,partNames}` и объединение по materialId теряют точный путь — начинать с `composition-expand.ts` и `showcase-materials.ts`.
- **Подстановка:** при пустой таблице автоматически показать предложение из точных `materials.passportSpec` связей, не писать его в БД до обычного «Сохранить». Совпадение лишь по названию показывать кандидатом с подтверждением. Неизвестный материал заполнять через источник и сразу видеть результат в документе. Уже заполненную таблицу обновлять через понятный diff «Добавится / Изменится / Останется вручную», не заменять молча.
- **Трассировка принятого выбора:** если нужна устойчивая связь после сохранения таблицы, добавить необязательные sourceRefs в строки materialsSpec, сохранив старые partIds и форматы. Тогда менять вместе parse/present/check, DTO, UI, копирование/шаблоны и PDF. Это отдельная часть ТЗ, не пытаться передать метаданные только в UI: текущий parser `materials-table.ts:62` их отбросит.
- **Вложенное изделие:** добавить product в новую воронку книжки с API-каталогом и self/cycle-проверкой. Строку показывать «Изделие комплекса» по контексту выбора, новый обязательный флаг комплекса не нужен. Состав вложенного изделия для материалов родителя не раскрывать автоматически.
- **Новое правило о покупном:** если владелец исключает прямое «Покупное» из нового выбора изделия, скрыть только этот пункт добавления. Существующие строки materialKind=purchased/fastener, техническое покупное в модулях и данные PDM оставить читаемыми и сохраняемыми. Не превращать их автоматически в part/product и не убирать при PUT состава. Это изменяет пользовательский сценарий, не классификацию старой базы.

Минимальный scope первого исправления: `book-composition-funnel.js` (nested product), `book-focus.js` и `product-fill-queue/techsheet-gaps` (одна задача состава и необязательная роль), `composition-expand.ts → showcase-materials.ts → materials-text.ts/materials-table.ts → tech-sheet-rows.ts` (источник и отображение), `products/form-fields.js` (безопасное принятие предложения), общий printable composition для книжки/PDF. Не склеивать passportParts, productParts и материалы по именам.

## 7. Повторная оценка C095 перед портом C152

**Критичное уточнение первоначального аудита:** modules[] — не всегда текстовый дубль BOM. Это существующая возможность описать виды модулей с собственными габаритами, рисунком и количеством. В первоначальной рекомендации о fallback не был учтён объём этого содержимого; общий сброс modules при наличии compositionSheet недопустим.

Факт порта:
- `passports/modules.js:13–24,26–166`: редактор до20видов, name/dims/qty/photoId, общий итог, загрузка/выбор рисунка вида module, сохранение с проверкой и очередью.
- `form.js:121–123,210`: legacy-форма встраивает этот редактор и сериализует результат.
- `fill/paint.js:172–185`: старый шаблон изделия встраивает modulesEditor и сохраняет в passportDefaults.modules.
- `book-blocks.js:113–132`: эталонная книжка умеет только показать name/dims/qty как текст; рисунок модуля не показан, самого modulesEditor нет. При непустом дереве fallback вообще скрыт.
- `passport-pdf-v2-layout.ts:228–252`, `passport-pdf.service.ts:308`: PDF умеет полное представление C095 с рисунком, габаритами и общим итогом. Производственный compositionSheet имеет только word/label/qty/unit/children, этих данных не заменяет.
- `book-focus.js:20`: общий переход «состав/modules» ведёт к редактированию физического состава, а не к полноценному C095-редактору. Поэтому объявлять порт в книжку законченным нельзя.

**Защита текущего выпуска до C152:** никогда не скрывать и не очищать modules[], если хотя бы у строки есть dims/photoId либо если список не совпадает с BOM. Физическое дерево и паспортные виды модулей в таком случае показывать рядом с различимыми заголовками. Дубликатом для показа можно считать только полностью plain name+qty без доп.полей, точно совпавшие с полным набором верхнеуровневых BOM-модулей по нормализованной подписи и количеству; совпадение одного названия недостаточно. Самый безопасный вариант — вообще не удалять modules[] при issue, а подавлять только доказанный текстовый дубль на уровне представления.

Если требуется сохранить старую печать issued буквально, условие подавления нового представления должно фиксироваться отдельно для нового выпуска. Не применять новое правило ко всем историческим issued задним числом. До полного порта допустим временный повтор двух блоков, если это сохраняет богатые данные, но такой предел явно указать в отчёте.

C152 — отдельное ТЗ на перенос редактора/рисунков/сохранения в эталонную книжку и принятие двух и более типов модулей. Сейчас реализовать лишь защиту существующей возможности, без автоматического переноса dims/photoId в схему физического BOM.
