# Техническое задание: приложение «Ночная смена» (nightshift)

Основание: документ «Стратегия тестирования и ночные прогоны.md» (разделы 1–14). Данное ТЗ превращает его в проверяемые требования. При расхождении приоритет у этого ТЗ; неясное фиксируется в `docs/DECISIONS.md`, а не додумывается молча.

## 1. Цель и границы

**Цель.** Отдельное Windows-приложение, которое ночью без участия человека: берёт копию боевого сайта, поднимает изолированный стенд, прогоняет наборы тестов, даёт локальному ИИ исправить мелочи и складывает результат в папку передачи для мощного ИИ.

**Входит:** CLI, GUI, стенд в Docker, наборы тестов, отчёты (JSON+HTML), история в SQLite, расписание, тандем «скрипт + локальный ИИ (Ollama)», папка передачи, упаковка в `nightshift.exe`.

**Не входит:**
- пульт управления;
- запись в боевой сайт, боевую базу, боевое хранилище (запрещена технически);
- шифрование и обезличивание данных (отложено до появления реальных клиентов, раздел 9.3 стратегии);
- автоматическое влитие правок ИИ в основной код.

## 3. Архитектура

```
nightshift/
  pyproject.toml, uv.lock, .gitattributes
  config/        profiles.yaml, limits.yaml, ai.yaml, components.yaml, project.yaml
  stand/         docker-compose.yml, isolation/, scripts
  suites/        regression/ load/ soak/ chaos/ fuzz/ mutation/ visual/ static/ backup/ monkey/
  orchestrator/  runner, scheduler, resume, resources, plugins
  ai/            roles/, prompts/, schemas/, loop, kb
  reports/       <дата>/
  handoff/       <дата_время>/
  data/          nightshift.db (SQLite), kb/
  logs/          с автоочисткой
  gui/           интерфейс
  tests/         тесты самой «Ночной смены»
  docs/          DISCOVERY.md, DECISIONS.md, SCENARIOS.md
```

Принципы:
1. Ядро (orchestrator) не зависит от GUI. GUI только вызывает команды ядра.
2. Набор тестов — плагин: папка в `suites/` с `suite.yaml` (имя, команда, лимит времени, приоритет, зависимости). Новый набор добавляется без правки ядра.
3. Всё состояние прогона — в SQLite и файлах; после сбоя прогон продолжается с последнего завершённого этапа.
4. Скрипт руководит, ИИ исполняет; проверяет только компьютер (раздел 8).

## 4. Функциональные требования

### 4.1. CLI (обязательно, раздел 11.2 стратегии)

| Команда | Действие |
| --- | --- |
| `nightshift run --profile night` | ночной прогон |
| `nightshift run --suite <имя>` | один набор |
| `nightshift stand refresh` | обновить стенд из боевого сайта или бэкапа |
| `nightshift status --json` | состояние прогона |
| `nightshift stop` | остановить прогон |
| `nightshift report latest` | путь к последнему отчёту |
| `nightshift doctor` | проверка компьютера и компонентов (раздел 4.8) |
| `nightshift scenarios sync` | сверка `scenarios.yaml` с кодом |

Коды выхода: **0** — успех; **1** — найдены ошибки в проверяемом приложении; **2** — сбой самой «Ночной смены». Вывод — UTF-8.

### 4.2. Стенд

- «Обновить стенд»: свежая копия кода, БД, файлов; допускается использовать готовые бэкапы.
- Разворачивается в контейнерах; пересоздаётся с нуля одной командой; перед каждым ночным прогоном сбрасывается к чистой копии.
- Успешный подъём из бэкапа = проверка бэкапа (результат в отчёт).
- **Изоляция (обязательна, тесты не стартуют без неё):**
  - письма/СМС/пуши → ловушка (Mailpit);
  - платежи только в тестовом режиме;
  - внешние ключи заменены заглушками;
  - сеть стенда не имеет доступа к боевой БД/хранилищу/изменяющим внешним системам (проверяется автоматическим тестом изоляции);
  - планировщики рассылок/синхронизаций выключены;
  - стенд закрыт от интернета и поисковиков.
- Если проверка изоляции не пройдена — прогон прерывается с кодом 2 и понятным сообщением.
- Конфигурации стенда и боевого сайта (версии сервера, БД, настроек) сравниваются; расхождения идут в отчёт.

### 4.3. Карта сценариев (раздел 6.6)

1. Разбор проекта: маршруты, страницы, формы, API, работа с БД, фоновые задачи, интеграции.
2. Файл `scenarios.yaml`: `id`, `title`, `steps`, `expected`, `priority` (critical / important / minor), `source` (файл кода), `status` (draft / approved).
3. Первые приоритеты предлагает исполнитель; владелец утверждает (`status: approved`). Неутверждённые сценарии не блокируют прогон, но помечаются.
4. Для каждого сценария — сквозной тест. Критичные идут первыми и в каждом прогоне; минорные — ночью.
5. При каждом прогоне карта сверяется с кодом; новое без сценария → раздел «не покрыто тестами».

### 4.4. Наборы тестов

| Набор | Содержание | Инструмент |
| --- | --- | --- |
| static | статанализ, зависимости на уязвимости, поиск секретов, покрытие кода | по стеку проекта |
| regression | полная регрессия, параллельно на всех ядрах, изолированное окружение на поток (своя копия БД, свой порт) | pytest + xdist, Playwright |
| backup | реальное восстановление из бэкапа и проверка целостности данных | свой скрипт |
| load / stress | наращивание нагрузки до деградации, поиск узкого места | Locust |
| chaos | обрыв сети, медленная БД, полный диск, нехватка памяти, падение внешнего сервиса; проверка отсутствия потерь данных и самовосстановления | Toxiproxy |
| soak | часы под умеренной нагрузкой; утечки памяти, рост логов, деградация | Locust + psutil |
| fuzz | фаззинг входов API/форм; для кода — по стеку | Hypothesis / фаззер по стеку |
| mutation | внесение мелких ошибок в код, проверка, что тесты падают | по стеку |
| visual | скриншоты экранов vs эталон, несколько браузеров и разрешений | Playwright |
| monkey | случайные клики и ввод часами; ошибки консоли, падения | Playwright |
| flaky | многократный перезапуск; нестабильные тесты помечаются | pytest |
| gpu (опц.) | нагрузочный тест собственных GPU-вычислений приложения, если они есть | по стеку |

Требования к любому набору: запуск одной командой; жёсткий лимит времени; код выхода; падение набора не останавливает остальные; работа только на стенде.

### 4.5. Профили и распорядок ночи

`profiles.yaml` задаёт порядок и лимиты. Профиль `night` по умолчанию:
1. обновить код, собрать (включая сборку с анализаторами);
2. static;
3. regression параллельно;
4. backup;
5. load, stress, chaos;
6. до утра: fuzz, mutation, soak, monkey, flaky;
7. за 1 час до конца: остановить долгие тесты, ИИ сортирует ошибки, bisect новых падений, сборка отчёта и handoff.

Время окончания ночи — параметр. Этап, не уложившийся в лимит, прерывается и фиксируется как «прерван по времени».

### 4.6. Устойчивость и безопасность ПК

- Продолжение с места остановки после сбоя/перезагрузки.
- Контроль свободного места (порог в `limits.yaml`; при нехватке — автоочистка старых логов/артефактов, затем остановка тяжёлых этапов).
- Контроль температуры CPU/GPU (nvidia-ml-py, psutil): при превышении порога — снижение параллелизма или пауза.
- Метрики CPU/RAM/диск/GPU пишутся на протяжении всего прогона.
- Расписание — Планировщик заданий Windows (запускает прогон при закрытом окне приложения).

### 4.7. Отчёты

Каждый прогон: `reports/<дата>/report.json` + `report.html` (Jinja2).

В начале — сводка: пройдено/упало/пропущено, новое по сравнению с прошлым прогоном, тренды деградации. Для каждой проблемы:
- набор и тест; дата/время; хеш коммита;
- ожидаемое и фактическое;
- ошибка, стектрейс, фрагмент логов;
- файл:строка (если определимо);
- как воспроизвести (команда/входные данные);
- повторяемость (всегда/иногда, N из M);
- метрики ресурсов;
- приоритет (critical / important / minor), связанный сценарий;
- группа (дубликаты схлопнуты).

Отчёт отсортирован по приоритету. Производительность сравнивается с прошлыми ночами; замедление выше порога (по умолчанию 10 %) считается ошибкой. Для новых падений выполняется автоматический `git bisect` по коммитам за день.
На каждую проблему формируется готовый блок-задание для ИИ (описание, шаги, логи, подозрительный код).

### 4.8. Проверка и установка компонентов (`doctor` + GUI)

Проверка: Windows, CPU, RAM, диск, GPU/VRAM, WSL2, Docker Desktop, Ollama, Git, драйвер NVIDIA. Профиль выбирается автоматически: **full** (ИИ на GPU) / **light** (меньшая модель) / **no-ai**.
Таблица статусов (установлен / нужна новая версия / отсутствует). «Установить всё» — через `winget` с правами администратора, прогресс, продолжение после перезагрузки. При неудаче — ссылка на официальную страницу и «Проверить снова». Установщики только из `winget` и официальных страниц; список и ссылки — в `components.yaml`. Модель ИИ качается при первом запуске с прогрессом, повторно не качается.

### 4.9. Тандем скрипт + локальный ИИ

**Правило:** положительным результатом считается только то, что скрипт проверил сам: код компилируется, упавший тест проходит, остальные проходят, формат ответа корректен.

Цикл для каждой проблемы (карточка со стадиями: новая → диагностика → исправление → проверка → готово / передано мощному ИИ; состояние хранится в SQLite):
1. скрипт собирает самодостаточный пакет (описание, логи, нужные функции по стектрейсу и поиску, карта проекта, схема ответа);
2. один запрос = одна роль: **сортировщик**, **диагност**, **исправитель**, **рецензент**;
3. ответ — только JSON по схеме Pydantic; нарушение → повтор с указанием ошибки;
4. исправление — пары «найти → заменить», применяются в отдельной git-ветке/копии;
5. скрипт запускает тесты; неудача → новый запрос с итогами прошлых попыток;
6. лимит попыток (по умолчанию 5) и времени на проблему; исчерпан → `needs_big_ai`.

Ограничения: ИИ ничего не запускает; не меняет основную ветку; не видит боевой сайт, БД, пароли и ключи; файлы тестов не должны меняться (проверка хешей); температура генерации низкая; все запросы и ответы логируются; успешные исправления пополняют базу знаний (похожие ошибки получают прошлое решение как пример).

Что чинит локальный ИИ: опечатки и тексты, проверки на пустое значение, простые ошибки условий/границ, предупреждения анализаторов, плюс сортировка, причины по логам, тестовые данные, черновики тестов (помечены `draft`). Всё, что затрагивает несколько модулей, БД, безопасность, архитектуру — только описание в `needs_big_ai`.

**Критерии попадания в `fix_history`** (все обязательны): упавший тест проходит; остальные проходят; тесты не удалены и не ослаблены; производительность не хуже порога; рецензент не нашёл подгонки; повторный полный прогон на чистом стенде зелёный. Неудачные попытки в историю не попадают.

### 4.10. Папка передачи

`handoff/<дата_время>/`: `README_FOR_AI.md`, `summary.md`, `summary.json`, `issues/`, `fix_history/` (`fix_history.md`, `fix_history.json`, `*.patch`), `needs_big_ai/`, `metrics/`, `environment.json`. Дополнительно — один архив с ограничением размера (важное первым). `README_FOR_AI.md` объясняет мощному ИИ порядок: перенести правки на актуальный код, разрешить конфликты, прогнать тесты, выкладывать только под контролем владельца.
Запись по каждому исправлению: проблема и тест, причина, патч и описание, затронутые файлы и сценарии, подтверждение проверок, хеш коммита, дата, число попыток, модель.

### 4.11. GUI

Экраны: список наборов с кнопками запуска; «Ночной прогон»; расписание; индикатор текущего прогона (этап, прогресс, «Остановить»); история прогонов и открытие отчётов; история починки; карта сценариев (просмотр/правка приоритетов); состояние компонентов и «Установить всё»; настройки (путь к проекту, модель, лимиты); итоговое окно (найдено/исправлено/путь, «Открыть папку», «Скопировать архив»). GUI не содержит логики тестирования — вызывает CLI/ядро.

### 4.12. Упаковка

Сборка `nightshift.exe` (PyInstaller или Nuitka) со всеми библиотеками, наборами и шаблонами. Настройки, список компонентов и ключи в exe не встраиваются. Обновление = замена exe.

## 5. Нефункциональные требования

- Windows-правила: `pathlib` везде; `subprocess` только списком аргументов, без `shell=True`; UTF-8 (`PYTHONUTF8=1`, явный `encoding="utf-8"` при чтении/записи); поддержка длинных путей; `.gitattributes` для окончаний строк. Папки проекта и стенда рекомендуется добавить в исключения антивируса (подсказка в `doctor`).
- Ни одна функция не пишет в боевые системы; это покрыто автотестом.
- Все пороги, лимиты, имена моделей, ссылки — в `config/`, не в коде.
- Логи с ротацией и автоочисткой; секреты в логи и отчёты не попадают (маскирование).
- Собственные тесты «Ночной смены» (pytest) обязательны для ядра, парсинга отчётов, цикла ИИ (на заглушке модели), изоляции.

## 6. Этапы и критерии приёмки

| Этап | Результат | Приёмка |
| --- | --- | --- |
| 0 | Разведка: `DISCOVERY.md`, список сценариев-черновик | владелец утвердил стек и способ скачивания |
| 1 | Каркас, CLI, формат отчёта, handoff-скелет | `run --suite demo` создаёт JSON+HTML и handoff; коды выхода верны |
| 2 | Стенд, изоляция, regression на всех ядрах, карта сценариев | стенд поднимается с нуля одной командой; тест изоляции зелёный; регрессия параллельна |
| 3 | Расписание, продолжение после сбоя, контроль ресурсов | прогон переживает принудительный kill и продолжается; расписание срабатывает при закрытом GUI |
| 4 | load, soak, chaos, backup | каждый набор укладывается в лимит и даёт метрики |
| 5 | fuzz, mutation, visual, monkey, flaky, bisect | отчёт содержит тренды и виновный коммит для нового падения |
| 6 | Локальный ИИ: сначала сортировка и диагностика, затем исправления | на искусственно внесённой ошибке цикл даёт проверенное исправление в ветке; попытка ослабить тест отклоняется |

| 8 | `nightshift.exe`, `doctor`, установка компонентов | на чистой Windows `doctor` и «Установить всё» доводят систему до рабочего состояния |

Общий чек-лист готовности: запуск одной кнопкой; ночной прогон по расписанию без человека; отчёт в описанном формате; история прогонов и починки в приложении; папка передачи целиком отдаётся ИИ.

## 7. Риски (кратко)

Подгонка кода под тест → проверка хешей тестов + рецензент + ревью мощным ИИ. Шум → группировка и приоритеты. Стенд ≠ боевой сайт → сравнение конфигураций. Сбой ночью → resume, контроль диска, лимиты. Конфликты с дневным кодом → маленькие ветки от свежего кода. Перегрузка человека → внедрение поэтапно (порядок выше).

## 8. Открытые вопросы к владельцу (до этапа 2)

1. Стек и способ скачивания проверяемого сайта (выяснит этап 0).
2. Время окончания ночи и желаемые пороги (деградация 10 %, температура, свободное место).
3. Нужен ли отдельный нагрузочный тест GPU-вычислений приложения.
