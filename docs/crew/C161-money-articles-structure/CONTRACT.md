# C161 — контракт статей и финансового табличного вида

Редакция19.11.2026. Только требования; данные и код не изменены. C158/CONTRACT.md остаётся источником фактов оплаты; этот документ не меняет его даты/суммы/сторно.

## 1. Справочник: одна коллекция, стабильные ID

Расширить существующую expensearticles, не создавать financialtransactions/EAV/копию incomes/expensearticles. Старый ID неизменен. Значения статьи — данные; в расчётах нет привязок к названию или количеству корней.

Поля записи:
`id`, `name`, `type: income|expense`, `parentId: id|null`, `nodeKind: group|article`, `selectable: boolean`, `sortOrder`, `archivedAt: date|null`, `version`, существующие `code/categoryIds/deletedAt/timestamps`.
- У нетронутой старой записи отсутствие type читается как expense (это семантика существующего реестра, не вывод из текста). У старого корня nodeKind=group; у ребёнка article. Не сохранять эти дефолты чтением.
- parentId — ссылка на тот же справочник, того же type. null — верхняя группа. Тип родителя наследуется при создании, но сервер сохраняет и проверяет type явно.
- Рекурсивное дерево/пути/потомки вместо top.children-only. Начальный план2уровня; третий и последующие уровни не требуют новых сущностей. Допустима техническая защита глубины/объёма, но не бизнес-ограничение2уровнями.
- Любой цикл, self-parent, родитель из собственного поддерева, удалённый/архивный родитель для новой ветки —400/409. Проверка внутри транзакции/CAS общей ревизии дерева, иначе параллельные A→B/B→A обойдут проверку.
- type существующего узла с детьми/ссылками не меняется простым PATCH. Нельзя превратить расходы в поступления одним переименованием. Неиспользованный лист допускает явную смену type и валидного parent; использованный — отдельная сверка/переклассификация, не массовое переписывание фактов.
- code=payroll остаётся стабильным машинным кодом. Его нельзя удалить/подменить, но можно переименовать/перенести в расходную группу. Seed/финансы ищут код, не PAYROLL_PARENT/русское имя; запуск не создаёт второй ФОТ после переименования.
- categoryIds — подсказки категорий склада для расходных selectable-узлов; не независимый источник денежных фактов. Несколько подходящих статей для одной категории дают выбор/предупреждение, не первую случайную запись.
- Дубли сверяются по нормализованным имени+type+parentId среди активных соседей. Одинаковые названия в разных ветках допустимы; в выборе показывается путь. Нормализация нужна для поиска/конфликта, не для автоматического слияния.

## 2. API и совместимость справочников

`GET /api/expense-articles` остаётся расходным деревом `{items,total}`, добавляет только необязательные поля и рекурсивные children. Старые справочники/ссылки expenseArticles не начинают возвращать доходы.
Новый универсальный read endpoint существующего модуля: `GET /api/financial-articles?type=income|expense&includeArchived=0|1`, `{items,total,revision}`. Без type — обе ветки, каждая несёт type. Это представление той же коллекции, не новая сущность.

Канонический редактируемый ключ `dicts/financialArticles` работает с теми же ID/коллекцией, показывает type, путь, родителя, active/selectable и usage. Старый expenseArticles — совместимый expense-only alias. Если нужен incomeArticles для существующего ref-компонента, это только alias type=income; отдельной коллекции нет.
Существующие GET/POST/PATCH/DELETE/restore dicts не менять несовместимо. Новые поля валидировать через их DTO/правила, parent selector умеет искать любой допустимый уровень, исключая себя/потомков/иной type. PATCH принимает version и expectedTreeRevision; stale→409, возвращает currentVersion/currentTreeRevision.

Архив — `archivedAt`, не удаление/не стирание ссылок. По умолчанию скрыт в новых выборах, но исторические документы/отчёты разрешают прочитать узел и предков. Сохранённое старое значение видно как архивное. Архив группы с активными детьми блокируется409; сначала перенос/архив детей или отдельное явное архивирование поддерева с предпросмотром. Восстановление не возвращает архивного родителя автоматически без проверки пути. Удаление unused-узла остаётся мягким; used-узел предлагают архивировать. Общий merge по имени не использовать для реорганизации.

Usage должен учитывать supplyrequests, expenses, Income.articleId, IncomePayment.articleId (если введён), allocations supplyinvoicepayments и их corrections, legacy snapshot/payroll references. Нельзя объявлять статью неиспользованной по двум старым коллекциям. Неизвестные/удалённые/циклические узлы вернуть в диагностике, не отбрасывать молча из отчёта.

## 3. Независимые связи операций

- type — направление факта income/expense, определяется источником оплаты, а не названием статьи.
- companyId — действительная наша компания-плательщик/получатель. Это денежный факт; нельзя менять его в форме аналитической классификации.
- articleId — что за поступление/выплата; только совпадающий type. Исторически может быть null.
- salesOrderId — аналитический объект/заказ; не заменяет статью. Сохранять настоящий ID, не строку адреса; свободный costObject/заметка допустимы, если заказ не установлен. Не создавать заказ по адресу автоматически.
- costCenter — существующее направление workshop/office/smr/order либо null. Не превращать «Цех/СИЮ/Донбасская» в имена статей вместо этих независимых измерений.
- counterpartyId при наличии истинной связи + counterpartyName исторический текст; не сливать организации по похожей строке.

В `incomes` добавить articleId на существующей позиции и optional articleId в PaymentDto для отдельной классификации платежа; новое значение копируется из позиции по явному правилу, не определяется по title/customer. Менять базовую статью позиции означает подсказку для будущих платежей; существующие оплаченные части не переклассифицируются молча. Legacy-платежи без статьи берут устойчивую исходную классификацию при её первом материальном введении; если факта ещё не классифицировали — показывать «Без статьи». Типизированные новые поля в схемах/DTO/ответах и MoneyMask должны согласовываться сразу.

Неоплаченная заявка/позиция может редактировать свои обычные связи существующим действием. Для уже оплаченного факта C158 хранит исходный снимок: правка справочника или будущей подсказки не переписывает его articleId/объект. У оплаченного факта разрешается отдельная аналитическая корректировка (§4).

## 4. Три разных изменения и аудит

A. Rename статьи: тот же id, новое name; история названия в audit. Факты не меняются. Отчёт использует текущее имя (если пользователь не запросил будущий отдельный исторический режим).
B. Reparent: тот же articleId во всех фактах, новое положение справочника; историческая разбивка по текущей структуре переходит в новую группу, денежные суммы/даты/количество операций неизменны. Аудит фиксирует oldParent/newParent, ревизию и before/after-план. Это не переклассификация платежа.
C. Исправление классификации одной оплаченной строки: original articleId/project/costCenter в снимке сохраняются; добавляется типизированный `classificationOverride` на соответствующую оплату/распределение с effectiveArticleId/effectiveSalesOrderId/effectiveCostCenter/effectiveCostObject, version, автором/временем/причиной. Существующий общий audit хранит before/after. Не создавать отдельную универсальную EAV-коллекцию/таблицу дублей расходов.

Каждое поле override: отсутствует=исходное значение; null=явно снять связь (если допустимо). Снять связь и откатить override к исходному — разные действия. Изменение производится через один серверный резолвер effectiveClassification, одинаковый во всех отчётах/планах/выгрузках. Исходное значение и прежние correction остаются в журнале. Root-группа не заменяет selectable-лист по умолчанию; старые прямые ссылки на группу отображаются в виртуальной строке «Без детализации» с прежним ID, не теряются.

Предлагаемый маршрут: `PATCH /api/finance/operations/:operationId/classification`, тело `{articleId?,salesOrderId?,costCenter?,costObject?,reason,clientUid,version}`; поддержать отдельное `resetToOriginal:true` с причиной без смешивания новых полей. Только эти поля: amount/date/type/companyId/paymentId/currency и состояние платежа запретить. Ответ — обновлённая строка и classificationVersion. Валидация same-type, доступного объекта/статьи, денег/whole/scope как у исходного документа; manager/accountant/director/admin в пределах текущих денежных прав. reason>=3, clientUid обязателен, другой payload с тем же ключом409; повтор того же возвращает прежний результат, не новый audit. Конкурирующий version→409.

Это классификация аналитики, а не перенос позиции производства в другой заказ: source Income.orderId/производственные брони/отгрузки не меняются от effectiveSalesOrderId финансовой операции. UI явно показывает «Уточнено для отчёта» и ссылку на исходный документ. Неверная сумма/дата/плательщик исправляется только механизмом C158/источника с его защитами, а не через classification. Правдивая оплата не сторнируется ради смены статьи.

Идентичность: ledger C158 — paymentId+requestId; expenses — expenseId; payroll — устойчивый ID выплаты; доход — incomeId+paymentId. Текущие IncomePayment не имеют ID и могут заменяться массивом: перед вводом адресной классификации нужны стабильные paymentId и их сохранение при обновлении платежей. Новые платежи получают ID на сервере; legacy-элементы — read-only план materialization и защищённое сохранение ID, не hash изменяемого title/date и не номер строки после сортировки. Не применить correction к неопределимой старой оплате:409+план сверки. Историческую синтетическую полную оплату по paidDate не перепутать с реальным элементом payments.

## 5. Табличное представление и фильтры

Режимы существующего раздела: «По статьям» (дерево/месяцы/кварталы) и «Операции» (табличные факты с серверной пагинацией). Канонические фильтры сохраняются в URL; articleId выбирает самого узла +всех потомков один раз. Виртуальные агрегатные строки не являются редактируемыми статьями.

Read-only `GET /api/finance/operations`:
`from,to,type?,companyId?,articleId?,includeDescendants=1,salesOrderId?,costCenter?,counterpartyId?|counterpartyName?,source?,unassigned?,page,limit,sort=date|amount,dir=asc|desc`.
Период/предельная длительность — как действующие финансы; ISO-дни и компания по стабильному ID. org старых routes остаётся совместимым alias на входе, не новый источник идентичности. Сортировка с operationId как стабильным вторым ключом.
Ответ `{items,total,page,limit,totals:{income,expense,net,currency:'RUB'},counts:{unassigned},filters}`. Итоги считаются по ВСЕМ отфильтрованным фактам до пагинации. Row: `{operationId,source,sourceId,paymentId?,allocationId?,date,type,amount,companyId,companyName,articleId,articlePath[],counterpartyId?,counterpartyName,salesOrderId?,projectName?,costCenter?,costObject?,docNo?,classificationVersion,classificationOrigin,sourceLink,warnings[]}`.

Всё питается одним каноническим набором C158: active факты с глобальным ledger/legacy исключением. Факт будущих дат не попадает сюда. Неполная валютная оценка/неоплаченный счёт/начисленная зарплата — не денежная строка. Финансовые суммы положительны, направление определяется type, отрицательные ошибки не маскируются. net=income−expense называется денежным результатом, не бухгалтерской прибылью. Кассовые выплаты налогов/ФОТ считаются только по своим подтверждённым движениям; имя «начислено» не порождает второй расход.

Совместимую сводку by-articles строить рекурсивно по effectiveArticleId для BOTH types; доходы по заказчикам/заказам остаются альтернативным раскрытием, а не исчезают. Архивные статьи с фактом входят в историю и итог; неизвестная/пустая статья видна отдельной строкой. Нулевые группы могут быть скрыты в отчёте, но всегда доступны в редакторе/выборе по правилам активности.

## 6. Реорганизация и проверка

ARTICLE-PLAN.md — построчный проект по183существующимID. Старые name/ID/categoryIds/systemCode сохраняются; символические new:* не являются ObjectId и не могут уйти в прод как parentId. Перед apply получить реальные ID новых согласованных групп и сохранить mapping.
План хранит sourceRevision/hash, oldParent/newParent и expectedVersion. Несовпадение before/usage→409/REVIEW, без перезаписи свежей правки. Очередность: создать явно согласованные группы→перенести допустимые листья→архивировать только пустые старые группы при отдельном решении. Повтор плана0изменений; rollback возвращает parent/order/activity по старымID, не удаляет факты. Названия не чистить и дубли не объединять в этой операции.

Риски: возврат займа/подотчёт/дивиденды/возврат по контракту смешаны в старом расходном реестре. Направление и вид движения проверять по фактам, не по имени; type-перенос used-статьи нельзя автоматически прогнать по183строкам. По снимку неизвестны скрытые/архивные узлы и counts использования, это обязательная read-only сверка перед применением. Начислено и на руки — метки старых статей, не основание суммировать две копии одной выплаты.

Источники прочитаны: expense-articles/articles-tree/service/controller; dicts.expense-articles и dicts.controller CRUD; income.schema/DTO; finance.controller/by-articles/cashflow.Op; money.js/money-articles.js/expenses.articleOptions; PRODUCT§5 и решения QUESTIONS§«Деньги». Live OpenAPI отдельного income-articles не содержит (снимок access в C158/data/income-articles-contract.json). Пользовательское обещание ограничено расширяемостью справочника и обратной совместимостью, а не отсутствием будущих требований.

## Решения координатора после ARCH-PLAN-REVIEW (19.11.2026)

Ниже приняты уточнения; при расхождении они уточняют §§1–5. Исходная матрица и обоснование — ARCH-PLAN-REVIEW.md.

1. Все writes дерева (create/update/reparent/reorder/archive/remove/restore/seed) через один transactional writer существующего модуля и общую treeRevision. Aliases financialArticles/expenseArticles/incomeArticles не обходят проверки. У существующего узла обязательны version и expectedTreeRevision; создание принимает expectedTreeRevision. Первоначальный seed выполняет тот же invariant/CAS, без повторного создания payroll по названию. Merge статей первым выпуском блокируется409 во всех aliases: сохранность original денежных снимков важнее старого generic reassign. Generic admin CRUD коллекции expensearticles также не обходит writer: делегировать ему либо оставить raw-таблицу только для чтения с переходом в справочник. Другие справочники не менять.
2. Каноническое дерево — /financial-articles. Старый /expense-articles сохраняет двухуровневую проекцию: каждый расходный корень и все selectable descendants под ним с прежними ID и полным path; actual parentId не подменяется. Старые прямые ссылки/пропуски видны диагностикой. Внутренние потребители переходят на каноническое дерево одним выпуском до переноса данных. Архивные значения читаются для истории, но не выбираются вновь.
3. group не selectable, article — лист, selectable допускает false. У превращённого в группу бывшего листа сохраняются categoryIds и исторические ссылки (виртуально «Без детализации»). Глубина максимум32, узлов в дереве максимум10000; достижение лимита400 с понятной ошибкой. Повреждённое старое дерево даёт диагностику, без бесконечной рекурсии и потери фактов.
4. Адреса и места хранения classification принимаются по source matrix ARCH-PLAN-REVIEW: ledger allocation; legacy invoice typed map keyedrequestId; Expense; embedded IncomePayment; synthetic income typed metadata. Legacy request безinvoice и payroll без доказанного stable payoutId первым выпуском read-only409 с classificationEditable=false/reason, денежные строки остаются видимыми. Legacy invoice→ledger переносит original/override/version/history и originOperationId атомарно, прежний адрес становится alias одного факта. До этого переход с неразрешимым override блокируется409, никогда не теряет классификацию.
5. Income paymentId выдаёт сервер. Существующий ID должен принадлежать этой Income; чужие/повторные/неизвестные отклоняются. После materialization замена массива без ID запрещена409 с указанием перечитать документ; не сопоставлять одинаковые части по индексу/сумме/дате. Все внутренние income forms сохраняют IDs. Удаление/замена классифицированной части или synthetic paidDate блокируется409 до явного поддержанного действия источника. Correction и source edit используют один source CAS; original и audit не стираются при обычномPATCH. Synthetic paidDate получает отдельный serverID в typed metadata, без создания денежной части/изменения итога.
6. Correction только articleId/salesOrderId/costCenter/costObject; reason3–1000символов, costObject≤1000, costCenter только workshop/office/smr/order/null. null снимает разрешённую связь; resetToOriginal отдельное тело без смешивания полей. Оплата/дата/компания/состояние непринимаемы whitelistDTO. Путь/дерево не дублировать во всех фактах; кэш учитывает type/archive/projection и инвалидируется source/override/tree.

### Уточнения UI/API для адресной работы (19.11)

- `GET /api/finance/operations/:operationId` возвращает canonical row плюс classificationOriginal/effective/history и classificationEditable/reason. Проверки исходного источника, роли и scope те же, что в списке/PATCH; неизвестный ID404. У неподдержанной коррекции факта read доступен с editable=false. Панель после refresh/deeplink читает этот маршрут; не восстанавливает исходную классификацию из случайной текущей страницы.
- Совместимый by-articles добавляет `articleRows`: recursive nodes `{id,name,type,children,values,total,...}` для обеих веток income/expense. Старые `rows` (расходы) и `incomeRows` (заказчики/заказы) сохраняются с прежним смыслом. UI показывает доходные статьи из articleRows, а `incomeMode=customers` переключает на существующее раскрытие по заказчикам/заказам. Не перегружать поле incomeRows двумя разными моделями и не дублировать денежный вклад в итогах.

- При canonical from/to до366дней by-articles возвращает `months` как упорядоченный список YYYY-MM именно за отфильтрованный период, в том числе через границу года. UI строит столбцы/кварталы по этому списку; квартал включает год. Старый вызов только year сохраняет12месяцев. Drill по ячейке ведёт в `/finance/operations` с теми же фильтрами, не в непагинированный legacy endpoint.

- У старого `DELETE /incomes/:id/payments/:index` после materialization серверныхID typed query принимает `expectedPaymentId` и source `version`; совпадение ID текущего элемента и версии проверяется атомарно. UI передаёт их вместе с прежней проверкой amount. БезID/при несовпадении409 с перечитыванием; не удалять другой факт после сортировки/конкурентного изменения. Старый путь сохраняется, дублирующий endpoint не нужен. Классифицированный факт/его history этим обычным действием не стирается.


### Явная подготовка идентичности старых доходных оплат

`GET /api/incomes/:id/payments/identity-plan` возвращает `{version,planHash,items,changesCount,totals,synthetic,canApply,blockers}`. `POST /api/incomes/:id/payments/materialize` без confirm (либо confirm:false) только dry-run; применение требует confirm:true/version/clientUid/planHash, права исходного документа и денег. Это присвоение метаданных существующим частям, без изменения суммы/даты/порядка/количества фактов. План привязан к исходному массиву/paidDate/версии; конкурентная правка409. Сервер генерирует ID только в атомарном apply, сохраняет идемпотентность и audit before/after в той же транзакции. Повтор того же намерения возвращает прежнее соответствие, не новые ID. Synthetic paidDate получает отдельный typedID и не дублируется реальным payments.

Неподготовленная legacy-часть может иметь только временный source-qualified read reference, привязанный к текущему содержимому/версии источника; это не устойчивый paymentId и никогда не адрес writes. При изменении источника такой read reference404 с предложением перечитать список, а не другой платёж по старому индексу. Apply возвращает `identityMapping:{oldOperationId:newStableOperationId}` для точного перехода после CAS-подготовки.

У доступных пользователю неподготовленных доходов canonical row содержит `classificationPreparation:{kind:'income-payment-identities',sourceId}`. В панели — «Подготовить историю оплат»: предпросмотр количества/сумм/дат и пояснение «Суммы и даты не изменятся; после подготовки можно уточнять статьи», затем явное подтверждение. Технические ID в подписи не показывать. Без подготовки старая часть остаётся видимой, но классификация read-only с причиной. Массовое применение на прод этим контрактом не поручено.


### Уточнения после первого post-code review дерева

- parentId=null означает только верхнюю группу (nodeKind=group). Новая/перемещённая article без родителя отклоняется400 с подсказкой выбрать родительскую группу.
