# ТЗ HA-TWO-SERVERS — два сервера с автопереключением

> Основа: совет архитектора (opus) 2026-10-30. Поведение Mongo 4.4 — из знаний, проверить на макете (`[макет]`).
> Правило 10 в `AGENTS.md` пересматривается только письменным «да»: код под `HA_ENABLED`, файлы в `deploy/ha/`, прод по умолчанию не меняется.

**Зачем (словами пользователя):** «выключил свет — переключился на другой», «упал один сервер — не теряем работу», «в админке галочка, какой главный», «сайт не должен тормозить».

**Класс:** XL · **Max agents:** 5 на этап · **Reviewers:** architect ☑ qa ☑ · **Max review loops:** 2 · **Проверки:** full + учебные отказы

## Факты (2026-10-30)
| | Основная VM | Sportin |
|--|--|--|
| Процессор | 1 ядро, без AVX | i7-14700, 14 ядер |
| Память | 5,8 ГБ, доступно 3,6 ГБ | 3,3 ГБ, доступно 2,4 ГБ; увеличить |
| Диск | см. `/health/disk` | свободно 455 ГБ |
| Связь | за домашним роутером, туннель на VPS | Keenetic, внешний IP, 8080 → 3001; SSH по ключу работает |
| Сейчас | прод и CRM kppdf | старая копия, работает отдельно |

Вход с интернета: VPS nginx `/db/` → туннель → :3001. CRM работает с той же Mongo с `directConnection=true`.

## Схема
- Replica set: главный + вторичный + арбитр на VPS. Приоритеты равные: без автовозврата и чехарды.
- Связь треугольником по WireGuard: VM–VPS, Sportin–VPS, VM–Sportin. Звезда через VPS не годится: падение VPS оставит базу только на чтение.
- Запасной канал, если WireGuard глушат: autossh с keepalive и `ExitOnForwardFailure`.
- Постоянные имена `dc1`, `dc2`, `dcarb` через `extra_hosts` в оверлее `docker-compose.ha.yml`.
- На VPS сторож раз в 5 с спрашивает `/api/health/role` у обоих. 3 совпадения подряд → новый `include` upstream, `nginx -t`, reload только при смене. `proxy_next_upstream` для POST не включать.
- Запись `w:1`. `majority` подвесит запись при падении вторичного.
- Галочка в админке — запрос «переключить», а не приоритет. Проверки: оба живы, лаг < 5 с, пауза 1 час, нет выкладки. Затем `rs.stepDown`. Исполняет хост-мост, у веб-процесса нет `clusterManager`.
- Вернувшийся старый главный остаётся вторичным. Вопрос в «Разборе»: «вернуть?».
- Фото: `rsync --ignore-existing --bwlimit` без `--delete`, очередь inotify и ночной проход. Не доехало — прокси с соседа, иначе заглушка и вопрос.
- Backend на вторичном трафика не получает. Фоновые задачи, сиды, `ensureIndexes` — только на primary (`HA_ENABLED`). Роль — через `isMaster`.
- Аналитика: read-only пользователь, `readPreference=secondary`, `maxTimeMS`, запуск при лаге < 60 с. Сайт вторичное чтение не использует.
- Копии вне дома: настройки общие (в базе), захват `job_locks` по дате, первым делает вторичный. Ссылка проверяется PROPFIND depth 0, 10 с, один повтор. Нет связи — статус без ошибки; 3 дня без копии — один вопрос.
- Секреты общие: `JWT_*`, `BACKUP_SECRET_KEY`, keyfile, пароли Mongo. Разные: `HA_SELF`, `DATA_DIR`. `HTTP_STAND` на Sportin убрать, прямой 8080 закрыть.
- Ступенчатая выкладка (правило пользователя 2026-10-30): новый код получает только главный. Второй сервер остаётся на прошлой рабочей версии и получает обновление через одну выкладку.
- Упал главный из-за обновления: сторож переключает на второй сервер, работа продолжается на прошлой версии. Главный чинится отдельно.
- Прошлая версия обязана работать с той же базой. Поэтому миграции только расширяющие, два выпуска подряд: удаление старого поля — не раньше следующей выкладки.
- Важно: база общая. Ступень спасает от падения кода, но не от порчи данных новым кодом: порча сразу доедет до второго. От порчи защищают бэкап перед выкладкой и откат.
- Рискованная выкладка — днём нет. Смена типа поля или массовая запись идёт вечером, с бэкапом.

## Ловушки (проверить обязательно)
1. **Тихая остановка точки фиксации.** Упал вторичный — change stream молчит без ошибки (`data-version.service.ts:41`), списки устаревают. Лечение: сторож через 15–30 мин ставит упавшему `votes:0, priority:0`; при лаге кэш выключается. `[макет]`
2. **Устаревший вторичный выигрывает выборы.** Обрыв VM–Sportin на часы, затем смерть VM: потеря часов работы. Защита — тревога по лагу > 60 с.
3. **Откат записей.** Старый главный вернулся — расхождения в `rollback/`. Нужен тип вопроса «откат, N записей». Старше 24 ч — полная пересинхронизация.
4. **CRM.** `directConnection` при главном на Sportin даёт чтение устаревшего и падение записи. Нужен `replicaSet=rs0`. При смерти VM CRM лежит: она только там.
5. **Смена имени `mongo:27017`.** Сначала `extra_hosts` у всех клиентов, включая kppdf, потом `rs.reconfig`. Иначе клиенты получат имя, которое не разрешают.
6. **Порядок старта.** WireGuard поднимается раньше docker, иначе контейнер не стартует.
7. **Транзакции.** Из 13 файлов с сессиями проверить ручные `commitTransaction`: повтор делает только `withTransaction`. Подтвердить `retryWrites`.
8. **Oplog.** `oplogMinRetentionHours` 72+. Замерить ГБ/час.
9. **Keyfile.** Сменить при подключении: он лежит в `.env` стенда.
10. **Celeron.** Репликация может занять заметную долю единственного ядра. Замер до Э2.

## Что нельзя обещать
- Ноль потерь: обычно 1–3 с, в худшем случае часы до разбора отката.
- Ноль простоя: 30–60 с при переключении.
- Разовую синхронизацию: повторится, если обрыв дольше окна oplog.
- «Один zip»: всегда нужны ключи WireGuard, проброс на роутере, запись на VPS.
- Живую CRM при смерти VM.
- Полное отсутствие нагрузки: канал, диск, часть ядра на VM. Цифры — после замера.
- Падение VPS: сайт снаружи недоступен, база цела. Так же и сегодня.
