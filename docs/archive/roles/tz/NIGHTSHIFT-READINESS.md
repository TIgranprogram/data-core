## Shared pack

- Nightshift — отдельный Python harness в `tests_ai_tiit/nightshift`, не пользовательское приложение и не текущая кнопка Pult «Ночной прогон».
- На проверенной машине `py -0p` сообщил, что Python не установлен; запуск `nightshift/.venv/Scripts/python.exe` завершился ошибкой `uv trampoline ... permission denied`; Docker CLI отсутствовал. Это состояние среды на 2026-11-03, а не диагноз кода.
- `pyproject.toml:1-16` задаёт Python `>=3.12`, зависимости и entry point. `BLOCKERS.md:3-23` сообщает о незавершённой установке/изоляции, тогда как `PROGRESS.md:20-28` отмечает этап 2 выполненным; нужно устранить противоречие по реальным проверкам.
- Текущий regression runner запускает pytest самого Nightshift (`suites/regression/run.py:1-7`), не интеграционные тесты DataCore. `static` — команда `print('static ok')` (`suites/static/suite.yaml:1-5`). CLI `status`/`stop`/`doctor` — заглушки (`orchestrator/cli.py:65-66, 112-116`).
- Отдельный Pult legacy-контур использует `dcnight`; Nightshift compose создаёт `nightshift-mongo` и `nightshift-app` (`stand/docker-compose.yml:3-27`). Не объединять их и не переключать Pult на Nightshift без отдельного решения.
- Не обращаться к production URL/Mongo, не запускать e2e на боевой БД, не удалять Mongo-данные и volumes. Любой восстановленный backup — только в новом уникальном тестовом контуре и без `--drop`.

## Что сделать

1. **Поддерживаемая установка и запуск.** Описать воспроизводимую установку поддерживаемого Python, `uv sync` с dev-зависимостями и CLI-команд. Реализовать `doctor` как настоящую read-only проверку версий, зависимостей и наличия Docker; вывод не должен раскрывать содержимое `.env.stand` или иных секретов. Исправить/объяснить причину, по которой текущий `.venv` запускается через недоступный uv trampoline.
2. **Один безопасный контур стенда.** Описать и проверить сборку/получение `nightshift-app:latest` (сейчас compose задаёт только `image`, без `build`, `stand/docker-compose.yml:25-44`), health-check сервиса и команды `up/status/down`. Имя compose-проекта, контейнеры, test DB и volume должны быть уникальны для Nightshift и не совпадать с `dcnight`. Сеть оставить внутренней; если нужен доступ браузера с хоста — только на явно выбранном loopback test-порту, не на боевых/API/Mongo портах.
3. **Безопасный refresh.** Сейчас `stand refresh` выбирает backup и выполняет `mongorestore --drop` для `datacore-night` (`orchestrator/stand.py:61-85`). Переделать так, чтобы запуск создавал новый пустой изолированный project/volume и восстанавливал туда копию без очистки существующей БД/volume. Автоматическая уборка старых volumes запрещена; неизвестный или существующий контур — отказ с понятным сообщением.
4. **Реальная проверка изоляции.** Доказывать её конфигурацией Compose и контролируемыми тестовыми sink/mock endpoints; не открывать соединения к production IP, VM, URL или Mongo даже «для проверки, что отказано». Проверять, что команда остановится, если нет однозначно уникального проекта, DB с суффиксом `-night` и внутренней сети.
5. **Реальный профиль `night`.** Явно определить минимум: unit-тесты Nightshift; backend typecheck/unit/import/lint; затем только согласованный набор регрессии против тестового API и тестовой БД. Regression не должен называться тестом сайта, если запускает только собственный pytest. Заглушки нагрузочных/backup/static и незавершённые suite либо реализовать, либо исключить/пометить `not implemented`; они не должны давать зелёный статус профиля.
6. **Безопасный выбор запуска.** Не запускать все обнаруженные suites молча при `nightshift run` без профиля/набора (`orchestrator/cli.py:26-46`); требовать явный профиль либо безопасный default. Реализовать реальный `status`/`doctor` или удалить команды до готовности.
7. **Достоверный отчёт.** Для каждого результата писать suite, команду, commit, время, статус и причину. Отдельно классифицировать ожидаемый demo-failure, runner error/timeout и реальную ошибку приложения. Сейчас любой exit code 1 превращается в `site_failure` (`orchestrator/report.py:11-34`), а свежий demo намеренно печатает `FAIL` и завершает кодом 1 (`suites/demo/fail_test.py:1-2`). Успешный отчёт также должен перечислять реально выполненные suites, а не только общий счётчик.
8. Синхронизировать `docs/BLOCKERS.md` и `docs/PROGRESS.md`: пункт можно отметить сделанным только после критериев ниже и сохранённого отчёта. В пользовательской инструкции явно различить Nightshift и legacy `tools/dc night`.
9. **Сквозная редакция секретов.** `mask_obj` уже вызывается из CLI и есть unit-тесты для синтетических ключей, Mongo URI, JWT и паролей; проверить все пути сериализации report/handoff/logs/subprocess output, чтобы они не сохраняли сырой секрет. Новый helper не считать подключённым без подтверждённого callsite.

## Критерии приёмки (проверяет QA и архитектор)

- [ ] На чистой поддерживаемой Windows-среде установка проходит повторяемо; `nightshift --help`, `doctor`, `status` возвращают реальные и безопасные сведения.
- [ ] `docker compose config` проходит; выделенный стенд запускается и отвечает health; существующие Pult/dcnight контейнеры, volumes и порты не затронуты.
- [ ] Изоляция подтверждена статически и контролируемыми тестами без сетевых обращений к production; все DB и URL в execution path явно тестовые.
- [ ] `night` выполняет реальные объявленные проверки DataCore на изолированном контуре; неисполненные/stub suites не считаются успехом.
- [ ] Тесты на ожидаемый demo-failure, runner error, timeout и реальный app failure подтверждают корректные категории отчёта; отчёт перечисляет suite и commit.
- [ ] Synthetic secret tests подтверждают redaction во всех persisted report/handoff/log surfaces и не используют реальные credentials; сырой stdout/stderr не попадает в пользовательские отчёты.
- [ ] Два последовательных тестовых прогона дают воспроизводимые сводки; ни одна команда не использует `down -v`, удаление Mongo volume/коллекций или `mongorestore --drop`.
- [ ] Python tests, TypeScript/unit/lint и тесты интеграции профиля прошли; отчёт приложен, `BLOCKERS.md` и `PROGRESS.md` согласованы. Никаких production e2e.

## Нельзя

- Подключаться к production, запускать e2e на боевой БД или использовать её URI в качестве fallback.
- Удалять Mongo данные, коллекции или volumes; применять `mongorestore --drop`; трогать `dcnight`/`datacore-mongo`.
- Считать `demo`, `print('... ok')` или собственный pytest Nightshift доказательством готовности DataCore.
- Менять Pult маршрутизацию/кнопки в этом ТЗ.
