# C170 — контракт и архитектурные условия до кода

Вердикт: направление ANALYSIS принять с уточнениями ниже. Это предкодовый план, не приёмка реализации. В C166/C164 ничего не включать; финансовые поля не менять.

## 1. Независимый выбор и общий барьер выпуска

`incomes.passportSelection` принадлежит домену passports: `{mode:'site'|'attachment', revision, attachmentId?, attachmentGeneration?, productIdAtSelection?, confirmedAt?, confirmedBy?, changedAt, changedBy, invalidatedAt?, invalidReason?}`. Отсутствие = site/revision0. Сброс в site сохраняет монотонную revision, удаляет ссылочные поля, аудит хранит before/after. Общий IncomeDto не принимает это поле.

Дополнительно `incomes.passportEpoch` — технический целый счётчик, отсутствие=0, независимо от финансовой version. Один session-aware helper `claimPassportLine(db, session, context, expectedEpoch, operation)` реально изменяет этот документ (`$inc:passportEpoch`) с проверкой живости позиции/заказа, orderId/productId/lineType/cancelledAt/deletedAt, прав и режима. Его используют выбор источника, создание позиционного паспорта и выпуск до номера/записи. Простого read selection внутри transaction недостаточно: write-conflict возникает на общем документе, а не на прочитанном snapshot.

Выбор attachment и выпуск с одного baseline: один commit, другой 409 STALE_CONTEXT. Callback transaction при retry не подменяет исходный expectedEpoch новой прочитанной версией. Номер, создание паспорта и аудит находятся в той же transaction, что guard; неуспех не оставляет новый номерной документ. Уже существующий черновик сохраняется. Для массового create+issue желательно одно действие на позицию/одна transaction; если используется два этапа, созданный черновик является самостоятельным уже завершённым действием, а issue повторно захватывает guard и может быть отвергнут после смены источника. Не обещать отсутствие любого черновика при двух отдельных commit.

Изменение productId (включая auto matching), orderId, lineType, cancel/delete/restore позиции должно атомарно bump epoch. При смене изделия attachment-выбор остаётся attachment, помечается PRODUCT_CHANGED, revision увеличивается; обратная смена изделия не возрождает выбор. Смена заказа перепроверяет ACL/контекст; источник не становится site автоматически. В C164/incomes точку интеграции назначает координатор на принятой базе; сохранять частичный $set, не заменять документ и не трогать source/sourceLine/payments/version-семантику.

## 2. Файл: версия подтверждения вместо неограниченного fanout

В productattachments добавить server-only `selectionGeneration`, отсутствие=0. PUT attachment хранит generation в passportSelection. Удаление/restore вложения меняет generation в том же атомарном DB-действии; выбор PUT в transaction условно изменяет guard/version attachment с проверкой `_id/productId/deletedAt:null/fileRemovedAt:null/notPurging` и ожидаемой generation. Тогда select/delete конфликтуют даже при вставке новой ссылки income. Новый технический guard не должен менять generation при обычном выборе другим сотрудником: generation меняет только жизненный цикл файла.

Корректировка предложения ANALYSIS: не требовать транзакционного updateMany всех доходов при удалении общего файла. Эффективная инвалидность ATTACHMENT_DELETED выводится из несовпадения stored/current generation; собственной selection revision она не подменяется. Это хранит историю, не ограничивает размер файла/число связанных заказов и не оживляет выбор после restore. Source-view/contextToken включает обе версии; повторное подтверждение после restore — явный PUT с новой generation. Если UI нужен materialized invalidReason, он вспомогателен, не источник корректности.

Availability helper использует существующий безопасный path resolver и `stat.isFile`, не ticket как доказательство наличия. В plan пакетно загрузить выбранные attachment IDs, stat — только уникальные выбранные файлы с ограниченной параллельностью; candidates — только запрошенную страницу. Preview/plan/source GET не пишут и не выдают тикеты. Утрата физического файла делает attached blocked; произвольное исчезновение файла после stat нельзя атомарно исключить Mongo-транзакцией — готовность означает проверено на момент ответа, скачивание проверяет повторно.

`purgeDeleted:85–95` сейчас читает удалённые записи и unlink делает позже: restore может попасть между чтением и удалением. До C170 исправить узко: CAS-claim purge по актуальным deletedAt/generation/fileRemovedAt с token/state=purging до unlink; restore/select не проходят purging; после unlink фиксируется fileRemovedAt, при crash состояние остаётся недоступным до reconcile. Не удерживать Mongo transaction во время filesystem IO. Успешное восстановление одного и того же физически пропавшего, но не удалённого attachment может вернуть availability при неизменной generation; это отдельно от delete/restore.

## 3. Минимальный API

Принять пути ANALYSIS: GET source, GET source/candidates `{items,total,page,limit}`, PUT source и POST source/download-ticket под `/api/passports/order/:orderId/lines/:incomeId/`. Уточнение владельца/координатора: GET order plan/source/candidates и POST source/download-ticket доступны READ (`admin/director/manager/user`) + существующий passports section + текущая проверка доступа к заказу/позиции, для файла пересечение с attachment read ACL. PUT source, create и issue остаются WORK. Выдача короткого тикета является чтением, не изменением выбора. Не расширять общий VIEW на все маршруты: изменить только эти четыре поверхности чтения. Секретные пути не отдавать; чужие ID дают безопасный 404/403 без метаданных.

Точечная проверка текущего orderPlan: возвращаются явные паспортные поля строки/сводные счётчики, selection/epoch/contextToken, безопасные метаданные вложения и краткая история; firm/firmChoices содержат только id/name/hasSeal/hasSignature. Денег, полной income/sourceLine и editor-only snapshot нет, поэтому существующий plan можно использовать для READ без нового endpoint или дублирования by-order. Придерживаться allowlist ответа; технический contextToken допускается READ для скачивания и не заменяет WORK/ACL на PUT. Метаданные attachment отдавать только при соответствии file.productId текущему income.productId; чужую/повреждённую связь обозначать недоступной без раскрытия имени файла.

READ-приёмка: user видит ready/attached/blocked/issued и может получить тикет на выбранный доступный файл, но PUT source/create/issue возвращают 403. Проверить отсутствие денежных полей/полной income/sourceLine/storedPath в plan/source/candidates; чужая позиция или файл не раскрываются. Интерфейс READ не показывает выбор/смену источника и выпуск, сохраняя просмотр готовности и истории.

PUT: `{mode,expectedRevision,contextToken,attachmentId?,confirm?}`. Строгие nested DTO/forbidNonWhitelisted; site запрещает attachmentId, attachment требует ObjectId и confirm=true. contextToken — подписанный opaque baseline `{incomeId,orderId,productId,lineType,cancelledAt,deletedAt,selectionRevision,passportEpoch,attachmentGeneration?}`. Он не является авторизацией: live права и контекст проверяются заново. Кандидата сервер валидирует по productId текущей позиции, не по incomeId происхождения. Содержание сотрудник подтверждает явно, MIME/папка не назначают паспорт автоматически.

Минимум действий UI: у доступного файла «Использовать как паспорт» одним PUT одновременно задаёт mode=attachment и attachmentId; контекст позиции уже известен, повторного выбора изделия и отдельной формы режима нет. Из плана заказа — одна правая панель выбора доступного файла с этим же подтверждением; никогда не выбирать первую декларацию автоматически. При наличии старого issued в том же подтверждении короткое предупреждение о сохранении истории, без второго мастера.

Ответ source-view включает selection, passportEpoch/contextToken, effectiveState, файл с безопасными метаданными/availability и отдельно sitePassports. Прежний revision/token →409 STALE_CONTEXT с предложением перечитать; файл не пригоден →409 ATTACHMENT_UNAVAILABLE; режим/DTO →400. Слепой retry не разрешает конфликт. Повтор успешно сохранённой формы со старой revision даёт 409, не второй аудит. PUT не создаёт паспорт/номер и не выпускает автоматически при возврате site.

POST download-ticket проверяет текущий выбор/contextToken и доступность; не меняет selection. Стандартный productattachment ticket — краткоживущее право чтения конкретного файла, выданное после этих проверок; смена источника после выдачи не обещает отзыва уже выданной ссылки. Если требуется строгая проверка selection при погашении, нужен отдельный line-bound ticket с incomeId/revision/epoch, не молчаливое обещание поверх текущего файлового тикета. Существующая механика снова проверяет живость записи и наличие файла при чтении.

## 4. Точки guard, история и PDF

Обязательные точки: `product-passport.service.ts:331 create` (включая legacy passportNumber→issued), `createPresentation`, `:431 createDraftsForOrder`, `:134 createReady`/его helper при incomeId; `passport-issue.ts:59` transaction до allocate; создание новой редакции/перепривязка позиции через update/copy, если они создают новый позиционный документ. При attachment-режиме, даже invalid/missing, новое создание/выпуск запрещено SOURCE_ATTACHMENT. Product-only preview/самостоятельный паспорт без incomeId не объявлять паспортом позиции: выбор относится к income.

`passport-order.ts:202 issueLines` должен пропускать attached и attachment-blocked раньше шаблона/фирмы; процессный mutex не защита, сервисные guards обязательны. Проверка уже issued в `passport-issue.ts:42` может вернуть тот же исторический документ идемпотентно без нового номера/снимка; она не делает текущий attachment источником site. UI явно различает «Текущий документ» и «Ранее выпущено на сайте»; старый issued не аннулировать и не перепривязывать.

`issuedOfOrder:502`/`passport-pdf.service.ts:225 orderPdf` фильтруют effective source=site до применения optional IDs; attachment исключается даже при старом issued и недоступном файле, причина SOURCE_ATTACHMENT в skipped. Для исторических экспортов не менять общий смысл выборки issued без отдельного explicit current-order scope. Индивидуальный `/passports/:id/pdf` и адресный исторический экспорт сохраняют прежние ACL/снимки. Order PDF использует согласованный DB snapshot выбора на начало сборки; не держать транзакцию/блокировку на весь PDF render. Смена источника после snapshot требует обновления плана, не ретроактивной переписи готового файла.

Счётчики ANALYSIS принять: total=issued+attached+ready+blocked, completed=issued+attached; ready не completed. Исторические issued при attachment показываются отдельно и не увеличивают completed повторно. Новый scoped-фильтр не должен скрывать историю или обходиться через IDs/legacy/createReady.

## 5. Порядок реализации и обязательные доказательства

   Epoch и generation пропорциональны разным гонкам: первый сериализует выбор с номерным выпуском на одной позиции без финансового CAS; второй фиксирует удаление/restore общего файла без fanout всех заказов. Это два локальных счётчика, не новая платформа блокировок. Исторический issued idempotent read в guards не блокировать.
