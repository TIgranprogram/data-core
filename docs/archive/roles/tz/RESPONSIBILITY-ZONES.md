# Зоны ответственности и экран «Сотрудники» (ЗО, аналитика 2026-10-29)

Класс XL. Аналитик до кода. Вопросы — `docs/QUESTIONS.md` «ЗО».

## 0. Название сущности

**«Зона»** (полностью — «зона ответственности»). Почему не другие:
- «участок» займёт производство (сварочный участок, покраска) — будет путаница;
- «ответственность» — длинно, не склоняется в подписях («Ответственности: 3»).
На экране: «Зоны», «Не назначено: Паспорта», «Зоны сотрудника».

Зона ≠ роль доступа. Роль (`roles`, `app-sections`) решает, что человек **может**. Зона решает, что ему **адресовано**.

## 4. Модель данных

Общие с CRM коллекции — только добавление необязательных полей.

### 4.1 `zones` (новая, только data-core)
`code` (уникальный, латиница, не меняется после создания), `name` (≤ 40 симв.), `hint`, `order`, `active`, `system` (true у 8 базовых: нельзя удалить, можно переименовать), `deletedAt` (soft-delete).
События привязаны к **коду** в коде сервера; директор правит только название и людей.

### 4.2 Связь сотрудник ↔ вход ↔ зоны
- `persons.userId?: ObjectId` — **добавить поле** (общая коллекция, только добавление). Уникально среди непустых (частичный индекс). Один вход — один сотрудник.
- `persons.zoneCodes?: string[]` — текущие зоны сотрудника (быстрый поиск). Альтернатива — только в истории; держим копию ради простых запросов, истина — `zoneassignments`.
- `users` не трогаем.

### 4.3 `zoneassignments` (новая) — история «кто когда отвечал»
`zoneCode`, `personId`, `from` (дата), `to` (null = сейчас), `byUserId`, `note`. Снятие = проставить `to`, не удалять.
Инвариант: `persons.zoneCodes` = все записи этого человека с `to = null`.

### 4.4 `handoffs` (новая) — передача объекта между людьми
`entity` (`supplyrequest` / `designtask` / `salesorder` / `passport`), `entityId`, `field` (`responsibleId` / `assigneeId`), `fromPersonId`, `toPersonId`, `at`, `byUserId`, `reason?`.
Пишется сервером при каждой смене ответственного. Показ — в карточке объекта и в истории сотрудника.
Почему не общий аудит: аудит хранит всё подряд; передачу нужно читать быстро и по человеку.

### 4.5 Ответственный у объектов (только добавление полей)
- `supplyrequests.responsibleId?: ObjectId` (persons). Старое `responsible` (текст) оставить — его пишет CRM.
- `salesorders.responsibleId?` — менеджер договора.
- `product-passport.responsibleId?` — позже, если нужен личный (иначе — зона целиком).
- `designtasks.assigneeId` — уже есть.

### 4.6 Адресация уведомлений
Уведомление остаётся личным (`userId` обязателен — экран колокольчика не меняется). Сервер раскладывает:
1. объект с личным ответственным → ему (через `persons.userId`);
2. иначе → всем людям зоны события с `userId`;
3. в зоне никого или ни у кого нет входа → зоне `management` + строка «Не назначено: <зона>».
В `notifications` добавить `zoneCode?` (из какой зоны пришло) — для фильтра и разбора «почему мне».

### 4.7 «Сегодня»
Каждому элементу ленты сервер ставит `zoneCode` (и `personId`, если есть личный). Переключатель «Моё / Всё»; по умолчанию «Моё» = зоны пользователя + личные. Директор (`management`) по умолчанию видит «Всё». Пользователь без связи с сотрудником видит «Всё» и подсказку «Вход не связан с сотрудником — скажите директору».

## 5. Перевод текстовых `responsible` в ссылки

На проде сейчас 181 заявка, поле пустое у всех → переносить нечего. План всё равно на случай CRM:
1. Только чтение: выгрузить различные непустые значения `responsible` с числом заявок.
2. Сопоставить с `persons` по ФИО (фамилия, «Фамилия И.», «Имя Фамилия»), без учёта регистра и ё/е.
3. Однозначные — `responsibleId` проставить, текст **не стирать**. Неоднозначные/не найденные — список директору («Ответственный не найден: …»), без записи.
4. Перед записью — бэкап коллекции; запись — с разрешения пользователя (`docs/DATA-FIX-USER.md`).
5. Дальше приложение пишет оба поля: `responsibleId` и текст ФИО (CRM видит привычное).

## 6. Экран «Сотрудники» (директор)

Меню: новая группа **«Управление»** → «Сотрудники». Доступ: роль admin (директор). Справочник «Сотрудники» в «Данных» остаётся для правки ставок; потом — ссылка на новый экран.

- **Список**: ФИО, должность, зоны (метки), вход (есть / нет), статус. Фильтр по зоне. Сверху плашка **«Не назначено: Паспорта, Склад»** — кнопка ведёт на зону.
- **Вкладка «Зоны»**: список зон, у каждой — люди. «Нет людей» — красным. Добавить / переименовать / скрыть зону (базовые — не удалять).
- **Карточка сотрудника** (правая панель): данные; «Вход в приложение» — выбрать пользователя из `users` или «Создать вход» (логин, роль); зоны — галочки; «История» — назначения в зоны и переданные объекты.
- **Пустые состояния**: «Сотрудник не связан со входом — ему не приходят уведомления».
- Уволенный сотрудник: зоны снимаются автоматически (с записью в историю), вход — предложить отключить.

## 7. Фазы

| Фаза | Класс | Что | Кто | Приёмка |
|--|--|--|--|--|
| ЗО-1 | M | `persons.userId` + выбор входа в карточке сотрудника | backend | Если директор связал сотрудника со входом и назначил ему задачу проектирования, то у этого пользователя появляется уведомление `task_assigned`. Если тот же вход выбрать второму сотруднику — отказ «Вход уже связан с …» |
| ЗО-2 | L | `zones` + сид 8 зон + `zoneassignments` + экран «Сотрудники» (список, карточка, зоны, плашка «Не назначено») | backend + frontend, проверка designer, qa | Если у зоны нет людей, то на экране плашка «Не назначено: <зона>» и уведомление директору раз в день. Если зону снять с человека, то в истории запись с датой «по». Базовую зону удалить нельзя |
| ЗО-3 | L | адресация уведомлений по зоне (§4.6) + `zoneCode` в уведомлениях | backend, проверка architect, qa | Если создана заявка, то уведомление получают только люди зоны «Снабжение». Если в зоне никого — получает директор с пометкой «Не назначено» |
| ЗО-4 | M | «Сегодня»: `zoneCode` в элементах, «Моё / Всё» | backend + frontend | Если кладовщик открыл «Сегодня», то он не видит оплат и задач проектирования. Если переключил «Всё» — видит всё, что ему разрешено ролью |
| ЗО-5 | M | `responsibleId` у заявок и заказов + `handoffs` + история в карточке | backend + frontend, qa | Если сменить ответственного заявки, то в карточке строка «Передано: Иванов → Петров, дата, кто». Текст `responsible` при этом заполнен ФИО |
| ЗО-6 | S | перенос текстовых `responsible` (§5) | data-steward | Если значений нет — отчёт «переносить нечего». Ни одно непустое значение не стёрто |

Общее: права не меняются (зона ничего не открывает и не закрывает). Схемы общих коллекций — только новые необязательные поля, синхронно в `D:\kppdf-8.0` не нужны (CRM их не читает).
