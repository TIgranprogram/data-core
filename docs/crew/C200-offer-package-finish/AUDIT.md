# КП: исходные решения, состояние и порядок завершения

Проверено 22.11.2026 по коду, истории Git и серверному архиву «Ведение проекта». Ключевой сценарий владельца — один раз выбрать изделия и получить три отдельных предложения от трёх фирм. У предложений общий заказчик и состав, свой номер, фирма, цена с наценкой, НДС и бланк. Число фирм задаётся выбором. Исторический пример из C070 — базовая цена, +3 % и +5 %. Предложения связаны в пакет, а условия конкретного принятого КП передаются в договор явным действием.

## Где сценарий прерывался и что проверять

1. **Корзина → несколько фирм.** Корзина каталога умела сохранять только одно КП. Пакет был доступен отдельной пустой воронкой или через создание дополнительных копий. Прямой вход из заполненной корзины закрывает повторный подбор и перенос ручных значений. В пакете НДС и фирменные условия относятся к соответствующей компании.
2. **Бланки.** Пакет допускал фирму с собственным бланком без отметки «По умолчанию», а PDF при этом мог взять общий или встроенный фон. Для каждого листа пакета используется только бланк выпустившей фирмы. При отсутствии собственного фона продолжение белое. Сверка действительных реквизитов и многостраничных фирменных оригиналов нужна при локальной приёмке.
   Пакет округляет цену каждой единицы до рубля, включая 0 % наценки. При ручной исходной цене с копейками расчёт корзины и пакетная сумма могут различаться. В итоговой приёмке проверить, нужно ли сохранять исходную цену для 0 %.
3. **Предпросмотр, PDF и ZIP.** Пройти создание трёх вариантов, проверить суммы, имена фирм и цены в трёх PDF, скачать ZIP из карточки пакета и проверить его состав. Автоматические проверки и визуальные примеры фиксируются отдельно. Текст на бланке, длинные строки и перенос страниц проверяются по реальным образцам при их наличии.
4. **Фото из каталога.** Для КП без явного URL поиск фото в PDF и проверке готовности обращается к устаревшему источнику `showcaseitems.photo`; фактические изделия используют `products` и `photoIds/mainPhotoId`. Следующая техническая задача — одна общая загрузка подтверждённого фото для PDF и статуса, с проверками существующих документов.
5. **Сбой или повтор.** Отметка отправки меняет несколько записей последовательно; сбой может оставить смешанные статусы. При добавлении копий исходное КП может получить пакет до успешного создания всех копий. Проверить транзакции Mongo 4.4, повтор запроса и согласованность при одновременных действиях. Завершить это до повседневной работы с пакетами.
6. **После принятия и следующие этапы.** Общая нумерация уже работает. Автоотмена остальных при принятии одного не согласована, существующие статусы остаются самостоятельными. Возможный этап после ручной приёмки — явное действие для закрытия оставшихся вариантов. Клиентский экран разбора входящей заявки и сопроводительное письмо отдельны от основного сценария. Спорные реквизиты из KP2-1 проверяет владелец по своим оригиналам.
