## 3. Предложение

**Продукт (`products`)**
- Короткое = `name` — фильтры, списки, подбор, доска «Проектирование», склад, резервы.
- Длинное = `fullName` — КП и документы без заказа.
- В заказе = `orderName` — «как обычно пишут в заказе» (шаблон по умолчанию для новых позиций).
- Позиция заказа `incomes.title` — то, что написал заказчик в этом конкретном заказе (снимок). `orderName` не заменяет и не перезаписывает его.
- Паспорт из заказа — `incomes.title`; из «Продукции» — `fullName`, пусто → `name`. Артикул всегда наш (ПНЗ.1, ПРЖ п.4).

**Покупное (`materials`)**
- Короткое = `name` (как сейчас, обязательное) — фильтры и списки.
- Длинное = `fullName` — документы, паспорт, подробное описание.
- «В счёте» = `invoiceName` — как пишет поставщик; поиск находит и по нему; при импорте счёта сопоставление идёт по нему.
- Строка заявки: `title` остаётся снимком «что просили/что в счёте»; при выборе из склада подставлять `invoiceName`, если есть, иначе `name` (**решает пользователь, см. Н-1**).

**Какие поля добавить (все необязательные):**
- Для `supplyrequests` — **ничего** (`title` + `materialId` достаточно; снимок уже есть).
- Для `incomes` — **ничего**; `productId` уже есть. Для показа «Наше: арт · name» — вычислять на сервере из `productId`.
- Для `products`/`materials` — **ничего** (ДМ.2 всё сделал). Только индекс на `invoiceName`, если поиск станет медленным (проверить; индекс — только после ответа архитектора, `ensure-indexes`).

**Миграция «текущее → короткое»** (скрипт, `--dry-run` → `--apply`, только на копии, потом прод по «да» пользователя):
1. `products`: где `name` пусто — взять `fullName`, иначе `orderName`; если и их нет — оставить (в списках показывать `sku`). Существующие `name` не менять.
2. `materials`: `name` не менять (он уже «короткое»). Если `name` длиннее 80 символов или совпадает с `invoiceName` — в отчёт «кандидаты на сокращение»; решает человек, автоматически не режем.
3. `incomes.title` не трогать никогда.
4. Отчёт: сколько строк, сколько пустых, дублей коротких названий (в `products` по ПРЖ — 12 повторов).
5. Откат: перед `--apply` — выгрузка `_id` + старых значений в JSON.

**Создание заказа:** после шапки сразу открывается перечень позиций (правая панель), без промежуточного шага. Это экранная правка `salesorders.js`, отдельное ТЗ для frontend.

## 4. Правила показа (единые для всех экранов)
- Списки, фильтры, подбор, резервы, доска — короткое.
- Позиция заказа — главное `title` заказчика; второй строкой серым «Наше: <sku> · <name>» либо метка «Подберите изделие».
- Карточка изделия — `name`; `fullName`, `orderName` — в просмотре отдельными строками.
- Документ — длинное (паспорт из заказа — `title` позиции).
- Пустое длинное или «в заказе/в счёте» — показывать короткое, без «—».

## 5. Критерии приёмки
1. Если у изделия заполнены три названия, то в «Продукции» список и фильтры показывают только `name`, карточка — все три с подписями.
2. Если `fullName` пуст, то КП и документ без заказа печатают `name`.
3. Если позиция заказа связана с изделием, то в ней главная строка — `title` заказчика, ниже серым «Наше: sku · name»; без связи — «Подберите изделие».
4. Если правят `name` изделия, то `incomes.title` не меняется.
5. Если паспорт создан из заказа, то наименование = `incomes.title`; из «Продукции» — `fullName`/`name`; артикул — наш.
6. Если в заявке выбрана позиция склада, то в `title` попадает название по правилу Н-1, `materialId` заполнен.
7. Если импортирован счёт, то название из файла пишется в `invoiceName` новой позиции, а не подменяет `name` существующей.
8. Если ввести «название в счёте» в карточке склада, то поиск находит позицию и по нему (уже работает, `stock-search.service.ts:116` — не сломать).
9. Миграция: `--dry-run` ничего не пишет; после `--apply` число изделий с пустым `name` = 0 или в отчёте; повторный запуск — 0 изменений.
10. Новые поля только необязательные: CRM kppdf читает `products`/`materials` без ошибок (e2e + проверка на копии).
11. API: формы `{items,total,page,limit}` и пути не меняются; `docs/openapi.json` и `MAP.md` — только при новых полях.
12. Создание заказа: после «Сохранить» шапки сразу виден перечень позиций с полем ввода.

## 6. Границы и риски
- Не смешивать с организациями: у них свои `shortName/fullName` (`organization.schema.ts:55–59`) — это контрагенты.
- Паспорт хранит собственные `name` и `textSnapshot` — выпущенные паспорта не пересчитывать.
- Порядок: ПРЖ-3 (`productId` в позиции) → ТИ-8 backend (вычисляемое «Наше…») → экраны (одним ТЗ для frontend) → ПНЗ.1 → миграция.
- Копии прода на ПК нет — сколько пустых `name` в проде, неизвестно (только после ПРЖ-0, чтение).
