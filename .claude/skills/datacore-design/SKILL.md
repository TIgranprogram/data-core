# Дизайн интерфейса (data-core)

Единственный источник правды по виду — `docs/DESIGN.md`; законы — `docs/CANON.md` §2. Этот скилл — порядок работы.

**Когда:** S (подпись, пункт меню, одно свойство на существующем классе) — без скилла, но токены и правая панель — всё равно. M — если появляется новый элемент или меняется раскладка. L-UI (новый экран, окно, компонент) — всегда (CLAUDE.md).

## 1. Перед правкой
0. **Ввод данных — только правая панель** (DESIGN §5): форма записи/счёта/позиции — `section.form` в `ui/card.js`; `modal` — только подтверждение или 1–3 поля. Новый вид окна или компонента — сначала запись в DESIGN §4/§8, иначе не делать.
1. Прочитай `docs/DESIGN.md` §1–§4 (характер, токены, раскладка, каталог). Не читай `base.css` целиком — ищи нужный класс grep'ом.
2. Определи: это **значение** (цвет/размер/отступ) → токен из §2; это **элемент** → компонент из §4; нет нужного → расширяй общий компонент (`ui/*.css` — base/list/form/screens/panels, `ui/*.js`), не раздел.
3. Жалоба пользователя «сливается / не отличить» — почти всегда иерархия: проверь, что заголовок отличается размером + жирностью + цветом `--heading` (§2.1), а соседние значения разделены промежутком.

## 2. Правка
- Цвета и размеры — только `var(--…)`. Новый токен → в `tokens.css` в **обе** темы (`:root` и `:root[data-theme='dark']`), контраст ≥ 4.5:1 посчитать и вписать в DESIGN §2.3.
- Заголовки — только `h1`/`h2`/`h3` (размеры задаёт `base.css`).
- Файлы в репо с CRLF — при правке скриптом сохраняй окончания строк (иначе дифф на весь файл).
- Service worker держит оболочку по версии `version.json` (её кладёт выкладка): после выкладки новая версия подтягивается сама, на стенде (без version.json) — «сеть, иначе кэш». Версию кэша вручную менять не нужно.

## 3. Проверка
0. Пройти как человек с пустой формы: каждую новую кнопку нажать до заполнения полей (не только «счастливый путь» скриптом).
1. Чек-лист `docs/DESIGN.md` §6 — пункт за пунктом.
2. Следовать `docs/UI-ACCEPTANCE.md`: снимки порученной правки UI разрешены; открыть и оценить заполненные и раскрытые состояния в обеих темах. Ограничения одним снимком нет.
3. Сохранить `UI-REVIEW.md` в папке задания. Только код, пустой стенд или непроверенный сценарий = PARTIAL, а не «принято». Проверить реальный выбор, фокус и вставку фото; сравнить с общим эталоном.

## 4. После
- Новое решение по виду → строка в `docs/DESIGN.md` §8 «Журнал решений»; новое правило → CANON §2.
- Пользователю — человеческими словами: что стало видно лучше и где посмотреть (CANON §1).
