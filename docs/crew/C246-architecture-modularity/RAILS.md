# Рельсы архитектуры (постоянно, не отдельный «большой рефакторинг»)

> Цель: каждая обычная задача **чуть укрепляет** направление, а не размывает.  
> Выбор: модульный монолит с хозяевами доменов — [DECISION.md](DECISION.md).  
> Сейчас кодим по [CHECKLIST.md](CHECKLIST.md). После C255 — [BEYOND-CHECKLIST.md](BEYOND-CHECKLIST.md).

## Правило одной поставки

1. Один этап = один коммит(ы) зелёных проверок; сайт без этапа работает.
2. Недоделанное не выкладываем.
3. Не смешиваем два архитектурных этапа в одном диффе.
4. Чужую коллекцию — только через хозяина-операций (не сырой `update`).
5. В `common/` — типы и чистые функции; правила домена — у хозяина.

## Мини-проверка перед коммитом (S/M по архитектуре)

- [ ] `node backend/scripts/audit-cycles.js` — 0 взаимных пар (после C256 — и длинные циклы по его REPORT).
- [ ] Нет нового `db.collection('<чужая>')` / чужой модели для **записи** мимо хозяина.
- [ ] Новый импорт из соседнего `modules/*` — через фасад/`index.ts` или DI хозяина, не «файл вглубь».
- [ ] Если трогали shared с CRM — поля по [C257 CONTRACT](../C257-shared-compat-contract/CONTRACT.md) (S/G без синхрона CRM не ломать).
- [ ] Трогали вход эндпоинта (DTO, `@Query`, тело) — шаги [PLAYBOOK](../C258-dto-by-touch-playbook/PLAYBOOK.md): поля клиентов собраны, новый 400 не появляется.

## Когда брать архитектурный пункт

Свободный лимит / «починить архитектуру» → открыть:

1. [CHECKLIST.md](CHECKLIST.md) — первый `[ ]` программы C246–C255.
2. Если C255 закрыт → [BEYOND-CHECKLIST.md](BEYOND-CHECKLIST.md) — первый `[ ]`.
3. Не начинать XL (CRM→API), пока нет явного «да» владельца.

## Чего не делать «между делом»

- Микросервисы, Nx, перенос всех папок (АБЗ-8).
- Массовый перевод на `raw-query` без сверки выдачи.
- Пакетный перевод всех Query-DTO. Один эндпоинт — [PLAYBOOK](../C258-dto-by-touch-playbook/PLAYBOOK.md) (замок L-258).
- Переписывание kppdf «заодно» с фичей экрана.
- Один коммит «починим всю архитектуру».
