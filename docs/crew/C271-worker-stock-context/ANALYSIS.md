# C271 — контекст материала: бизнес-правила и доступ

Анализ исходников 26.11.2026, опорный HEAD `3feff09c`. Прод, стенд и БД не читались. Это проверка контракта, не подтверждение фактических настроек живых ролей и не визуальная приёмка. C270 (создание номенклатуры, подтверждение количества, приёмка) не меняется.

## Вывод для координатора и архитектора

На существующем API можно корректно показать ожидания конкретного материала с датой поставки. Полный сценарий C271 для native stock-only требует серверного дополнения: создание заявки закрыто разделом `requests`; список активных броней не фильтрует materialId и ограничен 2000 записями до применения scope. Не принимать manager-мок с открытыми разделами за проверку роли рабочего. Не расширять роли до раздела «Заявки» ради одной кнопки.

## Источники и принятые решения

- `docs/PRODUCT.md`, разделы «Заявки» и «Склад и номенклатура»: материал — источник истины; заявка привязана materialId; у позиции есть «Создать заявку»; приход — отдельное действие. `docs/PATTERNS.md`, П-1: спрашивать только неизвестное, автоматически подставлять достоверное.
- `docs/QUESTIONS.md`, СК-6 и К-2: бронь закрытого/отгруженного/аннулированного или удалённого заказа сама не снимается. Следовательно, исключаются отменённые **брони**, но активная бронь отменённого **заказа** показывается с предупреждением.
- `backend/pwa/sections/stock-worker-details.js`: детали создаются отдельно на каждый `workerMaterialId(item)` внутри подстроки; сейчас характеристики/коды/даты соседствуют с историей. `stock-card.js` и `item-orders.js` — существующие потребители быстрых заказов, но их поведение нельзя переносить целиком (ниже ограничения).

## Ожидаемые поставки: существующего чтения достаточно

`GET /api/supply/requests?materialId=<id>&status=in_progress,requested,ordered,paid&page=1&limit=100` разрешён `@AppSection('requests','stock','stock-mobile')`, роли admin/director/manager/user. Источники: `supply.controller.ts:342`, `supply.service.ts:291–368`, `present:215–250`.

1. Scope применяется на сервере, фильтр materialId — точное множество ObjectId; не искать по названию, сечению, мойке или формату. По response.total/page/limit пройти все страницы. Ошибка любой страницы означает «Не удалось загрузить», а не «Поставок нет».
2. `ordered` в фильтре означает ordered с paid!=true, а `paid` — ordered с paid=true. Поэтому обязательно перечислять оба; in_progress («Ожидает») и requested («Заказать») тоже показывать, но как открытые заявки, без обещания фактической отправки поставщиком. received/cancelled/удалённые исключить.
3. Строка: id/num заявки, qty + собственная unit заявки, statusLabel, supplierName при наличии, invoiceId/invoiceNo при наличии, `invoiceDeliveryDate` (наследуется из `supplyinvoices.deliveryDate`). Дата заявки requestDate и дата счёта invoiceDate не являются сроком поставки. Нет invoiceDeliveryDate — «Дата поставки не указана»; deliveryNote можно вывести отдельно как исходный текст, не превращать в вычисленную дату.
4. При частичном приёме `receiveRaw` уменьшает qty до непринятого остатка, увеличивает receivedQty (`supply.service.ts:913–919`). Следовательно, отображать qty, **не** вычитать receivedQty повторно. Исходную unit не заменять единицей сетки. Суммировать можно только одинаковые единицы, иначе оставить отдельные строки.
5. `GET /api/stock/items/:id/ordered` также доступен stock-only (`stock.controller.ts:371`), строгий materialId, без обрезания открытых заявок. Но `StockSearchService.openRequests/itemOrdered` не возвращают deliveryDate/invoiceId; inTransit суммирует все открытые статусы и единицы. Для обещанной даты и достоверного итога брать список supply выше. `orderItem` при ошибке чтения подставляет пустой open — в C271 это недопустимо, т.к. скрывает уже заказанное.
6. Переход `#requests?open=id` и GET `/supply/requests/:id` закрыты native stock-only. В подстроке показать идентификатор и содержимое без обязательного перехода в закрытый раздел. Менеджеру с доступом requests можно оставить ссылку.

## Активные брони: данные есть, полного адресного чтения нет

`GET /api/stock/reservations?zoneId=...` доступен stock-only и возвращает группы `{key,name,batchId,createdAt,createdBy,salesOrder,salesOrderId,hanging,lines}`; строки `{id,materialId,name,unit,qty,issued,salesOrderId,salesOrderLineId,hanging}`. Источники: `stock.controller.ts:241–245`; `stock-reservations.service.ts:115–150`.

- Активность: status='active', isActive=true, deletedAt=null. Отменённые/снятые/исполненные не показываются. Назначение группы — groupName, затем orderId; подпись связанного заказа сервер уже обогащает без открытия раздела «Заказы». Нет связанного заказа — честная подпись «Без заказа», назначение сохранить.
- Для частично выданной активной брони qty — текущий остаток брони; issued — уже выдано. Не считать qty-issued (`stock-reservations.service.ts:263–267`). Показывать только lines с materialId выбранного варианта; не чужие строки группы с тем же сечением.
- Дефект полноты: `.limit(2000)` применяется глобально до scope, total считает лишь получившиеся группы. Параметр materialId не поддержан, пагинации нет; клиент не может узнать, что бронь потеряна. Групповая карточка по известному key не решает поиск всех броней материала.
- Дополнительное ограничение: list не возвращает notes каждой брони. Если «назначение» означает свободное примечание строки, его нельзя честно показать из этого ответа; существующее имя группы/заказ удовлетворяет минимальному варианту назначения, произвольный notes не выдумывать.

## «Заказать»: подтверждение и предел прав

`POST /api/supply/requests` и `/requests/bulk` наследуют `@AppSection('requests')`; они НЕ разрешены stock-only даже с эффективной ролью manager. `AppSectionGuard` проверяет реальную роль в серверном кэше, а `RolesGuard` отдельно — effectiveRoles. Название роли, theme и frontend session.baseRole сами по себе доступа не дают. Источники: `supply.controller.ts:37,396–417`; `common/guards/app-section.guard.ts`, `roles.guard.ts`, `common/app-sections.ts`, `common/stock-scope.ts`.

Для пользователя с requests + правом записи существующий POST достаточен: `{materialId,qty,unit,clientUid}`; сервер выводит title, дату и номер, status по умолчанию requested («Заказать»), paid=false (`supply.service.ts:504–549`, `dto.ts:5–39`). Qty > 0 контролировать явно: общий DTO допускает 0. Не подставлять 'шт', если unit неизвестна. Новая заявка — поручение снабжению, не заказ поставщику и не приёмка.

Первый клик открывает подтверждение: конкретная позиция + исходная единица, количество и открытые заявки этого materialId. Сохранение только отдельной кнопкой «Создать заявку». Отмена не пишет. При наличии открытых заявок по умолчанию остановить повтор и предложить посмотреть их в подстроке; если действительно требуется дополнительная закупка — отдельное явное подтверждение дополнительной заявки. Ошибка загрузки ожиданий блокирует создание до повтора чтения. Один clientUid сохраняется на все повторы одной отправки; двойной клик/повтор сети не создают вторую заявку. Это защита повторной отправки, не автоматическое объединение разных потребностей.

## Минимальные границы нового контракта для архитектора

1. Адресное чтение броней доступного materialId в разделе stock: фильтр материала и scope **до** лимита, стабильная пагинация и total/next; поля текущего остатка/единицы/назначения/заказа как выше. При необходимости notes — явно добавить. Можно расширить существующий маршрут или дать stock-facade; имя и устройство выбирает архитектор. Не загружать все брони приложения ради одной подстроки.
2. Узкое создание заявки из stock: фиксированный materialId доступной позиции, положительный qty, исходная unit, clientUid; сервер проверяет scope/право записи, задаёт requested, paid=false, автора и дату, делегирует штатному SupplyService.create с флагом `c262.supply.requests.api`/аудитом/идемпотентностью. Нельзя из этого входа задавать paid/received/цены/чужой materialId, создавать счёт или менять существующую заявку. Сохранять одну сущность supplyrequests и текущий supply write-path; не делать второй писатель Mongo.
3. Чтение открытых заявок уже есть; новый facade ожиданий необязателен. Если нужен единый лёгкий stock-context, контракт обязан сохранить полноту, точный materialId, единицы и неизвестную дату, а не оборачивать ошибочные агрегаты inTransit.
4. Настройки реальных Труборез/Лазер лист (baseRole, appSections, warehouseIds/stockCategoryIds) по локальному коду не доказаны. Координатор/access проверяет их отдельно без выдачи новых разделов. При read-only роли кнопка создания отсутствует; stock-only с предусмотренной записью работает через узкий контракт. Preview директором остаётся read-only.

## Наблюдаемая приёмка

- Если в одной строке сетки несколько materialId (длина/мойка/формат), то раскрытие показывает ожидания/брони каждого варианта отдельно; похожее название другого id не попадает.
- Если у материала >100 открытых заявок, то последняя страница видна; ошибка второй страницы не даёт пустого успешного результата. Оплаченная ordered видна; received/cancelled/удалённая отсутствует.
- Если дата отсутствует, то есть явная подпись; даты заявки/счёта не выдаются за поставку. Частичная поставка 10→приход3 показывает ожидание7 в исходной unit.
- Если глобально >2000 броней и нужная бронь старее лимита, то адресное чтение всё равно возвращает её. Active с qty7/issued3 показывает «В брони7», не4. Cancelled отсутствует; active отменённого заказа видна с предупреждением.
- Если родная stock-only роль входит без подмены manager/admin, то доступный материал читается, чужой отклонён403; «Заказать» после подтверждения создаёт одну requested-заявку в «Заявках» для менеджера. Рабочему не открывается чужой раздел. Повтор отправки с тем же ключом возвращает ту же заявку.
- Если пользователь отменил подтверждение, qty=0/отрицательное/нечисло, ожидания не загрузились, роль read-only или флаг записи выключен, то записи нет и причина понятна. Условия C270 по приёмке/количеству не дублировать.
- В pipe и sheet главный блок — история; характеристики/коды/даты изменения удалены по поручению, примечание сохранено; кошки/собаки и расписание глаз сохранены. Эти пункты подтверждаются отдельной браузерной приёмкой.
