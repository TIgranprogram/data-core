# VISION — зачем существует Personal Data Core

> Полный контекст проекта: откуда пришли, какую задачу решаем, какие были варианты и почему выбран этот.
> Дополняет [README](../README.md) (что это и как запустить) и [ROADMAP](../ROADMAP.md) (что делать).

---

## 1. Проблема

Раньше данные жили **внутри приложений**: пишешь приложение → закидываешь на сервер → данные в нём → переписываешь приложение или начинаешь новое → данные теряются, всё заново.

Нужно наоборот: **данные — отдельно и навсегда**, приложения — расходные.

## 2. Цель

Личная база данных, которая:

1. **Независима от приложений.** Приложение пишется, стирается, переписывается — база остаётся.
2. **Всегда доступна по одному URL + ключу.** Любая платформа подключается, зная документацию.
3. **Целостна.** Никто (включая будущие приложения) не может её сломать прямой записью.
4. **Не теряется.** Ежедневные бэкапы + проверенный restore.

### Примеры использования (реальные, из постановки задачи)

- **Google Sheets**: Gemini по документации создаёт подключение в таблице → таблица читает данные из базы и пишет в неё.
- **Новое приложение на Python / PHP / чём угодно**: подключаешься по той же документации и работаешь с теми же данными.
- **Агент (Gemini / Claude)**: получаешь URL + ключ + Swagger — и агент сам работает с данными.
- Разные формы ввода/вывода — **одна база**, всегда актуальная.

## 3. Ключевые принципы (не нарушать)

| # | Принцип | Практический смысл |
|--|---------|--------------------|
| 1 | **Единственный писатель — API** | MongoDB опубликована только на `127.0.0.1:27017`; наружу — только REST API за авторизацией. Прямой доступ к БД из приложений запрещён: он ломает счётчики, аудит, уникальность, soft-delete. |
| 2 | **Одна интеграция = один ключ** | Машинный ключ `kppd_...` с TTL и меткой; отозвал один ключ — отвалилась одна интеграция, остальные работают. |
| 3 | **Бэкап без restore — не бэкап** | `mongodump` по cron + **разовый restore-дрилл** после первого деплоя + копия вне NAS. |
| 4 | **Данные приложений — в свои пространства** | Новые приложения пишут в свои префиксы/коллекции (`app_*`); общие справочники (контрагенты, товары) — в канонические. Переписал приложение — не утащило чужое. |
| 5 | **Контракт важнее кода приложений** | Стабильный API + документация (`docs/CONNECT.md`, Swagger/OpenAPI) — то, что не меняется при переписывании клиентов. |

## 4. Как выбирали архитектуру (ретроспектива)

Рассматривались два варианта «ядра данных»:

| | Вариант A: готовый BaaS (Directus / NocoDB) | Вариант B: свой API поверх MongoDB |
|--|--|--|
| Плюс | Ставится часом, веб-админка из коробки | Полный контроль, своё |
| Минус | Живёшь по чужим правилам | Строить и поддерживать самому |
| **Решение** | Не выбран как основа, но **не отвергнут**: может быть добавлен сверху как админ-слой | **Выбран**: переиспользуем готовый production-бэкенд (авторизация, ключи `kppd_`, rate limiting, audit, MCP-прототип) |

Главный аргумент за B: в kppdf-8.0 уже был боевой бэкенд с ровно теми механизмами, которые нужны личному ядру (JWT + pairing-ключи, роли/права, транзакции Mongo). Вынести его дешевле, чем строить новое и поддерживать второй стек.

**Важно:** данные не привязаны к варианту. Если позже захочешь поверх поставить Directus — данные переедут одной командой, API просто сменит «окошко».

## 5. Что перенесено из kppdf-8.0 (источник)

Проект вынесен **целиком, без вычистки** (решение: сначала полный перенос, потом чистка):

- ✅ `backend/` — NestJS + Mongoose: auth, users, roles, permissions, settings, audit, health, ключи `kppd_` (модуль `desktop`), 92 модуля (включая CRM-домен, который будет чиститься)
- ✅ `docker-compose.yml` — `mongo:7` (Replica Set `rs0`) + backend, Mongo только на localhost
- ✅ `deploy/synology/` — деплой/бэкап (без секретов; реальные значения в gitignored `config.env` / `CREDENTIALS.md`)
- ✅ `docs/` — ARCHITECTURE, STACK, data-model (+audit), CONNECT (как подключаться)
- ❌ Не перенесилось (осталось в kppdf-8.0): frontend, desktop, mobile, задачи/очередь, данные (`data/`), аналитика

## 6. Текущее состояние (2026-10-17)

- Репозиторий: **https://github.com/TIgranprogram/data-core** (Private), локально: `D:\data-core`
- Код: полный бэкенд + compose + документация для подключений; инфраструктурные данные (IP/домены) вычищены из git, реальные значения — в локальных gitignored файлах
- **Работает прод-контур kppdf (на той же VM)** — data-core деплоится отдельным контуром (`/opt/data-core`, `/var/lib/datacore`), чтобы не трогать работающий CRM
- Не сделано: чистка CRM-модулей, Mongo-аутентификация, админка пользователей/ключей, публичный OpenAPI, MCP — см. [ROADMAP](../ROADMAP.md)

## 7. Чего здесь НЕ будет

- Не публичный сервис для всех — база личная, доступ по ключам.
- Не «универсальная модель на все случаи» — схемы растут из приложений, а не наоборот.
- Не прямой доступ к MongoDB «для скорости» — всегда API.
