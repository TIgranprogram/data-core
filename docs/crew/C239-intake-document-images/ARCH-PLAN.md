# C239 — минимальный план рисунков КП

Вердикт: **PASS для ограниченного single-writer сценария** в tooling+Пульте; существующих API достаточно, backend и публичный контракт не менять. Класс M: один модуль обработки изображений и его вызов из существующей панели; без универсального редактора PDF/сопоставлений.
1. Prepare ничего не пишет на сайт. Проверить фактический SHA локального PDF, owner/target, договор44 и наличие в его legal оригинала offer с тем же SHA/fileId; исходники и sourceLine не изменять.
2. Source-map аналитика: страница+bbox/xref+подтверждённые код/название/qty → существующая исходная позиция; не применять «N-я картинка=N-я строка». Логотипы/QR/печати/неоднозначные иллюстрации исключить; показать человеку карту9связей и8уникальных изображений.
3. Извлечённые файлы хранить локально с SHA, MIME, размерами и версиями extractor/source-map. Для этих небольших картинок PNG без EXIF, без увеличения/resize. Перед отправкой проверить размер≤3МБ и стороны≤2560px: иначе backend shrinkInPlace изменит байты и строгая SHA-сверка невозможна; такой случай остановить.
4. Plan/confirmation fingerprint включает owner, API target, source PDF SHA, legal offer uid/fileId, ID договора, исходную строку/её parent+sourceLine, imageSHA и список связей. Изменение после preview требует новой подготовки.
5. UI: действие «Рисунки…» у существующей строки отчёта → превью и явная отправка в той же панели. Использовать только текущий tokenProvider; JWT не сохранять и не передавать PDF/изображения внешней модели.
6. Локальный lock на корень и журнал на asset: prepared → uploadStarted → uploaded(photoId) → attached(lineIds). Сохранять состояние до POST, ID до прикрепления. Во время операции один writer для этих9позиций; не переключать контур/owner, не очищать журнал.
7. Stable originalFilename строить из полного digest(sourcePDFsha,imageSHA,formatVersion), ASCII, без rowID. Один рисунок, встречающийся в двух строках, получает один originalPhotoId с двумя связями.
8. Один GET /photos вне цикла, локальный индекс exact originalFilename. Recovery использует только variant=original, parentPhotoId отсутствует, deletedAt отсутствует, корректный ID/MIME; thumb/medium/full имеют тот же filename и не являются дублями original.
9. Перед reuse/recovery GET /photos/:id и скачивание только его безопасного /uploads пути в том же контуре; проверить SHA/размер PNG. Ноль/несколько original-кандидатов при journal.uploadStarted или расхождение байтов → pause. Не выбирать первое совпадение.
10. POST /photos/upload multipart только для asset, для которого ещё не было uploadStarted и нет кандидата. После ответа перечитать метаданные/байты, сохранить photoId. После неизвестного исхода обновить индекс один раз и искать; **не повторять upload при пустом поиске**, старый POST мог ещё не завершиться.
11. Перед каждым POST /incomes/:id/photos повторно проверить живую позицию, ожидаемый parent договора, sourceLine/code/qty/title и неархивный договор с прежним source offer. Прикреплять только оригинальный photoId через addToSet; не менять главное фото, не удалять/заменять старые.
12. После attach перечитать позицию: новый ID присутствует ровно раз, все прежние фото сохранены, parent/sourceLine/строки не изменились. После неизвестного ответа attach допустим повтор того же photoId: addToSet не дублирует связь, withLineWrite защищает архив.
13. Ограничение: multipart upload не имеет серверного unique/idempotency, а addPhoto не принимает expectedParent/version. Локальный журнал+single-writer+pause обеспечивают безопасное ограниченное выполнение; нельзя заявлять глобальную exactly-once или атомарную защиту от конкурентного переноса строки. Для таких обещаний понадобится отдельное расширение API, вне C239.
14. Тесты: prepare без POST; image reused в2строках; вариантыфото≠дублиoriginal; потерянныйuploadответ с/без кандидата; дваoriginalкандидата; AUTH/контур/hash/source/архивизменились; повторattach; сохранностьпрежнихфото; превью+confirm. Отдельно фото в позиции и печатном листе безcatalogmapping.

Реальная запись — только access по проверенному плану9связей; следующие документы проверять на копии. Никаких новых изделий/заказов/платежей; полноразмерный PDF остаётся исходным доказательством, а не заменяется вырезками. Код и данные при планировании не менялись.
