# Приёмка интерфейса: доказать удобство

Решение владельца 2026-11-11 (C086). Общий порядок для координатора, frontend, designer и QA; внешний вид — DESIGN, логика вопросов — PATTERNS. Этот порядок заменяет прежнее разрешение принимать вид только по коду и ограничение одним снимком.

## До реализации

В ТЗ указать пользовательский результат, входы в сценарий, пример заполненных данных, эталоны компонентов и проверяемые состояния. Для формы — таблицу применимости: контекст → нужные поля → источник значения → варианты → куда сохраняется. Не начинать раскладку универсальной анкеты вместо этой таблицы.

## Что означает «принято»

- **PASS** — проверены сценарии и внешний вид текущей версии; доказательства сохранены.
- **FAIL** — воспроизведён дефект; указаны шаги и ожидаемый результат.
- **PARTIAL** — только код/линтер, нет браузера, данных или части сценариев. Это не приёмка дизайна.

`Дизайнер: принято` разрешено только при PASS. Координатор проверяет доказательства перед этой меткой и перед выпуском. `Дизайнер: не нужно` — только правка подписи без изменения компонента, раскладки и поведения. Пустой экран не доказывает работоспособность заполненной формы. После исправлений повторно проверять затронутые состояния; старые снимки не подтверждают новый код.

## Обязательные доказательства

В папке задания — `UI-REVIEW.md`: версия/коммит (для незакоммиченного — список файлов и состояние diff), адрес стенда, данные/фикстура, тема, ширина окна и панели, сценарий, ожидание, результат PASS/FAIL/PARTIAL, путь к снимку, оставшиеся дефекты. Снимки открыть и оценить; наличие PNG само по себе не проверка.

Снимать изменённые состояния, а не весь сайт: заполненный список, раскрытая форма, открытый выбор, фокус/ошибка, длинное название и отсутствующее фото. Проверять обе темы; ширины по CANON §2, включая узкую панель на широком мониторе. В отчёте разрешена компактная матрица состояний. Скриншоты для порученной работы над интерфейсом разрешены этим решением; повторного разрешения не нужно. Явный запрет пользователя сохраняет силу: тогда визуальная приёмка PARTIAL.

Доступ и данные — по AGENTS: через access, без записи на прод. Нет заполненных данных — подготовить обезличенную фикстуру в изолированном тестовом контуре. Макет с подменой API годится для вида, но не для доказательства сохранения и выпуска.

## Проверка глазами и действиями

1. За несколько секунд понятны объект, его категория/контекст, готовность и следующий шаг. Название, статус и причины не слиты в одну строку капсом.
2. Акцент не окрашивает весь список. Основной текст спокойный; состояние обозначено словами. Отступы разделяют поля и группы; каждое поле имеет видимую подпись. Короткое число не занимает ширину длинного текста.
3. Переключатель режима — компактный второстепенный элемент, справа в шапке при достаточной ширине. На телефоне переносится без обрезания. Один главный призыв к действию в текущем шаге.
4. Сравнить каждый изменённый выбор/фото/кнопку с названным эталоном в другом разделе: одинаковы не только классы, но фокус, клавиатура, открытый список, вставка и ошибки. Проверить реальное раскрытие, а не только закрытое поле.
5. Зона загрузки: клик по пустой зоне даёт видимый фокус для Ctrl+V; отдельная кнопка «Выбрать файл» открывает диалог. Вставка попадает только в выбранный слот, не дублируется между слотами; работают drop, отмена, замена и ошибка. Уже загруженная миниатюра может открывать просмотр отдельным действием. Подпись назначения рисунка читается целиком.
6. Пройти от известного изделия до результата и повторить. Уточнения применимы именно к нему; известное не спрашивается повторно. Смена категории/типа не оставляет чужие варианты, скрытые обязательные поля или старую готовность.

## Защита от повторения

Детерминированный дефект закрепить тестом поведения или правилом `tools/site-audit.mjs` (например, поля без подписей, пересечение прямоугольников, горизонтальная прокрутка). При исправлении общей загрузки проверить минимум два потребителя. Тест применимости проверяет состав полей и вариантов, а не только число «готово». Автоматические проверки дополняют визуальную оценку и не объявляют сайт красивым.

Машинные ворота сегодня проверяют текст метки, а не доказательства (preflight.sh). До усиления ворот ответственность за проверку UI-REVIEW несёт координатор; не выдавать это правило за уже реализованную автоматическую блокировку.
