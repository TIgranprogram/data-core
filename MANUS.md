# MANUS.md — рабочие правила Manus для DataCore

Этот файл — памятка для Manus-сессий в репозитории. В начале задачи прочитай его и `AGENTS.md`; затем открывай только релевантные разделы документации и код. `CLAUDE.md` подключает `AGENTS.md` для Claude Code, но не считай, что он автоматически загружен в каждый Manus-чат.

## Источники истины и старт

1. Проверяй фактические `git HEAD`, ветку, `git status`, реализации и тесты. Не делай выводов только по описанию/старым отчётам.
2. Для любой работы с кодом смотри карту `docs/MAP.md`; для инвариантов — `docs/CANON.md` и относящийся раздел `docs/PRODUCT.md`; для задач — конкретный пункт `docs/TASKS.md` и ТЗ `docs/roles/tz/`.
3. Сверяй проектные инструкции, пришедшие в текущий чат, с этим файлом. Более новое явное решение пользователя имеет приоритет над устаревшей формулировкой; если два действующих требования действительно конфликтуют и выбор не очевиден, остановись и уточни.
4. Каждое существенное утверждение о состоянии кода подкрепляй точным `file:line` и/или результатом команды. Если подтверждения нет — указывай `PARTIAL`/`FAIL`, не выдавай предположение за факт.
5. Не перечитывай всё репо без необходимости. Запускай тесты только в указанном изолированном контуре и фиксируй фактические команды/результаты в `docs/TEST-LOG.md`.

## Пользователь и ответы

- Пользователь не разработчик и может диктовать голосом. Восстанавливай очевидный смысл из контекста; не заставляй пользователя читать diff, вводить команды или повторно пересказывать сохранённый handoff.
- Пиши по-русски, понятно и кратко. Давай один конкретный безопасный следующий шаг. Не говори «нажмите» без проверки, что действие безопасно.
- Для передачи работы между чатами смотри актуальный `docs/SESSION-HANDOFF-*.md`; сначала сверяйся с текущим HEAD и рабочим деревом, потому что handoff может устареть.

## Supply invoices — утверждённые правила

Пользователь 2026-11-03 явно подтвердил вариант B: **paid-счёт разрешено финансово исправлять до первой принятой строки**. Более новая принятая строка ставит финансовую блокировку для всего счёта. После неё разрешены только `fileIds`, `contractId`, `no`, `date`. Не возвращай поведение «paid блокируется сразу» без нового прямого решения пользователя.

- `amount` счёта — сумма `priceHint` строк без `deletedAt` и без `cancelled`; пересчитывай только через `recalcAmount` и внутри транзакции.
- `priceHint` заявки/строки счёта — сумма строки целиком, а не цена за единицу. `unitPrice` и `lineAmount` — только API-вход/выход; не смешивай эти значения.
- Дубль номера счёта не склеивается автоматически: ответ 409 содержит `existingInvoiceId`. Merge выполняется только явным действием.
- Не ломай `lockReason`, `recalcAmount`, duplicate 409, explicit merge route, price PATCH и financial lock без конкретного подтверждённого дефекта и регрессионных тестов.
- Paid-edit/add должны сохранять неизменяемый факт первоначальной оплаты; корректировки, причины и история цены ведутся отдельно. Удаление оплаченной строки и merge оплаченных счетов остаются запрещёнными до явного пересмотра правила.
- Не меняй схемы общих с CRM коллекций. Не трогай `/opt/kppdf*`.

## Данные, инфраструктура и выпуск

- Данные священны. Ничего не удаляй и не мигрируй в production Mongo. Не запускай E2E на production БД; E2E — только на проверенной disposable/test Mongo.
- Никогда не выполняй `docker compose down -v` и не запускай destructive Pult/Nightshift lifecycle. T23 устранён: только собственные immutable IDs, внутренние Mongo/backend, фиксированный loopback relay; остановка сохраняет три named volumes.
- Не запускай `tools/dc.mjs status` как локальную диагностику: это live production read. Доступ к production/стенду — только разрешённым проектным способом из `AGENTS.md` и deploy skills; секреты не читать/не печатать.
- Завершённый проверенный candidate коммитить и отправлять в GitHub; затем preflight должен дать ВОРОТА: ОК. Только после этого выполнять порученный выпуск.
- Проверяй `git status` перед работой и в конце. Не трогай чужие изменения, не восстанавливай чужие файлы и не используй `git add -A`; коммить только явно перечисленные свои пути после согласования.
- Не сообщай, что можно выкладывать, пока установленный проектом preflight не даёт `ВОРОТА: ОК` и обязательные gates не подтверждены.
