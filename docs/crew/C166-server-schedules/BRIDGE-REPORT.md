# C166. Мост двух серверов

20.11.2026. Локальная приёмка моста и выпуска прошла. 47 из 47 проверок. Проверки выполнялись в отдельной рабочей копии. Промышленные серверы, SSH, домен и данные для этих проверок не использовались.

## Работа штатного выпуска

Штатная выкладка получает замок `.ha-operation`, находит хостовый каталог `/host-switch` по монтированию контейнера и удерживает существующий `switch/.lock` на протяжении операции. Это исключает одновременную работу со старым мостом при первом обновлении. Занятый мост, неподтверждённое монтирование или изменившийся с предварительной проверки маркер останавливают выпуск. Это действует для полного, быстрого выпуска и штатного отката. После потери управляющего процесса незавершённая операция сохраняет свой маркер для разбора.

Один зафиксированный commit даёт полный архив backend, deploy и production compose с выпущенной version.json. Быстрый путь извлекает из него только экраны и штатный скрипт их обновления. После health, смоука оболочки и проверки полной version.json публикуются `.ha-releases/<commit>/release.tgz` и `manifest`. Манифест закрепляет commit, SHA-256 архива и хеш версии PWA. Сам архив содержит полную версию с серверным хешем. Последний шаг фиксации атомарно меняет `.release-commit`. Повторная публикация того же commit с другими байтами запрещена. Ротация оставляет три последних архива, текущий и версии, нужные сохранившимся штатным откатам.

## Обновление и восстановление

- До обработки заявки мост публикует `current` с ID и лишь затем убирает `request`. Истёкшее окно расписания завершается отказом. Недоставленный терминальный отчёт остаётся на диске для следующего цикла.
- Мост получает `dc-switch status` в свободном цикле cron. В штатной конфигурации прямые сведения о запасном обновляются с интервалом 60 секунд. При недоступном VPS в API передаются неопределённые значения владельца и обоих маршрутов с временем проверки. Наличие незавершённой операции на запасном исключает положительную оценку его здоровья.
- В режиме «Код и данные» главный проверяет принятый манифест, SHA-256 и неизменность маркера до и после передачи. Запасной сверяет SHA-256 повторно, распаковывает архив в собственный каталог задания и при необходимости собирает только образ backend. Сборка завершается до паузы записи на главном. Режим `code=0` использует существующую версию запасного.
- Запасной сверяет локальное имя хоста, HA_SELF активного backend, роль из локальной БД, отсутствие работающего kppdf-backend и направление домена. Свой замок он совмещает с существующим замком cron. После остановки только backend он снимает страховочный дамп, запоминает локальный scheduleRuntime, восстанавливает переданную БД и возвращает runtime до запуска приложения. scheduleConfig приезжает с главным дампом. Перед началом restore и активацией владелец проверяется повторно.
- Для активации используется собранный образ, локальные настройки хоста и пересоздание только backend с `--no-deps --no-build --pull never`. Проверяются health, версия, контрольные количества записей, роль и владелец. На запасном сохраняются тот же принятый архив и манифест для работы в обратном направлении.
- После ошибки старая версия восстанавливается по сохранённому image ID, прежнему коду и снимку данных. Коллекции, созданные неудачным кандидатом сверх исходного набора, при подтверждённом владении переносятся на этом же запасном в `datacore_ha_failed_<job>`, с сохранением данных. Ошибка отката либо неопределённый владелец оставляют локальный захват запасного и снимок для разбора. Главный получает отчёт об ошибке. При потере подтверждения владения в момент readonly решение о возврате записи ждёт свежего ответа VPS.
- При обычном подтверждённом переносе домена замок запасного удерживается через этапы повышения и изменения домена. Аварийный подъём по-прежнему требует отдельного задания. При неизвестном исходе команды на VPS мост проверяет его повторно по `current`.

## Замечания архитектора

Обычная выкладка и явный откат сохраняют общий замок вместе с прежним cron-flock после потери связи во время health или неподтверждённого отката. Успешный откат освобождает замок. Проверены отдельные отказы rollback и disconnect.

После перехода домена финальный отчёт нового главного должен подтвердить именно этот ID, состояние done и роль main/normal. При 503 сохраняются фаза switched на прежнем главном и захват запасного. На 409 мост сверяет статус через прежний закрытый endpoint. Завершение на стороне старого главного сверяет ID, терминальное состояние, требуемые роль и режим. Проверено повторное подтверждение на обоих концах без второй передачи данных или смены домена.

Дополнительно прошли синтаксические проверки Bash и `git diff --check` для изменённых отслеживаемых файлов выпуска. В тестовой модели выполняются настоящие shell-сценарии и операции с временными файлами, сверками хешей, манифестами и снимками. SSH, VPS, Docker, Mongo и rsync подставные. Git Bash не поставляет Linux flock, поэтому проверены реакции на получение и отказ замка. В Linux харнесс использует доступный системный flock. Фикстура выпуска теперь поддерживает `git -c ... archive`, полный ответ version.json, повторное чтение маркера и вычисленный SHA архива.

На действующих серверах отдельно проверяются доступность прямого адреса соседа, ключей обеих сторон, совместимость логинов и шифрования и полный возврат после новых записей. Наличие активной CRM на источнике исключает обычное переключение до согласованной остановки владельцем. При копировании с источника, на котором работает CRM, остаётся существующее предупреждение о внешнем писателе. Смена кодовой версии через сторонний старый `refresh-copy.sh` и ручные действия вне штатного моста/выкладки требуют отдельного согласования, поскольку такие процессы не участвуют в новом замке. Положительные ответы имитированных проверок не удостоверяют готовность рабочих серверов.
