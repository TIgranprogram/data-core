# Структура интерфейса и экономная проверка

Единый ручной запуск доступных локальных проверок — кнопка пульта «Все локальные проверки»: [порядок и границы C088](crew/C088-local-checks/README.md).

## Общий порядок проверок без повторов (12.11.2026)

Агент QA и кнопка пульта — два способа запустить одни инструменты на компьютере, а не две обязательные ступени. После успешного запуска агентом не нажимать ту же пачку через пульт ради повторного подтверждения.

| Когда | Что запускать |
|--|--|
| Небольшая правка | Проверки затронутой области по datacore-verify; записать состав файлов и результат |
| Приёмка вида | Изменённые состояния/общие потребители; геометрия и действия, затем целевые снимки |
| Перед общим выпуском с изменениями сервера | Один полный unit/e2e на зафиксированном наборе файлов, единый TEST-LOG; не ещё и dc check / «Все локальные проверки» |
| Долгий обход локальным ИИ | Отдельная исследовательская проверка сценариев на стенде; гипотезы не заменяют unit/e2e и приёмку |
| После выкладки | Версия, health, смоук и затронутый пользовательский путь; полный тестовый набор снова не запускать |

Повтор оправдан изменившимся проверяемым кодом/зависимостями/окружением, исправлением найденного дефекта либо незавершённым прогоном. Писать причину; повторять только затронутый объём. Результат переиспользуется только при совпадении проверенных файлов (hash/manifest), конфигурации, окружения и завершённом PASS; нельзя полагаться только на время или слово «готово».

**Текущее ограничение:** release/preflight.sh сам повторяет tsc и unit при серверных изменениях. Это обязательные ворота выпуска; не обходить и не использовать force ради экономии. Сейчас исключаем лишние ручные прогоны вокруг них. Безопасный перенос ранее проверенного результата в ворота требует отдельного механизма проверки fingerprints, которого пока нет.

Сводка и доказательства — в папке crew; локальные подробные логи — tools/logs и pult/logs. Ошибка соединения не считается найденной ошибкой приложения, ожидаемые 4xx отделяются от JS/5xx и гипотез модели.

Решение владельца 12.11.2026, C087. Цель — спокойное, предсказуемое рабочее место; меньше облачных токенов и повторного ввода. Приёмка — UI-ACCEPTANCE; устройство данных — VISION и CANON, не новая параллельная архитектура.

## Одна информация — одно место

Новый экран — представление существующих сущностей через API. Перед добавлением поля определить владельца данных, связь по id, источник автоподстановки и место сохранения. Не создавать вторую копию справочника под экран работника или чек-лист. Исключение — осознанный снимок выпущенного документа по CANON. Таблица «контекст → вопрос → источник → запись» обязательна для форм (PATTERNS П-1).

## Эталон и общие компоненты

Основной внешний ориентир — [формы Carbon](https://www.carbondesignsystem.com/building-blocks/core/patterns/forms): необходимые вопросы, подписанные поля, смысловые группы и постепенное раскрытие. Это источник решений, не подключённый CSS-фреймворк.

Сначала довести небольшой набор наших kit-компонентов: поле с видимой подписью, короткое число, выбор/поиск, компактный переключатель, секция, строка объекта, слот фото. Для каждого — один контракт поведения и витрина состояний: пусто, заполнено, фокус, ошибка, disabled, длинный текст, узкая панель, обе темы. Состояния списка и фото проверять открытыми и действием.

[Web Awesome](https://webawesome.com/docs/components/select/) — кандидат только на точечную пробу выбора. Ядро бесплатно, но Combobox и File Input — Pro; не обещать ими полностью бесплатную замену. Пока сторонние UI-компоненты в приложение не подключены. Не добавлять весь Bootstrap поверх существующей темы. Если собственного компонента достаточно — улучшить его, не мигрировать ради библиотеки.

## Порядок проверок и бюджет

1. Код, данные и геометрия: существующие тесты и site-audit. Неприменимые вопросы проверяются тестами правил; скриншот не доказывает правильность бизнес-логики.
2. Доступность: axe-core в site-audit на ширине 1024 для снятых состояний. Непроверенное и `incomplete` не считать успехом.
3. Пиксельное сравнение: pngjs + pixelmatch, одинаковые данные/браузер/шрифт/масштаб/тема. Эталон только после человеческой/дизайнерской приёмки; автоматическое обновление запрещено. Различие — сигнал, не приговор. Пока нет принятых эталонов паспортов — не выдавать сравнение за подключённую защиту всех экранов.
4. Локальная модель: только нужные изменённые снимки/области. До 3 изображений за запуск по умолчанию (предел 10), кэш по байтам и версии запроса. Одна модель обрабатывает последовательно; рассуждения отключены, вывод ограничен. Не крутить одни и те же снимки 24 часа.
5. Облачная модель: короткая сводка уникальных находок и только спорный снимок; не загружать весь альбом обхода. Окончательное решение по UI-ACCEPTANCE.

Сохранение PNG и локальное пиксельное сравнение не требуют токенов LLM. Локальная модель расходует ресурсы компьютера; её отчёт не становится доказательством без проверки. Скриншоты с ошибками хранить вместе с версией кода и сценарием.

Суточные прогоны полезны для разных сценариев/данных и устойчивости. Для неизменившегося вида достаточно кэша; частота сама по себе качество не улучшает. Запуски двух моделей одновременно на 16 ГБ не делать без измерения свободной памяти и нагрузки.

## Дневной прогон и вечерняя работа (договорённость владельца 12.11)

- Перед завершением изменения — обязательные целевые проверки по datacore-verify. Проверки данных, сохранения, выпуска документов и затронутой логики не откладывать на сутки. Перед выкладкой — требуемые ворота и приёмка.
- Расширенный поиск сценарных ошибок и длительные проверки — локальный дневной прогон на изолированном стенде, до 24 часов по запуску владельца из пульта. Не выполнять повторно одинаковый анализ снимка и полный Jest на каждом шаге. Автоматическое расписание этой договорённостью не создаётся.
- Каждая задача передаёт в своём CHECKLIST.md сценарии для локального прогона: входные данные/фикстура, действия, ожидаемый результат, проверка/команда, критерий остановки, место отчёта. Наличие чек-листа не означает, что новый сценарий уже подключён к тестировщику: это отмечать отдельно.
- Вечером координатор читает сводку уникальных ошибок, воспроизводит существенные, чинит и запускает целевые регрессии. Зелёный длинный лог не отправлять модели; повторные одинаковые находки склеивать.
- Сбой модели/браузера/сценария означает «не проверено», а не «ошибок сайта нет». Пустой экран не заменяет сценарий заполненного объекта.

## Темы и дальнейший порядок

Владелец считает светлую тему слишком яркой; предложен промежуточный спокойный вариант. Сначала проба токенов на витрине и форме паспорта, измерение контраста и приёмка. Не делать индивидуальные цвета на каждом экране и не обещать тему готовой до проверки. Добавление третьей темы — отдельный открытый пункт TASKS.

Первый рабочий образец — паспорта C086. После его приёмки переносить общие улучшения на формы по мере работы, проверяя минимум двух потребителей изменённого компонента. Архитектуру/данные проекта ради косметики не переписывать.

## Что подключено

- `tools/site-audit.mjs`: контроль видимых подписей и расстояний обычных полей, не только kit-контейнеров; axe при установленном пакете.
- `tools/design-checks/`: закреплённые версии axe-core, pixelmatch, pngjs, playwright-core; браузерная фикстура и сравнение снимков. Это инструменты ПК, не зависимости приложения.
- `tools/ai-tester/vision-review.mjs`: локальный анализ существующих изображений, кэш, ограниченные запросы, отдельный отчёт.
- Пульт: установка проверок, запуск локальной оценки последнего обхода и чтение отчёта.

Не подключено автоматически: обновление визуальных эталонов, круглосуточная визуальная генерация, исправление кода по предположению модели, публикация изменений.
