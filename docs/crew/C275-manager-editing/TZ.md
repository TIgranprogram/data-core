# C275 — редактирование заявок и возврат отдельных значений

Менеджер должен видеть дату и примечание в обычных формах заявки и реквизитов счёта. Для значения, которое можно безопасно вернуть из истории, человек получает понятное действие с подтверждением и новой записью аудита.

**Класс** L · **Исполнители** frontend и backend по разным путям · **Приёмка** QA, архитектор и дизайнер.

## Подтверждённые входы

1. «Заявки → Новая» и «⋯ → Изменить». `notes` и `requestDate` уже принимает `SupplyRequestDto`, но они распределены по разным частям формы. Вынести в понятное место формы и сохранить штатные имена, валидацию и историю. Быстрый ввод одной строкой остаётся доступен.
2. «Заявки → Счета → карточка → ⋯ → Реквизиты счёта». Дата доставки и примечание были удалены из формы в `fb3ab5e4`. Вернуть `deliveryDate` и `note` с текущими значениями, проверить разрешения и сохранение через существующий `PATCH /supply/invoices/:id`.
3. «Сегодня → Поставки → Перенести срок» отправляет `neededBy`, которое строгая валидация заявки не допускала. Это плановая дата той же заявки, отдельная от даты доставки счёта. Сохранение и очистка проходят через штатный PATCH.
4. Сверить менеджерские действия в задетых формах и основные бизнес-зоны. Существующую авторизацию, проверки состояний, аудит и ограничение доступа к денежным данным проверять отдельно. Не расширять права на удаление.

## Возврат значения из истории

- Использовать существующую карточку и видимый журнал. На первом этапе только однозначные нефинансовые поля с проверенной моделью. При клике видно поле, текущее значение и то, на которое оно заменится. Действие проверяет права и состояние на сервере.
- Проверяем отдельный PATCH только выбранного поля, условие на текущем значении или версии, конфликт без перезаписи чужого сохранения, отсутствие изменения остальных полей, историю с прежним и новым значениями. Исключаем суммы, количество, приёмку, состояние, складские движения, связи и удаления из первого этапа.
- Если существующий режим «Вернуть как было» открывает форму с несколькими полями, сначала документируем фактическое поведение. Атомарная запись из истории допускается только для явно перечисленных полей через штатный хозяин данных.
- Один проверяемый сценарий на первом этапе — `notes` через `PATCH /supply/requests/:id/restore-note` с `{expected,value}`. Секцию requests, менеджерскую роль, область склада, C262 и атомарную проверку значения применяет сервер. Обычное событие обновления сохраняется через аудит.

## Второй проход по зонам и экономия

- Координатор собирает только наблюдения с подтверждением и следующим действием. Аналитик сверяет исчезнувшие бизнес-поля, frontend и дизайнер — обычные сценарии менеджера, backend и архитектор — границы записи, data-steward — изменяемые данные и scope, QA — реальный isolated e2e, access и site-manager — доступность и публикация по действующим инструкциям.
- Исправить два подтверждённых локальных повтора проверок. Файлы `tools/dc.mjs`, `tools/run-all.mjs` и узкие тесты. Один обязательный тест рисунка паспорта со своим PASS/SKIP. Три уже выполняемых в `dc check` теста Пульта повторно не запускаются в том же маршруте. Все остальные проверки и прежние коды результата сохраняются.
- При уходе помощника по лимиту сохраняется базовый SHA, изменённые пути, последняя команда и её результат, следующий открытый пункт C275. Продолжает текущий координатор с этой точки. Повтор одного задания другой моделью нужен только при неполном или неподтверждённом этапе.
