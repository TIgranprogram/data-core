# C271 — минимальное дополнение API рабочего контекста

Статус: архитектурный проект, 26.11.2026; координатор принимает реализацию отдельно. Опорный HEAD `3feff09c`. Основание — `ANALYSIS-TZ.md`, бизнес-правила — `ANALYSIS.md`. Класс L: backend + UI, full/e2e перед выпуском. Код и данные этой работой не менялись.

## Дефекты и сохранённые границы

- `supply.controller.ts:409–415`: POST заявки закрыт разделом requests; stock-only пользователь не может заказать материал. Это новый явно запрошенный узкий сценарий, не основание открывать requests целиком.
- `stock-reservations.service.ts:115–121`: глобальные первые 2000 броней фильтруются по scope после выборки. Использование этого списка для материала теряет записи и не даёт достоверного total.
- `supply.module.ts:14,38` уже импортирует StockModule. Добавление SupplyModule в StockModule создаёт взаимную пару, запрещено L-256.
- L-254/L-262 сохраняются: пишет SupplyService/хозяин supply, новый сценарий подчиняется существующему `c262.supply.requests.api`; не трогает приход, бронь, flags C263–C265, CRM или shared-схемы.

## Маршруты и владельцы

### Создание заявки

`POST /api/stock/items/:id/request` → новый отдельный `SupplyStockRequestController` **в SupplyModule**, префикс контроллера `stock/items`, `@AppSection('stock')`, `@StockScoped()`, `@Roles('admin','manager')`, существующий audit action создания SupplyRequest. Владелец кода backend. Контроллер использует публичные SupplyService и StockService; StockModule не получает зависимости от supply. Возможность предусмотрена stock-пользователю с правом записи явно; доступ к остальным supply mutations и разделу requests остаётся прежним. `user` — наблюдатель (`roles-hierarchy.ts`), в POST его не добавлять; наличие worker-view/stockViews само по себе не право записи. Native роли должны подтвердить manager/director базу; при baseRole=user новый POST недоступен, отдельное разрешение требует отдельного явного решения владельца. Director наследует manager по существующему канону. UI показывает подтверждение только при той же серверной возможности, readonly=user получает только чтение.

DTO только `{ qty: number, clientUid: UUID }`: конечное положительное qty, UUID обязателен; остальные поля запрещены ValidationPipe. ID материала только из URL, `oid()` и существование активного материала обязательны при любом scope, в том числе null. Проверить доступ к материалу текущим StockScope до любого чтения результата повтора или записи. `assertMaterials()` отдельно недостаточен: `stock-core.service.ts:75` пропускает отсутствующие позиции. Использовать публичный scoped getter StockService либо узкий публичный метод проверки активного материала, если getter избыточен.

Owner action `SupplyService.createStockRequest(id,dto,userId,scope)` устанавливает materialId, название и unit из активного материала; отсутствие unit — 400 с понятным текстом, без подстановки «шт». `status=requested`, `paid=false`, дата и requestedBy/createdBy — серверные. Вызывает штатные `assertNew()` и `create()`, не пишет supplyrequests из stock. Не принимает цену, поставщика, заказ, статью, статус, дату, свободный title, categoryId, другой materialId или unit. Ответ 201: узкая проекция `{ id, num, materialId, qty, unit, status }`, без денег/контрагентов. На успешный повтор — тот же id и та же узкая форма; 400 невалидное тело/id/unit, 403 нет раздела/прав либо чужая позиция по принятой конвенции, 404 отсутствующий/архивный материал, 409 выключен C262 или конфликт ключа.

### Активные брони одного материала

`GET /api/stock/items/:id/reservations?page=1&limit=20` — StockController → StockService → StockReservationsService. `@AppSection('stock')`, `@StockScoped()`, роли как у чтения stock; query DTO только page/limit, целые page≥1 и 1≤limit≤100. Сначала проверить активный материал и scope, затем запрос **в Mongo** `{ materialId: oid(id), status:'active', isActive:true, deletedAt:null }`, стабильная сортировка `{createdAt:-1,_id:-1}`, skip/limit и countDocuments одного фильтра. Никакой глобальной выборки/группировки с последующим отбором.

Ответ `{items,total,page,limit}`; item — одна бронь: `{id, materialId, qty, unit, groupName, orderId, salesOrderId, salesOrderLineId, salesOrder, hanging}`. Неизвестные подписи/связи — null; unit из материала, qty уже остаток, issuedQty не вычитать. groupName/строковый orderId остаются самостоятельным назначением; salesOrderId — отдельная связь, не подменять им orderId. Заказы обогащать одним batch-запросом с узкой проекцией без финансов. Закрытый/удалённый заказ не отменяет активную бронь: сохранять её с hanging, историческое чтение удалённого заказа допустимо явно для этой пометки. Новый список не раскрывает чужие линии batch. Старый GET /stock/reservations и его ответ не меняются.

Типы ответа: id/materialId/orderId/unit — строки; qty/total/page/limit — числа; groupName/salesOrderId/salesOrderLineId/salesOrder/hanging — string|null. `salesOrder` — короткая подпись из orderNo/title; hanging — существующее человекочитаемое объяснение связи с закрытым/удалённым заказом. Не формировать ссылки на недоступный native пользователю раздел заказа. GET роли `admin,director,manager,user` с текущей иерархией и AppSection. Для page/limit применять явное числовое преобразование и IsInt/Min/Max, дробь/NaN/пустое значение/неизвестный query→400; absent→defaults. POST qty — JSON number (строку не принимать), finite >0; clientUid — UUID v4, trim/преобразование qty не подменяют валидацию. Неизвестные query у POST также не разрешать.

Для materialId/status/isActive/deletedAt и стабильной сортировки проверить explain на копии с нагрузкой; существующий отдельный materialId index достаточен для старта, но при тяжёлом запросе добавить адресный compound index в схему и `backend/scripts/ensure-indexes.js`; обязательный ensure-indexes после выкладки при добавлении. Цель тяжёлого запроса <300 мс; отсутствие замера не выдавать за PASS.

### Ожидания

Существующий `GET /api/supply/requests?materialId=<id>&status=in_progress,requested,ordered,paid&page=…&limit=…` уже допускает stock и scope; новый backend endpoint для него не обязателен. UI проходит страницы до total либо показывает явное «ещё»; первая страница не считается всем набором. Для рабочего контекста разрешены только узкие безопасные поля и действующее серверное скрытие денег; проверить реальным native JWT, что sum/priceHint/catalogCurrentPrice/финансовые вложения скрыты. Если существующий money interceptor не покрывает список/итоги, блокировать выпуск и добавить узкую worker-проекцию у supply, не расширять доступ к деньгам и не менять старый ответ.

requested/in_progress — открытые заявки; ordered/paid — заказано/оплачено, не называть все статусы «в пути». Только invoiceDeliveryDate — срок поставки; отсутствие → «Дата поставки не указана». requestDate/invoiceDate не срок. Каждая заявка сохраняет собственную unit, остаток qty вторично не уменьшать на receivedQty. Суммы разных unit не складывать.

## Идемпотентность owner action

UI создаёт UUID на подтверждённое намерение и сохраняет его до известного исхода. Повтор с неизвестным результатом отправляет тот же clientUid и Idempotency-Key; новый UUID только для нового намерения. Кнопка disabled — дополнительная UX-защита.

Существующий SupplyService.create (`501–506`) ищет clientUid; глобальный IdempotencyInterceptor кеширует после действия и сам не закрывает окно commit-before-cache/одновременный первый повтор. Не добавлять unique index ко всем историческим clientUid без аудита дублей.

Рекомендуемая узкая реализация без новой shared-схемы: сервер выводит стабильный request `_id` из первых 24 hex SHA256 с фиксированным префиксом C271 + actorId + UUID (не из qty); сохраняет server-generated clientUid `c271:` + полный SHA256 канонического `{actorId,UUID,materialId,qty,unit}`. Внутренний параметр `_id` доступен только owner action, не публичному DTO. Перед create проверить существующий `_id`; после 11000 по **этому `_id`** перечитать его. Совпадение persisted clientUid → тот же результат, несовпадение → 409. Проверять fingerprint, а не текущую qty: заявку позже могут частично принять/исправить. Повтор возвращает текущую безопасную проекцию. Остальные 11000 не маскировать. Это использует unique `_id` Mongo, сохраняет прежний create pipeline и не меняет shared-поля; серверный clientUid укладывается в существующие 100 символов. Побочные эффекты/afterCreate выполняет только победившее создание; счётчик может иметь пропуск номера, дубль номера/заявки запрещён. Допустима эквивалентная атомарная owner-реализация с доказанной гонкой, глобальную idempotency не рефакторить.
