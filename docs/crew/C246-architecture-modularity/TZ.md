# ТЗ C246 — Оценка модульности архитектуры

> Пишет координатор. Отчёт — `REPORT.md` рядом. Код не менять.

**Зачем (словами пользователя):** архитектура разрослась; хорошая — когда один модуль убираешь/заменяешь, и всё не рушится. Насколько у нас так? Честно и по сути, что делать.

**Зачем — глаголом:** архитектор за 1 проход отвечает: можно ли заменить блок без обрушения, где связность жёсткая, что чинить первым.

## Глубже
- **Результат:** честная оценка заменяемости модулей + 3–5 конкретных рычагов улучшения (не «надо лучше»).
- **Сырьё:** живой код `backend/src`, `audit-cycles.js`, `app.module.ts`, ARCH-PLAN диагноз, общие с CRM коллекции.
- **Метод:** тест заменяемости — «вынуть модуль X → что ломается»; граф импортов Nest; писатели общих коллекций; фасады vs прямые зависимости.
- **Внешний судья:** `node backend/scripts/audit-cycles.js` (+ `-v` при находках); числа импортов/писателей; файл:строка.
- **Смелая планка:** ≥3 модуля, которые реально можно выключить без падения ядра; явный список «нельзя вынуть без фасада».

**Класс:** L · **Max agents:** 1 · **Reviewers:** architect ☑ · **Max review loops:** 1 · **Проверки:** smoke (`audit-cycles.js`) · код не править

## Что сделать
1. Снять картину: Nest-модули, `common/` vs `modules/`, границы API/PWA/admin.
2. Прогнать `node backend/scripts/audit-cycles.js` (и `-v` если пары > 0).
3. Тест заменяемости на 5–7 ключевых доменах: stock, supply, finance/incomes, salesorders/orders, passports, catalog/product, auth. Для каждого: кто импортирует, кто пишет его коллекции мимо модуля, что сломается при замене.
4. Отдельно оценить жёсткую связку с CRM (общие коллекции, прямой Mongo у kppdf).
5. Сверить с открытыми АБЗ в `docs/ARCH-PLAN.md` (что уже сделано, что ещё жжёт).
6. Вердикт одной фразой + оценка «насколько хорошо» (шкала 1–5 или %) + что делать: 3–5 шагов по приоритету риска/пользы.
