# C156 — работа и переход между компьютерами

## Для владельца

1. Для настоящей работы нажмите в пульте **«Открыть рабочее приложение»**. Рабочие записи сохраняются через API Synology.
2. Для проверки изменений нажмите **«Запустить разработку»**. В приложении будет отметка «Разработка» с датой копии. Это отдельные тестовые данные.
3. **«Проверить подключения»** покажет доступность сайта, GitHub, Docker и локальной копии. Ошибка одной среды не переключает другую.
4. Перед переходом на другой ПК поручите агенту сохранить работу. Проверенные изменения он отправит в `main`, а открытые пункты отметит в `docs/BACKLOG.md`.
5. На втором ПК откройте тот же проект и нажмите «Забрать обновления из GitHub». Порядок продолжения указан в `docs/BACKLOG.md`.
6. После получения кода снова нажмите «Запустить разработку»: это пересобирает локальный backend, сохраняя тестовые данные. Рабочий сайт от Git pull не обновляется.

Вторая рабочая база не создаётся. Копия разработки не синхронизируется обратно с Synology. Обновить её данные — отдельная операция восстановления, не часть обычного запуска.

## Для агента: завершённая работа

- Начало: актуализировать origin, проверить ветку, upstream, dirty, чужие сессии и запись «Сейчас» в BACKLOG. Не прятать и не перезаписывать чужое.
- Рабочая ветка по умолчанию — `main`. Для независимых поручений агенты могут работать параллельно, а изменения в общих файлах вносятся по очереди. Координатор проверяет итог и коммитит конкретные файлы.
- Законченный участок: необходимые проверки → docs → отдельный commit → push в `origin/main` и сверка с локальным HEAD. В BACKLOG указать следующий шаг, в последней строке коммита — эстафету дома/работы.
- Другой ПК: только чистый checkout обновлять fast-forward. При расхождении/чужом dirty сначала установить происхождение, не делать автоматический reset/stash/merge.

## Для агента: незавершённая работа

- Основная очередь — BACKLOG в `main`. Отмечать, что уже проверено и чего ещё не хватает. Проверенный самостоятельный участок можно сохранить в `main`, если он пригоден без остальной реализации.
- Отдельная `codex/wip-<дата>-<задача>` нужна, когда незавершённый код нельзя безопасно включить в `main` и его надо сохранить для продолжения. После сохранения указать точный commit и остаток в BACKLOG. Секреты, локальные настройки, архивы БД и uploads в Git не добавлять.
- Из имеющихся WIP переносить в `main` только проверенные изменения с учётом актуального кода. Архивные ветки и данные сохранять до сверки.

## Ограничения проверки

Настройка и браузерный прогон выполняются на текущем ПК; физический второй ПК этим не проверяется. Переносимые пути и платформенные команды проверяются программно. Пароли/SSH-ключи, если их нет на втором ПК, переносятся существующим отдельным процессом, не через Git и не через чат.

Реальное бизнес-сохранение в главную БД не входит в C156. Выкладка backend на Synology — отдельное поручение после проверок. Ни ветка, ни запуск локальной разработки не являются выпуском.
