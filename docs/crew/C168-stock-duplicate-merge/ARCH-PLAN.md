# C168 — архитектурные условия до реализации

Вердикт: readonly preview можно реализовать; commit merge включать только после доказанного протокола писателей и размещений. Это план, не готовый механизм и не разрешение менять прод.

1. Доказанный обход уже внутри data-core: `stock-core.service.ts:75–78` выбирает первую zoneName и создаёт storageitem без проверки состояния Material; `stock-movements.service.ts:48` проверяет материал до транзакции, внутри снова вызывает loadStorage; `stock-reservations.service.ts:77` также вызывает loadStorage без проверки закрытого материала. Одной транзакции merge и deletedAt недостаточно: поздняя операция может воссоздать закрытый materialId.
2. Ввести общий transactional identity fence/resolver в common/catalog, используемый всеми писателями остатков, броней, приёмки, отмен, возвратов, составов и синхронизации. Писатель в той же session проверяет активную идентичность и действительно изменяет общий guard/revision материала; merge захватывает оба guard в стабильном порядке. Snapshot-read без общей записи не защищает новые ссылки/фантомы. Все проверки повторяются при retry транзакции.
3. `ARCHITECTURE.md:74,80–81` подтверждает отдельного CRM-писателя readWrite общей БД. Его конкретный протокол в этом scope не исследован: статус unknown, commit disabled. Не требовать остановки CRM по одному факту её существования. Достаточное доказательство — адресная проверка соответствующих CRM/import writers и тест запрета/разрешения закрытого ID после commit. Локальный mutex data-core и change stream этого не обеспечивают; временная пауза не решает позднюю запись после объединения.
4. Preview читает все размещения обеих позиций, включая архивные/недефолтные, и не вызывает defaultWarehouse(), способный писать. Первый исполнимый commit ограничить одним действующим default-складом и единственным размещением без zoneName; остальные случаи показывать с блокером. Это соответствует текущим move/cancel/reserve, адресующим default/первую зону; не обещать поддержку нескольких зон до изменения всего пути операций.
5. `storage-item.schema.ts:105–118`: уникальные ключи warehouse/material/zone и warehouse/material для null-зоны не включают deletedAt. Нельзя просто soft-delete источника и изменить его materialId при коллизии; суммировать в существующую целевую строку, исходную закрыть с исходным materialId/картой происхождения. Точную политику null/missing/пустой zoneName и наличие живых индексов доказать на копии. `materials.stockQty` не второй запас.
6. Минимальный API: POST /stock/material-merge/preview {sourceId,targetId,resolutions} → {planHash,expiresAt,canMerge,blockers,placements,references,conflicts}; POST /stock/material-merge {sourceId,targetId,resolutions,planHash,clientUid,confirm:true} → сохранённый результат операции. Строгие DTO; существующие stock edit/warehouse/category scope на обеих карточках и результате, деньги только денежным ролям. Неполнота writer/reference capability — явный blocker, без утечки чужих связей.
7. planHash включает нормализованное намерение, версии карточек/guard, размещений, броней и затронутых ссылок/конфликтов. На commit всё пересчитать в session; stale → 409 с новым preview, никаких частичных переносов. Guards должны покрывать вставку новых зависимых документов, а не только update прочитанных строк.
8. В одной Mongo4.4 transaction: проверить replay → захватить identity fences → проверить план/согласованность → изменить разрешённые живые ссылки и суммы по размещению → сохранить provenance/снимки/аудит → закрыть source → сохранить result. Не создавать движений приёмки/выдачи, не объединять брони, счета и платежи. Исторические qtyBefore/After и выпущенные снимки сохраняются.
9. Постоянный registry операции с уникальными clientUid и закрываемым sourceId: одинаковый ключ+намерение возвращает прежний result даже после дальнейших изменений; другой payload того же ключа → 409. Проверка актуальных прав обязательна и на replay. Первый выпуск не допускает циклы/перенос source с уже существующими входящими alias без отдельного транзитивного протокола.
10. Старый GET/URL разрешается к основной карточке с происхождением и текущей проверкой доступа; новая запись по закрытому ID → 409 MATERIAL_MERGED + canonicalId. Историческая отмена/возврат разрешает canonicalId и исходную бронь/размещение внутри транзакции, сохраняя исходные ID; публичный произвольный PATCH/restore дубля запрещён. Простое deletedAt не является протоколом merge.
11. Порядок: readonly preview/полная capability matrix → identity guard и все контролируемые писатели → ограниченный single-placement commit → гонки receive/reserve/cancel/merge + fault rollback/replay → UI/QA на копии → расширение размещений отдельным этапом. При неизвестной CRM-совместимости preview доступен, commit остаётся отключённым с точной причиной.
