# ВЛ-1 Вложения изделия — разбор аналитика (2026-11-05)

Источник: TASKS.md:388-397. Код и прод не трогались. Вопросы — QUESTIONS.md «ВЛ-1» (ВЛ-В1…В5).

## 1. Как грузятся файлы сейчас
- `POST /photos/upload` (`photos.controller.ts:54`): multer `diskStorage` (на диск потоком, не в память) → `uploads/<назначение>/<ГГГГ-ММ>/<uuid>.<ext>`. Лимиты: картинка 10 МБ, PDF 20 МБ, чертёж 50 МБ (`image-upload.options.ts:9,15,19,86`). Имя от клиента на диск не идёт.
- Чертёж уже есть: `purpose=drawing`, PDF/DWG/DXF, сигнатура (`drawingSignatureOk` :27), привязка `POST /products/:id/photos` (`product-photo-purpose.ts:5`), экран `pwa/sections/product-files.js` («Фото и файлы» → «Чертежи»). Это малый предшественник ВЛ-1.
- Отдача: `/uploads/*` публичная статика (`main.ts:124`), у `/drawing/` — attachment + nosniff. JSON-тело 1 МБ (`main.ts:74`) multipart не касается.
- Лимиты цепочки (то, что мешает 512 МБ): (а) nginx `/db/` `client_max_body_size 16m` (`deploy/synology/nginx-datacore-db.conf:17`) — 413 на любом файле >16 МБ (значит и чертежи 50 МБ через домен сейчас не проходят — проверить); (б) `proxy_request_buffering` по умолчанию включён: nginx копит всё тело на диске VPS, потом шлёт; нужен `off`; (в) `proxy_read/send_timeout 120s`; (г) Node `server.requestTimeout` по умолчанию 300 с — на узком канале 512 МБ идут дольше; в `main.ts` его нет, надо отключить для маршрута загрузки; (д) throttler `short` 60/мин — ок.
- Вывод: переиспользовать можно schema-приёмы и `decodeMulterOriginalName`, но **отдельный контроллер и multer-опции** (свой каталог, свой лимит, свой список форматов). `photos` не расширять: он завязан на картинки, миниатюры, `Photo`-записи.
- Правка nginx на VPS — только блок `/db/`, с бэкапом (AGENTS п.6). Лучше отдельный `location ^~ /db/api/attachments/` с `client_max_body_size 520m; proxy_request_buffering off; proxy_read_timeout/send_timeout 1800s`; общий лимит 16 МБ остаётся. Это действие пользователя/админа, пункт в `pult/todo.json`.

## 2. Данные
- Отклонение от предложения TASKS: не `products.attachments[]`, а **отдельная коллекция `productattachments`**. Причина: `products` общая с CRM; массив растёт, пишется целиком при конкурентной правке, фильтр «все файлы вида» и ZIP по заказу сложнее; CRM ничего не знает. Изделие поле не получает вообще (контракт CRM цел). Для списков — число файлов считать запросом/агрегацией.
- `productattachments`: `productId` (idx), `typeId` (ObjectId строки справочника), `originalName`, `storedPath` (относительный), `size`, `mime`, `ext`, `sha256` (необязательно; нужен для «уже загружен»), `uploadedBy`, `uploadedAt`, `deletedAt/deletedBy`. Индексы: `{productId, typeId, deletedAt}`, `{typeId}` (для usage справочника).
- Виды: не новая коллекция, а справочник `simpleList` в `dicts.defs.ts:141` (`dict_values`, dict=`attachmentTypes`): название, порядок, «допустимые форматы» (необязательно, текст). Получаем бесплатно: экран, usage («Используется: N»), запрет удаления занятого, объединение. Связь по id → переименование безопасно. Стартовые значения: Чертежи, Паспорта, Договоры/КП, 3D-модели (сид по `defaults`, пользователь правит).
- Права: список/скачать — `admin, manager, user` (кто видит изделие); загрузить — `admin, manager` (ВЛ-В3); удалить — только `admin`; справочник видов — как прочие справочники. Деньги не участвуют.
- Журнал: `@AuditAction` create/delete (`entityType: 'ProductAttachment'`) с именем, видом, размером; скачивание не пишем (шум), ZIP пишем одной строкой (заказ, число файлов).
- Удаление: по CANON — мягкое (`deletedAt`), файл на диске стирает ночная задача через 14 дней (ВЛ-В1). Без этого «удалил, а место не освободилось» (ещё и копии, см. п.4).

## 3. Защита файлов
- Путь: `uploads/attachments/<productId>/<typeId>/<uuid>.<ext>`; имя на диске только uuid (+ нижний регистр расширения из белого списка); исходное имя — в БД, при скачивании — `Content-Disposition: attachment; filename*=UTF-8''…` с очисткой `\ / : " \r \n` и точек в начале. Путь собирает сервер, ids проверяются как ObjectId.
- Проверка до приёма: расширение из белого списка TASKS:394; всё иное и исполняемые (exe, dll, bat, cmd, ps1, sh, js, vbs, msi, jar, com, scr, html, htm, php) — 400. Двойные расширения (`a.pdf.exe`) — смотрим последнее.
- Проверка содержимого после записи (первые 512 байт), таблица ext → сигнатура: PDF `%PDF`; DWG `AC10`; DXF текст `0\nSECTION`; PNG/JPG/TIFF/BMP/WEBP/GIF по магии; DOC/XLS/PPT/IPT/IAM/SLDPRT(старые) — OLE `D0CF11E0`; DOCX/XLSX/PPTX/ODT/ODS/F3D — `PK`; ZIP `PK`, RAR `Rar!`, 7Z `7z¼¯`; AI — `%PDF` или `%!PS`; CDR — `RIFF…CDR`; FBX `Kaydara FBX Binary`; 3DS `4D4D`; SKP `FFFE FF0E`; 3DM `3D Geometry File Format`; STEP `ISO-10303-21`; IGES — текст (строка 73 = `S`); STL — `solid` или бинарный (размер = 84 + 50·N); OBJ, TXT, CSV, SVG — текст без нулевых байт. Для форматов без надёжной сигнатуры (SLDASM, новые SLDPRT — проверить на образцах) — запрет исполняемых заголовков (`MZ`, `\x7fELF`, `#!`, `<script`, `<html`) вместо точного совпадения. Не совпало — файл удаляется, 400 по-русски (ошибки — `error-messages-ru.spec`).
- SVG: в `photos` запрещён (XSS, `image-upload.options.ts:10`). Здесь допустим только при отдаче строго `attachment` + `nosniff` + `Content-Type: application/octet-stream` и CSP `sandbox`; предпросмотра SVG на сайте нет.
- Архивы не распаковываем и не сканируем: исполняемый файл внутри ZIP остаётся риском; закрывается тем, что файлы отдаются только как скачивание. Антивирус на VM не нужен для старта; вопрос на потом.
- Скачивание только с токеном: `/uploads/attachments/` исключить из публичной статики (в `main.ts` запретить префикс; сейчас вся `uploads` публична, uuid — единственная защита). Эндпоинт `GET /api/products/:id/attachments/:aid/file` под JWT. Проблема: ссылка `<a href>` не шлёт заголовок, а `fetch→blob` для 500 МБ ест память браузера. Решение: `POST …/download-ticket` (JWT) → одноразовый тикет на 60 с (в памяти/коллекции с TTL) → `GET …/file?t=<тикет>` стримит с диска (`createReadStream`, поддержка `Range` для докачки). То же для ZIP.
- Ошибка клиента при обрыве: частично записанный файл удалять (`req.on('aborted')` / multer cleanup), иначе мусор в `uploads`.
- Лимит размера — из настройки (`ATTACHMENT_MAX_BYTES`, по умолч. 512 МБ) в multer `limits.fileSize`; общий потолок папки (ВЛ-В5): перед приёмом проверка `uploads/attachments` + свободное место, иначе 507/400 «Нет места».

## 4. Бэкап и диск
- `backup.sh:50-54`: uploads копируется `cp -al` (жёсткие ссылки) — файлы вложений не перезаписываются, копия бесплатна по месту. Но удалённый файл освобождает место только когда уйдёт копия (до 14 дней, `BACKUP_KEEP`=10) — это ещё одна причина «стирать через 14 дней».
- Риск: `offsite.ts:224-228` каждый день заново пакует `uploads-<штамп>` в zip, шифрует и льёт на WebDAV (Яндекс-Диск). С вложениями — десятки ГБ ежедневно: переполнит облако и канал, `keep` копий × размер. Нужно исключить `attachments/` из `.dcb` (ВЛ-В4) и дать отдельный режим (еженедельно/на второй диск). Это правка backend (`backupDirs`) и README.
- `bundle.sh:123` (`tar -czf` всей uploads) и `verify-restore.js` — тоже исключить/предупредить; иначе перенос на другую ВМ тяжелее.
- Диск: `disk.controller.ts:47-62` `computeHeavy` уже считает `uploadsBytes`; добавить `attachmentsBytes/attachmentsFiles` (обход `uploads/attachments`, кэш 1 ч уже есть) и в «Состояние» — строка «Вложения: N файлов, X ГБ» + предупреждение жёлтое/красное, когда свободно < 15 % / < 10 ГБ или вложения > потолка. Использовать существующий `diskState` (`disk-usage.ts`).
- Свободное место VM сейчас неизвестно (занято 29 ГБ из ?) — **замер на проде нужен до старта** (`datacore-access`, `GET /api/health/disk`). Если свободно < 100 ГБ, потолок вложений ставить жёстко.

## 5. ZIP по заказу
- Цепочка: заказ `salesorders` → позиции `incomes` (`orderId`, `productId`, `lineType`; `income.schema.ts:20,23`) → изделия `products` → `productattachments` (`deletedAt` пусто, выбранные `typeId`). Позиции `service` и без `productId` пропускать; одинаковые изделия — один раз. В ответе заранее: «N файлов, X МБ».
- `GET …/salesorders/:id/attachments.zip?types=a,b&t=<тикет>`: `archiver` уже в зависимостях (`offsite.ts:3,225`) → `archiver('zip', { store: true })` (форматы уже сжаты, CPU не тратим), `createReadStream` каждого файла, `pipe(res)`; Zip64 автоматически; в память ничего не грузится. Структура: `<№ заказа>/<код изделия — название>/<вид>/<файл>`; дубли имён — суффикс ` (2)`; имена очищены. Обрыв клиента → `archive.abort()`, закрыть потоки. Не больше 2 одновременных ZIP, потолок размера (например 5 ГБ) с понятным сообщением. Роли — `admin, manager`.
- Отсутствующий на диске файл — пропустить и записать `_ПРОПУЩЕНО.txt` в архив, не обрывать.

## 6. Экраны (pwa)
- Виды: `pwa/sections/dicts.js` строит из `DICTS` (`dicts.defs.ts`) — новый справочник «Виды вложений» появляется сам в группе (предложение: «Изделия и паспорта»). Ничего нового в вёрстке не придумывать (CANON, правило «только эталоны»).
- Карточка изделия: `products.js:119` `extra` уже содержит `productFilesBlock` («Фото и файлы», правая панель, секции `kit.section`). Новый блок **«Вложения»** рядом: `sections/product-attachments.js`; на каждый вид — `section({title: вид, count})`, внутри `row` (иконка, имя, размер, «Скачать», «Убрать» только admin) + зона загрузки. Загрузка 512 МБ нужна прогресс (XHR `upload.onprogress`, кнопка «Отмена»), не `photoDrop` (он для картинок). Пустые состояния с подсказкой, ошибки через `errText`. Виды без файлов показывать свёрнутыми «Пусто», чтобы менеджер видел, куда класть. Ввод — только правая панель; на телефоне — полный экран (DESIGN-MOBILE).
- «Чертежи» из «Фото и файлы» не удалять (ВЛ-В2); чтобы не путать, подписать подсказкой «Для больших файлов — блок Вложения».
- Скачивание пакетом: в карточке заказа (`salesorders.js`) пункт «Скачать вложения (ZIP)» → правая панель: галочки видов, итог «N файлов, X МБ», «Скачать». Помощь «?» (`help-flow-data.js`) — обновить.
- «Состояние» — строка из п.4 (админка/pwa, где показан `health/disk`).

## 7. Разбивка на ТЗ (порядок)
0. **До кода** (пользователь/админ, пункт в pult): замер диска VM; nginx-блок для вложений (п.1); ответы на ВЛ-В1…В5.
1. **BE-1 (architect → backend)**: справочник `attachmentTypes`, схема `productattachments`, загрузка (multer, лимиты, белый список, сигнатуры, requestTimeout), список/удаление/restore, тикет и скачивание с Range, закрыть публичный `/uploads/attachments/`, аудит, юнит на сигнатуры и пути. Критерии: `.exe` как `.pdf` → 400; файл 512 МБ идёт без роста памяти процесса; без токена → 401; чужой/удалённый id → 404.
2. **BE-2**: ZIP по заказу (стрим, лимиты), disk-метрики и предупреждение, исключение `attachments` из offsite/bundle, ночная чистка удалённых.
3. **FE-1**: блок «Вложения» в изделии, загрузка с прогрессом, скачивание по тикету.
4. **FE-2**: ZIP из заказа, строка в «Состоянии», помощь «?».
5. **QA**: e2e (загрузка/запрет/права/скачивание/ZIP), нагрузочная проверка 512 МБ на стенде (не на проде), проверка nginx-цепочки через стенд. **Designer** — после FE-1 и FE-2 (виды, пустые состояния, телефон).
- Риски: (1) нет замера диска — можно забить VM; (2) offsite-копия раздует облако, если не исключить; (3) таймауты по цепочке VPS→туннель→VM для 512 МБ — проверять реальной загрузкой на стенде; (4) сигнатуры 3D-форматов не подтверждены официальными спецификациями — собрать образцы файлов от пользователя; (5) публичный `/uploads` — вложения из него вывести до выкладки, иначе «только с токеном» не работает; (6) `products` общая с CRM — полей в неё не добавляем.
