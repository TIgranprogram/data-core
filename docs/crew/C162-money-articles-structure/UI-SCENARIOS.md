# C162 — сценарии компьютерной приёмки и границы UI

Статус19.11.2026: сценарии реализованы по CONTRACT.md и проверены серверным QA; точные доказательства и ограничения визуального прогона — UI-REVIEW.md. Архитектурные замечания закрыты адресными исправлениями (ARCH-REVIEW.md). Идёт итоговая приёмка перед сведением с актуальным main и выпуском. Примеры относятся к изолированной копии; производственные статьи и счета пока не изменялись. Факты оплаты и денежные ограничения остаются C158.

## Поведение и URL

Один существующий раздел «Деньги»: «По статьям» показывает дерево и периоды; «Операции» показывает подтверждённые факты таблицей. Переключатель режимов сохраняет период, компанию, тип факта, статью, объект, направление затрат, контрагента и источник. Возврат восстанавливает раскрытие по ID, а не имени; смена фильтра сбрасывает страницу на1. Итоги берутся из сервера по всему набору, не складываются браузером по странице.

Реализованная маршрутизация: сохранить `tab=articles`, добавить отдельный `view=articles|operations`; существующий `mode=company|object` не переиспользовать под новый переключатель. Канонические `from/to/type/companyId/articleId/salesOrderId/costCenter/counterpartyId|counterpartyName/source/unassigned` общие для режимов; `page/limit/sort/dir` относятся к операциям. Старый `org` читается совместимо. Точное принятие URL-ключей — после решения архитектора; это предложение интеграции, не новый принятый API.

Таблица операций: дата → поступление/выплата → сумма,₽ → наша компания → статья/полный путь → контрагент → объект/заказ → направление затрат → документ/источник → разрешённое действие. Полный путь/длинное название читаются раскрытием строки; дату, номер и сумму не обрезать. В итогах подписи «Поступления», «Выплаты», «Денежный результат».

Справочники: существующий редактор финансовых статей, рекурсивное дерево из API. Выбор типа → ветка → статья или поиск по полному пути; group/selectable не приравнивать к наличию parent. Новая классификация не предлагает архивные узлы, сохранённый архивный ID показывается вместе с путём. Название, перемещение статьи и классификация отдельного факта — три разных действия.

## Приёмка и артефакты

Компьютер: обе темы1920×1080 и1024×900; заполненная таблица/редактор также2560. Снимки: начальная таблица, операции с totals/страницей2, фильтр/поиск/раскрытие, форма до заполнения, третий уровень, rename, before→after parent, used archive,409, классификация и история. Невидимая кнопка, отсутствующее поле, непрошедшая запись и неудобный вид фиксируются раздельно.

Для каждого ID записать PASS/FAIL/PARTIAL/SKIP и ссылку на screenshot/API-check в UI-REVIEW.md. Никакого «принято по коду». Подключение к копии — только после review сценария координатором через access BROWSER, сессия stdin; секреты в evidence не сохранять. Мобильные замечания записать отдельно и не блокировать ими текущую приёмку.

Ожидает архитектора: принятие CONTRACT; точные ID/endpoint формы classification и operation identity для income legacy; page/limit API операций; защиту revision и правило архива поддерева. Отсутствие готового backend не компенсировать локальной фильтрацией/новым реестром/догадкой по имени. Production ARTICLE-PLAN остаётся отдельным согласованным действием после свежего usage, копии и бэкапа.
