# Единые данные склада и снабжения: CRM kppdf + приложение «Склад · Снабжение» + Google-таблицы

> Цель: **одна база — одни данные**. CRM, приложение `/db/app/` и Google-таблицы читают и пишут
> одни и те же коллекции; приложения отличаются только видом. Новые поля добавляются по мере надобности
> (синхронно в схемах обоих репозиториев).

## Было до объединения (утро 2026-10-18)

| Что | CRM kppdf читает | Приложение `/db/app/` и синхронизация таблиц пишут |
|--|--|--|
| Номенклатура | `materials` (1 запись) | `app_warehouse_items` (252) |
| Остатки | `storageitems` (0) | поля в `app_warehouse_items` |
| Движения | `stockmovements` (0) | `app_warehouse_movements` (143) |
| Заявки снабжения | `supplyrequests` (0) | `app_supply_requests` (157) |
| Поставщики | `organizations` (0) | текст в заявке (18 разных) |

Две параллельные модели → CRM не видит данных приложения и наоборот.

## Решение

**Общие коллекции — коллекции CRM** (`materials`, `categories`, `warehouses`, `storageitems`, `stockmovements`, `supplyrequests`, `organizations`). Причины: у них уже есть схемы, логика остатков и экраны в CRM; в проде они почти пусты (переносить нечего). Коллекции `app_supply_*` / `app_warehouse_*` выводятся из работы.

- **data-core** получает API к этим коллекциям (схемы — копия kppdf, логика остатков — как в `StockMovementService` kppdf). Приложение `/db/app/` ходит в этот API.
- **CRM kppdf** не меняется: она уже работает с этими коллекциями.
- **Синхронизация Google-таблиц** пишет туда же.

## Сопоставление

### Лист «Склад» → `materials` + `storageitems`
| Таблица | База |
|--|--|
| Наименование ТМЦ | `materials.name` |
| Ед. изм. | `materials.unit` |
| Категория (Метизы, Расходники, Покупные изделия, Оборудование) | `materials.categoryId` → `categories` (недостающие создаются) |
| — (артикула в таблице нет, а в CRM он обязателен) | `materials.article` = автокод `СКЛ-0001…` (можно поменять в CRM) |
| Текущий остаток / Забронировано / Мин. остаток | `storageitems.quantity / reservedQty / minQuantity` на «Главный склад» |
| Вес 1 шт. | `storageitems.weightKg` |

### Лист «Снабжение» → `supplyrequests`
| Таблица | База |
|--|--|
| Наименование | `title` (+ `materialId`, если такая позиция есть в номенклатуре) |
| Категория | `categoryId` |
| Кол-во / Ед_изм. | `qty` / `unit` |
| Поставщик | `supplierId` → `organizations` (создаётся по имени, без дублей) |

| Заказчик | `orderLabel` |

| Цена с НДС | `priceHint` |

| Примечание | `notes` |

| Статус в таблице | `status` | `paid` |
|--|--|--|
| ⏳ Ожидает | `in_progress` | — |
| ✅ Заказать | `requested` | — |
| ⚙️ В работе | `ordered` | — |
| 💰 Оплачено | `ordered` | `true` |
| ☑️ Получено | `received` | — |
| ❌ Отменено | `cancelled` | — |

### Лист «Движение склада» → `stockmovements`
История: «Ввод начального остатка» → `adjust`, «Списание / Выдача» → `out`, «Приход» → `in`. **Остатки не пересчитываются** (они уже пришли с листа «Склад») — записи помечены `source: 'google-sheets'`.

### Лист «Реестр счетов»
В CRM своего места нет (модуль `invoice` — счета продаж). Пока остаётся в `app_supply_invoices`; решение — отдельно.

## Реализация (2026-10-18)

- data-core: `modules/stock` (`/api/stock`: warehouses, items, items/:id/move|history|photos) и `modules/supply` (`/api/supply`: requests, requests/:id/receive, lookups). Схемы — копии kppdf (`stock/schemas/*`, `supply/supply-request.schema.ts`) с общими новыми полями (`clientUid`, `sheetSource/sheetKey/syncHash`, `notes` у движения, `num/requestDate/sheetExtra` у заявки) — добавлены в обоих репозиториях.
- Склад по умолчанию: `warehouses.isDefault` (если не назначен — первый действующий, «Главный склад»).
- Синхронизация: `modules/sheets-sync/sheets-sync.targets.ts` (адаптеры supply / stock / movements). Номенклатура при исчезновении строки из таблицы **не удаляется** (на неё ссылаются CRM и движения). Заявки досвязываются с позицией склада, когда она появляется.
- Новые поставщики без ИНН получают заглушку `БЕЗ-ИНН-<хэш>` (ИНН обязателен и уникален) — заменить на настоящий в CRM.
- Коллекции `app_supply_requests`, `app_warehouse_items`, `app_warehouse_movements` больше не пишутся (архив; удалить — только по решению пользователя). `app_supply_invoices` — «Реестр счетов», пишется как раньше.
- e2e: `stock-supply.e2e-spec.ts` (6), `sheets-sync.e2e-spec.ts` (9).

## 2026-10-19: хозяин данных — приложение

Запись, изменённая или удалённая в «Рабочем месте» (и любое движение по позиции склада), помечается `editedInApp`. Синхронизация таблиц такую запись больше не меняет (в т.ч. остаток), не удаляет и не воскрешает — в итоге прогона это видно как «не тронуто (изменено/удалено в приложении) N». Строка, убранная из листа и возвращённая в него, — возвращается. Автосинхронизацию выключить, когда таблицы перестанут вести (TASKS 0.2).
- **Поля только data-core (SK-5, 2026-10-24) в `stockmovements`:** `reason` (причина списания — название из справочника «Причины списания», без enum) и `isReturn` (возврат со сборки: приход с `salesOrderLineId`). Необязательные; kppdf их не пишет и не читает; `type` движения не менялся. В копию схемы kppdf не вносить.
