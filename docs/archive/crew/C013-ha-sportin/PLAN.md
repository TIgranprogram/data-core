# C013 — что осталось, по приоритету

Цель пользователя: второй сервер почти сразу повторяет главный, при пропадании света домен сам уходит на живой, данные не пропадают, в админке главного можно сменить так же без потерь.

Честная развилка. Сейчас это суточная замена базы файлом. Цель из ТЗ — общий replica set (журнал Mongo) плюс сторож домена на VPS. Второе первым не заменяется. Пока не закрыта ловушка макета (обрыв канала, потом смерть главного — потеря ~30 % записей), автомат включать нельзя. ТЗ само запрещает автомат раньше двух недель замеров и письменного «да» на этапах со звёздочкой.

В `docs/roles/tz/HA-TWO-SERVERS.md` три схемы сразу: треугольник WireGuard и `w:1`; звезда через VPS и `w:majority`; HAProxy и автовозврат по priority. Макет подтвердил только первую ветку с оговорками. Новую схему не кодить, пока одна не выбрана и не прогнана на макете.

## Решения 2026-11-03 (зафиксировано)

- Цель P2: WireGuard-треугольник, `w:1`, сторож с лагом; dual-write нет.

## P1 — доделать то, что уже написано (кнопка, не «почти сразу»)

Это сценарий «переключить в админке», не сценарий «свет погас — само». Простой на время дампа: в ТЗ 1–2 минуты, потолок моста 10 минут. Потери подтверждённых записей API в задумке нет: сначала пауза 503, потом дамп, потом сверка. Не проверено на живых ssh, rsync и nginx. Сверка по умолчанию — 5 коллекций, не вся база.

1. Обновить код Sportin: `refresh-copy.sh --code`. Ежедневная задача код не возит. На 31.10 там был `695d89c`, прод 3.11 — v1.481. Для кнопки версии должны уметь одну базу (ступень выкладки — это уже P2).
2. `setup-tunnel.sh`, затем `setup-switch.sh` без `--enable`, проверка `dc-switch status` (оба туннеля health). Потом `--enable` и перезапуск backend. Боем это не проверялось.
3. SW-7 ночью: смена дом → Sportin и обратно. Смотреть: запись встала, домен уехал, числа коллекций сошлись, старый главный остался только для чтения, ежедневная задача не затёрла нового главного (она и так встаёт, если Sportin не запасной).
4. Закрыть прямой вход `:8080` в обход домена до того, как кнопкой начнут пользоваться всерьёз. Иначе люди пишут в обход «главного». `refresh-copy.sh --code` дописывает `HTTP_STAND=1` — для боя это убрать, как в ТЗ.
5. Задача Windows. Она уже создана на этом ПК и 1–2 ноября доезжала. Дыры: только при выполненном входе; код не обновляет; цепочка одного направления (дом → Sportin). Обратной суточной копии нет: если главным станет Sportin, дом сам не догонит — только обратная кнопка.
6. Координатору поправить устаревшее: `pult/todo.json` («только вручную»), `docs/audit/SERVERS-STATUS.md` (задача «не подтверждена»). Факт — в `INVENTORY.md`.

Пароль Sportin и память 3,3 ГБ — до replica set (HA-3), не до учебной кнопки. Пароль пользователь отложил 31.10.

## P2 — цель «почти сразу» и автодомен (только письменное «да»)

Порядок из ТЗ, одной строкой на шаг. Код прода под это не начинать раньше выбора одной схемы.

1. Выбрать схему письменно. Опора макета: `w:1`, `retryWrites`, при падении вторичного дольше 60 с — `votes:0`, автовыборы отставшему запрещены, ручная смена — `stepDown` (~2 с на макете). `w:majority` и HAProxy из поздних абзацев ТЗ макетом не подтверждены. Звезда через VPS — отдельный макет HA-1а, его нет.
2. HA-2 замеры: журнал ГБ/час, канал обоих домов, обрывы, RAM и CPU VPS (539 МБ; мини-копия базы туда не встаёт, арбитр — только после замера).
3. HA-3: память Sportin, есть ли ИБП. Иначе «пропал свет» бьёт оба смысла сразу.
4. HA-4/HA-6 сеть. Откат — убрать оверлей.
5. HA-7: `HA_ENABLED`, роль через `isMaster`, фоновые задачи и сиды только на главном, кэш при лаге. Выкладка с выключателем. Бэклог пишет, что ручной `commitTransaction` в category уже переведён на `withTransaction`; HA-9 в ТЗ всё ещё открыт — сверить файл перед Э2 (этим аудитом не читался).
6. HA-8 строка CRM `replicaSet=rs0`, если CRM к тому времени ещё жива. Иначе при главном на Sportin CRM читает старое и не пишет.
7. HA-10 начальная синхронизация ночью, `priority:0`, фото `rsync` без `--delete`.
8. HA-11 наблюдение (в ТЗ было 2 недели; 31.10 срок сократили до 3–5 дней, если замеры чистые).
9. HA-12 арбитр и сторож домена. Не раньше защиты по лагу.
10. HA-14 учебное выключение каждого узла. Критерий ТЗ: сайт снова пишет за ≤ 60 с. Ноль потерь ТЗ не обещает: обычно секунды, при откате — часы до разбора файлов `rollback/`.
11. HA-13а ступенчатая выкладка. Общая база: новый код портит данные — порча сразу на втором. Спасает бэкап перед выкладкой, не второй сервер.
12. HA-15…17: восстановление VPS, TTL DNS, упаковка узла — после учебного отказа.

## Что не делать

- Не называть суточный `refresh-copy` «почти в реальном времени».
- Не включать автопереключение домена на текущих двух Mongo: при смерти дома переносить нечего, кроме последнего дампа.
- Не править `backend/` и `deploy/synology/` ради Sportin. Отличия — `SRV-ERP/` и `.env`.
- Не обещать живую CRM при смерти домашней VM: CRM стоит только там.
