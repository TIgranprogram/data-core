# C246 — выбор архитектуры (решение 24.11.2026)

> Уточнения второго взгляда: [REVIEW-NOTES.md](REVIEW-NOTES.md).

## Что выбираем

**Модульный монолит с хозяевами доменов** внутри одного NestJS + Mongo.

Не микросервисы. Не переписывание с нуля. Не смена фреймворка.

## Почему это лучший вариант для нашего продукта

1. **VISION:** данные живут отдельно, снаружи — один API и ключ. Один процесс API это и есть «одна дверь».
2. **Одна команда, один сервер, одна база** с CRM. Микросервисы дадут сеть, деплой и боль без выигрыша (уже отвергнуто в ARCH-PLAN).
3. **Рабочее место** — одно приложение на том же API. Ему нужны чёткие хозяева таблиц, а не разнос по сервисам.
4. **Общие с CRM коллекции** пока пишутся и kppdf. Реалистичный путь: сначала порядок внутри data-core, перевод CRM на API — отдельное явное решение владельца позже.
5. **Скорость сайта** чинится запросами и кэшем, не «новой архитектурой ради архитектуры».

## Правила хозяина домена

Хозяин отвечает за **бизнес-операцию и её правила** (не за голую обёртку `update`): валидации, сессия/транзакция Mongo при необходимости, аудит, защита от повторного выполнения. В ТЗ этапов C251+ это фиксировать явно.

| Домен | Хозяин записи | Чужой модуль делает |
|--|--|--|
| Остатки / движения / брони / склады | `stock` | только через `StockService` |
| Заявки снабжения | `supply` | только через `SupplyService` |
| Доходы | `incomes` | только через сервис хозяина |
| Заказы клиентов | `salesorders` | только через сервис хозяина |
| Изделия | `product` (или явный фасад каталога) | не сырой `products` из витрины |
| Общее | `common/` | только типы и чистые функции |

### Границы `common/`

В `common/` — типы, нормализация текста, сырые хелперы без доменных правил.  
Правила доходов, склада, каталога, паспортов — **у хозяев**, не в `common/`.

### Ограничение гарантий при CRM

Гарантия «запись только через хозяина» действует **внутри data-core**.  
kppdf пишет shared-коллекции напрямую в Mongo — это отдельный писатель. Для shared фиксируем ограничения совместимости схем/полей; полный контроль владения — только после перевода CRM на API (отдельное «да»).

## Что сознательно не делаем сейчас

- Nx / микросервисы / брокер сообщений
- Перенос папок «для красоты» (АБЗ-8)
- Перевод kppdf на API без отдельного «да»
- Одновременный большой рефакторинг нескольких доменов в одном коммите

## Критерий успеха всей программы

- Зависимости между доменами **явные** (через фасад/`index.ts` или DI хозяина).
- **Любых** циклов модулей нет (пары и длиннее; `audit-cycles.js` + доп. проверка).
- Чужих записей мимо хозяина в data-core нет.
- «Вынуть любой домен и всё живо» — **не** обязательный критерий для связанных доменов.
- Каждый этап сам по себе зелёный: приложение работает без следующих этапов.
