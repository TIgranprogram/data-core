# Топология сайта для ИИ (лёгкая модель тоже)

**Зачем (владелец, 18.11):** один раз навести «картотеку» на всё приложение, чтобы любой ИИ (в т.ч. локальный лёгкий) понимал, *где* менять, *что* ещё связано, и не бродил / не пропускал входы. Не про паспорта отдельно — про весь сайт.

## Что уже есть (не начинать с нуля)

| Слой | Где | Что даёт |
|--|--|--|
| Карта для людей и ИИ | `backend/pwa/sections/atlas-data.js` + `dc atlas` | Блок → шаги → файлы → связи |
| Участки файлов | `tools/areas.mjs` + шаг в `dc check` (C128 волна 1) | Файл → участок; файл без участка — сигнал |
| Законы / вход | `AGENTS.md`, `CANON`, `MAP`, роли | Куда смотреть по типу задачи |
| Точечные ворота | пример: `book-etalon-gate.test.mjs` (C141) | «Эталон сменился → старые входы запрещены» |
| ТЗ C128 | `TZ.md` здесь же | Ворота учёта: registry + `dc gate` + пульт |

**Дыра:** карта и участки *описывают*, но ещё не *заставляют* ИИ брать только свой участок и не дают автоматический «impact» (что ещё поправить). Без волны 2–6 лёгкая модель снова читает полпроекта.

## Чего не хватает (один пакет, не «ещё доки»)

1. **`dc gate` + registry** (C128 волны 2–5) — журнал: участок менялся / проверен / устарел; `dc gate next` для ночи.
2. **Impact-лист у участка** — в atlas или `tools/registry/<area>.json`: `etalon`, `entries[]` (файлы-входы), `forbid[]` (паттерны старых путей), `related[]` (соседние участки). Смена эталона → ворота как у C141, но шаблон один на все блоки.
3. **Правило сессии:** `dc start` → `dc gate <участок>` → ТЗ только с файлами участка → коммит только своих путей → программа обновляет registry. В CLAUDE.md одной таблицей.
4. **Контракт API в коротком виде** — не openapi целиком: `dc atlas --json` + кусок MAP по модулю; для лёгкой модели — ≤ 2–4 КБ контекста на задачу.
5. **Пульт «Состояние сайта»** — плитки зелёный/жёлтый/серый (C128 волна 5).

Ночной ИИ и локальная модель — *потребители* этой картотеки, не замена ей.

## Порядок «несколько дней» (не сейчас в одном коммите)

| День | Результат | Готово когда |
|--|--|--|
| 1 | Волна 2: `tools/registry/*.json` + `dc gate` / `dc gate <area>` | `node --test` на state; строка в `dc start` |
| 2 | Шаблон ворот эталона (обобщение C141): `tools/etalon-gate.mjs` + 2–3 пилота (паспорта, заказ, склад) | Красный тест при старом входе |
| 3 | Волна 3: testing/audit/design пишут `checks` в registry | После прогона виден участок |
| 4 | `dc gate next` + Старожил только по устаревшим | Ночь не гоняет весь сайт |
| 5 | Пульт «Состояние сайта» + правило в CLAUDE.md | Владелец видит плитки |

Оценка: **~3–5 рабочих дней** инструментов (без выкладки прода, без смены бизнес-логики экранов). Класс L, код приложения почти не трогать — `tools/` + atlas + тонкие ворота в `pwa`.

## Критерий «любой дурак / лёгкая модель поймёт»

- Задача → один `area` из atlas → ≤ 10 файлов в ТЗ.
- Правка эталона → автотест ворот красный, пока все `entries` не на эталоне.
- `dc gate` зелёный по участку = можно выкладывать этот кусок.
- Локальной модели дают: `dc gate <area> --json` + ТЗ, **не** весь репозиторий.

## Не делать

- Не плодить вторую «карту» рядом с atlas.
- Не ждать ночного тестировщика вместо ворот.
- Не описывать всё openapi в чат — только grep / atlas / gate.
