# C242 — единицы, поля и порядок таблиц всего склада

23.11.2026. Только адресное чтение локального кода, без обращения к prod, изменения данных и рабочего кода. Scope расширен владельцем: основной склад, трубы, листы, деревообработка; допустимый план нормализации, а не только перестановка столбца.

## Где лежат данные

- `backend/src/modules/material/material.schema.ts:25–42,46–118`: общая CRM-коллекция `materials`; `assortment:string`, `materialGrade`, `unit`, `dimensions:[{type,value,isImmutable}]` в мм. Допустимые оси включают length/width/**height**/thickness/diameter/depth. `washed` и `typeName` — необязательные поля data-core.
- `backend/src/modules/stock/schemas/storage-item.schema.ts:47–60`: общие `storageitems`, quantity/reservedQty/minQuantity в **единице материала**. Складские остатки, брони и движения не являются полями справочного описания.
- `stock-search.service.ts:180–185` отдаёт assortment/materialGrade/washed/dims. `metal.ts:10–28` сейчас проецирует только length/width/thickness/diameter: **height теряется**, хотя деревообработка пытается его показать (`wood-grid.js:76–79`).
- Отдельных достоверных `piecesCount`/количества целых труб нет. В основном списке floor(m/length), в сетке round(m/length,2). Это вычисления, не результат инвентаризации; для смеси длин/кусков они не доказывают число физических заготовок.
- Длина хлыста уже есть: materials.dimensions[type=length] мм; UI `metal.js:106,112–137` переводит м↔мм. Стенка есть как thickness; диаметр — diameter. Прямоугольное B×H пока надёжно представлено только строкой assortment: текущий `Dims` не содержит height, а форма трубы обнуляет width.
- Отдельного поля «основной материал» нет: materialGrade хранит марку, а иногда общее «Нержавеющая сталь»; pipeKind ещё определяет нержавейку по имени (`core/facets.js:73`). Нельзя превращать всякую нержавейку в AISI304 или иной конкретный сплав.

## Полнота сортировки, preferences, коллизии

- `stock-search.service.ts:56–89` сортирует **все** доступные строки до `slice(skip,limit)`; `stock.types.ts:ITEM_SORT` не разрешает assortment или dimensions. Просто добавить `sort:'assortment'` во frontend недостаточно.
- Второй stable-sort по attentionRank при `priority=1` перегруппирует результат и нарушает глобальное возрастание сечений. Для явно выбранного размерного порядка приоритет следует согласованно отключать либо явно показывать группы; не молча смешивать оба порядка.
- Нужен серверный числовой tuple, не строковый localeCompare и не числовая сортировка текущей страницы: трубы `(B,H,t)`/круглые `(D,t)`, листы `(t,W,L)`, дерево — согласованные подписанные оси. Парсить только строго распознанное сечение; запятые как десятичные, ×/x/х/* как разделители, `Ø/⌀` как диаметр. Числа ГОСТ/марки/длины не должны попадать в tuple; неизвестное/пустое — в конец, затем стабильные name/id. Ориентацию B/H не переставлять автоматически.
- `pipe-grid.js:25–33` делает `row.cells[key]=item`: несколько материалов одной ячейки **перезаписываются**, не суммируются. В ключе нет конкретной марки/AISI; разная нержавейка одного сечения/длины может скрыться. Для нормализации сначала выявить такие коллизии; простая сумма скрыла бы разные материалы.
- `ui/kit/list.js:24,132–145` использует порядок массива `stock.list.columns`; сохранённой настройки порядка/видимости этих столбцов не найдено. `list-view.js:36–52` запоминает лишь вид таблица/доска/галерея; сортировка приходит из URL `P.sort` либо статического `sortDefault`. Старый `?sort=name` перекроет новый default — это нужно учитывать в приёмке, не чистить все preferences пользователя.
- Основной heldStockList умеет обходить страницы (`core/stock-list.js:34–45`), рабочие pipe/sheet grid — нет. Сохранить пагинацию/счётчики/экспорт: экспорт должен использовать тот же порядок и поля, а выборка зоны — прежние ограничения доступа.

## Безопасная нормализация plan → apply

1. Steward/access выгружают адресно только читаемые поля материалов/остатков/зон/брони, связывают IDs и сохраняют исходный снимок. Считают коллизии по типу/чистому сечению/марке/мойке/длине/единице; сверяют references CRM/снабжения. Этот шаг ещё не выполнен.
2. Безопасный план чистки метаданных: `40 x 40 x 2 мм` → `40×40×2` только при однозначной исходной размерности; длину/марку/мойку выносить лишь по явному подтверждённому источнику. Конфликт name↔structured dims, неоднозначный тип/длина/единица → список вопросов, не угадывать. Старые fullName/invoiceName/источники сохранять.
3. Для однородной трубы известной длины можно показать вычисляемые штуки только при целочисленном отношении с оговорённым допуском. Остаток 20 м при длине6 м не означает ни «3 шт», ни «3,33 физических трубы». Неизвестные куски → «количество требует пересчёта», без записи придуманной длины/штук.
4. Базовую `materials.unit`, quantity/reservedQty, историю stockmovements/броней **не переписывать** ради красивого вида. Для позиции в шт с доказанной длиной допустима отдельная проекция метража; это не миграция исторической единицы. Смена единицы требует отдельного плана со всеми зависимостями и согласованием CRM.
5. Сначала read-only projection/таблица/сортировка на копии. Затем ограниченный approved plan→apply метаданных через API с expected-before/CAS, audit и обратным планом; повторный plan=0. Не объединять дубли/удалять материалы и не менять остатки автоматически.

- Frontend: `sections/stock.js`, `pipe-grid.js`, `sheet-grid.js`, `wood-grid.js`, `metal.js`, `core/facets.js`; общий list/table-kit трогать только при доказанном отсутствии локального решения. Atlas: `sections/atlas-stock.js` и шаги `help-guide-data.js`.
- Backend: `stock/stock-search.service.ts`, `stock.types.ts`, `metal.ts`, OpenAPI-декораторы stock.controller.ts; схему materials/storageitems менять только если после проекции доказан реально отсутствующий факт. Общие CRM-схемы и единицы — архитектурное согласование, не попутная миграция.
- Этап A: аудит данных/единиц/коллизий и утверждение четырёх матриц колонок. B: серверная сортировка + нормализованная read-only projection + четыре экрана. C: адресная чистка подтверждённых метаданных plan→apply. D: неизвестные длины/куски — физический пересчёт, отдельные штатные операции.
- Проверки: numeric cases 20/40/100, 2/2,5/3,5, Ø/прямоугольные/невалидные; граница страниц/descending/ties, приоритет, зона/роль/нулевой и полностью забронированный остаток; нет потерь коллизий; м/мм/шт/листы и rounding; before/after quantity/reserved/movements неизменны. Существующие тесты `stock/metal.spec.ts`, `stock-summary.spec.ts`, `stock-bulk.spec.ts`, `core/facets.test.mjs`, `sections/wood-grid.test.mjs`; добавить адресные тесты сортировки API/pipe-sheet rows и desktop-приёмку.
