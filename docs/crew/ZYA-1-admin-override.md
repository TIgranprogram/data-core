# ЗЯ-1 · Администратор может всё — отчёт аналитика (2026-11-05)

Правило: admin обходит блок, если склад и деньги остаются сходными. Иначе — предупреждение + связанное действие, иначе блок. Код: `Роли admin` уже стоят в `@Roles` почти везде; блокируют сервисы (проверки не смотрят на роль). Блоки делятся на: **A** обход без риска · **B** обход с предупреждением и связанным действием · **C** остаётся блок.

## 3. Журнал «было → стало»
- Общего плагина «before/after» нет. `database/audit.plugin.ts` пишет только `updatedAt/updatedBy` в документ. Журнал — `AuditService.log` (`modules/audit`, коллекция `auditlogs`; `details {before, after, meta}` в схеме есть, `record-history.ts:55` их читает).
- `@AuditAction` (`common/interceptors/audit.interceptor.ts:86-96`) пишет только `{after: ответ}`; `before` не пишет. Для обхода нужна запись вручную в сервисе: `audit.log({action:'supply.request.admin_override', details:{before, after, meta:{rule:'<код блока>', reason}}})` либо расширение `details(data, params)` хелпером `withBefore`.
- Хелпер `adminOverride({rule, entityType, id, before, after, reason, actor})`: пишет в `auditlogs`, вызывается только если `actor.role==='admin'` (или `isOwner`) И блок реально обойдён (не на каждую правку).
- В счёте уже есть свой журнал `paymentAdjustments` (supply-invoice:94-108) — использовать для денег, дублировать в `auditlogs`.
- Причина обязательна (≥3 симв., как `stageReason` в salesorders:410) для B-обходов.
- Зависимость: `SupplyService`/`SupplyInvoiceService` сейчас без `AuditService` — внедрить; `actor.role` передан только в `supply.update` (`void userRole`, :490) — протащить в остальные методы.

## 4. Где в PWA правка скрыта у не-admin
`session.isAdmin` есть (`core/api.js:42`); `isOwner` приравнен к admin. Места:
- `sections/invoice-workspace-state.js:12-18` — `linesAdmin`, `boundary`; **уже admin** для строк до приёмки. Нужно: показать правку цены после приёмки (п.7), «Снять оплату», «Откатить приёмку».
- `sections/requests.js:187-188` — «Получено» убрано из статусов формы; `request-step.js:55-61` — только вперёд (`NEXT`, requests.js:45), назад шага нет. Нужны: «Откатить приёмку» в меню строки, возврат статуса для admin.
- `sections/invoice-workspace.js:157` — плательщик `disabled: !p.finance`.
- `sections/orders.js:161,267-312` `LOCKED_KEYS`/`locked` — у не-admin поля названия/qty/цены скрыты на этапе после «новый»; `order-line-actions.js:21`, `salesorders.js:227,261` (`stageBack` уже admin).
- `sections/offers.js` — «Оплачено» (нет проверки роли, блок только сервера).
- Движения (`movements.js`) — кнопка «Отменить» по типу; admin-кнопок нет.
- Подсказки: `invoice-workspace-state.js:reason` — менять тексты для admin («Администратор может…»), справку `help-flow-data.js` синхронизировать.

## 5. Порядок и разбивка на ТЗ
Порядок: (1) backend-ядро → (2) backend-B-обходы по блокам → (3) frontend → (4) qa. Класс L; агентов ≤ 4.
- **ЗЯ-1a backend (1 исполнитель, сначала):** хелпер `adminOverride` + журнал; протащить `actor` в supply/invoice; обходы A (п.3,4,25,26); тесты на каждую роль: admin обходит, manager получает прежнюю ошибку. Файлы: supply.service, supply-invoice.service, supply.controller, audit, offer-rules/offers.service.
- **ЗЯ-1b backend (после 1a):** B-обходы с предупреждением: два шага API — `?dryRun=1` (возвращает `warnings[]`, `relatedAction`) и подтверждение `confirm:true` + `reason`: п.2, 6, 7(цена), 9, 11, 12, 15, 17, 18, 22, 24. Отдельные эндпоинты: `POST requests/:id/rollback-receipt`, `POST invoices/:id/unpay`. Пересчёт: `recalcAmount`, `recordPrices`, `orders.recheck`, календарь (`finance.service.ts` — не должен видеть снятую оплату).
- **ЗЯ-1c frontend (после 1b):** кнопки/меню admin в местах §4, диалог предупреждения с суммой/позициями, поле «Причина». Дизайнер — перед выкладкой. Язык менеджера: без кодов.
- **ЗЯ-1d qa:** сценарии «до/после»: (а) откат приёмки при достаточном/недостаточном остатке; (б) снять оплату → календарь и `paymentAdjustments`; (в) правка цены принятой строки → сумма счёта и `materialprices`; (г) manager/user — прежние 400/409; (д) журнал `before/after` пишется; (е) удаление заказа с оплатами не оставляет платежей в календаре. Full перед выкладкой.

## Риски / вопросы пользователю (в QUESTIONS.md не вносил)

2. Снятие оплаты (п.9): отменять запись календаря или оставлять отметку «сторно»? По умолчанию — сторно с причиной.
3. `isOwner` без роли admin — считать админом на сервере? В PWA да; на сервере в guard'ах `owner-only` отдельно — проверить в 1a.
4. Общие с CRM коллекции (`supplyrequests`, `materials`, `stockmovements`): откат статуса меняет только поля, которые уже пишет `update` (`receivedQty/At/To/receiveUid`); новых полей не вводить.
