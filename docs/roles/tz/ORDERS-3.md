# ТЗ ORDERS-3 — заказы, этап 3: отмена и перенос

**Зачем (словами пользователя):** «Какие-то позиции отменить, потому что автоматически загрузились не туда». Аудит: `docs/audit/AUDIT-ORDERS-2026-10-31.md`, раздел 3 и «План».

**Класс:** XL · **Max agents:** 3 (backend, frontend, designer) · **Проверки:** full на ПК + обход на стенде. Лимиты: недельный 98 % — свернуться, полный коммит и пуш, недоделанное в отдельную ветку.

## Решения пользователя (2026-10-31, приняты)
- Менеджер меняет и отменяет позиции с причиной до «Готово к отгрузке», дальше только админ.
- Отменённая позиция: серая строка с причиной, в суммы и производство не идёт.
- При отмене показать, что зависит от позиции, и спросить, снимать ли брони и задачи.
- Директор и бухгалтер кнопок правки не видят.
- Закрытый заказ возвращает в работу только админ, с причиной.

## Сначала проверить
1. `incomes` общая с CRM? Новые поля `cancelledAt`, `cancelReason`: не мешают ли CRM. Читать `docs/ARCHITECTURE.md` «Единая база». Если мешают — стоп, вопрос координатору.
2. Какие расчёты читают `incomes`: суммы договора, долги, готовность, сопоставление, очередь паспортов, проектирование, отгрузки. Составить список до кода. Отменённая позиция должна выпасть из каждого. Это главный риск этапа.

## Сервер, по порядку
1. `GET /salesorders/:id/dependencies`: по договору и позициям брони, задачи проектирования и работы, заявки, паспорта, отгрузки, оплаты.
2. `POST /incomes/:id/cancel {reason, cascade}`: без `cascade` при зависимостях 409 со списком. С `cascade`: снять брони, закрыть задачи. Оплаты и отгрузки блокируют всегда. `POST /incomes/:id/restore-cancelled`.
3. Смягчить `assertOrderOpen` (`incomes.service.ts:28,249-254,290,346`) для manager: разрешить до `ready`, иначе 409 со списком причин. Проверку admin и ключей `kppd_` не менять.
4. `POST /incomes/:id/move {toOrderId}`: перенос со ссылками: `designtasks`, `reservations`, `supplyrequests`, `passports`. Запрет при оплатах и отгрузках. Запись в audit.
5. `POST /production-orders/:key/move-contract {toProductionNo}` с `ensureDetachable` (`salesorders.service.ts:399`).
6. Правила этапа в `PATCH /salesorders/:id` (`:373`): разрешённые переходы, назад — с причиной. Отгрузка `stageAfterShipments` не ломается.

## Экран
- Строка позиции: `⋯` → «Отменить позицию», «Перенести в другой договор». Окно до 3 полей: причина и список зависимостей с галочкой «снять».
- Договор: `⋯` → «Перенести в другой заказ».
- Отменённая строка серая, с причиной и «Вернуть».
- Поле «Этап» в форме договора убрать: путь назад через воронку, с причиной, только админ.

## Также в этом этапе, если останется лимит
Доска «Проектирование»: одна карточка на `productionNo`. Описание — раздел «В очередь» аудита.

## Критерии приёмки
- [ ] Менеджер отменяет позицию в производстве с причиной. Сумма договора и долг уменьшились.
- [ ] Отмена с бронью спрашивает и снимает бронь.
- [ ] Позиция с оплатой или отгрузкой не отменяется, причина видна.
- [ ] Перенос позиции и договора: связи переехали.
- [ ] e2e на каждое действие и отказы ролей.
- [ ] full, обход на стенде: `QA_BASE=http://localhost:3102 QA_DIR=tools/.night node backend/scripts/qa-smoke.mjs`.

## Нельзя
Менять данные прода и схемы общих с CRM коллекций без проверки. Выкладка — кнопкой пользователя: пункт в `pult/todo.json`.
