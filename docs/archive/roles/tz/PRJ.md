# ТЗ ПРЖ — артикулы из каталога, два названия позиции, «Проектирование»

> Совещание 2026-10-24: аналитик, архитектор, хранитель данных, дизайнер. Координатор свёл их отчёты в этот файл.
> Состав: общая часть (решения, вопросы, чек-лист), затем ТЗ по шагам ПРЖ-0…ПРЖ-7. Исполнитель читает общую часть и свой шаг.

**Зачем (словами пользователя):** «В Excel — позиции текущих заказов, они уже есть в проекте, но им проставили грамотные артикулы по категориям. Надо грамотно достать данные и перенести их, чтобы при создании новых продуктов артикулы формировались автоматически. Названия могут расходиться: грамотно подобрать и дополнить заказы. В заказе два представления: название, как прилетело, и рядом наше, из продуктов. Это подбор продукта под заказ. Паспорт отдаём с их названиями. Нужна страница „Проектирование“ — комбайн по нашему дизайну: картинка, заполнение из заказа, приоритет и дедлайн из заказа».

**Роли:** аналитик ☑ (совещание) · архитектор ☑ (совещание) · хранитель данных ☐ (ПРЖ-0) · backend ☐ · frontend ☐ · qa ☐ · дизайнер ☐

## Исходные данные

- Excel: `данные для анализа и внедрения/Каталог оборудования СпортИН-ЮГ.xlsx`, лист «Перечень изделий 2026». Остальные листы (цены конкурентов, реестр КП 2022, регионы) к задаче не относятся.
- Выгрузка из Excel (в git не попадает, папка `/для анализа/` в .gitignore): `для анализа/каталог-2026-10-24/`
  - `catalog.csv` — 249 строк: row, type, groupName, groupNo, sku, name, series, certNote, photo.
  - `photos/<артикул>.<ext>` — 61 фото, ~18 МБ.
  - `match-catalog.js` — скрипт сопоставления хранителя данных. Читает только выгрузки `.jsonl`, команда выгрузки — в его шапке.
- Что в каталоге:
  - 243 изделия с артикулом и 6 пустых групп (13, 37, 55, 57, 58, 59).
  - Артикул = **номер группы NN + номер в группе NN**, 4 цифры. Все уникальны, без пропусков.
  - 3 типа оборудования = 3 раздела: спорт (группы 10–13), благоустройство (31–40), детские площадки (51–61). Групп 25.
  - Тип по первой цифре **не вычисляется**: «Трибуны» = 40.
  - 12 названий повторяются под разными артикулами («Скамейка» ×4, «Урна» ×4, «Игровой комплекс» ×5…). Дубли внутри каталога: «Жим от плеч» 1002/1023, «Стенд информационный» 1224/3901.
  - Самая полная группа — 12 «Воркаут», занято 79 из 99.
- Что есть в проекте (БЗ-5):
  - «Продукция» = `/showcase` поверх `products` (sku, name, раздел→группа в `categories`, series).
  - `/showcase/import` сопоставляет **только по артикулу**.
  - Позиции заказа — `incomes`, у них `title` и `productId`.
  - «Из заказов» создавал изделия с временными артикулами `ЗК-xxxxxx`. Поэтому прямой импорт по артикулу дал бы 243 дубля.
  - У заказа (`salesorders`) **нет приоритета**.
  - Паспорт печатает своё `name`; сейчас оно подставляется из изделия.
- На проде (DB-AUDIT 2026-10-24): `products` 252, `incomes` 143, `categories` 21.
- Копии прода на этом ПК нет, поэтому настоящего сопоставления каталога с базой ещё нет. Его делает ПРЖ-0.

## Решения совещания (принять, если пользователь не скажет иначе)

1. **Где хранится номер группы:** поле data-core `categories.groupNo` (строка '10'…'61'), только у групп-детей.
   - CRM это поле не читает: прецедент — `products.series` и `designerId`. Схему CRM не меняем, пишем сырым `db.collection`.
   - `skuPrefix` занят CRM, его не используем.
   - Уникальность `groupNo` среди живых групп проверяет сервис.
2. **Автоартикул:**
   - Выдаёт сервер при `POST /showcase` без `sku`, если у группы есть `groupNo`.
   - Нумерация монотонная: после максимума, считая корзину. Дыры не заполняем, номер после удаления не повторяется.
   - Счётчик: `CounterService.nextSeq(entity, prefix)`, атомарный `$inc` (Mongo 4.4). Занятый номер (`skuRegex`, вместе с ручными и корзиной) пропускается.
   - Если seq > 99 — 409 «в группе „…“ заняты номера 01–99». С 90-го номера — предупреждение.
   - Код — в новом `showcase/showcase-sku.ts`.
3. **Правила для артикула, который уже стоит:**
   - Ручной артикул по-прежнему можно ввести; номер чужой группы — предупреждение, не запрет.
   - Смена группы артикул **не меняет**. Для перенумерации — кнопка «Присвоить артикул группы» с подтверждением «паспортов N».
   - Артикул не по шаблону (не `ЗК-`) автоматически не трогаем.
4. **Два названия:**
   - Название заказчика = `incomes.title`, никогда не перезаписывается. Наше = `products.name`.
   - В позиции заказа главная строка — название заказчика, второй строкой серым — «Наше: 3410 · Скамья». Если изделия нет — метка «Подберите изделие».
   - В карточке изделия и на доске «Проектирования» главное — наше название, название заказчика — в панели справа.
   - Документ про конкретный заказ (паспорт) печатает название заказчика, документ без заказа — наше. Артикул печатаем всегда наш.
5. **Подбор изделия под позицию, правила по порядку:**
   1. Уже выбранный `productId` не трогать.
   2. Точное совпадение по мягкому ключу (ё/е, кавычки, регистр, пунктуация). Название, которое есть у двух и более изделий, автоматом не привязываем.
   3. Такое же название уже было у подобранной позиции — то же изделие.
   4. Похожие — только подсказки под галочку.
   5. Не нашлось — «Выбрать», «Создать изделие» (группа обязательна, артикул автоматически) или «Без изделия».
   - Одно изделие на много позиций — норма.
6. **«Проектирование»:**
   - Новый модуль `modules/design`, коллекция `designtasks` (`core`).
   - Задача привязана к позиции заказа ссылками: `incomeId`, `orderId`, `productId`. Можно и свободную задачу, без заказа.
   - Номер D-N — `nextSeq('DesignTask','D')`.
   - Статусы: `queue` «На распределении» → `work` «В работе» (нужен исполнитель) → `done` «Завершены». `paused` «Приостановлены» — с причиной.
   - На позицию — одна открытая задача (unique partial по `incomeId`). После «Завершено» можно создать новую.
   - Исполнитель — `persons`, сотрудник-проектировщик, аватар = инициалы.
   - Приоритет и срок берутся из заказа при выдаче списка (пакетно `$in`, без N+1), не копируются. Своё значение — только у свободной задачи или при ручной правке (с меткой).
   - При «Завершено»: если у изделия «Кто проектировал» (`designerId`) пуст — ставится исполнитель.
   - Цен и сумм в задачах нет.
   - Файлы чертежей — не в этой волне.
7. **Приоритет заказа:** новое поле `salesorders.priority` ('urgent' | 'high' | 'normal' | 'low', по умолчанию нет = обычный). Добавить в `SalesOrderDto`, иначе запрос с ним получит 400. В кэш позиций не включать.
8. **Перенос из Excel:**
   - Не через `/showcase/import`, а скриптом `backend/scripts/catalog-import.js`: по умолчанию план, `--apply --map проверенная.csv`, откат-JSON «до».
   - Фото — через `PhotosService.upload` (нужны миниатюры `thumb`), в `products.photoIds`. Ставить только изделиям без фото.
   - Применение на проде — только координатор, после бэкапа и «да» пользователя.
9. **Вид:**
   - Нового окна нет: `ui/list.js` + `L.board`, карточка `.tcard`, модификатор `.board.board-pics` (картинка 4:3 на белом), поля `foot`/`done` в `board.card()`, маленький `.avatar.sm`.
   - Приоритет «Обычный» не показываем, бейджи — только отличные от него.
   - Срок: просрочен — `--danger`, ≤ 2 дней — `--gold-deep`, у завершённых — серый.
   - «Завершены» и «Приостановлены» показываются компактно, порциями.
   - Ввод — только правая панель (`of=design&new=1`).
   - Перед правкой вида — skill `datacore-design` и записи в DESIGN §4 и §8.

## ПРЖ-1 — номер группы и автоартикул (backend)

**Что сделать**
1. `categories.groupNo` (только группы-дети type product):
   - выдача в `/showcase/groups` и форм-значениях;
   - задание при создании/правке группы (PATCH);
   - уникальность среди живых групп — 409.
2. `CounterService.nextSeq(entity, prefix)`: без года и форматирования, атомарный `findOneAndUpdate` с `$inc`, upsert. При E11000 — один повтор. Плюс `setSeqAtLeast(entity, prefix, n)` для засева.
3. `showcase/showcase-sku.ts`:
   - `nextSku(groupId)` = groupNo + pad2(seq);
   - занятый номер (`skuRegex`, включая корзину) пропускается, цикл ≤ 100;
   - больше 99 — 409 с понятным текстом.
4. `POST /showcase`: `sku` необязателен.
   - Без него и с группой, у которой есть `groupNo`, — автоартикул.
   - Без группы или без `groupNo` — как сейчас (или `ЗК-…`, как в «Из заказов»).
   - Ручной `sku` работает как раньше.
5. «Из заказов» и «Из паспортов»: если группа известна — автоартикул вместо `ЗК-`.
6. `POST /showcase/:id/assign-sku`: присвоить артикул группы изделию. Ответ-предупреждение с числом паспортов, без `confirm` — только отчёт.
7. Юнит: гонка (2 параллельных), пропуск занятого, > 99, корзина, удалённый номер не повторяется.

**Файлы**
- читать: `modules/showcase/showcase.service.ts`, `showcase-common.ts`, `modules/counter/counter.service.ts`, `modules/category/category.schema.ts`.

5. Выдача пакетом, без N+1:
   - `code` 'D-N';
   - `title`: «Чертежи <артикул> ЗНП <№ заказа> поз <№>»; без изделия — короткое название заказчика;
