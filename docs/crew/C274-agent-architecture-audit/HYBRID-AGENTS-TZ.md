# Пилот местных отчётов для Codex

После действующего ночного прогона `dc night` каждый завершённый запуск оставляет сводку для Codex в `tools/logs/codex-handoff/`. В журнале прогона появляется путь к ней. В «Тесты кода и экранов» кнопка «Сводка ночных проверок для Codex» собирает итог последнего запуска по запросу. Оператор может открыть сохранённую сводку в Codex из этого рабочего каталога.

## Что передавать

| Работа | Основание | Результат и следующий шаг |
|--|--|--|
| Сборка фактов для QA | Ночная смена сохраняет `tools/.night/runs/<запуск>/summary.json` с SHA, результатами и сигнатурами этапов. Последний исходный отчёт содержит также сырые хвосты логов. | Файл для QA и Codex с проверенным SHA, составом прогона, группами сбоев и ролями для разбора. Это работа пилота. |
| Сверка ошибок интерфейса | ИИ-тестировщик ведёт свои `REPORT.md` и снимки, а `dc errors` обращается к журналу рабочего сайта. Сырые замечания модели и живые события требуют разной проверки. | В перспективе QA готовит короткий воспроизводимый пример по материалам изолированного стенда. Данные рабочего сайта требуют отдельного поручения владельца и участия агента доступа. |

Ночной итог фиксирует технические факты отдельно. | Координатор смотрит состав прогона, назначает владельца и выбирает релевантный журнал. Вывод модели о причине сбоя остаётся гипотезой до воспроизведения. |
| Сверка документов | В Пульте уже есть очередь «Разбор и отправка», отдельное решение проверяющего и подтверждение передачи. | Будущий помощник может формировать обезличенный реестр сомнений для ответственного. Допустимые типы документов, границы папки и список полей утверждает владелец. |

## Формат и правила пилота

- Сводка использует фиксированные поля знакомого JSON. В неё попадают проверяемый SHA, текущий HEAD, режим, время, количество этапов и форматированные сигнатуры известных этапов. Текст ошибок, хвосты журналов, имена клиентов, реквизиты и снимки остаются в источнике.
- Итоговый JSON ограничен 256 КиБ. Перенаправленные пути и неизвестная структура отклоняются. Автоматическая сводка привязана к каталогу конкретного прогона. Если последнему запуску ещё предстоит завершиться, кнопка сообщает о незавершённом прогоне.
- Несовпадение SHA, незакоммиченные изменения, неполный набор проверок, аномалия времени или возраст свыше 36 часов указаны рядом с итогом. Такой отчёт служит справкой о прогоне. Быстрый режим покрывает только пять перечисленных групп.
- Сбои группируются по этапу, коду возврата, признаку таймаута и проверенной сигнатуре. Одинаковая сигнатура служит подсказкой для навигации. Причину подтверждает исполнитель. Идентичное содержимое получает тот же ID и уже существующий файл.
- Сбой подготовки записывается как один этап `tool` с кодом 2 и неизвестным SHA. По нему видно, что проверки не начались. Код выхода отражает результат подготовки и проверок. Сбой её сохранения виден в журнале, исходный итог остаётся доступным.
- Пилот опирается на действующий запуск и локальный Git. Расписание и доступ к API определяет владелец.

## Условия следующего шага

- Для первых десяти разных запусков записывать ID, совпадение SHA и состав этапов, время до выбора следующей проверки, подтверждение сбоя, первоначального и итогового владельца. Сохранить примеры, где сводки оказалось недостаточно.
- Продолжить роль сборщика QA, если хотя бы семь сводок помогли выбрать проверку за две минуты, а все десять указали правильный запуск. Сверить, что поля остались в разрешённом составе и давний прогон вызвал адресную перепроверку.
- Выделить постоянного разборщика, если три прогона дали подтверждённые находки или одна сигнатура повторилась в двух воспроизведённых запусках. Выделить самостоятельную маршрутизацию, если хотя бы три разбора потребовали переназначения между зонами.
- Повтор одной сигнатуры в двух отдельных подтверждённых запусках либо впервые упавший TypeScript, E2E или проверка прав идёт владельцу зоны и координатору. До назначения дефекта исполнитель сверяет точный SHA и результат адресного воспроизведения. Эскалация в пилоте выполняется вручную.
- Для документов первый этап — отдельно согласованный набор синтетических или обезличенных документов. Помощник выводит локальный список полей для сверки и ссылку на исходник для ответственного. Ответственный подтверждает исправления в существующей очереди Пульта. Передача документа, сохранение в DataCore и доступ к другой папке требуют отдельного решения владельца.

## Проверка ошибок конкретного выпуска

Одинаковый сбой в журналах разных версий имеет одну сигнатуру. Общая сводка по сигнатуре может показать последнюю запись от старого клиента. `GET /api/client-errors/top?hours=2&version=0794ccce` отбирает точное сохранённое значение `version` до группировки и лимита. В фильтрованном ответе есть `{items, version}`. Общий запрос возвращает `{items}` и доступен действующей роли `admin`, как и запрос с фильтром.

Проверка после выпуска и `doctor` берут SHA интерфейса из `version.json` и проверяют подтверждение версии в ответе. Для автоматического осмотра используется короткий SHA, чтобы маскировка длинных строк при записи не дала ложный ноль. `doctor` предупреждает, если весь возвращённый топ из 100 групп отнесён к шуму. Отчёт локального пилота остаётся сводкой тестовых прогонов.

Критерии изолированной приёмки. Одинаковый сбой на двух версиях считается раздельно, запрос без фильтра включает исторические записи без версии. Повторный параметр и пустое значение дают 400. Старый API, неполный ответ и ошибка транспорта дают явный статус проверки.
