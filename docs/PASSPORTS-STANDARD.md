# Стандарт выпуска паспортов ПС-1.0

**Владелец:** владелец DataCore. **Основание:** поручение21.11.2026 прекратить постоянные переделки и завершить раздел по единому проверенному стандарту. **Статус:** требования зафиксированы для независимой приёмки; окончательный PASS/утверждение ещё не получены. Номер стандарта не является полем presentationVersion документа.

Это единая точка требований и критериев завершения. Подробные сценарии проверки — [C173](crew/C173-passport-independent-release-check/TZ.md), предметные поля — PRODUCT/схемы, технические детали — MAP/OpenAPI. Исторические ТЗ и предлагаемые улучшения не являются разрешением менять принятый стандарт. Новое явное решение владельца имеет приоритет и записывается как изменение версии требований.

## 1. Что считаем завершённым продуктом

Менеджер без помощи разработчика создаёт правильный паспорт из шаблона изделия либо позиции заказа, проверяет образец, выпускает с номером и печатает. Известные данные не вводятся повторно. Повторные рисунки Inventor обновляют действующие экземпляры редакцией с прежним номером; история и файлы сохраняются. Завершённый оплаченный заказ хранит неизменяемый комплект документов. Сценарий одинаково предсказуем при повторе, отмене, ошибке и одновременной работе.

**Граница ПС-1.0:** компьютерный интерфейс, поддерживаемые категории изделий, short/full в существующем объёме, standalone/заказ, Inventor-импорт, образец/выпуск/редакции/печать/защита истории, архивная граница. Телефон, новый внешний вид, новые категории/модули и новые способы импорта не добавляются ради «улучшения» в приёмку этой версии.

## 2. Обязательные правила

| ID | Фиксированное поведение | Как доказать |
|--|--|--|
| ПС-01 | Шаблон относится к изделию; образец без номера и выпуска; экземпляр/номер относятся к конкретной поставке/позиции либо самостоятельному выпуску | Открытие/preview не создают номер/лишний документ; две одинаковые модели в разных строках не смешиваются |
| ПС-02 | Один повторный запрос/двойной клик — один выпуск и один номер. Фирма, дата, номер изделия, паспорт и талон согласованы | Повтор и потеря ответа, сверка всех страниц/счётчиков/связей |
| ПС-03 | Short не требует лишнего производственного состава; full содержит применимые подробности. Категория/назначение/способ установки определяют состав полей и разделов | Матрица категорий/вариантов, смена контекста, сохранение/возврат без чужих обязательных полей |
| ПС-04 | У каждого рисунка одно назначение: общий вид, габариты, монтаж/фундамент и другие применимые виды. Монтаж по схеме невозможен без приложенной схемы | Разные распознаваемые изображения и проверка реального PDF; anchor→mounting, concrete→foundation, оба варианта |
| ПС-05 | Справочники и изделие — источники типовых данных; свои тексты/обложка/нецелевые рисунки не теряются. Параметры анкеров/основания не выдумываются | До/после по API и PDF, отмена автозамены, реальные подтверждённые данные проектировщика |
| ПС-06 | Одна подтверждённая отправка Inventor меняет актуальные рисунки/одобренные числа одной операцией. Неполная ошибка не оставляет частичного успеха | Повтор, отказ от чисел, PNG-сбой, ошибка второго паспорта, конфликт контекста, атомарный rollback |
| ПС-07 | Действующий выпущенный паспорт можно изменить новой редакцией; номер прежний, предыдущие поля/изображения/источники печати сохранены. Неизменные входы не создают редакций | Реальные разные PDF до/после; восстановленные исторические sources; защита всех старых файлов/дублей от удаления |
| ПС-08 | Закрытый и полностью оплаченный заказ фиксируется неизменяемым архивным комплектом; обычная правка, ключ/импорт/каскад и удаление файла не обходят фиксацию. Возврат — отдельная авторизованная операция с причиной/историей | Проверка оплаты и состава комплекта, серверные запреты всех писателей, race с закрытием; исходный архив не перезаписывается |
| ПС-09 | Прикреплённый готовый PDF и выбранный вложенный паспорт — явные источники. Автогенератор не подменяет их и не скрывает потерю файла | Готовность/скачивание/печать, broken-file, возвращение к источнику сайта, понятные предупреждения |
| ПС-10 | Чтение/печать старого образца не мигрирует его формат и не меняет номера/данные/историю. Изменение Inventor — отдельная согласованная редакция действующего экземпляра | Legacy, аннулированный, закрытый заказ, readOnly API/повторная печать |
| ПС-11 | PDF читаем и согласован: единицы/размеры/масса, подписи, иллюстрации, страницы, таблицы, логотип/фирма/талон, корректная раскладка буклета | Проверка всех страниц, эталонные PDF, реальный пробный отпечаток A4/буклета |
| ПС-12 | Роли, границы разделов, API/ключи и конкурентная работа защищены на сервере | Матрица прав + прямые HTTP-вызовы, реальные контролируемые гонки create/issue/photos/import/close |

**Нынешний пробел:** ПС-08 полностью ещё не реализован. C172 пропускает все closed-договоры только в импорте и не проверяет оплату. Это временная консервативная защита, а не полный архив. Полное завершение раздела по ПС-1.0 нельзя объявлять, пока ПС-08 не выполнен либо владелец явно не утвердил отдельный сокращённый этап с перечисленными исключениями. Требования — [ARCHIVE-RULES](crew/C172-inventor-image-flow/ARCHIVE-RULES.md).

## 3. Документы, которые действительно нужны

Не создавать десяток новых ТЗ на одно поведение. Нужны следующие согласованные артефакты:

1. **Этот стандарт** — что обязано работать и когда раздел закрыт.
2. **Таблица применимости** `C173/APPLICABILITY.md`: для каждой поддерживаемой категории/варианта/установки — обязательные поля, тексты, виды рисунков, источники и правила отсутствия. Подтвердить по существующим правилам и фактическим изделиям; противоречия вынести координатору, не решать самовольно кодом.
3. **Эталонный комплект** `C173/GOLDENS.md` + файлы: ID фикстуры, входные значения, изображения, параметры печати, версия стандарта/кода, контрольные суммы и подтверждение владельца. PDF618 с дефектом — исходный пример ошибки, не утверждённый эталон.
4. **Независимая приёмка** `C173/REPORT.md`, FINDINGS/CASES/EVIDENCE и список закрытых находок с регрессиями.
5. **Короткая инструкция менеджеру** в существующей справке приложения: создать/проверить/выпустить/изменить/архивировать, в том числе куда смотреть при отказе. Не дублировать её отдельными противоречащими памятками.
6. **Лист приёмки** `C173/SIGNOFF.md`: перечень требований/эталонов/проверок, итоговый SHA/версия, нерешённые вопросы, кто и что подтвердил. Подтверждение владельца нельзя вписать от его имени.

## 4. Минимальный эталонный набор

| Эталон | Что подтверждает |
|--|--|
| Урна/BLG short, анкеры | Простой основной сценарий; общий вид, размеры и реальная схема крепления |
| BLG short, бетонирование | Фундамент и глубина; отсутствующая схема блокирует применимый выпуск |
| TRN short + full | Оба варианта, применимые признаки/описание/поля/монтаж без лишнего для short |
| DIO | Применимая зона безопасности и данные категории; никакой подстановки чужой схемы |
| Full со сборкой | Состав/материалы/модули/сборочные рисунки в существующем поддерживаемом объёме |
| Одинаковая модель в двух позициях/фирмах + standalone | Принадлежность, номера и реквизиты не смешиваются |
| До и после второй редакции | Новые рисунки/числа, прежний номер; старый комплект и файлы сохранны |
| Закрытый оплаченный заказ + вложенный готовый PDF + legacy | Неподменяемость архива/явного источника, совместимость старых документов |

Для эталонов проверить обычный PDF/буклет, монохромный/цветной и комплект паспорта/талона там, где применимо. Не размножать одинаковые снимки без причины: матрица покрывает разные правила, а не произвольное число файлов.

## 5. Условия окончательного завершения

- [ ] Нет неразрешённых противоречий по ПС-01…12 и применимости; scope/исключения явно утверждены.
- [ ] Таблица применимости и эталоны заполнены реальными подтверждёнными входами, все страницы просмотрены.
- [ ] Независимый C173 завершён; все P0/P1/P2, нарушающие стандарт, исправлены и повторно проверены; нет скрытых FAIL/SKIP обязательного пути. Неблокирующая косметика не запускает перепроектирование.
- [ ] Полные unit/e2e/build/проверки PWA и права зелёные на итоговом зафиксированном SHA, доказательства/manifest сохранены.
- [ ] Настоящий Inventor прошёл экспорт→загрузка→редакция→PDF; выполнен пробный физический отпечаток, если в объём включено обещание правильной печати буклета. Не считать эмуляцию API исполнением VB.
- [ ] Архивная граница реализована и проверена по ПС-08, либо отдельное уменьшение объёма письменно принято владельцем — не скрыто в отчёте ИИ.
- [ ] Менеджер самостоятельно проходит обычный и повторный выпуск без подсказок разработчика; владелец подтверждает нужные эталоны/содержание. Независимый ИИ помогает подготовить это решение, но не подменяет владельца/проектировщика.
- [ ] Итоговый код безопасно выпущен по datacore-deploy, выполнен post-release smoke на затронутом пути, версия/SHA зафиксированы; старые документы и данные сохранены. Разрешение на выкладку следует обычным правилам проекта.
- [ ] SIGNOFF заполнен фактическими подтверждениями, стандарт получает статус **«ПС-1.0 принят, раздел в сопровождении»**, бэклог завершённого убран в архив.

«100% завершено» означает выполненные и подтверждённые критерии согласованного объёма. Это не обещание отсутствия любых будущих ошибок, новых товаров или изменений требований.

## 6. После приёмки: как прекратить постоянные переделки

1. **Никаких инициативных переделок ИИ** формы, текста, архитектуры, правил обязательности или PDF. «Мне кажется красивее/проще» — предложение в бэклог, не задача к исполнению.
2. Любая правка относится к одному из трёх оснований: воспроизведённый дефект против ПС-ID; новое явное требование владельца; подтверждённое изменение обязательных внешних требований. Указывается основание, затронутые эталоны и ожидаемое различие.
3. Координатор определяет минимальные файлы и регрессии. Сам исполнитель независимой проверки получает FIX-TZ только по подтверждённым F-ID, не переписывает раздел по полному списку пожеланий.
4. Исправление дефекта не меняет стандарт. Новое поведение оформляется как ПС-1.1 с решением владельца, миграционными границами/историей и обновлением применимых эталонов.
5. Эталонные PDF нельзя автоматически заменять результатом падающего теста. Отличие сначала объяснить и согласовать; затем обновить только утверждённый эталон. Не ослаблять тесты ради зелёного статуса.
6. Предыдущие принятые версии/документы остаются воспроизводимыми. Справочники и новый шаблон не переписывают архивный комплект. Периодическая проверка неизменного кода — сопровождение, не новый цикл разработки.

## 7. Что должен добавить независимый исполнитель

В C173 подготовить `STANDARD-GAPS.md`: ПС-ID → что уже доказано → чего не хватает → дефект/данные/решение/открытый этап → минимальное действие → критерий закрытия. Также APPLICABILITY/GOLDENS и **проект** SIGNOFF. Ограничиться тем, что необходимо для завершения ПС-1.0; новые функции вынести отдельно. Координатор сведёт предложения в один FIX-TZ, после чего этот же исполнитель исправит подтверждённое. Стандарт и статус приёмки не менять без решения владельца.
