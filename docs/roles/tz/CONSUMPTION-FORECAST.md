# Прогноз потребности материалов (CONSUMPTION-FORECAST)

Класс XL, аналитик до кода (2026-10-29). История цен — отдельно: `DATA-ANALYTICS-AUDIT.md`. Код не менялся. Прод-замеров нет (вход на прод не делался): оценки по коду, помечены «оценка».

## 1. Сигналы
| Сигнал | Где | Что показывает | Близость к реальному расходу |
|--|--|--|--|
| Заказано | `supplyrequests`: `materialId`, `qty`, `unit`, `requestDate`, `invoiceDate`, `status`, `priceHint` (supply-request.schema.ts:36-96,144-148) | Сколько просили купить | Дальше всего: закупают с запасом и пачками |
| Получено | `receivedQty` (:83), `stockmovements type='in'` (stock-movement.schema.ts:13-34) | Сколько пришло | Средне |
| Выдано | `stockmovements type='out'`, `date`, `qty`, `materialId`, `salesOrderId` (:82) | Ушло в работу | Ближе всего: это и есть потребление |

Вывод: прогнозировать потребность по **выдачам** (`out`), а календарь закупок строить по **заказам** (когда и на какую сумму реально платим). Заявки нужны для периодичности и суммы; выдачи — для объёма. Если выдач у материала нет (склад ведут не по всем) — запасной сигнал: заказано со статусом `received`.

## 2. Пробелы
- **Без materialId.** Связь из sheets-sync только по точному совпадению названия (`sheets-sync.targets.ts:67-73`, `normText`), плюс дозапись `relink` (:113-117). Любая опечатка, лишнее слово, цвет в названии, новый материал — заявка остаётся со свободным `title`. Оценка: 20–40 % заявок без связи (на проде не замерено). Заявки с экрана приложения: связь есть, если выбрали из каталога; «свободная строка» разрешена схемой (:32).
- **Единицы.** `unit` — свободная строка, не справочник. Одинаковый материал может быть «шт», «штук», «м.п.», «м». Складывать нельзя без приведения. Единица базовая у материала — сверить с `materials.unit` (не проверено в этом ТЗ).
- **Дата.** `requestDate` необязателен; `invoiceDate` ставят позже, часто пуст. Запасная дата — `createdAt` (есть всегда, но для импортированных это дата импорта, а не заявки: искажает историю). Для выдач `date` обязателен — надёжнее.
- **Дубли материалов.** Единого слияния нет; дубль даёт два ряда истории и ломает периодичность. Слияние дублей — предпосылка фазы 2.
- **Количество.** `qty` по умолчанию 1: пустая ячейка в таблице превращается в «1» (`num(r.qty) ?? 1`, targets:98) — шум.
- **Сумма.** Только `priceHint` (подсказка, не факт); в прогнозе денег уже на нём (`finance.service.ts:193`). Факт цены — `materialprices` (см. DATA-ANALYTICS-AUDIT).

Достаточно ли полей: **да для объёмов и периодичности, нет для качества** — новых полей в `supplyrequests` и `stockmovements` не нужно (общие с CRM, не трогаем). Нужно чистить связь с материалом и единицы.

## 3. Что копить: свёртка или на лету
- **На лету**: один aggregate по `supplyrequests`/`stockmovements` с группировкой по материалу и месяцу. Плюс: ничего не хранить, всегда свежо. Минус: каждый запрос — скан всей истории; для карточки материала (по одному `materialId`, индекс есть) дёшево, для общего прогноза — тяжело.
- **Свёртка `consumption_monthly`** {materialId, month 'YYYY-MM', unit, qtyOrdered, qtyReceived, qtyIssued, amount, requests, orders (число заказов), updatedAt}; ключ уникальный {materialId, month}. Новая коллекция data-core (не общая с CRM, безопасно). Пересчёт: ночная задача по образцу `setInterval` в `disk/offsite.ts:72` (в проекте нет @nestjs/schedule — не подключаем), окно: текущий и прошлый месяц; полный пересчёт — по кнопке/скрипту. Идемпотентно (upsert), без триггеров на запись.
- **Выбор:** свёртка. Объём малый (материалов сотни × месяцы), данные нужны сразу многим экранам (Деньги, Сегодня, карточка), а ночной пересчёт не нагружает ввод. Карточка материала может в начале считать на лету — ей свёртка не обязательна.
- Журнал выдач для расхода брать по `type='out'` без перемещений между складами (`transfer`) и без `adjust`.

## 4. Метод прогноза (простой, объяснимый)
Единицы: считаем в базовой единице материала; если единица заявки не приводится — материал исключён, подпись «единицы не сходятся».
- **Месячная потребность** = среднее `qtyIssued` за 3 месяца (если месяцев с данными < 3 — за сколько есть, но не меньше 2). Рядом показываем среднее за 6 и 12 — пользователь видит разброс. Основная цифра — 3 мес; «год» = средняя за 12 мес × 12 (пока < 12 мес истории: средняя × 12 с пометкой «грубо»).
- **Периодичность**: медиана интервалов между датами заказов (нужно ≥ 4 заказа), «обычно раз в N дней». Следующий заказ = последняя дата + медиана. Если разброс интервалов > 50 % медианы — «нерегулярно», дату не обещаем.
- **Сумма**: средний объём заказа × последняя известная цена из `materialprices`; нет цены — без суммы.
- **Сезонность**: только при ≥ 24 месяцах (иначе нечего сравнивать год к году); при 12–23 — не показываем. Сейчас, вероятно, не нужна.
- **Минимум для показа**: ≥ 3 месяца с движением и ≥ 3 заказа/выдачи. Меньше — «мало данных» вместо цифры. Любая цифра показывается с формулой: «среднее за 3 мес = X».

## 5. Где показать
1. Карточка материала: таблица «по месяцам» (заказано / выдано / сумма), «обычно заказываем раз в N дней, последний раз …, ориентир следующего …». Фаза 1.
2. «Деньги → Прогноз» (`finance.service.ts:176`, `forecast.ts`): отдельная строка-слой «Ожидаемые закупки (оценка)» по материалам с регулярным циклом, отличать от реальных счетов (серым/пунктиром), не смешивать в сумме «обязательств»; включать переключателем. Не дублировать закупки, по которым уже есть открытая заявка с суммой.
3. «Сегодня»: блок «Скоро заказывать» — материалы, у которых ориентир заказа в ближайшие 7 дней или остаток < потребности месяца и нет открытой заявки (`today.service.ts`).

## 6. Фазы (каждая выкладывается отдельно)
- **Ф0 (S) Чистка входа.** Отчёт «заявки без материала» (число и список) через datacore-access; подсказка в форме заявки «выберите из каталога»; единицы — справочник/подсказка. Данные прода не менять без «да».
- **Ф1 (M) Карточка материала на лету.** Один aggregate по `materialId`, таблица по месяцам + периодичность. Без новых коллекций. Тест на примерах (юнит).
- **Ф2 (M) Привязка и слияние.** Массовая привязка по названию (нечёткая, с подтверждением человеком), слияние дублей. Прод-данные — только после «да».
- **Ф3 (M) Свёртка `consumption_monthly`.** Схема, ночной пересчёт (+ кнопка в админке), полный пересчёт скриптом, юнит + e2e.
- **Ф4 (L) «Прогноз» в «Деньгах».** Слой ожидаемых закупок по свёртке и `materialprices`; переключатель; юнит на `forecast.ts`; full-проверка.
- **Ф5 (S) «Сегодня → Скоро заказывать».**
- **Ф6 (S, позже) Сезонность** — когда будет ≥ 24 мес.

## 7. Риски
- Склад ведут не по всем материалам: выдач мало — прогноз по выдачам пустой (запасной сигнал — получено).
- Разовые крупные заказы под один проект сбивают среднюю; использовать медиану и исключать выбросы (> 3× медианы) в Ф3.
- Общие с CRM коллекции — только читаем; свёртка своя.

## Вопросы пользователю — `docs/QUESTIONS.md` («ПР»)

## Решение 2026-10-29 (ПР-1)
Основа прогноза — **заявки со счетом** (дата счёта `invoiceDate`, иначе `requestDate`; количество и сумма из заявки). Выдачи со склада — только сверка (показатель «выдано из купленного»), не основа. Причина (пользователь): деньги и счёт — надёжный факт; склад могут забыть провести.
