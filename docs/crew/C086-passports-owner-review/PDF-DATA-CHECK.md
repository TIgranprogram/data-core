# C086 — причина отсутствия рисунков в PDF (read-only)

Проверено 12.11.2026: внешний `evidence/ui-scenario.mjs`, результаты `ui-scenario-fill.json`/`ui-scenario-more.json`, два PDF и локальный код. `session.local.json`, содержимое `evidence/stand`, учётные данные, API стенда/прода не читались. Код не менялся.

## Что установлено

Оба файла `passport-600.pdf` и `order-9-short.pdf` имеют 9 страниц и 0 встроенных изображений (повторная проверка PyMuPDF). Это не доказательство исправной печати рисунков.

В сценарии НЕТ подстановки фиктивных URL. Есть генерация тестовых PNG через canvas: белая картинка 320×200 с текстом `C086 чертёж A` (строка 212), либо `C086 overview/dimensions/foundation` (строка 273), затем обычный ClipboardEvent/paste и загрузка через UI. Это валидные файлы-заглушки для проверки вставки, а не реальные чертежи. Проверка фото по умолчанию использует табличку, не указатель.

Однако сохранённый `ui-scenario-fill.json` для указателя, выпущенного как №600, содержит `вставленоРисунков: []`, `былоОбязательных: []`, состояние `ready` ДО выпуска. Значит, этот конкретный прогон вообще не добавлял рисунки указателя. Он использовал уже подготовленное состояние стенда. Из разрешённых артефактов нельзя установить, кто и когда привязал предыдущие фото, их storageUrl и были ли файлы физически в uploads. Утверждение «сценарий подменил рисунки фиктивными URL» не подтверждено.

## Почему возможен issued без картинок

- `passport-rules.ts:235` проверяет присутствие вида (`kind`) в массиве изображений; существование записи photos, файла и декодирование не проверяются.
- `passport-issue.ts:34` принимает readiness, затем freezeImages сохраняет ссылки и выдаёт номер. PDF при выпуске не генерируется и байты рисунков не проверяются.
- `passport-pdf.service.ts:55–65`: недопустимый путь пропускается; ошибка чтения/декодирования файла даёт предупреждение и `undefined`.
- Там же `:228–243`: в PDF попадают только успешно прочитанные буферы; отсутствующая photos-запись, недоступный файл или повреждение приводят к пропуску. Поэтому наличие привязок в БД может дать ready/issued при пустом PDF.

Это подтверждённый механизм расхождения, но точную первопричину конкретных файлов (нет загрузок в копии, битые ссылки, иное) без разрешённой проверки конкретных photos/storageUrl/серверного лога установить нельзя. Наиболее вероятное объяснение — данные фото есть, сами файлы недоступны; это гипотеза, не установленный факт.

## Короткий вариант и ссылки на схемы

Короткий вариант НЕ скрывает общий вид, габариты и фундамент при бетонировании: `passport-variants.ts:21,46–54`. Он убирает дополнительные виды; зона безопасности исключается вне DIO, фундамент исключается при анкерах. Поэтому отсутствие всех рисунков нельзя объяснить вариантом short.

В проверенном `order-9-short.pdf` есть необеспеченные ссылки:

- Физическая стр. 3, пункт 3.6: порядок крепления приведён «на схемах, прилагаемых к паспорту».
- Там же 3.3: размеры зоны безопасности приведены в приложении или проекте площадки.
- Физическая стр. 4: бетон марки, указанной в схеме установки или указаниях изготовителя.
- Физическая стр. 5, 9.6: исключение гарантии при монтаже с отступлением от «прилагаемых схем».

Пункт 3.6 прямо обещает схемы, которых в этом PDF нет. Остальные формулировки допускают внешние указания/проект либо также ссылаются на приложения. Текущий основной `backend/scripts/passport-texts.v2.json` уже содержит более осторожное «если они приложены»; проверенный выпущенный PDF всё ещё содержит прежнюю формулировку. Это соответствует сохранению снимка текста выпущенного паспорта и требует отдельной проверки фактической ревизии/снимка, а не вывода по текущему JSON.

Итог: выпуск №600 доказан, успешный путь реального рисунка до PDF — НЕ доказан. Следующая минимальная проверка через ответственного за доступ: только фото-ссылки №600, доступность/декодируемость соответствующих файлов и предупреждения PDF-загрузчика. Никаких изменений данных до подтверждения причины.
