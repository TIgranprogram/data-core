# C086 — паспорт: применимость вопросов и спокойная форма

**Класс L.** Результат: менеджер открывает позицию заказа, видит изделие и категорию, дополняет только применимое и выпускает паспорт. Повторный проход не спрашивает сохранённое.
**Max agents: 4**, без второй команды: исполнитель, QA, дизайнер; архитектор при изменении серверного контракта. Координатор сейчас правит только документы. Код и проверки этой задачи принадлежат отдельному исполнителю; чужие изменения не откатывать.

## Порядок реализации

1. Сначала `APPLICABILITY.md` рядом: перечислить поддерживаемые категории и группы из кода/справочников; категория + тип/признаки → применимые поля/рисунки/варианты → обязательность → источник → место сохранения. Отделить «обязательно», «применимо, необязательно», «не применимо», «неизвестно». Проверить настройки через access только чтением, если нужны живые данные. Нет доступа — зафиксировать и использовать явно названные фикстуры; не выдавать их за прод.
2. Не выводить обязательность в применимость: необязательное поле бывает полезным. Не считать широкую BLG типом ограждения. При неизвестном типе — понятное уточнение. Детерминированные значения из изделия/правил подставлять; гипотезы названия подтверждать. Нормативные значения не сочинять. Ручные правки сохранять.
3. Согласовать модель полей экрана и серверную готовность/выпуск. Один источник правил; без отдельного списка исключений в каждом экране. Смена категории/типа пересчитывает варианты и готовность. Несовместимое сохранённое не стирать молча; объяснить и предложить исправление. Полный режим не возвращает неприменимые поля.
4. Список: название нормальным регистром отображения без изменения исходных данных; отдельно категория, краткий статус и следующее действие. Не печатать все пробелы в шапке каждой строки. При раскрытии видны изделие/категория/тип; заполненное компактно, доступно для правки.
5. Режимы компактно справа сверху (на телефоне перенос). Поля с видимыми подписями и промежутками; короткие числа ограниченной ширины. Похожие поля объединить логично. Один следующий шаг и одна главная кнопка. Использовать общий form/section/row/segmented; расширение варианта — kit + витрина, без индивидуальной темы паспортов.
6. Общий компонент фото: единые рамки/состояния и контракт UI-ACCEPTANCE. Убрать перехват клика всей пустой зоны. Приоритет фокуса над hover, ровно один получатель Ctrl+V. Сравнить паспорт и второй реальный потребитель; сохранить просмотр загруженного, замену, удаление, загрузку по кнопке и drop.
7. Закрепить воспроизводимые дефекты тестами и измеримыми правилами site-audit (подписи, пересечения, overflow). Не добавлять тест «класс существует» вместо проверки поведения. Проверить, что правило падает на исходном дефекте и проходит после исправления.

## Критерии приёмки

- [ ] Указатель BLG: без вопросов про пользователей, возраст, падение, площадку и элементы ограждения при подтверждённом типе; применимые размеры/материалы/рисунки не потеряны.
- [ ] Контрольные TRN/DIO и ограждение: их применимые обязательные параметры остались. Все поддерживаемые категории покрыты матрицей и тестами правил.
- [ ] Нет типа/нет категории: одно понятное уточнение, отсутствие вариантов объяснено, неверное «готово» не появляется.
- [ ] Из заказа, изделия и нового паспорта используется одинаковая применимость; повторное открытие сохраняет ответы.
- [ ] C075: заполнение позиции → готовность → выпуск; C078: «Да, верно» и «Другой вариант», без записи догадки до подтверждения.
- [ ] Длинные названия, несколько пробелов, пустые значения: иерархия читается; каждый select подписан и раскрывается без обрезания.
- [ ] Фото: фокус A, мышь над B, Ctrl+V → только A; клик зоны не открывает диалог, кнопка открывает. Проверены два потребителя.
- [ ] Темы и ширины по CANON, включая узкую панель; UI-REVIEW с открытыми списками и просмотренными снимками. QA и designer без блокирующих находок.
- [ ] Проверки по verify: типы, юнит, тесты PWA/аудита, полный прогон перед выпуском L; e2e только изолированная БД. Непройденное явно PARTIAL.
