# C094 — тексты паспортов подходят к изделию: план правки условий (аналитик, 2026-11-12)

Прод — только чтение. Выгрузки: `tools/logs/c094/` (gitignored): `x_<кат>.json` (тексты), `texts.txt` (все пункты), `products.json` (491 изделие), `d_*.json` (справочники).
Требования безопасности не сокращаю и не переписываю: правятся только условия `when` (строка признаков: пробел «и», `|` «или», `!` «не»).

## 1. Главные находки (важнее самих пунктов)

1. **«Для всех» на проде — старая версия.** `passporttemplates` `ALL_V2` v2 (активна) без единого `when`; без «ids». Исправления из `backend/scripts/passport-texts.v2.json` (`!atTree`, `concrete`, `bolts|welds`, `anchors`, `wood`, `moving`) на прод **не попали**: `v2All()` берёт базу, код — только когда базы нет (`product-passport.service.ts:727-731`). Поэтому в PDF указателя «анкеры» (3.9) и «зона безопасности» — это не ошибка кода, а версия в базе. Тексты исправлены в коде, но `passport-templates-polish.js` (замена текстов) на прод не запускался и вообще не умеет ставить `when`.
2. **Данные не дают условиям работать.** По 455 изделиям с категорией: `materialIds` пусто **0 из 455** (и у образца № 500) → признаки `wood` и `metal` не определяются нигде; `joints = bolts+welds` у 87 из 90 заполненных — одинаково и у деревянного указателя, и у скамьи (условия `bolts|welds` не различают); вид изделия (`elements`) пуст у 92 из 168 BLG, 20 из 30 DIO, ≈65 WRK; способ установки пуст у ≈110 изделий.
3. **Условие «признака нет» = «пункт выпал».** Для игрового комплекса 6102 (нет видов, нет установки) выпадают нужные пункты: DIO «функциональный осмотр» (`moving`), гарантия на износ подвижных частей. Условия на новые признаки нельзя вводить «положительно», пока данные пусты: иначе требование безопасности пропадёт молча (см. §5, правило П-1).
4. **Условие по категории выразить нельзя.** `when` смотрит только признаки (`PASSPORT_TRAITS`, `common/passport/traits.ts`), а часть «чужих» фраз чужая именно по категории (зона безопасности — BLG).
5. **Категории изделий смешаны:** в BLG 9 «Качели», горки, карусель, балансир (см. QUESTIONS Паспорта п.4 — «качели в благоустройство?»); в DIO — 8 баскетбольных стоек. Тексты у них «не те» из-за категории, условия это не лечат.

## 4. Данные: без них условия вредят

Правило П-1: пункт, зависящий от **вида изделия** (`users` не нужен), включается, пока вид не указан (три состояния «да / нет / неизвестно», как у `bolts`/`welds` — но без блока выпуска, только список «не знаю» в отчёте). Для условий по материалам — то же.
До включения условий выполнить (все — запись данных, пользователь запускает по обычному порядку):
1. Заполнить `materialIds` изделий (0/455) — либо вывод из `materialsSpec` (скрипт-подсказка). Без этого `wood`/`metal` пустые.
2. Виды изделия для 92 BLG, 20 DIO, ≈65 WRK и способ установки для ≈110 изделий.
3. `joints` по умолчанию `bolts+welds` у деревянных — вопрос, оставить ли «оба» по умолчанию (это скрывает смысл условия `bolts|welds`).
4. Поставить `traits` в справочниках: `passportElements` — `guards` (Ограждение (перила), Ограждение площадки, Поручень, Лестница, Площадка, Борт, Кровля?), `bin` (Урна, Корпус (ёмкость)), `bars` (Турник, Брусья, Рукоход, Шведская стенка, Комплексы), `landing` (Горка, Качели, Карусель, Балансир, Рукоход, Лестница, Площадка, Канатная сеть).
5. Категории: BLG-качели (9) — решение владельца (QUESTIONS Паспорта п.4).

## 5. План правки (для скрипта и кода)

Версии, не перезапись (как `passport-templates-polish.js`): активная версия → неактивная, новая `version+1`. Выданные паспорта читают `textSnapshot` — не меняются. № 600 (указатель, выпущен 11.11) → перевыпуск отдельной ревизией по решению владельца.
Порядок:
1. **Код (architect/backend):** добавить 5 признаков в `PASSPORT_TRAITS`; `users` — вычислять из `passportCategory`; три состояния для видо-зависимых признаков (П-1); тест порядка разделов не трогать. Не менять тексты и `ids`.
2. **Скрипт (расширить `passport-templates-polish.js`, режим `when`):** форма `{cat, key, id, when}`; применять только если текст пункта в активной версии **точно** совпадает с кодовым (иначе пропуск «правили руками» — пользовательские тексты не теряются); по умолчанию без `--apply` — план «было → станет» + список «пропущено». Новая версия ALL_V2 v3 = активная v2 + `when`, **без подмены** текстов; тексты (общий список CHANGES скрипта: «приложение», «ежедневно», «изменения могут быть не отражены», «Изготовитель отвечает…», приёмка с упаковкой) — отдельным шагом, требуют «да» владельца (они подтягиваются из `passport-templates-polish.js`, не из условий).
3. **Данные:** справочники `traits` + изделия (§4).
4. **Проверка:** для 4 эталонов и по 1 изделию каждого вида (BLG/WRK/TRN/DIO) вывести «что войдёт в PDF» (`excluded[]` снимка, экран «Что попадёт в PDF»); сравнить с таблицей §2; PDF через предпросмотр.
5. Выпущенные № 600 и 342 старых — не пересчитывать.

Скрипт готов к написанию: условия (§3, колонка «после») однозначны для 25 пунктов; блокирует **код признаков** и **данные** (§4 п.1–2). Без этих двух условий включать нельзя: пункты безопасности начнут выпадать у ≈ 190 изделий без вида.
