# Склад по-новому — требования пользователя и план (2026-10-23)

> Требования записаны со слов пользователя (разговор 2026-10-23). Это общий документ задачи: по нему координатор режет ТЗ `SK-1…SK-8` (ниже чек-листы), аналитик уточняет логику, архитектор решает «как хранить». Принцип пользователя: **одна база всё объединяет** — новых таблиц не плодить, где можно — представление существующих (заявки ↔ счета ↔ склад ↔ заказы ↔ продукция).

## Требования (словами пользователя, сжато)

**Фильтры и поиск («хлебные крошки» М4, М6, М8, «Болт мебельный»…)**
- Нравится. Число после значения убрать («М6 19» путает). Значение с нулём не показывать.
- В свёрнутом виде не мозолить глаза: большой заметный значок поиска; нажал — можно вводить текст, и раскрываются фильтры.
- Фильтры — как в интернет-магазине: панель слева (на телефоне — выезжающая), галочки; группы (категория, тип, резьба…) — выпадающие, по умолчанию свёрнуты; короткие — раскрыты.

**Кто работает:** кладовщик. У человека может быть **несколько ролей** (кладовщик + инженер…) — видит разделы и поля всех своих ролей.

**Склад — одна страница:** главные действия «Принять», «Выдать», «Забронировать» (+ «ещё»: списать, пересчёт); остатки ниже; движения — история (последние + «вся история»). Набросок координатора — в разговоре 2026-10-23, принят как основа.

**Принять:** в основном по заявке (через приложение); бывает «купили без заявки, есть оплаченный счёт» — тоже принимаем. Будет раздел **«Бухгалтерия»** со счетами (позже — договоры): счета связаны с заявками; **одна база — это представление** заявок/счетов, а не новые таблицы.

**Выдать:**
- под **позицию заказа**: заказ № → позиции 1, 2, 3… (обозначение вида «№ заказа-№ позиции», например `552-2`); при выборе кладовщик видит **название позиции и картинку изделия**, а не цифры; выбор — выпадающие списки с поиском;
- **сотруднику** (расходники) — без заказа;
- «под что» указывать не всегда: «просто выдано» сотруднику или на заказ;
- если выдано под позицию, привязанную к изделию «Продукции», — **состав изделия копится**: «6 болтов, 12 гаек…» → со временем у изделия полный состав и себестоимость (цены — из заявок/счетов). Изделия бывают стандартные и индивидуальные (под проект); стремимся к стандартным.

**Забронировать:**
- под заказ клиента (выбор заказа и позиции из списка; если указано в спецификации — подставляется само);
- бронь можно править (изменилось при проектировании);
- **«Выдать по брони»** — одной кнопкой выдать забронированное под заказ; бронь снимается сама;
- инженер загружает **спецификацию** (Excel по шаблону / пачкой) → позиции бронируются под заказ автоматически.

**Пересчёт и списание:** на карточке позиции — «Пересчитать»: ввёл фактическое количество → корректировка (было 9, по факту 10/12). Остаток всегда актуальный; следит менеджер. Списание (брак и пр.) — «Списать» с причиной.

## Что уже есть (беглая сверка координатора, уточнит аналитик)
- Движения склада: `in`, `out`, `adjust`, `reserve`, `unreserve`, `count` (пересчёт — «сколько лежит всего») — `stock/stock-movements.service.ts`, `stock/dto.ts`. Пересчёт и корректировка на сервере **есть**.
- Бронь `reservations`: `orderId` (строка), `salesOrderId`; брони по заказу — индекс `{orderId, status}`. Общая с CRM.
- Состав изделия: `products.composition` + «Изменить состав» в «Продукции» (БЗ-5), себестоимость — по последней закупке.
- Позиция заказа = `incomes` (+ `productId` на изделие), заказ — `salesorders`.
- Роль пользователя — **одна строка** `users.role` (`user/*.schema.ts`, коммент «можно расширить до string[]»). Коллекция `users` — проверить, общая ли с CRM (архитектор).
- «Операции» (`sections/ops.js`) — быстрый ввод списком; «Остатки», «Движения» — отдельные вкладки.
- Импорт спецификации — не найден беглым поиском (аналитик: есть ли «пачкой» где-то в заявках/операциях).

## Чек-листы (ТЗ режет координатор; порядок — сверху вниз)

**SK-1. Фильтры «как в магазине»** — frontend, мелко
- [ ] Убрать число у значений фильтров; значения с нулём не показывать.
- [ ] Свёрнутый вид: крупная кнопка-поиск; по нажатию — ввод текста + панель фильтров (слева на компьютере, выезжающая на телефоне).
- [ ] Группы фильтров — сворачиваемые; длинные свёрнуты, короткие (≤ 6 значений) раскрыты; галочки.
- [ ] designer — проверка; запись в DESIGN §8.

**SK-2. Аналитика склада** — analyst (до кода)
- [ ] Сценарии: принять (по заявке / по счёту без заявки), выдать (позиция заказа / сотрудник / просто), забронировать, выдать по брони, спецификация → бронь, пересчёт, списание — шаги, поля, что пишется в какие коллекции (`stockmovements`, `reservations`, `incomes`, `products.composition`).
- [ ] Ссылка выдачи на позицию заказа: формат «заказ-позиция», где хранить (поле движения), как показать с картинкой.
- [ ] Накопление состава изделия из выдач: правила (стандартное vs индивидуальное изделие, повторные выдачи, возвраты), подтверждение человеком или автоматически.
- [ ] Спецификация: шаблон Excel, сопоставление строк с позициями склада, заказ/позиция из файла.
- [ ] Критерии приёмки для SK-3…SK-7; вопросы — в QUESTIONS.

**SK-3. Решение архитектора** — architect (до кода)
- [ ] Несколько ролей у пользователя: `users.role` → массив без поломки CRM и `kppd_`-ключей (общая ли `users`), права = объединение ролей.
- [ ] Видимость разделов/блоков по роли: где хранить (роль → список разделов), как проверять на сервере и в приложении.
- [ ] Ссылка движения на позицию заказа и на сотрудника — поля в `stockmovements` (общая с CRM: только добавлять необязательные поля).
- [ ] «Бухгалтерия → Счета» как представление заявок (без новой коллекции).

**SK-4. Склад — одна страница** — frontend (+ backend при нужде)
- [ ] Кнопки «Принять / Выдать / Забронировать / ещё ▾ (Списать, Пересчёт)» → правая панель; «Операции» — режим «несколько позиций» внутри «Принять» и «Выдать».
- [ ] Остатки: остаток / в брони / свободно; «заканчивается», «в брони» — сверху.
- [ ] История: последние 5 + «вся история»; в карточке позиции — её история и те же кнопки.
- [ ] Убрать вкладки «Движения», «Операции» (адреса старых вкладок — переадресация).

**SK-5. Выдача под позицию заказа и сотруднику** — backend + frontend
- [ ] Выбор «Кому / подо что»: позиция заказа (поиск по № заказа и названию, картинка изделия), сотрудник (`persons`), «просто выдано».
- [ ] В истории и в карточке заказа — что выдано под позицию.

**SK-6. Бронь и «Выдать по брони»** — backend + frontend
- [ ] Бронь под заказ/позицию с выбором из списка; правка брони.
- [ ] «Выдать по брони»: одной кнопкой по заказу (с подтверждением списка), бронь снимается.
- [ ] Спецификация Excel → брони под заказ (шаблон, отчёт «что не сопоставилось»).

**SK-7. Состав изделия копится из выдач** — backend + frontend (после SK-2/SK-3)
- [ ] Выдача под позицию заказа с изделием → предложение «добавить в состав изделия» (правило — из SK-2); себестоимость — по ценам заявок/счетов.

**SK-8. Несколько ролей и видимость разделов** — backend + frontend (после SK-3)
- [ ] У пользователя несколько ролей; в «Пользователи → роли» — галочки разделов/блоков; меню и экраны — по ролям.

**SK-9. Пересчёт и списание на карточке** — frontend (сервер есть)
- [ ] «Пересчитать» в карточке позиции: ввод факта → корректировка с подсказкой «было N, станет M»; «Списать» с причиной.
