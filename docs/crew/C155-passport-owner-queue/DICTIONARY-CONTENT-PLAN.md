# C155. Наполнение нового короткого паспорта

Применение только через штатные API справочников и шаблона изделия. Исходные 38 видов и их категории сохранены. Точные поля, значения до записи, ID и тексты находятся в [dictionary-content-plan.json](dictionary-content-plan.json). Основания — рабочие выгрузки, [DICTIONARY-API.md](DICTIONARY-API.md) и рисунок изделия 1066.

## Пакет на рабочий сайт

| Справочник | Запись | Было → станет |
|---|---|---|
| Части изделия | Буквы `6afd50dd7485414ce8b73561` | Пусто → буквы / букв |
| Части изделия | Указатель `6afd4bc97485414ce8b72e9b` | Пусто → указателя / указателей |

«Каркас» и «Гриф» уже исправлены. Проверка по GET. «Шит» и «Щит» имеют ссылки. Источники ссылок и смысл «Шит» требуют проверки до решения об исправлении. Значения `categories` влияют на список частей в таблице материалов. Допуск «Каркаса» в этот список для TRN предусмотрен отдельной пробой на QA. Краткая фраза уже может ссылаться на эту действующую часть.

Четыре признака и восемь значений добавляются в существующие `productFacets` и `productFacetValues`. Каждый признак имеет `step:false` и `multi:false`. В JSON указаны точные поля запроса, ключи сопоставления и ожидаемые связи.

| Признак | Контекст | Значения |
|---|---|---|
| `trn.contact` | Тренажёр для ног | Две платформы для ног и рукоятка. Применять при подтверждении каркаса, рукоятки и обеих платформ |
| `wrk.climb` | Кольца, канат, скалодром | Гимнастические кольца · канат · скалодром с зацепами |
| `blg.sign.form` | Информационные стенды и указатели | Стенд с информационной панелью · указатель с обозначением направления |
| `blg.tribune.form` | Трибуны | Зрительские места · лестничный модуль |

На рабочем сайте добавляются записи словарей. Применение по виду, заполнение карточек и перепроверка старых значений проходят на QA. Для трибуны JSON сопоставляет прежние `blg.seats.*` с двумя функциями модуля. Ограждения, скамьи и совмещённые тренажёры используют уже имеющиеся значения. Сначала учитывается подтверждённый вид изделия, затем конструкция или упражнение. Положение, нагрузка, исполнение и особенности становятся вопросом только при различии применимых фраз. Известные `trn.kind`, `trn.muscles`, `trn.load`, `trn.build` используются как есть.

## Пакет на QA

1. **1066 Хипс.** Действующий вид «Тренажёр для ног» и значение `trn.contact.two-platforms-grip` автоматически выбирают словарный лист «Тренажёр состоит из каркаса с рукояткой и двух платформ для ног.» Ссылки ведут на «Каркас», «Ручка» и «Ногоступ». Одна ссылка на ногоступ описывает тип части, количество выражено в предложении. Основная приёмка проверяет `simpleDescriptionSource.kind=dictionary` при пустых собственной фразе и явном выборе этого корня. Значение нагрузки и назначение «Ноги» сохраняются. Приоритет собственной фразы проверяется отдельным временным изменением на копии. Способ монтажа должен подтвердить конструктор из-за расхождения с выбранной анкерной фразой.
2. **Однозначные виды.** Загрузить 18 веток `qa` с одной применимой фразой. В частности, турник, брусья, шведская стенка, уличный стол, городские и детские качели, качалка на пружине. Фразы описывают общую конструкцию вида. Материал, размер, нагрузка, комплектность и скрытые детали остаются данными конкретного изделия.
3. **Виды с несколькими конструкциями.** Загрузить ветки `qa-conditional` с подтверждёнными значениями. В разделе выбора показывать только недостающий признак, от которого зависит фраза. Для ограждений и скамей подходят существующие критерии. Для колец/каната/скалодрома, стендов/указателей и типов модулей трибуны предусмотрены новые значения. Для трибуны сохранённое число мест определяет зрительский модуль, сохранённая лестница — лестничный. Число мест повторно не спрашивать. Отсутствие спинки определяется явным значением, «Доска» описывает другой признак.
4. **Подтвердить по изделиям.** Твистер, навесы и велопарковки имеют готовые фразы-кандидаты. Ветки открываются после проверки соответствующих конструкций по рисункам или паспортам. Для десяти широких видов нужен подтверждённый состав конкретного изделия. Комплексы описывать по реальному перечню модулей. Разновидности движений тренажёров добавлять к конкретному виду, когда подтверждены разные конструкции и получаются разные тексты. Группа мышц уже известна из назначения и для выбора состава здесь не нужна.
5. **Существующие поля на QA.** Добавить недостающие части «Подвес», «Пружина», «Столешница» с формами из JSON. Для назначения велопарковок есть точная новая фраза в существующем разделе. Для экотропы есть готовая фраза «Настил для экотропы». Применять её к виду после подтверждения, что изделия вида являются настилами. Эти привязки назначения и проба `categories` могут поменять выбор в прежней воронке, поэтому входят в проверку на копии. Для DSP в исходном каталоге отсутствуют изделия и виды. При появлении изделия проверять категорию и имеющиеся `dsp.kind`/ `dsp.age`.

Новые `simple-description`, `kindIds`, `partIds` и шаблонный `simpleDescription` используют контракт нового сервера. Для короткого описания выбраны явные предложения. Подстановка `{parts}` без количества может вывести «из каркасов» для одного каркаса.

## Применение и проверка через API

- Для `production.patch` и `production.verifyOnly` начать с GET `/api/dicts/<словарь>/<id>`, сверить ID, имя, текущие поля и сохранить ответ. Совпадение с целевыми полями означает, что запись уже сделана. При отличии от `expected` пропустить запись и зафиксировать расхождение. При совпадении с `expected` передать только `changes` в PATCH того же адреса, затем повторить GET и сверить результат с исходной записью. В журнал внести исходные поля, запрос, ответ и контрольное чтение.
- Для `production.addFacets` перед POST выгрузить оба списка с пагинацией и сверить ключи. Создать признак, затем его значения с полученным `parentId`. Совпадающую запись переиспользовать. Расхождение по тому же коду или совпадение по имени под другим кодом требует сверки. Контрольный GET по ID должен подтвердить все переданные поля и пустые ссылки на назначение, монтаж и элементы.
- На QA сначала сверить ключи и значения по GET списка. Для новых критериев совпадение определяется `code` и категорией, для значений — `code` и ID родителя, для частей — нормализованным именем. Для фраз — секцией, точным именем и ID родителя. Символы `@value:`, `@part:`, `@phrase:` внутри плана заменить фактическими ID из GET. Ключи плана используются при сопоставлении, запрос содержит только поля штатного API. Создавать через POST `/api/dicts/<словарь>` только при нуле совпадений. Повторное применение переиспользует найденные записи, каждую запись и её связи подтверждает GET. Дубли и отличающиеся совпадения требуют отдельной сверки. При ошибке записи повторно прочитать список перед повтором.
- Последовательность QA — части, признаки, значения, корни `simple-description`, листья, карточка и шаблон 1066. Сначала сохранить подтверждённое значение конструкции через PATCH карточки вместе с прежним значением нагрузки. Затем указать вид через PATCH шаблона, сверив ID, артикул и прежние собственные данные. При неопределённом критерии показать подходящие варианты или предложить собственную фразу. При несовместимом сохранённом значении исключить чужие листья. Проверить отсутствие повторного вопроса при сохранённом значении и когда есть одна применимая фраза.
- В QA сверить пять случаев. «Хипс» получает словарную фразу при первом открытии и после перезагрузки, турник подставляет одну фразу, ограждение с сохранённой калиткой выбирает её текст, ограждение без признака предлагает выбор, игровой комплекс без подтверждённого состава показывает пробел в описании. Отдельно проверить приоритет собственной фразы, полный вариант и сохранённый старый выпуск.

## Спорные записи

Подтверждённых записей для удаления нет. «Шит» и «Щит» заняты. У двух фраз «Информирование» одинаковый текст, одна ограничена отдельной группой. Для выявленного дубля сначала установить все живые ссылки и каноническую запись, затем проверить перенос ссылок штатным API и выполнить мягкое удаление. Снимки старых выпусков сохраняются.
