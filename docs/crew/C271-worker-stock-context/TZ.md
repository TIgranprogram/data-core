## Backend ownership

Исполнитель backend работает только в backend/src, backend/test, backend/scripts, по конкретному списку owner-файлов ARCHITECTURE.md. Узкий SupplyStockRequestController находится в SupplyModule, новый GET reservations — в stock, никакого Stock→Supply импорта/цикла. Существующие маршруты/ответы, shared Mongo-схемы и глобальные guards не менять. Индексы общей БД не добавлять. Никакой прямой записи supplyrequests из stock.

Реализовать два добавочных endpoint и owner createStockRequest строго по ARCHITECTURE: положительное конечное qty+UUIDv4 без лишних полей, unit/material/status/автор задаются сервером, scope и активный материал проверены до повтора; существующие manager/admin права, user-наблюдатель403. Replay после частичного прихода не сравнивать с изменённой qty заявки. C262 off→409.

Брони адресно в Mongo по materialId+active до skip/limit, стабильная pagination/total, только безопасные поля и batch-enrichment заказа без финансов. Старый reservations list не менять. ## Frontend ownership (следом за C270)

Перед началом получить от координатора подтверждение готовности backend-контрактов. Рабочие worker-details/history/context helper и scoped kit/preload/tests, адаптируя C270 без отката её функционала. История компактной матрицей, реальные даты, quantity с unit, один открытый ряд. Характеристики/коды/даты изменения удаляет текущий frontend владелец C270.

Для каждого materialId лениво загрузить ожидания и адресные брони, без веера запросов при входе, ограничить concurrency и кэшировать в view. Ошибка страницы не считается пустым успехом. Пагинация до total или явное «ещё», не cap100/2000. Открытые заявки статусов requested/in_progress/ordered/paid различать, дата только invoiceDeliveryDate; неизвестная дата явно неизвестна, qty уже остаток, unit каждой заявки своя. Бронь qty уже остаток, её issued повторно не вычитать; активную бронь отменённого заказа показать с предупреждением hanging. Назначение и номер заказа читаемы; не заставлять рабочего открывать недоступные requests/orders разделы.

Заказать: короткий ввод qty в unit материала, список уже открытых заявок; явное «Создать заявку», Отмена без записи. Не создавать при ошибке ожиданий/неизвестной unit/readonly/qty≤0. При существующих открытых заявках явно подтвердить дополнительную потребность, не маскировать повтор как новый заказ. UUID и Idempotency-Key сохраняются до известного исхода, повтор использует тот же ключ; двойной click disabled. Успех показывает номер созданной заявки и обновляет ожидания только этого materialId. Backend C262409/403/сеть показываются понятно. Все реальные тестовые записи — только disposable e2e или browser interception.
