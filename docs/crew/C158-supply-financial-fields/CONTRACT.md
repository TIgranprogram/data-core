# C158 — контракт учёта счетов и платежей

Статус: предметные решения до кода, 19.11.2026. Основание: поручение владельца начать C158, TZ.md и PARALLEL-REVIEW.md. Существующий заголовок «отложено» в раннем ТЗ заменён новым поручением; импорт C157 всё ещё запрещён до приёмки и выпуска. Это не разрешение миграции прода.

## 1. Результат и источник истины

Менеджер записывает документ поставщика и каждый подтверждённый факт оплаты один раз. Дата документа, фактическая дата платежа и момент регистрации — разные данные. Подтверждение «Оплачено» не является подтверждением получения товара. Возвратный залог, комиссия банка и доля чужого счёта не превращаются автоматически в обычную покупку на полную сумму.

Решение: отдельная дочерняя коллекция `supplyinvoicepayments`, только Data Core, не второй реестр расходов. Каждая запись принадлежит `supplyinvoices`. В `supplyrequests` не добавлять валюту/новую историю платежей: это общая коллекция CRM. Существующие зеркала обновлять в прежних полях только как результат полного погашения.

У счёта добавить `paymentAccountingVersion: 1` при атомарном переходе на новую модель. Отсутствие маркера означает старую модель. Маркер не снимается, даже если все новые платежи сторнированы: иначе вернётся прежний расход.

## 2. Денежные поля счёта и строки

Публичные `amount`, `priceHint`, `unitPrice`, `lineAmount` остаются рублёвыми величинами с включённым налогом. Их нельзя переопределить как валютные. `amount` остаётся суммой рублёвых строк. Для старых документов без новых полей всё считается как прежде.

Новые поля PATCH `/api/supply/invoices/:id`:
- `currency`: `RUB|USD|EUR|CNY|UE`, по умолчанию RUB для нетронутого старого документа.
- `currencyName`: строка до100символов, обязательна для UE; она описывает единицу из договора. UE не означает USD.
- `exchangeRate`: положительное число, до8знаков после запятой, рублей за1исходную единицу; `null` очищает только до финансовой блокировки. Для RUB не требуется.
- `exchangeRateDate`: YYYY-MM-DD, обязательна вместе с exchangeRate; реальная календарная дата, не будущая для фактической оценки.
- `exchangeRateSource`: текст до300символов, обязательный при ручном курсе: договор, сообщение, банковский документ. Автоматически курсы не загружать.
- `confirmedAmountRub`: число >=0, до2знаков, или null; явная подтверждённая рублёвая оценка документа имеет приоритет над пересчётом по округлённому курсу. Обязателен `conversionNote` до1000символов и/или fileIds, объясняющие подтверждение. Не подставлять это поле из догадки.
- `conversionNote`: примечание пересчёта.
- `vatMode`: `included|excluded|none|mixed`; `vatRate`: 0,5,7,10,20,22 или null; `declaredVatAmount`: сумма налога в исходной валюте документа или null.

Данные исходных строк хранить на стороне счёта, ключ — requestId; не расширять общую схему CRM. PATCH существующего `/api/supply/invoices/:id/lines/:lineId` дополнительно принимает `sourceUnitPrice?`, `sourceLineAmount?`, `vatMode?`, `vatRate?`, `declaredVatAmount?`. Количество остаётся qty. `sourceLineAmount` имеет приоритет над произведением округлённой sourceUnitPrice на qty. Явный итог первички не подгонять под округлённую цену; возвращать предупреждение о расхождении.

Производные новые поля ответа:
- `sourceAmount`: сумма исходных gross-итогов строк; не ручная независимая сумма.
- `accountingAmountRub: number|null`, `accountingState: resolved|unresolved` — известна ли рублёвая оценка документа. При unresolved старое `amount` не выдавать за валютную сумму; для нового валютного черновика оно0, а дополнительное состояние явно показывает «Рубли не определены». Ноль документа и неизвестная рублёвая оценка — разные состояния.
- В каждой строке `sourceUnitPrice`, `sourceLineAmount`, `sourceGrossAmount`, `sourceVatAmount`, `vatMode`, `vatRate`, `accountingLineAmountRub`.
- `calculatedVatAmount`, `declaredVatAmount`, `vatDifference`, `warnings[]` — исходная валюта обязательно подписана.

RUB: исходные и рублёвые итоги совпадают; новые source-поля не обязательны. Иностранная валюта: сначала фиксируются исходные строки; рублёвая оценка берётся из подтверждённого итога или суммы пересчёта строк. При confirmedAmountRub распределить его пропорционально gross-строкам, остаток копеек — детерминированно; сумма priceHint строго равна amount.

Без исходных строк/оценки разрешено сохранить черновик. Валютный документ без рублёвой оценки может быть выставлен только как документ с положительной sourceAmount, номером, датой, поставщиком и нашей компанией; в рублёвый прогноз его не включать, вместо вымышленной суммы показывать «Нужен пересчёт». Новый платёж при этом разрешён только с подтверждёнными фактическими рублями и суммой погашения в исходной валюте (§3). Legacy `/pay` без тела для такого счёта возвращает409 с требованием уточнить пересчёт, а не платит0или840руб за840USD.

## 3. Факт платежа и агрегаты

`SupplyInvoicePayment`:
- `id`, `invoiceId`, `clientUid`, `requestHash` — стабильная идентичность операции.
- `date: YYYY-MM-DD` — дата факта; `amount` — фактически перечисленные рубли, строго >0, максимум2знака.
- `payerCompanyId` — действующая наша компания, по умолчанию из счёта, но сохраняется в платеже независимо от будущих изменений справочника.
- `sourceAmount` — сумма погашения в исходной валюте; для RUB равна amount и может не передаваться; для иной валюты обязательна, строго >0, до2знаков. Все платежи одного документа используют его currency/currencyName.
- `exchangeRate?`, `exchangeRateDate?`, `exchangeRateSource?` — реквизиты фактического пересчёта. Из подтверждённых amount/sourceAmount сервер может вернуть effectiveRate с пометкой «из фактических сумм», не выдавая его за официальный курс. Подтверждённые рубли первичны; разные платежи могут иметь разные курсы.
- `fileIds[]` максимум20существующих доступных файлов, `note` до1000символов; сам файл не доказывает дату/сумму без проверки источника.
- `createdAt`, `createdBy`; `state: active|voided`, `voidedAt?`, `voidedBy?`, `voidReason?`, `voidClientUid?`. Финансовое содержимое платежа не переписывается; исправление — сторно и новая запись.
- `allocations[]`: requestId, amountRub, sourceAmount, сохранённые title/num/qty, invoiceNo, supplierId/name, categoryId, articleId, salesOrderId, costCenter/costObject и payerCompanyId. Это снимок на момент платежа, не динамическая подстановка старой статье из текущей заявки.

Индексы: unique(invoiceId,clientUid); invoiceId+date+_id; payerCompanyId+date; invoiceId+state. Уникальный ключ сохраняется и для voided-платежа: его повтор не создаёт замену. Новая исправленная операция имеет новый clientUid и ссылку replacementOf при наличии.

Ответ GET списка и карточки счёта дополняется:
- `paidAmount` — сумма active-платежей в рублях; `sourcePaidAmount`, `sourceBalance` — погашение и остаток в исходной валюте.
- `balanceDue: number|null` — остаток RUB для RUB; для валюты это **оценка остатка исходного обязательства** по документному курсу/подтверждённой оценке, а не amount−paidAmount. `balanceEstimated: true` для валютной оценки, без курса/оценки balanceDue=null. Сумма реальных рублей может отличаться от оценки из-за разных курсов.
- `paymentState: unpaid|partial|paid`; для RUB paid, когда paidAmount=amount; для валюты paid, когда sourcePaidAmount=sourceAmount. Показывать оплаченную валютную сумму и реальные рубли отдельно.
- `paymentsTotal` во всех представлениях; `payments[]` (первые100последних записей, включая voided) только в карточке GET/:id. GET списка счетов содержит агрегаты, без истории/подтверждений; полный список платежей — пагинация отдельного GET, limit≤200. Итоги списка считаются пакетным агрегатом Mongo4.4, не загрузкой всех фактов в Node.
- При нетронутой legacy-записи агрегаты строятся из имеющегося snapshot либо paid/paidAt, с `paymentSource: legacy`, без записи/выдумывания даты. Несогласованность старых сумм возвращается warnings, не чинится чтением.

Существующий status не расширять: draft/issued/paid/cancelled сохраняются. Частичная оплата остаётся issued + paymentState=partial; полная — paid. `paid=true` в общих заявках ставится только после полного погашения; status=received не откатывается в ordered. `paidAt` — дата последнего фактического active-платежа, завершившего полное погашение; при partial/unpaid зеркало снимается, сами факты остаются. `paymentSnapshot` новых событий не заменяет ledger; legacy snapshot сохраняется как история, но не денежный источник при наличии маркера.

## 4. API

`POST /api/supply/invoices/:id/payments` →200 полная свежая карточка счёта с агрегатами и платежами.
Обязательное тело: `{clientUid, date, amount}`; дополнительно `{payerCompanyId?, sourceAmount?, exchangeRate?, exchangeRateDate?, exchangeRateSource?, fileIds?, note?, version?}`.
- clientUid1…100символов, обязателен для UI/импорта.
- date строго YYYY-MM-DD, существующий день, <=сегодня в Europe/Moscow; дата регистрации — серверная, отдельно. Для совместимости Date-зеркало новой бизнес-даты сохраняется нормализованным UTC00:00, чтобы существующий iso() не сдвигал день; createdAt — реальный timestamp.
- version — ожидаемая версия; UI передаёт всегда. Отсутствие допускается внешним старым клиентам, но сервер всё равно делает CAS по прочитанной версии.
- Повтор ключа с тем же каноническим финансовым телом возвращает текущую карточку без второй записи; проверка повтора идёт ДО проверки устаревшей version/остатка. Другой payload с тем же ключом —409.
- Сумма свыше непогашенного обязательства —409. Для валюты ограничение по sourceAmount, фактические рубли с допустимым расхождением курса не являются переплатой. RUB-остаток ровно в копейках.
- Состояния draft/cancelled запрещены; issued разрешён, в том числе если товар уже принят. При полном погашении новый незнакомый ключ не создаёт платёж,409.

`GET /api/supply/invoices/:id/payments?page=&limit=` → `{items,total,page,limit}`, стандартная пагинация/пределы проекта; записи включают state. Финансовые права/stock scope как у карточки. Частичному stock scope не отдавать полные суммы скрытых строк: отфильтровать allocations и суммы по видимым строкам, вернуть partial:true; whole-суммы и действия записи доступны только assertWhole.

`POST /api/supply/invoices/:id/payments/:paymentId/void` → тот же dry-run контракт `{dryRun,canProceed,warnings,blockers,relatedAction}` без confirm или при ?dryRun=1. Выполнение: `{confirm:true, reason, clientUid, version?}`, reason>=3, только admin/владелец как у существующего unpay.
Сторно здесь означает отмену ошибочно зарегистрированного факта: он исключается из своего периода, но остаётся в истории. Это **не возврат денег от поставщика** и не автоматическая отрицательная операция сегодня. Реальный возврат поставщика — отдельная будущая возможность. Повтор успешного void с тем же ключом безопасен; чужой invoiceId/paymentId —404; конфликт version —409.

Существующий `/pay` без тела/с {} сохраняется: оплатить весь непогашенный остаток RUB сегодня от нашей компании счёта. При уже paid — вернуть карточку200 без второй оплаты (безопасный повтор потерянного ответа). В новый ledger вести через тот же сервис; не иметь две реализации оплаты. Валюту без подтверждённого рублёвого остатка не угадывать. Непустое неизвестное тело не игнорировать:400. Новые клиенты всегда используют /payments.

Существующий `/unpay`: прежние admin/dry-run/confirm/reason и блок приёмки. Для ledger сторнирует все active-платежи счёта одной транзакцией, сохраняет историю, ставит issued, снимает paid-зеркала. Повтор уже выполненного unpay возвращает план «снимать нечего»/текущее состояние, не новую корректировку. Новая карточка преимущественно предлагает сторно конкретной ошибочной оплаты.

Права добавления платежа — admin/director/accountant/manager плюс действующие money/stock/whole проверки; просмотра — как у финансовой карточки. Обязательно включить новые денежные поля, allocations и валютные суммы в серверное маскирование, а не только session.canMoney.

Ошибки:400 — типы/точность/даты/поле вне whitelist;403 — права;404 — нет объекта/он чужому счёту принадлежит;409 — версия, повтор ключа с другим телом, переплата, финансовая блокировка, непригодная legacy-история, неизвестный пересчёт legacy pay. Возвращать понятный message и machine code; никакого частичного сохранения при ошибке.

## 5. Заморозка, конкуренция и первая приёмка

После ПЕРВОГО active-платежа ledger финансовая база строк фиксируется: qty, рублёвые/исходные цены и суммы, валюта/единица, налог, документный пересчёт, поставщик, состав строк и привязка нашей компании не меняются обычным PATCH. Добавление/удаление/объединение строк запрещено. Это сознательное ограничение нового сценария, предотвращающее смену знаменателя распределения после аванса. Интерфейс объясняет: сначала административное сторно ошибочного факта, затем исправление; действительную оплату не сторнировать ради удобства.

Номер/дата документа, файлы/договор/примечания разрешаются в прежних пределах; записанные снимки платежей не переписываются при такой правке. Новый факт оплаты разрешён и после приёмки: товары и деньги независимы. Сторно оплаты после первой приёмки сохраняет старый запрет:409 с порядком отката приёмки. Финансовая правка после приёмки обычному менеджеру запрещена; существующий admin override не удалять. Если администратор осознанно меняет принятую/оплаченную строку, только существующим явным механизмом с причиной и before/after; это изменение обязательства, не переписывание фактов ledger. В первой поставке C158 новые валютные/налоговые поля через нерасширенный admin override не пропускать: отдельное точное расширение или409, без обхода защиты.

После сторно всех платежей финансовая база может быть исправлена только если приёмки не было; paymentAccountingVersion остаётся1. Старые нетронутые legacy paid-счета продолжают прежнее поведение правки до приёмки. При их первой новой финансовой операции требуется явная сверка несогласованного snapshot; не применять новую блокировку ретроактивно простым открытием карточки.

Добавление платежа/сторно/изменение строки/приёмка должны конкурировать за один invoice.version/receiptBoundary. Транзакция повторно проверяет версию и финансовые ворота, создаёт платёж, фиксирует allocations, меняет агрегаты/зеркала/аудит атомарно. Проверять matchedCount, не возвращать успешную оплату после0обновлений. Lost-response и параллельные одинаковые ключи: один факт, остальные получают тот же итог; разные платежи, в сумме превышающие остаток: проходит только допустимый.

## 6. Распределение и календарь без двойного учёта

Для active-платежа распределить sourceAmount пропорционально зафиксированным gross-итогам строк; amountRub — по той же базе. Считать в целых минимальных единицах; сначала целые доли вниз, оставшиеся единицы — по наибольшей дробной части, при равенстве по стабильному requestId. Сумма allocations всегда равна платежу; нулевые доли можно не выдавать операциями. Один и тот же алгоритм и сортировка во всех сервисах; финансовый UI не считает независимую истину.

Выбор источника делается ДО фильтра даты и компании:
1. Найти все релевантные invoiceId с paymentAccountingVersion=1, независимо от диапазона запроса и наличия active-платежей в нём.
2. Исключить для этих invoiceId ВСЕ legacy snapshot и paid-заявки из фактов и legacy pending. Во всех периодах маркер имеет приоритет.
3. Подставить active-ledger allocations только с фактической date в выбранном диапазоне и payerCompanyId выбранной компании.
4. Для нетронутых legacy-счетов сохранить прежний источник и итоги; existing snapshot-приоритет также применять глобально по invoiceId, чтобы он не возвращал paid-заявку в другом месяце.
5. Валютный счёт unresolved не является0руб расходом/нулевым долгом. Pending: RUB — реальный непогашенный balanceDue, валюта — известная оценка остатка с пометкой; без оценки — список «Нужен пересчёт», без влияния на остаток. Не выводить в pending полную неоплаченную заявку после уже внесённого аванса.

ID денежной операции — paymentId:requestId, не только requestId. Статья/заказ/направление — снимок allocation. Новая запись expenses поверх платежа запрещена. Реальные факты позднего ввода отображаются в прошлом месяце и пересчитывают остатки от старта учёта по существующему правилу; createdAt на период факта не влияет.

## 7. Переход legacy без массовой записи

Чтение не мигрирует. Перед первым новым действием одной транзакцией:
- Если legacy не оплачен, маркер1 и0старых фактов.
- Если есть корректный paymentSnapshot с положительным итогом, датой и точной суммой строк, создать1active-платёж с clientUid `legacy:<invoiceId>`, исходным paidAt/автором/allocations, затем маркер1. Не округлять и не менять его исторический день.
- Без snapshot допустим единственный целостный paid/paidAt набора строк: все строки оплачены, дата одна, сумма согласована. Сохранить существующую фактическую дату. Если paidAt отсутствует, разные даты/флаги, сумма0, удалённые позиции или сумма snapshot расходится с текущим обязательством —409 `LEGACY_RECONCILIATION_REQUIRED` с read-only планом; не заменять дату датой счёта/сегодняшним днём.
- Инициализация и запрошенная новая операция атомарны: ошибка нового действия откатывает обе. Старые данные не удаляются, legacy snapshot остаётся историей.
- №4816 уже оплачен, повтор не импортировать. Если потребуется когда-либо уточнить его дату/историю — отдельная сверка, не повторное создание.

Массовый перенос — отдельный план без записи и отдельное разрешение на --apply. Проверка повторного плана0новых переносов; выгрузка before/after/rollback-ID обязательна. ## Допущения и границы

- Возвраты денег, банковская сверка, валютная переоценка и отдельный учёт нескольких банковских счетов не входят в C158. Не маскировать их как сторно ошибки.
- Переплата не принимается без отдельного бизнес-решения; исходный факт переплаты не уничтожать — сохранить во входящих/списке сверки и получить решение об авансе/возврате.
- Последующее изменение обязательства по реально оплаченному документу требует явной корректировки; C158 не предлагает сторнировать достоверную оплату ради редактирования. В первой поставке обычный менеджер такую корректировку не выполняет.
- Вопросов владельцу до реализации нет: все опасные неоднозначности закрыты явным запретом автоматической догадки и маршрутом сверки. Если архитектор меняет физическую модель хранения, публичные поля/инварианты этого контракта сохраняются либо документируется новая согласованная редакция до кода.

## Legacy с несогласованными суммами — уточнение приёмки

Если старый RUB-счёт помечен paid, а сохранённая сумма/целостный snapshot расходятся с текущими строками, чтение возвращает `reconciliationRequired:true`, `reconciliationReason`, `paymentState:'reconciliation'` («Требует сверки»), `sourceBalance:null`, `balanceDue:null`. Не считать полный sourceAmount погашенным только по status=paid и не выдавать разницу старых источников за подтверждённый долг. sourceAmount/accountingAmountRub показывают текущие видимые строки, amount — сохранённый документ; расхождение объяснено предупреждением без скрытых чисел. Без snapshot при конфликте paidAmount/sourcePaidAmount=null; с целостным snapshot известная оплаченная сумма сохраняется, частичному складу только по его allocations. Чтение не исправляет базу и не переписывает существующую legacy-историю финансов. Неоднозначный переход в ledger остаётся409 LEGACY_RECONCILIATION_REQUIRED до отдельной сверки первички.

Обязательный пример с копии: №21427, документ36824,24₽, текущие строки153980₽, snapshot отсутствует. Нельзя одновременно показывать «Оплачен», sourceBalance0 и долг117155,76₽ как достоверные новые факты.
