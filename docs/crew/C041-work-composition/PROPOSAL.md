# C041-A — Предложение: части изделия × виды работ → план, Гант, часы

Принцип: не строим заново, а достраиваем то, что есть (маршрут, задание, Гант, табель). Минимум новых коллекций, `composition` и CRM-поля не трогаем.

## 1. Модель данных

1. **Справочник «Части изделия»** — новый `dict_values` `productParts` (название, категории паспортов, порядок). Не `passportParts` (там падежи для текста паспорта и мусор); при желании связь «берём из passportParts» — позже. Новая часть, введённая в карточке, сразу попадает в справочник («новое сохраняется»).
2. **Состав по умолчанию в изделии** — новое необязательное поле `products.parts[]`: `{ _id, partId, name, qty, ops:[{ workTypeId, hours? , note }], checked, checkedAt, checkedBy }`. `ops` — виды работ по части (операция = часть × вид работ, норма часов — на единицу изделия). Существующий `products.workTypes[]` остаётся для совместимости и пересчитывается из `parts[].ops` при сохранении (запуск и Гант продолжают работать без правки).
3. **Состав в позиции заказа** — новая коллекция `orderlineplans` (по одной на `incomes._id`, индекс уникальный): `{ incomeId, productId, origin:'product'|'order', parts:[{ _id, partId, name, qty, fromProductPartId?, changed:bool, checked, checkedBy, checkedAt, ops:[{ _id, workTypeId, hours, assigneeId?, start?, days?, checked, checkedBy, checkedAt, factHours? }] }] }`. Создаётся лениво при первом открытии карточки позиции копией `products.parts[]` (пока `parts` пусто — из `composition`-строк-модулей и подсказки маршрута). Правки в заказе меняют только этот документ.
4. **«Сохранить и в продукцию?»** — при сохранении изменённых частей/работ в позиции панель спрашивает: «Только в этом заказе» (по умолчанию) | «И в продукцию (изделие)». Второй вариант пишет в `products.parts[]` и ставит `checked` только у подтверждённых. Кнопка «Что изменено против продукции» показывает разницу (`changed`). Так продукция исправляется постепенно.
5. **Зелёная галочка «Проверено»** — на части и на виде работ; ставит менеджер (роль `manager`/`admin`), хранит кто и когда. Непроверенное в плане видно серым. Запуск разрешён и при непроверенном (предупреждение, не запрет — допущение).
6. **Задание `worktasks`** при запуске снимает копию из `orderlineplans` (а не из `products.workTypes`): шаг = `{workTypeId, name, partId, lineId?, hours, assigneeId?, plan{start,days}}`. Добавляются необязательные `route[].assigneeId`, `route[].hours`, `route[].partName` (сейчас Mixed-массив, схема не меняется). Исполнитель на задание остаётся как «ответственный».
7. **Часы факт (Э3)** — новая `workhours` `{ taskId, stepIndex, personId, date, hours, source:'task' }`; сумма за месяц по человеку подставляется в `payroll_timesheets.hours` (кнопка «Взять из работ», не автоматом — табель остаётся ручным, пока пользователь не решит). Деньги: часы × `persons.rate` для почасовых; для оклада — только отчёт «стоимость изделия = Σ часы × `worktypes.hourlyRate`» (себестоимость, не выплата).

Время изделия = Σ часов частей; срок в Ганте = сумма цепочки (как сейчас `work-plan.ts`), части разных видов работ у разных исполнителей могут идти параллельно (Э2: поле «параллельно с предыдущим»).

## 2. Экран: правая панель «Позиция заказа»

Открывается из строки позиции в карточке заказа (`order-lines.js` / `order-work.js`). **Выбор формы — воронка П-1 (kit `funnel`) + таблица `table/row` итога**, обоснование: данные иерархичны (часть → вид работ → исполнитель → даты), каждый шаг сужает следующий (исполнители — с нужным видом работ, `work.service.ts:264`), ответ запоминается в источнике; пользователь сам просил «воронкой».
- Шапка `entityPanel`: фото, название позиции, изделие, кол-во, «Состав: из продукции / изменён» + главная кнопка «Запустить в работу».
- Секция «Части изделия» (`section`, список строк): строка = часть, кол-во, ✔ проверено, ⏱ часов, ✎ Внутри — виды работ части (строки с ✔, часы, исполнитель, даты).
- «+ Часть» → воронка: 1) часть из справочника (поиск, «Часто в этой группе», внизу «Создать новую» → в справочник) → 2) виды работ (мульти-выбор плитками, из маршрута группы) → 3) исполнитель (только с этим видом работ, `people?workTypeId`) → 4) даты (по умолчанию — цепочка от запуска). «Дальше: …» подсказывает пустое; пройденный шаг — строка «Часть: Стойки ✎».
- Нижняя панель итогов: часы всего, срок, ✔ n из m. Кнопка «Сохранить» → вопрос п. 1.4.
- Существующий блок «Маршрут изготовления» в карточке изделия остаётся для правки состава «по умолчанию»; вид — тот же компонент.

## 3. Связь с Гантом и часами

Гант (`ui/gantt.js`, `L.gantt`) уже рисует шаги и двигает их. Добавить: подпись полосы «Часть · вид работ», фильтр/группировка по исполнителю шага (сейчас по заданию), перетаскивание пишет в `route[i].plan` (как сейчас). Часы факт вводит исполнитель/мастер в карточке задания.

## 4. Этапы

- **Э1 (без Ганта и денег):** справочник частей; `products.parts[]`; `orderlineplans`; панель позиции с воронкой; галочки; вопрос «в продукцию?»; запуск берёт план позиции. Тесты: сервис плана, копирование/разница, права проверки. Класс XL (общая `products`), только необязательные поля.
- **Э2 (Гант):** `route[].assigneeId/hours/partName`, группировка по исполнителю шага, параллельные шаги, длительность из часов (часы/8 ч).
- **Э3 (часы/деньги):** `workhours`, подстановка в табель, себестоимость изделия, отчёт в «Деньги».

## 5. Риски

1. `products` общая с CRM — только необязательные поля; перенос маршрута в `parts[]` не ломает `workTypes[]` (дублируется).
2. Две правды (продукция vs позиция): смягчено флагом `changed` и вопросом «в продукцию?»; без него состав позиции быстро устареет.
3. Справочник частей снова засорится — завести с фильтром по категории и слиянием (как `dicts.controller.ts` merge); не импортировать мусор из `passportParts`.
4. Объём ручного ввода на 483 изделия: первый заход — из подсказки `productmodules`/`composition`; мастер дозаполняет через вопрос «в продукцию?». Нужен замер покрытия на проде.
5. Деньги: ставка человека или вида работ — решение пользователя (вопрос Q4).
6. Параллельные шаги усложняют цепочку `work-plan.ts` — только в Э2.
