# C158 — что можно продолжить в отдельном чате

19.11.2026. Проверка координатора паспортов по поручению владельца. Это дополнение к TZ.md, не запуск выкладки или импорта счетов.

## Вывод

Работу по счетам можно вести параллельно C155: предметные файлы не пересекаются. Сначала аналитик фиксирует CONTRACT.md, затем сервер и интерфейс реализуют один сценарий оплаты. Добавление одних полей недостаточно.

Проверено по текущему коду:
- `SupplyInvoice` хранит одну `paidAt` и один `paymentSnapshot`; `pay()` ставит дату `new Date()` и оплачивает всю сумму. Исторические даты и несколько фактов пока не поддерживаются.
- `PatchInvoiceDto` принимает рублёвую `amount`, но не валюту или НДС документа. При строгой whitelist новые поля без DTO будут отклонены.
- Финансы читают и оплаченные заявки, и snapshot счёта. Новый источник платежей должен исключать обе старые ветки для того же факта, в том числе когда платёж вне выбранного периода. Иначе будет двойной расход или возврат старого snapshot в другой период.
- `unpay()` и изменения строк уже используют блокировку первой приёмки, версии и журнал. Новый список платежей обязан сохранять эти ограничения; проверки только кнопкой интерфейса недостаточно.

## Очередь исполнения в другом чате

1. CONTRACT.md: модель платежа, рубли/исходная валюта, дата факта отдельно от ввода, идемпотентность и конкуренция, округление/разнос строк, НДС, старый `pay` без тела, сторно и первая приёмка. Использовать готовые примеры TZ.md и C157/GAPS.md.
2. Сервер: supply DTO/schema/service/controller и финансовые выборки. Один владелец сервера для транзакций оплаты и запрета двойного учёта. Новая дата факта не исправляется через дату счёта.
3. Интерфейс: карточка/реквизиты/строки счёта и единый ввод оплаты из всех входов. Показывать оплачено/остаток из сервера, не вычислять независимую истину в браузере.
4. На отдельной тестовой базе проверить повтор и параллельную оплату, частичные платежи в разные периоды, сторно, legacy snapshot, первую приёмку, права и реальные примеры ТЗ. Затем приёмка вида и отдельное решение о выпуске.

## Границы параллельности

- C158 владеет `modules/supply/**`, `modules/finance/**` и экранами счетов/денег. C155 владеет паспортами, showcase, паспортными справочниками и product/order-passport UI. Общие `main.js`, `index.html`, atlas/help, MAP/OpenAPI/BOARD изменять согласованно или отдельным коммитом после сведения.
- Второй чат должен использовать отдельную рабочую копию по CLAUDE.md, не сбрасывать незакоммиченное C155 и не включать его в свои коммиты. Локальный стенд C155 и его базу не пересоздавать/не очищать: для C158 отдельный проект/порт и тестовая БД.
- Новые справочники паспортов по API не требуют изменения финансовой модели. Разрешение владельца на паспортные справочники не распространяется автоматически на оплаты и загрузку счетов.
- До проверенного выпуска C158 загрузка оставшихся C157 отложена. №4816 уже существует, повторно не создавать. Само наличие PROMPT.md не считается разрешением деплоя.

## Дополнение к приёмке

Обязательный случай: старый snapshot и новые платежи по одному счёту расположены в разных месяцах. При переключении месяца ни один устаревший источник не должен повторно становиться расходом. Проверить также потерянный ответ успешной оплаты и повтор с тем же ключом; итог и число фактов не изменяются.
