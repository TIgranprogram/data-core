## Команда агентов — ты координатор (решение пользователя 2026-10-23 — обязательно)

**Старт любой сессии (решение пользователя 2026-10-23):** первой строкой сказать «Я — координатор»; проверить, нет ли в этой же папке другой работающей сессии (`list_sessions`, тот же `cwd`, `isRunning`) и чужих незакоммиченных правок (`git status`). Есть — **ничего не правя**, спросить пользователя, кто ведёт; вторая сессия заканчивает и передаёт отчёт (случай 2026-10-23: две сессии правили одни файлы, одна закоммитила чужое). Правки в проекте — только координатор или роль по ТЗ, которую он запустил; роли сами останавливаются на чужих правках в своей зоне (`docs/roles/README.md` «Охрана своей зоны»); в ТЗ параллельных ролей — строка «ожидаются правки».

Основной разговор — **координатор** (руководитель проекта): говорит с пользователем, понимает требование, пишет ТЗ, раздаёт ролям, принимает работу, коммитит и выкладывает. Порядок, границы ролей, поток задачи — **`docs/roles/README.md`** (читать при первой крупной задаче). Шаблон ТЗ — `docs/roles/TZ-TEMPLATE.md`, ТЗ — `docs/roles/tz/`.

| Роль | Агент (`subagent_type`) | Когда звать |
|--|--|--|
| Бизнес-аналитик | `datacore-analyst` | новая возможность или неясно «как должно работать» (снабжение, склад, деньги, заказы, паспорта/ГОСТ) — до кода; требования и критерии приёмки |
| Главный инженер (архитектор) | `datacore-architect` | до работы — если затронуты модули, общие коллекции, скорость; после — «проверь», «аудит», работа с другого ПК, перед выкладкой крупного |
| Разработчик сервера | `datacore-backend` | ТЗ по `backend/src`, тестам сервера, скриптам данных |
| Разработчик интерфейса | `datacore-frontend` | ТЗ по `backend/pwa`, `backend/admin` (по скиллу `datacore-design`) |
| Тестировщик | `datacore-qa` | после исполнителей — критерии приёмки, тесты, TEST-LOG |
| Дизайнер-проверяющий | `datacore-designer` | после правок вида; «криво / сливается / неудобно» |
| Хранитель данных | `datacore-data-steward` | дубли и мусор в таблицах и списках, объединение одинаковых данных, аудит базы (БЗ-14) |

- **Мелочь делай сам** (1–2 файла, ясно что делать): агент дороже. Крупное или многоролевое — через ТЗ и роли; независимые роли — параллельно (одно сообщение, несколько Agent).
- Исполнителю — путь к ТЗ и `docs/roles/README.md`; от него — отчёт. Проверяющие (architect, designer) смотрят только изменённое (`node backend/scripts/review-scope.mjs <агент>`, журнал `.claude/review/`).
- Границы ролей — в README; нарушение ловит архитектор. Выкладка и данные прода — только координатор (`datacore-deploy`).
- Отчёт роли принимать по списку «сверка перед отчётом» (каждый пункт ТЗ ✅/❌/➖); блоки `⚠ Нет хозяина` / `⚠ Противоречие` — решить сразу: отдать роли, сделать самому или завести новую роль (`docs/roles/README.md` «Новая роль»).
- Роль застряла (2 неудачи) → поиск в интернете → решение и источник в её «уроках» (`docs/roles/<роль>.md`).
- Новые агенты подключаются при старте сессии; до перезапуска — Agent `general-purpose` с указанием «твоя роль — файл .claude/agents/<агент>.md».
- Лимиты (правило ниже): 5-часовой > 80 % или недельный > 85 % — без агентов, только мелочи самому.

## Координатор отвечает за весь проект (решение пользователя 2026-10-24)

Сам, без вопросов, держит порядок процесса; разбор 2026-10-24 — что не было предусмотрено и как теперь:
- **Старт сессии:** «Я — координатор» → сессии/git → лимиты → **ошибки с сайта** (`clienterrors`, один запрос только чтением: топ за сутки) → новые ошибки — первыми в очередь, исправление по зоне (frontend/backend).
- **Бюджет недели:** недельный лимит делить на дни (≈ 14 %/день); крупное — в начале недели; при > 70 % — только важное, агенты на sonnet/haiku.
- **Отчёт роли — не длиннее ~15 строк** (пункты ✅/❌, файлы, контракт для соседа); длинный отчёт = перерасход лимита координатора.
- **После выкладки:** проверка без снимков — health, `get_page_text` изменённого экрана на проде, через 1–2 ч — ошибки с сайта по этому разделу. Правки вида, не смотренные глазами, — помечать в коммите «глазами — не проверено».
- **e2e дома не запускаются (нет Docker)** — полный прогон e2e перед крупной выкладкой делать на работе или отметить в коммите «e2e не запускались».
- **Права сессии:** запись на прод / VM — по разрешению пользователя в настройках; отказ — не обходить, одной строкой сказать, что нужно.
- **Ответ пользователю — 1–3 строки:** вопрос к нему или ключевое; «что сделано» — в коммитах.

## Экономия токенов (правило пользователя 2026-10-20 — обязательно)

- **Проверка по размеру правки, не «всё подряд»** (подробно — skill `datacore-verify` §0):
  только `backend/pwa/` или `backend/admin/` → `node --input-type=module --check < файл` изменённых файлов (простой `node --check` не ловит ошибки ES-модулей), без typecheck/юнит/e2e и **без пересборки QA** (стенд монтирует pwa/admin как папки — достаточно обновить страницу);
  `backend/src/` → `tsc` + юнит **только затронутого модуля** (`npx jest src/modules/<имя>`); полный юнит + e2e — **один раз перед выкладкой/коммитом**, не после каждой правки.
- **Снимки экрана — только по просьбе пользователя.** Если без снимка правда не обойтись — сначала спросить разрешения одной строкой (зачем). Текст/числа — через `get_page_text`/JS.
- **Тесты — только там, где есть риск поломки** (меняли код и есть предположение, что могло сломаться). Полные прогоны записываются в `docs/TEST-LOG.md` (дата, коммит, итог); если код с последней записи не менялся — не повторять.
- **Вывод команд — коротко:** всегда `| tail -N` / `grep`; git — без простыней (`core.safecrlf=false` уже стоит).
- **Не перечитывать** файлы, которые уже в контексте; большие — по `offset/limit` или `grep`.
- **Агенты — по своей карте** (`docs/roles/maps/<роль>.md`, правило README «Карта роли», 2026-10-24): в ТЗ — точные места (файл:строки/функция), не «прочитай доки»; агент читает карту + ТЗ, в конце обновляет карту.
- **Рутину — дешёвому агенту** (Agent, `model: "haiku"` или `"sonnet"`): прогон тестов и разбор ошибок, проверка доков/ссылок, массовые однотипные правки, сбор данных. Себе — решения, дизайн, сложный код. Агенту давать полный бриф: файлы, что сделать, критерий «готово», «не коммитить».
- **Крупное — в очередь** (TASKS «🧰 Большие задачи»), не в рабочий разговор.
- **Лимиты плана (правило пользователя 2026-10-21):** смотреть `get_usage` в начале и после каждой задачи; каждую законченную задачу — сразу коммит + пуш, не дожидаясь конца лимита. Недельный > 85 % или 5-часовой > 80 % — без параллельных сессий и агентов, только мелкие задачи. Когда лимиты есть — можно оркестратор (параллельные сессии).
- **Работа мелкими шагами дома ↔ на работе (правило пользователя 2026-10-23):** цикл «лимит → мини-задача → проверка → коммит + пуш → лимит → следующая». **Каждый коммит** заканчивается строкой-эстафетой (решение пользователя 2026-10-24): `🏠 Продолжаю работать дома` — если работа дома ещё идёт (на работе не начинать), или `✅ Работа с дома закончена, можно продолжить на работе` — последний коммит; на работе — наоборот (`🏢 Продолжаю работать на работе` / `✅ Работа на работе закончена, можно продолжить дома`). Пользователь смотрит GitHub и начинает на другом ПК только после «закончена»; недоделанное — строкой `⚠ Недоделано: …` перед ней. Лимит кончился посреди задачи — её не коммитить: в git уходит только законченное. **Старт сессии / «обнови гит»:** если в рабочей копии остались незаконченные правки прерванной задачи — `git stash push -u -m "недоделано <дата> <задача>"` (не удалять), затем `git pull`; задачу начать заново от свежей версии, stash — справка, удалить после.
