# C168 — правила объединения складских дублей

Статус: бизнес-правила подготовлены; полнота ссылок и безопасность всех писателей — обязательная проверка архитектора до реализации. Код, API и живые данные не изменялись. Источник фактов P120 — GET-аудит, переданный координатором; аналитик повторно на прод не входил.

## 1. Результат и границы

Менеджер с правом изменения обеих позиций подтверждает, что это один физический товар, выбирает основную карточку и получает одну доступную для новых операций номенклатуру. Это объединение идентичности товара, а не инвентаризация, повторная приёмка, отмена закупки или исправление денег.

Для исходного примера: №188 `6ad52bf6863df73f344ea82b` — 45 шт., без фото; №256 `6ad9c48373a959084d2007ae` — 0 шт., фото `6ad9c6dd73a959084d2007b7`. Один товар подтверждён владельцем. Безопасное предложение: оставить №188 основной, присоединить фото №256. Выбор основной остаётся явным. Результат — 45 шт., обе полученные заявки по 50 шт. и их разные счета сохранены. Корректировка №256 от 20.11: `delta=-50`, `qtyBefore=50`, `qtyAfter=0` остаётся в истории. Ни 95, ни 100 шт. из истории закупок не восстанавливать.

Сверка решений: PRODUCT §2 — единая номенклатура, последняя закупка отдельно от прайса, отмена движения обратной записью; QUESTIONS «Решено», СК-1…9 — возврат под ту же позицию заказа, висящую бронь снимает человек, состав меняется только с подтверждением; ЕН-1/2, СКЕ-1/2, Н-1 — сохраняются снимки заявок и история цен. Противоречий с этими решениями нет. Объединение не отменяет эти правила.

### Паспорт: отдельные идентификаторы и снимки

- `materials.passportSpec.materialId` ведёт к `dict_values` вида `passportMaterials` — подтверждено `common/catalog/passport-link.ts:7–13`. Это свойство карточки, а не ссылка на складской materials-дубль. Значения двух карточек сравниваются как конфликт; не заменяются на ID основной.
- `products.materialsSpec`, `productpassports.materialsSpec`, `passporttemplates.materialsSpec`: `rows[].materialId`, `coatingIds[]`, `coatingTexts[].materialId` также относятся к `dict_values.passportMaterials`; `partIds` — `passportParts` (`common/catalog/materials-table.ts:10–16,102–116`, `passport-template.schema.ts:30–32`). `productpassports.materialIds[]` — тоже справочник (`product-passport.schema.ts:226–231`). Их не переносить как ссылки materials.
- Внутри таблицы есть `rows[].sourceRefs[]`, включая `refId` и `path[].refId`, строковые ID источников состава с именами/кодами (`common/catalog/material-source-refs.ts:4–10`). `kind=part/purchased/fastener/raw/material` потенциально описывает складской materials, а product/module — другие сущности. Парсер прямо определяет это как метаданные описания, не новую производственную связь. Сохранить исходные ID/name/code/path/lineId как происхождение; поиск текущего источника должен разрешать историю объединения. Нельзя механически менять все refId без kind и контекста. Повторную генерацию живой таблицы/черновика проверяет архитектор отдельно от миграции ссылок.
- `productpassports.bom[]` содержит pos/code/name/qty/unit/note/size/mass/photoId без ссылки на складской материал (`product-passport.schema.ts:35–52,210–211`); `compositionSheet` — снимок дерева с word/label/qty/unit (`:247–250`); `textSnapshot` и `printSnapshot` — снимки печати (`:73,260–261`). При merge эти снимки и готовый printFile не менять. Issued/annulled и legacy без статуса остаются замороженными; draft не переписывать побочно самим merge. Отдельное штатное обновление черновика допускается только по правилам паспорта.

**Оставшееся ограничение карты:** ссылки в объявленных схемах и предметных источниках перечислены; полнота всех runtime-обращений, неописанных полей продуктов, legacy CRM и внешних клиентов не доказана. Архитектор закрывает эти неизвестные точечным поиском читателей/писателей и инвентаризацией копии БД, включая скрытые/удалённые документы. Нельзя объявлять ссылку отсутствующей только по schema. До утверждения реестра обработки всех найденных ссылок merge недоступен.

## 3. Остатки и бронь

1. Истина для объединения — согласованный текущий остаток каждой складской строки на момент подтверждения. Для размещения `L`: `Qпосле(L)=Qосновной(L)+Qдубля(L)`. Остаток другого склада/зоны в это число не включать. Merge не создаёт приход, расход, пересчёт и не меняет физическое местоположение.
2. Сохранить каждую действующую бронь и суммарный резерв по тому же размещению. Перед выполнением доказать согласованность `reservedQty` с действующими бронями по существующему правилу; нельзя суммировать qty всех статусов: у fulfilled поле qty имеет другое значение. Выданную часть не резервировать заново. Висящие брони сохранять и подсвечивать.
3. Если количество/резерв отрицательны, нечисловые, резерв превышает остаток или счётчик резерва расходится с действующими бронями — блокировать, показать размещение и расхождение. Merge не лечит недостачу и не скрывает её остатком другого размещения.
4. Порог `minQuantity` не физический запас: при совпадении размещения предложить максимум двух порогов с явным выбором менеджера; при разных размещениях сохранить каждый. Иные конфликтующие свойства размещения показать отдельно, не терять молча.
5. `materials.stockQty` не прибавлять к storageitems как ещё один запас. Его роль/согласование проверяет архитектор. Список stock сейчас агрегирует размещения только default-склада (`stock-search.service.ts:128–178`), `loadStorage` выбирает первую зону (`stock-core.service.ts:75–78`): этот список недостаточен для preview всех остатков и безопасных дальнейших операций.

**Обязательный gate нескольких размещений:** preview запрашивает все warehouses/zoneName обеих позиций, включая недефолтные и архивные связи; stockzones рассматривает отдельно как доступ. При наличии запаса/брони в недефолтном складе или нескольких зонах merge блокирован, пока не доказаны корректные выдача, отмена, возврат, пересчёт и снятие брони для каждого размещения после объединения. Сумма в одном видимом списке не заменяет эту проверку. Неподдержанные размещения нельзя переносить на default-склад и нельзя скрывать.

## 4. Карточка, история и дальнейшие действия

- Разные названия, пустое поле против заполненного, разные фото сами по себе не блокируют. Менеджер выбирает финальные имя, полное имя, «в счёте», артикул и категорию; все прежние значения остаются в аудите и поиске. Неподтверждённое назначение «по нерж.» не распространять автоматически как доказанную характеристику.
- Все пригодные photoIds объединить без повторов; главное фото явно выбрать, оно обязано принадлежать итоговому набору. Фото №256 сохранить и при выборе основной №188. Объекты файлов не удалять. Лимит коллекции/галереи, конфликт идентификаторов поставщика/PDM/синхронизации — блок до разрешения, без усечения.
- Разные подтверждённые размеры/марка/зернистость/покрытие/назначение/единицы, materialKind или принадлежность разным организациям означают отказ. Конверсию единиц, объединение разных BOM/маршрутов деталей, устранение циклов и объединение профиля с форматом в этот механизм не включать. Совместимость двух деталей с собственными составами/workTypes отдельно доказать; безопасный первый выпуск их блокирует.
- После успеха дубль доступен как закрытая карточка происхождения и не принимает новые записи/правки/восстановление как обычное удаление. Все писатели должны соблюдать это, включая CRM и синхронизацию; иначе отказ в доступности merge. Сохранять sheetKey/sheetSource/syncHash и прочие внешние идентификаторы в карте происхождения, не подменять одним другим.
- Отмена прежнего движения/пакета и возврат под заказ должны разрешать актуальную номенклатуру и прежнее размещение; сохраняются штатные проверки остатка и брони. Сам merge нельзя отменить кнопкой «Отменить движение» или bulk/restore. Автоматическое разъединение не обещать: после новых операций нужен отдельный разбор.
- Печатный текст выданных паспортов, счетов и иных сохранённых документов не пересобирать из нового имени. Исторические цены, before/after и снимки остаются фактами исходной карточки. Живые шаблоны/составы разрешают основную карточку; их новая печать не должна менять уже выданный документ.

## 5. Preview, отказы и проверяемая приёмка

Preview показывает две карточки, выбранную основную, разрешение каждого конфликта, результат по каждому размещению (лежит/бронь/свободно), сохраняемые фото, количество связей по типу и список блокеров. Цены видны только существующим денежным ролям. Нет права на одну из карточек/связей или на результирующую категорию — безопасный отказ без раскрытия чужих деталей.

Если идентичность не подтверждена, совпал один ID, одна карточка удалена/уже объединена, не доказана полнота ссылок, есть неразрешённый конфликт, повреждены остатки/брони, не обеспечен контроль писателей или изменились карточки/остатки/брони/зависимые документы после preview — подтверждение не выполняется. Менеджер получает причину и новый preview. Повтор успешно выполненного подтверждения возвращает прежний результат; другой новый выбор не применяется как повтор.

| Если | То — критерий приёмки |
|---|---|
| Копия P120: 45 + 0, две заявки по 50 и разные счета, корректировка -50 | Доступна одна карточка с 45, фото сохранено; две заявки/два счёта и корректировка неизменны; движение merge не имитирует приёмку. |
| В одном размещении 7+8, бронь 2+3 | После merge 15, бронь 5, свободно 10; две исходные брони и частичные выдачи прослеживаются. |
| Те же числа находятся в разных складах/зонах | Остаются раздельные размещения; ни одна бронь не переносится на другое место. |
| Обе позиции встречаются в одном составе с разными строками/размерами | Меняются ссылки, ID строк и нормы сохраняются; строки не удаляются и потребность на изделие сохраняется. |
| Возврат/отмена выдачи выполнены после merge | Возврат остаётся у того же заказа; отмена использует исходную бронь и размещение, не создаёт закрытый дубль заново. |
| Открыт старый URL/сделан поиск по прежнему артикулу | Основная карточка найдена с отметкой происхождения; запись через закрытый ID не создаёт новый запас. |
| Изменилась зависимая запись, пришла конкурентная операция или произошёл сбой в середине | Либо одна полная операция, либо никаких изменений; конкурентная запись учтена ровно один раз, повтор merge не удваивает результат. |
| Открыт старый выданный документ/паспорт | Содержимое снимка и финансовые суммы совпадают с состоянием до merge. |

## 6. Передача архитектору и координатору

Требуют доказательства до кода: закрыть оставшуюся неполноту карты (§2), проверить реализацию разрешения паспортных sourceRefs и выбора последней цены по подтверждённой семантике, индексы storageitems/артикулов/PDM, все читатели размещений, транзакционную конкурентность с прямой записью CRM/синхронизацией, работу отмен/повторной приёмки по прежним ID. Простого updateMany или одного флага на Material недостаточно для заявленной бизнес-гарантии. Необработанная связь — блок, а не предупреждение после записи.

**Обязательный gate прямого CRM-писателя:** на период подтверждения исключить обход протокола всеми писателями общей базы, включая CRM, импорты и синхронизацию. После успеха те же писатели не должны записывать под закрытым materialId и воссоздавать дубль. Пока это не доказано, merge отключён даже при локально корректной транзакции data-core. Допустимая техническая мера (согласованный протокол/блокировка конкретных операций/иной способ) — решение архитектора; одной блокировки HTTP data-core недостаточно. Требование не означает разрешения менять или останавливать живую CRM в ходе этого анализа.

Вопросов владельцу сейчас нет: безопасные допущения приведены выше. Живое объединение выполняется отдельным поручением после конкретного preview; C166/C164 не затронуты.

Якорь для карты аналитика: `C168 → ANALYSIS.md §§2–5: карта ссылок, контроль полноты, суммы по размещениям, сохранение всех закупок/броней/снимков; коммит: не закоммичен`. Изменение карты передано координатору, поскольку владение этого этапа ограничено данным ANALYSIS.md.
