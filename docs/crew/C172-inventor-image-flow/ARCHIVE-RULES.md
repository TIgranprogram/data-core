# C172 — закрытие заказа и неизменяемый архив

Основание: уточнение владельца 21.11.2026, переданное координатором: выпущенный паспорт разрешено обновлять новой редакцией, пока заказ не полностью закрыт и оплачен. Это уточняет прежнее ВП-4 («выданные не пересобирать»); Д-2 («архив только просмотр и печать») сохраняется. Код и данные не менялись; проверка только исходников, без проверки живых данных.

## Уже есть
- `salesorders` — договор заказчика, позиции и оплаты — `incomes.orderId`. «Заказ производства» — вычисляемая группа договоров с общим `productionNo`, а не отдельная коллекция (`production-orders.ts:1–28`). Группа показывает самый отстающий этап живых договоров, поэтому закрытие одного договора не закрывает остальные.
- Этап `closed` и фильтр закрытых есть (`sales-order.schema.ts:48`, `salesorders.service.ts:95–100`). Возврат на предыдущий этап для обычного пользователя запрещён: администратор указывает причину ≥3 символов (`salesorders.service.ts:466–477`). Это правило пропускает машинные ключи и вызовы без actor.
- Оплата строки считается по `incomeDerived`/`incomePayments` (`income.schema.ts:117–150`): массив платежей первичен; `paidAmount` — сумма; `paidDate` — дата достижения полной оплаты. Старый вход без массива, но с `paidDate`, означает полную оплату. Частичная оплата не равна полной. Агрегаты шапки учитывают `paidAmount`, если `paidDate` отсутствует (`salesorders.service.ts:66–78`).
- У паспорта есть `salesOrderId`, `incomeId`, `images`, `printSnapshot`, `revision`/`revisions`; отдельное хранилище истории паспортов для C172 не нужно (`product-passport.schema.ts:65–87,194–198`).

## Пробелы
- `closed` сейчас не означает «оплачено»: `update` проверяет допустимость движения этапа, но не полноту оплаты/отгрузки. Групповое `setStage` переводит все отстающие договоры даже сразу в `closed`, без проверки денег (`production-orders.service.ts:399–411`).
- В исследованных схемах/переходах нет отдельной фиксации архива (дата, автор, причина, версия состава). Нет общего запрета любых изменений закрытого договора: `incomes.assertCanChange` ограничивает лишь часть полей для менеджера и пропускает admin/keyScope/внутренний вызов (`incomes.service.ts:340–355,426–443`). Следовательно, наличие `closed` и готовых снимков ещё не доказывает неизменяемость полного заказа. Другие модули на архивные защиты не обследовались.

## Ближайшая граница C172: защита импорта
1. Перед обновлением каждого паспорта получить договор по `salesOrderId` и проверить согласованность с `incomeId → orderId`. Если связанный живой договор `closed`, паспорт пропускать с явной причиной `order_closed`; это консервативная временная защита, включая закрытый договор с неоплаченными строками. Не представлять этот gate как реализованный полный архив.
2. Для живого договора другого этапа выпущенный паспорт обновляется редакцией с прежним номером и сохранением старой печати. `annulled`, удалённый паспорт и прикреплённый готовый PDF остаются под уже заданными ограничениями C172. Удалённый/не найденный/противоречиво связанный договор — безопасный пропуск с отдельной причиной; паспорт без обеих связей можно обновлять как «Без заказа», явно сообщив это.
3. Проверку выполнять внутри commit и защищать от гонки с закрытием; один предварительный contextToken этого не гарантирует. Продукцию и её актуальные картинки можно обновить: они нужны будущим заказам, архивные экземпляры продолжают печататься из собственных сохранённых источников. Поле заказа и паспорт не переносить в другую коллекцию.

## Полный архив — отдельная задача
- Вариант по умолчанию: единица фиксации — договор; заказ производства попадает в архив целиком, когда каждый его действующий договор зафиксирован. Отменённые договоры хранят историю, но не подтверждают исполнение; группа только из отменённых — «Отменена».
- Пользователь завершает обязательства (изготовление, поставка, монтаж и документы, если предусмотрены договором). Сервер разрешает «Закрыть и архивировать» только при подтверждённом завершении и полной оплате каждой действующей строки, включая услуги. Пустой договор, неизвестная/нулевая стоимость или неоднозначная валюта требуют отдельного подтверждённого основания; равенство нулей оплату не доказывает. Сравнивать деньги по существующему денежному округлению; не компенсировать недоплату строки переплатой другой.
- Архивировать одной согласованной операцией: зафиксировать дату/автора/основание и версию комплекта в существующих сущностях, заморозить состав/суммы/платежи/источники печати/ссылки на документы; сохранить используемые файлы. Нужные поля и механизм согласования проектирует архитектор. Новая таблица сама по себе не защищает от изменения и создаёт риск двух истин.
- После фиксации сервер запрещает любые обычные изменения архивного комплекта: UI, API, машинный ключ, фоновые импорты, каскады из изделия/справочников, удаление файлов; администратор также не обходит защиту обычной правкой. Общую карточку изделия и справочники не замораживать, изолировать исторические экземпляры снимками. Границы комплекта для склада/отгрузок/задач должны быть перечислены в отдельном ТЗ, а не следовать из слова «всё».
- Исключение — отдельное действие администратора «Возобновить» с обязательной причиной и журналом. Прежний архивный комплект остаётся доступным неизменным, корректировки идут в новой рабочей редакции; повторное закрытие создаёт следующий архивный комплект. Обычный возврат stage назад не должен снимать архивную защиту.

## Проверяемая приёмка
- Если паспорт выпущен вчера, договор открыт, сегодня присланы другие картинки, то создаётся следующая редакция того же номера; вчерашняя печатается как вчера.
- Если договор закрыт, то C172 возвращает `skipped` с причиной, не меняет поля/редакцию/печать его паспорта; открытый договор с тем же изделием обновляется.
- Если закрытие конкурирует с импортом, то результат соответствует одному согласованному порядку операций: после фиксации архива импорт не меняет комплект.
- Если оплаты частичные, договор пустой либо есть неопределённая стоимость, то полное архивирование не происходит; сервер перечисляет препятствия.
- Если один договор группы не закрыт или не оплачен, то группа не считается полностью архивной; закрытые экземпляры других договоров остаются защищены.
- Если архивный комплект пытаются изменить администратор, ключ или каскадная операция, то получают отказ; просмотр, скачивание и печать прежних редакций работают.
- Если администратор возобновляет с причиной, то прежний комплект не меняется; история содержит автора, время, причину и связь с новой редакцией.

Открытый выбор владельца для будущей задачи: достаточно архивировать каждый договор отдельно либо требуется одновременное закрытие всей производственной группы; по умолчанию — отдельно, статус группы вычисляется по всем договорам. Данный отчёт не разрешает реализацию полного архива в C172.
