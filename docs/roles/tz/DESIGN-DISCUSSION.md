# ТЗ DESIGN-DISCUSSION — задачник проектирования: обсуждение, чек-лист, напоминания, чертежи, исполнения изделий

**Зачем (словами пользователя, 2026-10-27):** работу проектирования переносим из YouGile на сайт. У задачи — маленький задачник без нагромождения; чертежи хранятся с заказом и копируются в «Продукцию»; у изделия — код и исполнения.

**Класс:** XL (новая возможность + новое поле в `products`, общей с CRM) · **Max agents:** 5 · **Reviewers:** qa ☑ architect ☑ designer ☑ · **Max review loops:** 2 · **Проверки:** full
**Язык менеджера:** да · **Приёмка:** карточка задачи D-N, вопрос менеджеру, ответ, плашка «требует ответа» в списке.

## Что было в YouGile (`для анализа/yougile-2026-10-27/mcp-export.json`, 92 задачи)
- Сообщения — у 87 из 92, всего 238, максимум 15 на задачу → **обсуждение — главное**.
- Срок — 91/92, исполнитель — 83/92, «готово» — 63 → уже есть в `design-tasks`.
- Стикеры: приоритет («Обычный» 72, «Срочно» 5) + 4–5 стикеров-состояний → уже есть (`designstickers`).
- Чек-листы — 3 задачи (один шаблон «Лист / Труба / Дерево»), подзадачи — 8, описание — 1 (ссылка).
- Колонки — 8, основная масса в одной (58) → хватает статусов queue/work/paused/done.
- **Вывод — не хватает:** обсуждение (с файлами), чертежи/файлы, вопрос менеджеру. Чек-лист — простой, без шаблонов. Подзадачи — не делаем (заменяет чек-лист). Описание — уже есть `note`.

## Shared pack
**Решение 1. Одна сущность записей — `designnotes`** (новая, только data-core, CRM не читает). Модуль — внутри `modules/design` (новые файлы `design-note.*`), не отдельный модуль.

| Поле | Тип | Смысл |
|--|--|--|
| `taskId` | ObjectId, index | задача D-N (обязательно) |
| `orderId`, `incomeId` | ObjectId | копия из задачи — для выборки по заказу |
| `kind` | enum `comment` \| `question` \| `check` \| `remind` | вид записи |
| `text` | string ≤ 4000 | текст / пункт чек-листа |
| `authorId` | ObjectId User | автор (из токена) |
| `replyTo` | ObjectId | ответ на `question` |
| `needsAnswer` | bool | у `question`: true, пока нет ответа |
| `answeredAt`, `answeredBy` | Date, ObjectId | ставит сервер при ответе |
| `done`, `doneAt`, `doneBy` | bool, Date, ObjectId | для `check` и `remind` |
| `remindAt`, `remindTo` | Date, ObjectId User | для `remind` |
| `order` | number | порядок пунктов чек-листа |
| `fileIds` | ObjectId[] | вложения (см. решение 2) |
| `source` | `user` \| `coordinator` | вопросы аудита ЗНП |
| `deletedAt`, timestamps | | soft-delete, как везде |

Индексы: `{taskId:1, createdAt:1}`, `{needsAnswer:1, deletedAt:1}` (partial needsAnswer=true), `{remindTo:1, remindAt:1, done:1}`. Всё работает на Mongo 4.4.
Правила: ответ (`comment` с `replyTo` на `question`) снимает `needsAnswer`. Править/удалять — только автор или admin, 15 мин для комментария (дальше — только admin). Аватар — `users.avatarUrl`, нет — инициалы (на клиенте).
В задаче — счётчики для списка: `notesCount`, `openQuestions` (пересчёт сервером при записи).

**Решение 2. Файлы — новая коллекция `files`** (`modules/files`). `photos` не подходит: только картинки, sharp-превью. Чертежи — PDF, DWG, DXF, STEP, XLSX, картинки.
Поля: `name`, `mime`, `size`, `path` (`uploads/files/{uuid}.{ext}`), `sha256`, `kind` (`drawing` \| `file`), `owner` {`type`: `designTask`\|`salesOrderLine`\|`product`, `id`}, `orderId`, `incomeId`, `copiedFrom` (fileId), `locked` (bool), `uploadedBy`, soft-delete.
- Картинки дополнительно получают превью через существующий `photos` (`photoId`), остальное — значок типа.
- **С заказом:** владелец `salesOrderLine` (incomeId). После отгрузки заказа `locked=true`: удалить и заменить нельзя (409 «Заказ отгружен»), только добавить «дополнение».
- **В продукцию — одна сторона:** кнопка «В продукцию» (и авто при `done` задачи, если у позиции есть `productId`) → новая запись `owner=product`, `copiedFrom`, тот же `path` (файл не дублируется, sha256). Удаление в продукции не трогает заказ. Из продукции в заказ — нет.
- Ограничение: 50 МБ на файл; типы — белый список; имя файла — uuid (как `image-upload.options.ts`).

**Решение 3. Код и исполнения изделия.** `products` — общая с CRM (каталог). Индекс `{organizationId, sku}` уникален → две записи с одним `sku` нельзя. Схема:
- Исполнение = **отдельное изделие** (свои состав, фото, файлы, паспорт).
- Новые необязательные поля `products`: `baseSku` (артикул семейства, «3404»), `variant` (номер исполнения, 1, 2…), `variantName` («с крышкой», «оцинк.»).
- `sku` = код: исполнение 1 — «3404» (как сейчас, печатные паспорта не меняются), следующие — «3404.2», «3404.3». Сервер выдаёт следующий номер: `POST /showcase/:id/new-variant` → копия изделия с `variant = max+1`.
- Существующие: `baseSku = sku`, `variant = 1` — вычисляются на чтении, миграция не нужна (запись — по первой правке).
- CRM: поля только добавляются, `sku` остаётся строкой → не ломаем. Схему менять синхронно с kppdf (одна строка на поле).
- Позиция заказа (`incomes`): уже `productId` → указывает на конкретное исполнение. Добавить снимок `productCode` (sku на момент привязки) — название в заказе своё (`name`), каноническое — у изделия.
- Экран: в «Продукции» колонка «Код» (`3404.2`), в карточке — блок «Исполнения» (список кодов + название исполнения, «Новое исполнение»). В позиции заказа и в задаче D-N — «Изделие: 3404.2 · Урна Диагональ (с крышкой)».

**API (контракт)**
- `GET /design-tasks/:id/notes` → `{items}` (по `createdAt`); `POST /design-tasks/:id/notes` {kind,text,replyTo?,remindAt?,remindTo?,fileIds?}; `PATCH /design-notes/:id` {text?,done?,order?}; `DELETE /design-notes/:id`.
- `GET /design-notes/open-questions?orderId=` → `{items,total,page,limit}` — вопросы с `needsAnswer`; `GET /design-notes/reminders?mine=1&due=1`.
- `GET /design-tasks` — в строках `notesCount`, `openQuestions`; фильтр `needsAnswer=1`.
- `POST /files/upload` (multipart, owner) · `GET /files?ownerType&ownerId` · `DELETE /files/:id` · `POST /files/:id/to-product`.
- `POST /showcase/:id/new-variant`; в `/showcase` строках — `baseSku`, `variant`, `variantName`.
- Права: как `design` (чтение — раздел, запись — admin/manager); писать комментарии — все с разделом `design`. Координатор — машинный ключ `kppd_` со scope `design`, `source=coordinator`.
- `docs/openapi.json` и `docs/MAP.md` — обновить.

**Экран (карточка задачи D-N — `backend/pwa/sections/design.js`, правая панель).** Порядок блоков:
1. Шапка: D-N, позиция, изделие (код), статус, исполнитель, срок, стикеры — как есть.
2. **«Требует ответа»** — жёлтая плашка с числом открытых вопросов (если есть), клик → к вопросу.
3. **«Обсуждение»** — лента: кружок (аватар / инициалы), имя, время («сегодня 14:05»), текст, вложения. Вопрос — с меткой «Вопрос менеджеру» и кнопкой «Ответить». Поле ввода внизу + «Файл» + переключатель «Вопрос».
4. **«Чертежи и файлы»** — список (значок, имя, кто, когда), «Добавить», «В продукцию»; у отгруженного — замок «после отгрузки не меняется».
5. **«Чек-лист»** — пункты с галочкой, «Добавить пункт»; пустой — «Нет пунктов. Добавьте, что проверить».
6. **«Напоминание»** — кому, когда, текст; одно активное достаточно (список — свернуть).
7. Описание (`note`), история.
В списке задач — значок «вопрос» с числом и счётчик сообщений. Без служебных кодов (`kind`, `source` — не показывать).

## Этапы
1. **Обсуждение + вопросы менеджеру** (нужно для аудита ЗНП): `designnotes` (comment/question), API notes + open-questions, блоки 2–3, счётчики в списке. Без файлов.
2. Файлы: `modules/files`, вложения в обсуждении, блок 4, `locked` после отгрузки.
3. Чек-лист + напоминания (напоминание — в «Главной»/колокольчик, без почты).
4. Исполнения изделий: поля `products`, `new-variant`, `incomes.productCode`, копирование файлов в продукцию.

## Критерии приёмки
- [ ] Если менеджер пишет в задаче, то запись видна с его инициалами/аватаром и временем.
- [ ] Если координатор (ключ `kppd_`) создаёт вопрос, то в задаче и списке — «Требует ответа: 1».
- [ ] Если на вопрос ответили, то `needsAnswer=false`, плашка исчезает, счётчик 0.
- [ ] Если чужой (не admin) правит чужую запись, то 403.
- [ ] Если заказ отгружен, то удалить файл позиции нельзя (409), добавить — можно.
- [ ] Если файл отправлен «В продукцию», то он есть у изделия; удаление у изделия не трогает заказ.
- [ ] Если создано исполнение 3404, то код «3404.2», CRM читает изделие без ошибок.
- [ ] Если позиция заказа привязана к 3404.2, то в ней видно «3404.2», название позиции — своё.
- [ ] Ничего не сломано: full — юнит + e2e (новые e2e для notes и files) + строка TEST-LOG.
