# Отделы и воронка «от продажи до готовой продукции» (аудит до кода, 2026-11-01)

Класс XL. Код не менялся. Всё ниже проверено по коду.

## 0. Что уже есть (проверено)
- **Отделы** — строки справочника `dict_values` (`departments`): Сварочный, Деревянный, Малярный. Это просто имена, связей у них нет. Пользуется только телефон склада: `stock-mobile.js:122` пишет имя отдела текстом в `stockmovements.issuedTo`.
- **Виды работ** — коллекция `worktypes` (общая с CRM). В ней уже есть **необязательное текстовое поле `department`** (`work-type/work-type.schema.ts:21`). Нигде не используется и не показывается.
- **Сотрудник**: `persons.workTypeIds[]` (список) и старое `workTypeId`; сервер уже умеет (`common/catalog/person-work-types.ts`). Прежний аудит (29.10) писал «списка нет» — теперь есть.
- **Маршрут изделия** `products.workTypes[]` (`product.schema.ts:63`) и экран «Как делается» (`work-route.js`). Есть.
- **Задание «В работе»** `worktasks` (`modules/work`): одна карточка на позицию заказа, шаги = виды работ маршрута, исполнитель, история, доска, Гант. Есть.
- **Готовность заказа** `order-readiness.ts:27`: пункт «Изделия изготовлены» появляется, если по заказу запускали задания. Есть.
- **Отгрузка** `modules/shipments`: есть, но от готовности изделия не зависит.
- **Чек-листов у отдела нет нигде** (чек-лист только в заметках проектирования).

## 1. Модель: что минимально
Отдельную коллекцию «Отдел» **не создаём**. Хватает справочника и одной связи.

| Связь | Как хранить | Почему |
|--|--|--|
| Отдел ↔ вид работ | `worktypes.department` (поле уже есть) = имя отдела из справочника; в «Справочниках» выбирается списком | Один вид работ — один отдел. Новых полей нет, CRM поле уже знает |
| Сотрудник ↔ отдел | Не хранить. Берём из его видов работ: отдел = отделы его видов работ | Нет дублей, нет рассинхрона |
| Задание ↔ отдел | Не хранить. Шаг задания = вид работ, значит отдел шага известен | Снимок маршрута уже есть |
| Выдача ↔ отдел | `issuedTo` = имя отдела (как сейчас) | Менять не надо |

**Дыра сейчас:** телефон группирует людей по названию вида работ («Сварка»), а сравнивает с названием отдела («Сварочный отдел»). Не совпадает, поэтому после выбора отдела показываются **все** сотрудники. Связь `worktypes.department` это чинит.

Риск: имя отдела — текст. Переименование в справочнике рвёт связь с виду работ и старыми выдачами. Решение: переименование отдела меняет текст в `worktypes.department` (каскад в сервисе справочников; у `departments` уже заведено «где используется» только по `stockmovements.issuedTo`). Нужно добавить `worktypes.department` в «где используется».

## 2. Воронка заказа по шагам
| Шаг | Что делает человек | Что считается само | Разрыв |
|--|--|--|--|
| 1. Продажа: заказ и позиции | заводит заказ | № заказа, этапы | — |
| 2. Проектирование | двигает по доске | статус позиции | — |
| 3. Снабжение и склад | заявки, брони, выдача | остатки | выдача в отдел не привязана к заданию |
| 4. Запуск в работу | кнопка «Запустить в работу» в заказе | карточка W-N по маршруту изделия | у большинства изделий маршрута нет, карточка «Изготовление» одним шагом; отдел не виден |
| 5. Работа по отделам | отдел двигает карточку по шагам | колонка доски | шаг без исполнителя и без отдела на карточке; **нет чек-листа внутри шага** |
| 6. Готово | последний шаг | «Изделия изготовлены» в готовности заказа | не ведёт к выдаче |
| 7. Выдача/отгрузка | оформляет отгрузку | расчёт отгрузки | можно отгрузить недоделанное |

Главные разрывы: (а) нет связи отдел ↔ вид работ; (б) нет чек-листа и отметки «готово» по пунктам; (в) «Готово» не включает кнопку/подсказку «к отгрузке».

## 3. Чек-листы отдела
- **Где хранить.** Шаблон чек-листа — в виде работ или в изделии: список пунктов (текст, обязательный да/нет). Рекомендация: **в `products.workTypes[]` у шага** (поле `checklist: string[]`; необязательное; CRM его игнорирует), а если у изделия нет — общий шаблон вида работ (`worktypes.checklist[]`, необязательное). При запуске заданий пункты копируются в **шаг маршрута** `worktasks.route[]` (снимок, как сейчас с маршрутом), отметки — `route[i].checks: [{text, doneAt, by}]`. Новой коллекции нет, схемы CRM не затронуты (`worktasks` — только data-core).
- **Кто отмечает.** Сотрудник отдела (исполнитель шага) или бригадир; отмечает на телефоне. Кто и когда — пишется.
- **Шаг «готов»**, когда отмечены все обязательные пункты. Тогда карточка идёт в следующий шаг сама (или кнопкой «Передать дальше» — см. вопрос О-3).
- **Изделие «готово к выдаче»**, когда последний шаг маршрута «готово» (это уже есть как `status=done`) и в заказе пункт «Изделия изготовлены» зелёный. Тогда на позиции заказа появляется отметка «Готово к отгрузке», а в «Отгрузке» такие позиции стоят сверху; недоделанные — с предупреждением (не запрет, см. О-4).

## 4. Что видит отдел и руководитель
**Отдел (телефон):** экран «Мои задачи» — карточки только его шагов: название изделия, № заказа, срок, чек-лист крупными галочками, кнопка «Готово». Фильтр по отделу берётся из видов работ сотрудника. Выдача материалов в свой отдел — в этом же экране («Что нам выдали сегодня»).
**Руководитель (компьютер):** доска «В работе» с группировкой колонок по отделам (колонка = вид работ, над ними заголовок отдела), счётчики «ждёт / в работе / готово» по отделу, просрочка. В карточке заказа — полоса воронки: проектирование → снабжение → отделы (сварка 2/3, малярка 0/3) → готово → отгрузка.
Экран отдела — новая раскладка: перед ним `datacore-design` и дизайнер до выкладки; единые эталоны kit «mobile».

## 5. План этапов (порядок по пользе)
1. **ОТД-1 (S, ~1 день): связь отдел ↔ вид работ.** В «Справочниках» у вида работ — список «Отдел» из справочника отделов; телефон склада после выбора отдела показывает людей этого отдела (через виды работ). Результат сразу виден: выдача в отдел работает по-настоящему. Заполнение 8–10 видов работ на проде — вручную пользователем или скриптом по «да».
2. **ОТД-2 (S): сотрудникам проставить виды работ** (сейчас ни у кого). Список на проде без записи — пользователь.
3. **ОТД-3 (M): отдел на карточке и доске «В работе»** — колонки по отделам, фильтр «мой отдел», «исполнитель» из людей отдела.
4. **ОТД-4 (M): чек-листы** — шаблон в виде работ/изделии, снимок в задание, отметки на телефоне, шаг «готов» при полном чек-листе.
5. **ОТД-5 (M): «Мои задачи» на телефоне** для отдела.
6. **ОТД-6 (L): готово → к отгрузке.** Отметка на позиции, подсказка в отгрузке, полоса воронки в заказе.
7. **ОТД-7 (M): выдача материалов под задание** — выдача в отдел может ссылаться на карточку W-N (поле необязательное в `stockmovements`; общая с CRM — только добавление необязательного поля, по согласованию архитектора).
Этапы 1–2 дают пользу сразу; этапы 3–6 — ДМ.7 (производство по модели kppdf) не заменяют: часы, сдельная оплата и Гант по людям остаются в ДМ.7.

## 6. Совпадение с решённым
- `TASKS.md` «Подразделения в работе и на складе» (п.1 «куда ушла работа», п.2 список при выдаче) — ОТД-1 и ОТД-3 закрывают его; п.2 уже сделан на телефоне, на компьютерном складе (`issue.js`) отдела нет.
- Зоны ответственности (`zones`) — офисные, к отделам не относятся; противоречий нет.
- Для переноса в ДМ.7: «задача → позиция заказа, виды работ» уже частично есть (`worktasks`); при реализации ДМ.7 не плодить вторую сущность задания.
