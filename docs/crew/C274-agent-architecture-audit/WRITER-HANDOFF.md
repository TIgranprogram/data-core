# Аварийная передача записи между API и CRM

Штатный писатель шести общих коллекций — API DataCore. Начальное значение C260–C265 для новой базы — `true`. После появления флага в базе запуск API сохраняет его значение, активность и дату изменения. Это исправляет `forceOn`, который повторно включал сохранённый аварийный `false`.

Учения выполняются с одноразовыми базой и пользователями. Перед рабочим переключением владелец отдельно утверждает окно, права CRM, изменение флагов и доступ к рабочим данным. Координатор отвечает за порядок, оператор инфраструктуры за остановку писателей, администратор Mongo за проверку фактических ролей и отзыва записи.

## Карта операций и проверок

| Флаг | Что проверять на API при передаче | Общие записи |
|--|--|--|
| `c260.warehouses.api` | Создание, правка и снятие склада получают `409` | `warehouses`. Даже чтение может восстанавливать отсутствующий склад по умолчанию. |
| `c261.materials.card.api` | Создание, правка, снятие и дублирование карточки `/materials` получают `409` | `materials`. Складской каталог также создаёт материалы и ячейки своим входом. |
| `c262.supply.requests.api` | Создание, изменение, удаление и возврат поля из истории заявки получают `409` | `supplyrequests`. Корзина, фото, счёт и приход имеют свои пути записи согласно C262. |
| `c263.stock.move.api` | Самостоятельное движение, пересчёт, правка и отмена получают `409` | `stockmovements` и `storageitems.quantity`. Выдача и пересчёт могут уменьшить бронь. |
| `c264.stock.reserve.api` | Бронь, снятие, выдача и применение спецификации получают `409` | `reservations`, `storageitems.reservedQty`. Выдача также обновляет остаток и журнал движений. |
| `c265.supply.receive.api` | Приход заявки, счёта, прямая поставка по счёту и откат прихода получают `409` | `supplyrequests`, `stockmovements`, `storageitems` и при необходимости `materials`. Вложенное движение использует решение владельца прихода. |

Флаги проверяются перед входом в отдельные операции. Для передачи общего писателя требуется остановка всего пишущего контура прежнего владельца: проверьте фоновую запись, служебные скрипты и синхронизацию. Если операцию можно задержать после проверки флага, один ответ `409` ничего не говорит о завершении этой операции. На стороне Mongo отзыв `readWrite` уходит до выдачи права второму писателю, а обе проверки выполняются через независимые подключения. Пауза с двумя запретами записи предусмотрена процедурой.

## API → CRM

1. Запишите фактические версию и состояние шести флагов, владельцев подключений и идентификатор свежего проверенного бэкапа. Убедитесь, что CRM и её фоновые писатели остановлены, а учётная запись CRM получает отказ записи.
2. Закройте вход новых операций API и остановите фоновых писателей. Дождитесь завершения или отмены уже начатых записей и транзакций. При закрытом внешнем входе сохраните для всех шести флагов `enabledByDefault: false`. Сверьте значения повторным чтением. Перезапустите сборку с сохранением флагов, проверьте тот же `false` и ответы `409` по карте, пока у CRM ещё нет записи. Подтверждение `409` получают тестовыми запросами без записи на рабочей базе только в отдельно утверждённом окне.
3. Остановите все экземпляры API, которые используют общий набор коллекций, и закройте их пишущие подключения. При необходимости инфраструктурной блокировки используйте отдельно утверждённый отзыв Mongo-роли у учётной записи API и проверьте отказ из прежней сессии. Перед следующим шагом подтвердите, что старых активных транзакций нет и оба контура остановлены или отклоняют запись.
4. Верните CRM только утверждённое право, затем запустите её. Сверьте фактические права, состояние процессов, доступность и результаты разрешённых проверок CRM. При отказе остановитесь на подтверждённом состоянии, закройте запись CRM и восстановите API обратной процедурой.

## CRM → API

1. Закройте вход новых операций CRM, остановите фоновые задачи, дождитесь завершения текущих транзакций и остановите CRM. Отзовите право записи CRM. Проверьте отказ и отсутствие её активных транзакций.
2. При закрытом внешнем входе восстановите штатное Mongo-право API, если оно изменялось, и поднимите API, пока сохранённые флаги выключены. Проверьте версию, здоровье и `409` на контрольных операциях. Вернуть `true` в рабочем контуре может администратор по разрешению владельца.
3. Восстановите утверждённые значения флагов, проверьте повторный запуск и откройте рабочий вход. Сверьте здоровье сайта, журнал и владельца записи. Сохраните метки времени последней записи CRM и первой записи API или результаты контрольных проверок, если окно было только учебным.

Откат приложения на сборку с `forceOn` может включить все шесть флагов. Безопасный запуск такой сборки возможен после остановки CRM и подтверждённого отзыва её записи.

## Проверенные учения

- HTTP `c274-writer-handoff.e2e-spec.ts` на MongoDB 4.4.30 проверяет шесть начальных `true`, семь `409` до и после перезапуска Nest с той же базой, сохранение `isActive`, подписи и времени изменения, затем успешные операции после возврата `true`. Проверены итоговый остаток, бронь, статус принятой и откатанной заявки.
- На отдельной MongoDB 4.4.30 с авторизацией проверены пять фаз для шести общих коллекций. Две тестовые учётные записи на прежних подключениях подтвердили запрет обоим при отзыве роли, единственный разрешённый контур в каждом активном состоянии и целостность контрольной записи. Локальный журнал `tools/logs/c274-followthrough/mongo-role-rehearsal.log`.
- Hermes Hy4 Flash проверил узко гонку между чтением флага и commit, первый upsert при конкуренции и порядок выдачи прав. Проверка кода подтвердила, что чтение флага идёт напрямую из Mongo, а некоторые записи видят флаг раньше commit. Фактический барьер — остановка и запрет предыдущего писателя. Первый HTTP-прогон выявил конфликт `updatedAt` с глобальным Mongoose audit hook. Владелец `featureflags` использует Mongo `$setOnInsert`, и повторный прогон подтвердил сохранение всех полей при перезапуске.
