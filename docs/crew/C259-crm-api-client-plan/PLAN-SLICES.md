# План срезов C259 — снять прямую запись kppdf

**Статус:** план. Кода нет. **«Да» владельца 24.11.2026.** Уточнение того же дня: kppdf-8.0 — старый проект, его не развиваем. Побайтный diff схем не делаем и не ждём. Цель срезов — выключить прямую запись kppdf в Mongo и уйти со старого CRM. Паритет полей «навсегда» не держим.

Пока процесс kppdf ещё на VM, он и data-core пишут одну базу `datacore`. Срез не портит живые документы. Это защита общей Mongo, не развитие kppdf.

**C260+ не начинать,** пока координатор не примет этот файл (`[x]` C259) и не поставит L-259: «код перевода только после принятого плана». Дальше один срез и одна приёмка. Пакета «да» нет. Выкладка на прод — отдельное «да» на выпуск.

Опора: [C257 CONTRACT](../C257-shared-compat-contract/CONTRACT.md), [C254 REPORT](../C254-shared-collections-layer/REPORT.md), [UNIFY](../../UNIFY-SUPPLY-WAREHOUSE.md), [C250](../C250-raw-query-inventory/INVENTORY.md), [BEYOND](../C246-architecture-modularity/BEYOND-CHECKLIST.md). Diff с деревом kppdf в опору не входит.

## Как устроен срез

Один сценарий записи. Один флаг. Включён — сценарий пишет только API data-core. Выключен — снова прямой Mongo. Два писателя одного сценария запрещены. Чужой сценарий флаг не трогает. Откат — флаг назад. Документы не переносят: API пишет в те же коллекции. Схему shared не менять. `replaceOne` / `save()` всего документа запрещены: сотрут `editedInApp` и ключи, которых нет в схеме. Только `$set` известных полей. Снятие с учёта — `deletedAt`. Mongo 4.4. Ключ `kppd_` лежит в env kppdf, не в репозитории и не в логе. Роль ключа проходит `@Roles` (запись склада и заявок — admin/manager).

В ТЗ среза — список мест записи этого сценария (только чтение kppdf). Это не сверка схем. Нашёлся соседний write — стоп, срез молча не расширять.

Шесть shared закрыты этими строками. C263–C265 — критичные сценарии: одна операция пишет две или три коллекции, резать её по коллекции нельзя.

## Порядок

C260 → C261 → C262 → C263 → C264 → C265.

Сначала запись без остатка. Карточка раньше движений. Заявка раньше прихода. Правила движения раньше прихода, который их вызывает. Бронь отдельно: `orderId` строка, у заявки — ObjectId, `salesOrderId` — другой ключ.

## Риски, пока kppdf жив на VM

1. Остаток строки — `storageitems.quantity`. `materials.stockQty` его не заменяет. Ошибка обнулит склад всем.
2. `orderId` движения и брони — строка. У заявки — ObjectId. В одно поле не сливать.
3. `source: 'google-sheets'` не пересчитывает остаток. Такой документ не «исправлять».
4. Пока часть флагов выкл, kppdf и API пишут разные сценарии в одни коллекции. Так уже живут CRM и «Рабочее место». Один сценарий — один писатель.
5. Право `readWrite` пользователя Mongo `kppdf` не снимать внутри среза. Иначе откат и ещё живые сценарии сломаются. Снятие права — после C265 и отдельного решения.
6. Повтор движения без `clientUid` удвоит остаток. Повтор того же ключа не создаёт второе движение.
7. Неизвестные ключи живых документов не вычищать заменой документа. `$set` только известных полей.

## Что остаётся прямым Mongo

- Чтение шести коллекций экранами kppdf — до выключения процесса. Чтение на API не переводим.
- Запись сценария, чей флаг ещё выкл.
- `categories`, `organizations`, коллекции `kind: 'crm'`. Экраны старого CRM этим планом на API не переносим.
- Таблицы Google, белый список `backend/scripts` (C254), админка «Таблицы» — это не писатель kppdf.
- «Рабочее место» уже ходит в API. Его писателей не трогать.

После C265 у kppdf нет записи в шесть shared. Гасить процесс на VM и забирать право записи — отдельное решение владельца. Этот план процесс не выключает.

## Не делать в C259

Код перевода. Правки `backend/src` и `D:\kppdf-8.0`. Diff схем ради паритета. Копия новых полей в схему kppdf. Новые `required` и `default` на shared. Микросервисы. Один флаг на все срезы.
