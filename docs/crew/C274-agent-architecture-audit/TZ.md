# C274 — аудит архитектуры и работы агентов

Владелец хочет получать проверенный результат с меньшим расходом лимитов. Код проверяет воспроизводимые условия. Агенты исследуют причины и отдельно рецензируют изменения с риском для данных, доступа или архитектуры.

**Класс** XL · **До трёх исполнителей одновременно** · **Приёмка** QA и архитектор · **До двух раундов ревью**.

## Исходные данные и границы

- Аудит от `ac33fa20`. Проверяем Git-дельту и границы модульного монолита по [LOCKS](../C246-architecture-modularity/LOCKS.md), зоны по `docs/roles/ownership.json`, состояние рабочих копий и реальные проверки. Указываем авторство Cursor только при наличии метаданных Git.
- Расход измеряем по локальным событиям `token_count`. Контекст с кэшем, вывод и отдельные вызовы Hermes учитываем раздельно. Без детализации провайдера суммы списаний неизвестны.
- Координатор принимает дифф и результаты. Hermes Hy4 Flash получает компактный запрос с подтверждёнными фактами для независимого анализа. Выводы проверяются по коду. Рабочие данные, ключи, логи авторизации и приватные конфигурации не передаются.
- Схемы общих коллекций и правила отката CRM проверяем по контракту. Любой переход по архитектурному замку требует свидетельства о конкретном дефекте.

## Работы и приёмка

1. **Backend, P1.** Проверить сериализацию общего списка заявок и остальных ответов того же контроллера. Исправить выдачу `invoiceAmount` и `invoiceNote` для ролей без денежных прав на существующей границе маскирования. Тест должен отличать роль без права от разрешённой роли и подтвердить форму списка и доступные роли. Основные файлы `backend/src/common/roles-hierarchy.ts`, действующий юнит денежной маски и при необходимости существующий тест списка заявок.
2. **Надёжность складской сетки.** Воспроизвести принятие нулевого количества после неуспешной записи и пустую координату из-за фильтра или пагинации, если факты это подтверждают. Сохранение через Enter и выход из поля, штуки в сетке, метры в раскрытии и различимость материалов остаются критериями. Выделить минимальное исправление с тестом. Для случаев с неоднозначной идентичностью материала спроектировать защиту на сервере с учётом существующих записей. Проверка наследованных имён, скрытых фильтром записей и двух конкурентных созданий обязательна перед выпуском такой защиты.
3. **Автоматические проверки.** Использовать `review-scope`, проверки карты, PWA/admin, циклов и границ. Сделать повторяемый компактный вход для локальной и GitHub-проверки на основе существующих сценариев. Ветка PR и `main` должны получать независимый результат от локального `core.hooksPath`. Выдавать команды и ошибки только при необходимости. Технически проверить маршрут зон, запуск из чистой рабочей копии, реакцию команды на сбой, отсутствие секретов и доступа к рабочему стенду. Архитектор принимает новые постоянные ворота.
4. **Архитектурные дефекты.** Подтвердить инвариант одного активного склада по умолчанию, своевременность исправления и контракт переключателей CRM→API. Для подтверждённых сбоев записать точные условия, владельца, порядок безопасного внедрения и проверку на изолированных данных. Устранить срочные дефекты, для которых определён совместимый контракт.
5. **Роли и порядок.** Назначить владельцев проверкам, выпуску, экономии, локальной конфигурации и совместимости. Для проверяемых задач использовать код под действующей ролью. Новая ИИ-роль нужна при отдельной постоянной ответственности без действующего владельца. Убрать только доказанные временные артефакты. Резервы, рабочие копии с уникальными данными и Git-объекты проверяются отдельно.
6. **Финальная проверка.** Выполнить тесты изменённых модулей, полный доступный локальный прогон и проверку отпечатка итогового коммита. Зафиксировать доказательства, незавершённые работы, состояние GitHub и воспроизведение настройки Hermes.
