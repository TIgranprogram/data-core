Дата: 2026-11-12. Исполнитель доступа: отдельная проверка на изолированном стенде, прод не затрагивается.

## Предварительные проверки

- Настройки прочитаны программно с выводом только разрешённых полей: LM Studio `http://localhost:1235`, приложение `http://localhost:3102`; оба loopback, порты строго проверены. Значение API-ключа не выводилось.
- Принадлежность: current-stand → `stands/<id>/run.json` → реальный Docker inventory → assertOwned. PASS, owner `datacore-night-v1`, project `dc-5dcd3eaa0174c7e66f457e92-night`, 4 контейнера.
- Прямой старый вход runner не использовался: он читает credentials, может создать их и чинить аккаунт, а обычный запуск регистрирует watchdog. Координатор поручил безопасный режим `--session-stdin --no-watchdog` через `api.sh stand BROWSER`.
- Токены передаются только в памяти/анонимном stdin, SESSION-файл не создаётся. Новое расписание для пробы не разрешено и не устанавливается.

## Результат

**PARTIAL по качеству ИИ; 15-минутный процесс завершён.** Запуск около 01:58–02:13 МСК. Модель `google/gemma-4-12b-qat`, роль API **admin**, `isOwner=false`; это НЕ проверка менеджерской роли. LM после пробы отвечает HTTP200, модель присутствует в `/models`. Зависания и аварии LM не зарегистрированы. Watchdog не установлен этим запуском, `run.json` после завершения отсутствует; продолжение 12/24ч не включалось.

37 новых попыток, 332 шага: 13 «получилось», 24 «не получилось» по журналу модели. Успешные самоотчёты не равны независимой функциональной приёмке. Много повторов, остановок за зацикливание, путаницы глобального поиска и локального фильтра; один сценарий остановлен по лимиту времени. С нуля создано 3 заявки, доказательство — created-журнал и ответы API.

Выход процесса **1**: в отчёте 1 техническое событие и 18 сообщений модели. Ниже события разделены; «19 ошибок сайта» из этого результата делать нельзя.

## Уборка

15-минутный запуск загрузил runner **до финального исправления cleanup**. Его штатная уборка использовала исходную сессию и завершилась сообщением «Не удалось войти на стенд» после истечения access. Итоговый код1 скрывал этот отдельный сбой уборки; не считать штатный cleanup этого запуска успешным.

Хранитель доступа затем сверил через `api.sh stand GET` все 3 ID с журналом, меткой ТЕСТ-ИИ и createdAt внутри интервала пробы; выполнил только эти DELETE и повторный GET404:

- `6af4f3bd464400ca1ef42010` — №433;
- `6af4f514464400ca1ef42593` — №434;
- `6af4f696464400ca1ef42a81` — №435.

Все три удалены мягко (`deleted:true`); `tools/logs/ai-tester/created.json=[]`. Аудит уборки — `tools/logs/c088-trial-cleanup.json`. Прежние записи ТЕСТ-ИИ и другие данные не удалялись. Проба не гарантирует отсутствие любых правок старых записей моделью: журнал учитывает созданные, не является полным rollback изменений. Контур — исключительно тестовая копия.

## Короткая проверка финального runner

После уборки отдельно запущен текущий код на 1 минуту с новой сессией через stdin и без watchdog. SHA256 `tools/ai-tester/run.mjs` до и после запуска: `D36601BBCD993419D168887BC1D086A349D048457E280C16FB0BB1B812A3D783`.

Завершено около 02:15 МСК: три попытки (заявка успешно, сотрудники — loop-stop, документация остановлена по времени). Создана 1 новая тестовая заявка №436; **штатный cleanup текущего кода сообщил «Убрано тестовых записей: 1»**, created-журнал пуст, run.json отсутствует. Таким образом короткий путь создания/уборки действительно испытан, а не no-op. Истечение/обновление сессии за 15+ минут на этой финальной версии отдельно не проверялось.

Код выхода1 обусловлен накопительным отчётом дня, где осталось HTTP400 первой пробы. Новых технических событий короткая проба не добавила; добавлена одна гипотеза глобального поиска. Накопительный итог41 строк задач включает37 предыдущих + служебную строку нового запуска +3 попытки; находок20=1 техническая+19 гипотез. Отчёт дня смешивает прогоны, поэтому для решения использовать разделение этого TRIAL.

## Что остаётся до длительной работы

1. Выделенная учётная запись **manager** для ИИ на изолированном стенде; подготовка офисным агентом обязана проверить фактическую роль через API. Сегодня общую admin-учётку не меняли. Не переиспользовать её для длительной менеджерской пробы.
2. Следующий воспроизводимый кандидат: `#fill?g=exp-cost` → заявка из счёта → только направление затрат → сохранение. Снять точный PATCH и проверить, не присылает ли форма лишние общие поля. Пока подтверждён только HTTP400, не дефект.
3. Два кандидата на ручную проверку, пока **неподтверждённые**: локальный поиск сотрудников против глобального поиска; поиск номенклатуры по существующему названию против названия категории. Начинать с чистого состояния, фиксировать hash/выбранный элемент, не доверять пересказу модели.

Длительный запуск требует отдельного решения после оценки качества. Без независимого воспроизведения гипотезы не превращать в задачи исправления сайта.
