# C161 — архитектурная оценка до реализации

19.11.2026, база179c6239 + текущие документы C161. Проверены TZ/CONTRACT/ARTICLE-PLAN и адресные места expense-articles, dicts, incomes, finance. Код/данные не менялись; прод не читался; вывод не является приёмкой реализации.

**Вердикт: основу можно принять; до кода закрыть три P1-контрактных пробела ниже.** Одна существующая коллекция статей, стабильные ссылки, дерево произвольной глубины и типизированная классификация достаточны. Новая бухгалтерская модель, EAV, дублирующая таблица фактов, хранение полного пути во всех платежах и периодические массовые переписывания не нужны. Дерево/пути можно собирать из parentId в памяти один раз на ревизию:183узла этому соответствуют.

## P1 — correction для старых расходов не имеет определённого места хранения

CONTRACT§4 перечисляет ledger/expenses/payroll/incomes, но пропускает нетронутые legacy supply snapshot и paid-заявки. Это действующие источники C158; их нельзя исчезающе переклассифицировать через текущую заявку либо заставлять мигрировать денежный факт ради статьи. Идентификатор requestId сам по себе не определяет, какой источник был выбран до перехода в ledger. Историческая классификация legacy сейчас может читаться из текущей заявки/категории, что противоречит обещанию неизменного original.

Дополнить контракт таблицей source adapter для КАЖДОГО источника: operationId, sourceId, стабильный payment/allocation key, где лежат original/override/version, что делать при void/delete/legacy→ledger. Для legacy supply выбрать явное lazy materialization **только классификации** на документе-источнике с CAS, без вымышленной оплаты/даты. Если корректировка ещё не поддержана для конкретного старого источника — read-only строка с объяснением и409 при PATCH, а не мнимая универсальность endpoint.

При фактическом переходе legacy supply→ledger исходная/effective классификация и история должны сохраняться либо явно блокировать переход планом сверки. Два active override для одного выбранного источника недопустимы. Выбранное решение нужно описать до назначения backend-задачи.

### Рекомендуемая конкретная source adapter matrix

| Источник | Устойчивый адрес | Где хранить классификацию; переход |
|--|--|--|
| C158 ledger allocation | `supply-payment:<paymentId>:<requestId>` | В allocations соответствующего SupplyInvoicePayment: original неизменен, typed override/classificationVersion рядом. Не менять amount/sourceAmount/date/company/state. |
| Legacy invoice paymentSnapshot | `supply-legacy:<invoiceId>:<requestId>` | На SupplyInvoice отдельная типизированная map `legacyClassifications[requestId]` с original/override/version; snapshot остаётся неизменным. При переходе в ledger перенести classification в соответствующую allocation той же транзакцией, сохранить originOperationId. Старый operationId может стать alias на новый, но не вторым фактом. |
| Legacy paid-заявки внутри invoice без snapshot | Тот же `supply-legacy:<invoiceId>:<requestId>` | Та же map на SupplyInvoice; original фиксируется при первом явном материальном введении классификации по read-only плану, с указанием источника/версии. Если первичная денежная история неоднозначна —409, не изобретать факт. |
| Legacy paid-заявка без invoiceId | `supply-request:<requestId>` | Первым выпуском read-only classification с409+планом сверки. Не добавлять ради этого структуру в общую CRM supplyrequests без отдельного решения. Поддержку такого source можно добавить типизированным адаптером позже; строка и сумма уже видимы в таблице. |
| Прочий expense | `expense:<expenseId>` | Original+override/version на самом Expense; source edits не должны молча стирать override. |
| IncomePayment | `income:<incomeId>:<paymentId>` | На embedded payment с server ID и typed override/version; Income.articleId — только подсказка новым оплатам. Synthetic paidDate имеет отдельный server-issued ID в typed legacy-payment metadata Income до адресной correction; не создавать новый платёж из-за одной статьи. |
| Payroll выплата | `payroll:<stable payoutId>` | На существующем документе выплаты после проверки реального stable payoutId; если источник только вычисляемый/ID нестабилен — read-only до отдельного source adapter. Не классифицировать начисление или календарный ожидаемый платёж как реальную выплату. |

Эти map/embedded поля — метаданные исходников, не новая таблица расходов. Таблица операций может быть полной до включения correction для последнего редкого legacy-источника. В ответе предусмотреть `classificationEditable`/причину недоступности; запрет проверяет сервер. Передать backend ownership по источникам явно; frontend получает готовый единый row contract и не разбирает source internals.

## P1 — CAS дерева должен охватить весь жизненный цикл через все aliases

CONTRACT§1/2 требует транзакционной проверки дерева, но описывает version/revision только для PATCH. Реальные записи проходят общие `DictsService.create/update/remove/restore/merge` (`dicts.service.ts:202–271`). Сегодня `toDoc` выполняется до записи, update фильтрует только `_id` (:230), restore просто снимает deletedAt (:252), merge вызывает reassign и удаляет старый узел (:267–268). В `dicts.expense-articles.ts:104–112` reassign непосредственно меняет articleId в заявках/expenses. Проверка parentId только в новом PATCH не защищает остальные пути.

Дополнить контракт: один специализированный writer существующего модуля для create/reparent/type/kind/archive/restore/remove/reorder; оба dicts-ключа и read aliases используют его. Каждая структурная операция атомарно проверяет и повышает одну treeRevision; version узла проверяется там, где есть узел. Проверки same-type/cycle/active-parent/duplicate выполняются в той же транзакции; DELETE/restore и начальный seed тоже не обходят это правило. Общие справочники других модулей не рефакторить ради C161.

Для article merge первым выпуском явно вернуть409 во всех aliases, либо отдельно определить атомарный dry-run+apply, который сохраняет original, corrects effective classification и usage. Фраза «общий merge не использовать» недостаточна, пока публичный маршрут остаётся доступным. Ошибка во второй половине merge/restore не должна оставлять половину нового дерева. Отдельный тест: A→B и B→A одновременно; restore удалённого родителя; income→expense через старый alias; merge используемой ledger-статьи.

## P1 — сохранность income paymentId при старых writes

CONTRACT§4 верно требует стабильные ID, но не задаёт переход для старого клиента, приславшего весь payments без ID. `PaymentDto` сейчас содержит дату/сумму/метод/примечание/clientUid (`incomes/dto.ts:7–11`), `toFields` пересобирает каждый элемент только из этих полей (`incomes.service.ts:167–174`). Механика paidDate может заменить/снять старую оплату (`income.schema.ts:122–124`, `incomes.service.ts:245+`). Простое добавление ID в схему оставит возможность стереть IDs/override следующим старым PATCH.

До кода задать правила: paymentId выдаёт сервер, существующий ID принадлежит только этой Income, не меняется при сортировке/изменении примечания; неизвестный/повторённый/чужой ID отклоняется. После materialization старый массив без ID не сопоставлять по date/amount/index: одинаковые части возможны. Либо409+план обновления клиента, либо отдельный совместимый read-only путь; нельзя молча выдать новые ID. Удаление/замена классифицированного платежа, paidDate-only ввод и снятие оплаты должны иметь явный согласованный механизм источника и сохранять историю. Correction CAS и изменение исходной оплаты конкурируют за один source version; idempotency проверяется до stale-version. Необходимо определить synthetic paidDate payment при первом materialization и последующем переходе к реальному payments.

## P2 — уточнения границ, достаточности и совместимости

1. **Legacy read contract.** CONTRACT§2 называет рекурсивные children совместимым расширением, но старые потребители реально обходят только top.children (`articles-tree.ts:27–37`, `by-articles.ts:57–65`, `pwa/expenses.js:28,38`). После переноса листа на третий уровень старый клиент перестанет его видеть, даже если JSON формально совместим. Выбрать до кода: сохранять старому `/expense-articles` двухуровневую проекцию всех selectable descendants с исходными ID/полным path и новым необязательным parentId, а новому `/financial-articles` отдавать каноническое дерево; либо явно версионировать deep-режим и ограничить обещание совместимости. Все внутренние потребители обновляются одним согласованным выпуском до переноса данных.
2. **nodeKind/selectable.** Сейчас два поля могут расходиться с наличием children. Зафиксировать допустимые сочетания: group имеет детей и не выбирается для новых фактов; article — selectable-лист либо временно невыбираемый лист. Превращение листа с историей в группу оставляет исходные ссылки в «Без детализации»; нельзя очищать categoryIds автоматически как это делает старый toDoc для корня (:73). Альтернатива — вывести kind из структуры и оставить только selectable; не хранить три независимые противоречащие истины. Технические пределы глубины/узлов/объёма задаются явно и возвращают400, а повреждённое старое дерево не зацикливает read.
3. **Effective resolver и хранение аудита.** Определить точный DTO override/reset; ограничения длины, допустимые null и код costCenter. PATCH только типизированных полей с forbidNonWhitelisted, совпадение права записи с source (включая закрытый payroll/stockscope). Override+version+устойчивая запись повтора+before/after audit фиксируются атомарно. Audit-интерцептор после ответа сам по себе не гарантирует историю. Одинаковый resolver нужен и в календаре/summary/by-articles/operations/выгрузке/usage, но изменение аналитического объекта не должно менять права доступа к исходному документу.
4. **Пагинация и скорость.** Новый GEToperations не должен сначала читать все платежи за все годы, а затем slice. Один нормализованный filter применяется до итогов/пагинации; отдельный источник truth на каждый тип, batch joins, суммы в минимальных единицах, стабильный source-qualified operationId. Префикс источника исключает совпадение ObjectId двух коллекций. До реализации указать max limit/диапазон и план индексов по source/дате/компании/payment key, а также сценарий измерения на наполненной большой истории. Итоги по всему фильтру и drill-down обязаны сходиться. Не требуется заранее строить materialized financial ledger.
5. **Кэш/отчёты.** `ExpenseArticlesService.tree()` сейчас использует единственный ключ и versions коллекции (`expense-articles.service.ts:55–58`). Ключ нового read учитывает type/includeArchived/режим проекции. Изменения override/source/tree инвалидируют соответствующие эффективные отчёты; raw-driver writes и seed должны повысить данные версий. Иначе переименование отразится в редакторе и останется старым в выборе/таблице. UI должен после сохранения перечитать сохранённый ID/путь, а не находить его по name.
6. **План главных групп.** ARTICLE-PLAN сохраняет14корней и предлагает лишь11переносов. Это безопасный переход, но не полное обещание новой укрупнённой структуры. В отчёте владельцу назвать его первым этапом. Следующее объединение смысловых веток можно выполнить переносом существующих корней под новые согласованные группы без изменения ID и денежных фактов; механизм не требует очередной перестройки кода. Названия/точный состав определяет предметная сверка, не архитектурный if.

## Безопасные этапы внедрения

1. **Закрыть решения выше и снять usage.** Принять source adapter matrix/старые writes/совместимую read-проекцию. Read-only проверить живые, архивные/удалённые и orphan-узлы, references всех источников/overrides, дубли соседей. Никакого применения ARTICLE-PLAN.
2. **Выпустить только инфраструктуру дерева.** Общие recursive utilities+диагностика, transactional writer/aliases/revision, кодовый payroll seed без зависимости от названия, архив/usage, рекурсивные селекторы и адаптированные readers. Данные пока остаются на двух уровнях. Тесты гонок, rename/reparent/restore/alias bypass, tsc/unit/e2e и видимая приёмка редактора.
3. **Доходные связи и идентичность.** Income.articleId, snapshot статьи новых частей оплаты, server-issued paymentId; защищённые DTO всех старых writes. На копии materialization legacy income IDs по read-only плану. Пока без кнопки correction. Приёмка: расходная статья отклоняется, старые доходы остаются «Без статьи», одинаковые по дате/сумме две части сохраняют разные IDs, массив без ID не стирает materialized историю.
4. **Единая таблица и операции только чтением.** Сначала серверный source-qualified operationId/canonical filter/read/total/пагинация, затем UI. Original classification resolver уже общий, но writes коррекции ещё закрыты. Приёмка третьего уровня, обоих types, archived/none/orphan, прямых ссылок на группы, точного drill-down и производительности. Сохранить существующее раскрытие доходов по заказчикам. До запуска следующего этапа таблица уже полезна владельцу и итогами сверена с текущими денежными экранами.
5. **Адресные аналитические corrections.** По source matrix: ledger и expenses, затем стабильные income parts/legacy invoice map; payroll только после проверки ID реальной выплаты. Один effective resolver для всех отчётов, CAS/idempotency/атомарный audit. Отдельная приёмка смены/снятия/reset классификации, legacy→ledger, source edit и override одновременно, scoped прав. Общие суммы/даты/число фактов сверить до/после. Неподдержанный source read-only с явной причиной, сумма не исчезает.
6. **Применить реорганизацию отдельно.** Наполненный стенд → подписанный план/hash/revision → бэкап → конкретное разрешение на прод → применение старых IDs → контроль/повторный plan0/rollback. Не смешивать перенос183узлов с выпуском кода или загрузкой счетов C157.
