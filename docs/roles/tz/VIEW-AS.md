# ТЗ VIEW-AS — «Смотреть как роль» (только просмотр)

> Аудит: `docs/crew/C019-admin-view-as-role/REPORT.md`. Решение пользователя 2026-11-04: **только смотреть** доступы роли, без записи и без перелогина.

**Зачем:** админ проверяет, правильно ли настроена роль (меню, деньги, кнопки правки), не выходя и не входя заново. У не-админа пункта нет.

**Класс:** M · **Max agents:** 2 (frontend + qa; designer после UI) · **Reviewers:** qa ☑ designer ☑ · architect ☐ · **Max review loops:** 2 · **Проверки:** smoke  
**Язык менеджера:** да — «Смотреть как», «Только просмотр», русские названия ролей · **Приёмка:** глазами по чек-листу C019

## Почему так (просто)

Обычный приём у разработчиков — либо тестовые учётки на каждую роль (долго), либо «View as» в админке.  
Для вашей цели («как выглядит и какие доступы») **достаточно клиентского просмотра**: JWT и роль в базе не трогаем. Сервер по-прежнему знает, что вы админ; в интерфейсе временно показываем выбранную роль. Все изменения данных в этом режиме **блокируются** на клиенте.

**Ограничение (явно):** зоны склада и 403 «раздел закрыт» на сервере этим режимом не эмулируются. Меню, галочка «Деньги», кнопки «Изменить / Создать» — да. Если позже понадобится полная серверная маска — отдельная волна (JWT `viewRole`).

## Shared pack

- Кто видит select: `session.isAdmin` (роль admin или isOwner) **по реальной сессии до наложения просмотра**.
- Хранение выбора: `sessionStorage` ключ `dca_viewAs` = код роли или пусто (сброс при закрытии вкладки ок).
- Настоящий профиль админа в `sessionStorage`/`localStorage` (`dca_user`) **не затираем навсегда**: хранить рядом снимок `dca_viewAsUser` или накладывать поля поверх копии при чтении.
- Список ролей: `GET /api/roles` (уже доступен admin).
- Запись: любой не-GET через `api()` при активном viewAs → не слать запрос, `toast('Сейчас только просмотр роли — менять данные нельзя')` (или ApiError 403-подобный).
- Исключения записи, которые всё же нужны в просмотре: **нет** (включая сохранение профиля и prefs). Смена роли просмотра и сброс — только локально + при необходимости GET.

## Что сделать

### Frontend (`datacore-frontend`) — основной объём

1. **`core/api.js` (или рядом `core/view-as.js`)**  
   - `getViewAs()` / `setViewAs(code|null)` в sessionStorage.  
   - `session.realUser` — пользователь без наложения (для canViewAs и сброса).  
   - При чтении `session.user` / геттеров `role`, `canEdit`, `canMoney`, `sees`, `isAdmin`: если viewAs активен — подставить `baseRole`, `role`, `roleLabel`, `sections`, `canMoney` из выбранной роли (как в ответе `/auth/me` после `resolveForAuth`: sections через те же правила, что сервер кладёт в me — брать `appSections` роли; admin-роль в списке для просмотра не нужна как цель, но «как обычно» = сброс).  
   - `canViewAs`: только если **реальный** user admin/owner.  
   - В `api()`: если viewAs и method не GET (и не «безопасный» HEAD) → блок до fetch.

2. **Применить роль из `GET /roles`:** по коду найти роль; `baseRole` / встроенная; `label`; `appSections`; `money` → `canMoney`. Для встроенных без документа — те же правила, что клиент уже знает (`canEdit` по baseRole, sections `null` = как иерархия / полный набор для не-admin с пустыми sections = «как раньше» по `sees()`).

3. **`profile.js`:** если `canViewAs` — поле «Смотреть как»: «Как обычно (моя роль)» + опции из ролей (без дубля текущей admin как «цель», либо с ней = сброс). Смена → `setViewAs` → событие `dc:view-as` → пересобрать shell и карточку. Подпись: «Только просмотр: данные менять нельзя».

4. **`main.js`:** полоса/бейдж «Сейчас как: {roleLabel} · только просмотр» + кнопка «Вернуть свою роль». На `dc:view-as` и после `/auth/me`: если реальный user уже не admin — сбросить viewAs. Пересборка sidebar как при смене sections (~550).

5. Проверка синтаксиса: `node --input-type=module --check` на изменённые файлы.

### Backend

- **Не менять** в этой волне (ни JWT, ни guards).  
- Если `GET /roles` для списка неудобен (тяжелый) — допустим уже существующий лёгкий список; не плодить эндпоинт без нужды.

### Вид

- Select в профиле + предупреждающая полоса в шапке (токены DESIGN, не новый «бренд»).  
- Новый эталон kit — нет.  
- После UI — `datacore-designer`.

## Критерии приёмки (qa)

- [ ] Admin: в профиле «Смотреть как»; выбор роли → меню/кнопки/деньги как у роли; полоса «только просмотр».
- [ ] Любая попытка сохранить/создать/удалить → отказ с понятным текстом, запрос на сервер не уходит.
- [ ] Снова профиль → другая роль или «как обычно» без выхода.
- [ ] Не-admin: блока нет.
- [ ] После сброса — полный админский вид; ссылка в админку снова есть.
- [ ] Реальная роль пользователя в БД не менялась (проверка: `/auth/me` без viewAs-полей сервера — role как был).
- [ ] Smoke: module-check изменённых js; ручной сценарий выше.

## Нельзя

- Менять `users.role` в Mongo.  
- Полагаться на «тихий» write через обход UI без блокировки в `api()`.  
- Обещать в текстах UI проверку зон склада (её нет в этой волне).
