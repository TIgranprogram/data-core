# C170 — вложенный паспорт позиции заказа

Статус: узкий аудит и предлагаемый контракт для утверждения архитектором. Код и данные не менялись; реализация — после приёмки C166. C164 и финансовые источники неприкосновенны. Новая возможность не означает проверку юридической пригодности содержания файла: сотрудник явно подтверждает, что выбрал паспорт этой позиции.

Основания: PRODUCT §5а — изделие является источником шаблона, выпущенные документы сохраняют историческое содержание; C170 добавляет явную альтернативу для конкретной позиции, не меняет шаблон изделия. Поиск относящихся решений QUESTIONS не обнаружил принятого правила, автоматически считающего декларацию или произвольное вложение паспортом. Нормативную достаточность файла этот аудит не оценивает.

**Услуги:** текущий orderPlan не проецирует lineType и сам не выделяет service в отдельный счётчик: без изделия позиция blocked. В C170 сохранить текущий набор позиций/знаменатель и прежние правила услуг, не делать скрытый рефакторинг. Если на принятой базе координатора уже есть исключение услуг, сохранить именно его и зафиксировать тестом; C170 не делает услугу готовой по вложению и не превращает её в изделие.

## 2. Storage: отдельное владение паспортным выбором

Предложение: необязательное вложенное поле `incomes.passportSelection`, отдельное от `source`, `sourceLine`, платежей и классификации денег:

```ts
passportSelection?: {
  mode: 'site' | 'attachment';
  revision: number;                  // серверная монотонная версия, отсутствие = 0
  attachmentId?: ObjectId;            // только mode=attachment
  productIdAtSelection?: ObjectId;    // привязка к изделию в момент подтверждения
  confirmedAt?: Date; confirmedBy?: ObjectId;
  changedAt: Date; changedBy: ObjectId;
  invalidatedAt?: Date;
  invalidReason?: 'PRODUCT_CHANGED' | 'ATTACHMENT_DELETED';
}
```

Отсутствие поля = site, revision=0, без миграции старых данных. В site attachmentId и productIdAtSelection не сохранять; прежнее значение сохраняется в аудите. Только сервер ставит время/сотрудника/revision; revision не сбрасывать при отмене и возврате. Не хранить URL, тикет, путь, копию файла или его имя как идентичность. Имя/размер/MIME — отображение из attachment; исходный выбор и контекст фиксируются в аудите before/after. Разные позиции того же изделия имеют независимый выбор.

При изменении productId выбранная attachment-связь помечается PRODUCT_CHANGED с увеличением revision в той же атомарной операции изменения контекста. Не превращать выбор молча в site и не возрождать подтверждение после обратной смены изделия. Смена orderId также меняет контекст CAS; перенос позиции сам по себе файл того же изделия не делает чужим, но доступ к новому заказу перепроверяется. Изменение title/qty не переписывает файл и не меняет источник; подтверждение сотрудника относится ко всей позиции и её количеству — безопасное допущение, без модели файлов на каждый экземпляр.

При мягком удалении выбранного файла сохранить ссылку для истории, пометить все действующие выборы этого attachment как ATTACHMENT_DELETED и увеличить их revision. После restore нужен явный повторный выбор; автор подтверждения не подменяется администратором восстановления. Физически пропавший файл без удаления определяется readonly-проверкой наличия; план не пишет в БД. После временного восстановления того же файла доступность может восстановиться при неизменном выборе; файл с новым ID требует нового подтверждения.

Аудит действий: `passport.selection.changed` и `passport.selection.invalidated`, entityType=Income, id позиции, orderId, before/after, attachmentId, контекст изделия, сотрудник/время. Не записывать тикеты/содержимое файла/секретные пути. Выбор не создаёт ProductPassport, номер, printFile и финансовый факт.

## 3. Предлагаемый API/DTO

Маршруты в домене passports, с существующими WORK и проверками доступа к целевому заказу/позиции; для файла дополнительно существующее право чтения соответствующего вложения. Это пересечение прав, не их расширение.

`GET /api/passports/order/:orderId/lines/:incomeId/source` → `{orderId,incomeId,productId,selection,contextToken,attachment,effectiveState,missing,sitePassports}`. `contextToken` — непрозрачная серверная подпись/версия актуальных orderId/productId/lineType/cancelledAt/deletedAt и revision выбора; не финансовых платежей. Поле `attachment` содержит id, productId, originalName, mime, ext, size, availability=available|deleted|missing|product_changed|forbidden; недоступные чужие сведения не раскрывать.

`GET /api/passports/order/:orderId/lines/:incomeId/source/candidates` → стандартное `{items,total,page,limit}`: живые физически доступные productattachments текущего productId; каждое item содержит id, имя, вид, размер, MIME, scope/incomeId происхождения и доступность. `attachmentTypes` — подсказка группировки, не автоматическое подтверждение. Не создавать жёсткую зависимость от русской подписи папки «Паспорт»: сотрудник сам выбирает файл и подтверждает назначение. Если существует формально заданный вид «Декларация», UI предупреждает о виде перед подтверждением; один только PDF/JPG/название файла не делает его паспортом. Архитектор сохраняет существующий allowlist форматов вложений; C170 не добавляет обработчики новых форматов.

`PUT /api/passports/order/:orderId/lines/:incomeId/source`:

```json
{"mode":"attachment","attachmentId":"<ObjectId>","confirm":true,"expectedRevision":0,"contextToken":"<opaque>"}
```

Для возврата: `{"mode":"site","expectedRevision":1,"contextToken":"<opaque>"}`. В site attachmentId запрещён; в attachment attachmentId и confirm=true обязательны. expectedRevision — обязательное целое ≥0. Только эти поля разрешены, неизвестное →400. Ответ 200 — тот же source-view с новой revision и актуальными причинами/счётчиками; отсутствие данных шаблона не запрещает возврат site и само по себе не создаёт черновик.

Проверки записи: живые заказ и позиция, принадлежность income.orderId указанному заказу, позиция не отменена; живое выбранное изделие; attachment.productId равен текущему productId; deletedAt/fileRemovedAt отсутствуют; файл реально является доступным файлом внутри uploads по существующему resolver; ACL; свежесть контекста и selection. Валидность не выводить из списка UI. Файл загруженный через другую позицию того же изделия разрешён согласно фактическому решению 15.11; attachment другого изделия запрещён даже при подставленном ID.

Ошибки: 400 SOURCE_INVALID — DTO/неподтверждённый выбор; 403 — права (без чужих деталей); 404 — отсутствующая/чужая целевая позиция или файл; 409 STALE_CONTEXT — смена контекста/revision; 409 ATTACHMENT_UNAVAILABLE — выбранный файл удалён/недоступен до записи. Повтор формы со старой revision →409 и перечитать; второй аудит/запись не выполняются. Для сохранения и инвалидирования нужен атомарный протокол со сменой изделия/удалением файла, иначе проверка-перед-записью оставит гонку.

Общий PATCH /incomes не принимает passportSelection; новый DTO не разбирает и не передаёт финансовые поля. Не использовать IncomeDto как DTO данного endpoint, не менять C164 sourceLine-защиту. Точный участок доходов для hook смены изделия согласовать с координатором на принятой базе.

## 4. Готовность, счётчики и выпуск

Существующий `GET /passports/order/:orderId/plan` расширить добавочно: каждой строке `source`, `selectionRevision`, `attachment`, `historicalIssuedCount`; state допускает новое `attached`. Для site прежние state/паспорт/missing сохраняются. Для выбранного доступного attachment: state=attached, missing=[], причины шаблона/фирмы не вычисляются как препятствие, passport не изображает новый issued. Для attachment недоступного: state=blocked, source=attachment, missing только о конкретном файле/смене изделия, без fallback к шаблону сайта. Старые живые паспорта перечислять отдельно как sitePassports/история, не терять их из карточки.

Счётчики эффективного состояния позиций: `total = issued + attached + ready + blocked`; `completed = issued + attached`. issued — текущий выбранный source=site с выпущенным паспортом; ready — только source=site, готов к выпуску; attached — подтверждённый доступный файл. Исторические issued при source=attachment не удваивают счётчик и показываются отдельно `historicalIssued`. cancelled сохраняется как сейчас. Подписи: «Документы готовы X из N», отдельно «Выпущено на сайте», «Вложенные», «Готовы к выпуску», «Требуют заполнения/выбора файла». Ready не включать в completed. Готовность — на позицию, не на qty экземпляров.

У режима site новый выбор не обязателен: он действует по умолчанию. Отмена attachment возвращает обычные проверки; существующий черновик переиспользуется штатно, issued признаётся по прежним правилам. Выбор attachment поверх issued допустим как смена текущего источника с явным предупреждением «Паспорт сайта останется в истории»; номер и снимок не отменяются. Уже выпущенные паспорта нельзя переписывать, удалять или аннулировать этой командой.

`POST /passports/order/:orderId/issue` пропускает **все** source=attachment, включая потерянный файл: причина «Выбран вложенный паспорт» или «Выбранный файл недоступен». Повторно проверить выбор атомарно непосредственно перед createDraft/issue; ранее построенный plan не разрешение на выпуск. Прямые создание/выпуск позиционного паспорта, draft-all и иные пути той же позиции должны соблюдать тот же запрет; редактирование/чтение существующего исторического паспорта не подменять новым выпуском. Если гонка источника и выпуска — выигрывает одна операция, другая получает conflict, без лишнего номера/черновика от неуспешного выбора. Архитектор доказывает протокол, process-local mutex недостаточен.

Order PDF сайта исключает позиции source=attachment независимо от наличия старого issued и независимо от ids=…; фильтровать сервером через актуальный выбор, а не кнопкой UI. Исключение сообщать в метаданных/существующем skipped-механизме с причиной SOURCE_ATTACHMENT. Если не осталось паспортов сайта — 400 NO_SITE_PASSPORTS с объяснением, а не пустой PDF. Исторический паспорт по собственному /passports/:id/pdf остаётся доступен как исторический документ в рамках прежних прав. Фильтр заказного PDF не означает запрета индивидуального чтения истории. ZIP общего реестра паспортов не превращать в архив attachment; поведение адресного исторического экспорта сохранить. Отдельный ZIP/склейку для C170 не создавать.

Открытие/скачивание выбранного файла — через `POST /api/passports/order/:orderId/lines/:incomeId/source/download-ticket`: 200 `{ticket,url,expiresIn}` с существующей механикой файлов. До выдачи проверить текущую selection/revision, доступ и stat, после — стандартная проверка живого файла при погашении тикета. Нельзя хранить тикет как выбор. При пропаже/удалении файл не открывается, UI перечитывает plan. Raw storedPath наружу не отдаётся.

## 5. Приёмка и границы следующего этапа

| Если | То |
|---|---|
| В заказе одна issued-site, одна ready-site, одна attached, одна blocked | total=4, issued=1, ready=1, attached=1, blocked=1, completed=2; видно происхождение каждого документа. |
| Вложен файл декларации, но выбор не подтверждён | Готовность не меняется. Выбранный сотрудником паспорт хранится ID, а не первым файлом папки. |
| Шаблон пуст, фирма не задана, выбран доступный attachment | Строка attached; нет требований сайта и нового номера/черновика. |
| Файл удалён/стёрт/физически пропал | Строка blocked с причиной файла, выпуск сайта не запускается. Restore удалённого требует повторного подтверждения; новый файл сам не подставляется. |
| Сменено изделие, затем возвращено прежнее | Старое подтверждение инвалидировано; файл требуется подтвердить заново. |
| Выбран файл другого изделия или чужая целевая позиция | Сервер отказывает, даже если клиент подставил ID вручную. Файл того же изделия из другой точки загрузки допустим по решению 15.11. |
| Две формы меняют источник, либо одновременно идут delete/product-change/issue | Побеждает одна согласованная операция; другая conflict/перечитывание, без ложной attached и двойного выпуска. |
| Вернулись из attachment в site | Ни файл, ни старые issued не меняются; показывается актуальная готовность сайта без автоматического выпуска. |
| Массовый выпуск/PDF вызван вручную с ID attachment-позиции | Новый паспорт не выпускается, старый не попадает в текущий order PDF; причина пропуска видна. Исторический отдельный PDF остаётся читаемым. |

Не закрыто этим аудитом: реальное изображение folderTile и причина узкой геометрии, браузерная приёмка 1920/1024/тем, полный граф всех обходных create/issue/ZIP, точный транзакционный протокол и ACL принятой базы. Это адресные задачи архитектора/реализации/QA, не подтверждённые результаты. Услуги и C164 не расширять до рефакторинга. Продовые отметки не заполнять.

Якорь карты: C170 → ANALYSIS.md §§2–4: независимый passportSelection, ID общего вложения изделия, readonly availability, отдельные счётчики и запрет выпуска/заказного PDF; коммит: не создан. Карту обновляет координатор по границам владения; изменён только этот файл. Вопросов пользователю нет: допущения о действии выбора на позицию/количество и повторном подтверждении после удаления явно изложены.
