# C100 — совет архитектора: «Вид изделия» без угадывания (2026-11-13)

**Решение: B (отдельный справочник «Виды изделий») + A (группа задаёт вид по умолчанию). C — нет.**
- Вид изделия = `dict_values` с `dict:'passportKinds'`: `name`, `passportCategory`, `elementIds[≤3]`, `purposeLeafId` (лист воронки passportPhrases), опц. `facetValueIds`. Один вид полностью определяет «что это», назначение, категорию и тип (productType).
- В `categories` третий уровень НЕ делать: `products.categoryId` должен указывать на группу (groupNo → артикул, дерево CRM, showcase.ensureCategory). Группе — только поле `passportKindId` (сырым db.collection, как groupNo/passportCategory; CRM лишнее поле не мешает).
- Изделию — `passportDefaults.kindId`. Цепочка: своё у изделия (kindId или явные elements/textChoices) → вид группы → пусто = один обязательный вопрос «Вид изделия» (список видов категории группы). Угадывания нет нигде.
- C отвергнут: элементов у изделия до 3 (турник+брусья) — назначение от элемента неоднозначно; это и есть угадывание другим способом.

**Порядок шагов**
1. `common/passport/kind.ts` — одна функция `resolveKind(db, prod)` → `{kind, source:'own'|'group'|null, groupName}`. Её зовут все: passport-gaps.ts (purposeState, элементы, категория), check/PDF, passport-applicability (тип из вида). Иначе анкета и PDF разойдутся.
2. Справочник видов — DictBase в `modules/dicts/` (рядом с productGroupDefs): поля, `usage` (сколько изделий/групп), `beforeRemove` — запрет при использовании.
3. `dicts.product-groups.ts:43-98` — поле `passportKindId` (select ref passportKinds) в fields/row/toDoc, как `passportCategory`. Категория группы при заданном виде берётся из вида (или проверить совпадение — несовпадение 400).
4. DTO изделия: добавить `kindId` во вложенный класс passportDefaults (whitelist+forbidNonWhitelisted → иначе 400 у клиента). Сразу проверить, что старые клиенты его не шлют лишним.
5. Удалить `common/passport/name-suggest.ts` целиком, `suggestValue` (passport-gaps.ts:154), `elementSuggest`, поле `suggest` в GapItem и его спеки. Признаки: пусто → обычный вопрос; значения по умолчанию — из `kind.facetValueIds`.
6. Клиент `pwa/sections/passports/fill/control.js:14-30`: вместо «Похоже… по слову» — строка-источник «из вида «Урна» (группа «Урны»)» / «своё»; кнопка «Изменить вид». Правка atlas-data.js и help-guide-data.js в том же коммите.
7. Скрипт `backend/scripts/c100-kinds.js` (план → `--apply`, на проде запускает пользователь): создать виды для 9 однородных групп по их 22 заполненным изделиям (уникальные сочетания категория+элементы+назначение), проставить группам `passportKindId`. 22 изделия НЕ трогать: их значения — «своё», остаются главнее. Совпадает с видом группы — можно позже очистить отдельным шагом.
8. Смешанные группы (Тренажёры, Воркаут, Спорт оборудование, «Благоустройство…»): вид группы пустой; виды-подвиды (Кардио, Ноги, Турник+брусья…) заводит менеджер, изделия получают вид в анкете или массово из списка группы. «3207 Стелла» — перенести в группу «Информационные стенды…» (DATA-FIX-USER), а не править код.

**Подводные камни**
- Листья фраз с `groupIds` (phrase-tree.ts:99-104) остаются детерминированными, но приоритет: своё → вид → groupIds; иначе два источника назначения спорят. Задокументировать в PATTERNS/CANON.
- Сохранённый `textChoices[purposeRoot]` у изделия главнее вида; удалённый лист вида → обязательный пункт «выберите заново», а не тихая подмена.
- Mongo 4.4: резолв в коде, без $getField/$setWindowFields; индекс `{dict:1, deletedAt:1}` уже есть у dict_values — проверить.
- Схему CRM `categories` не трогать; поле только сырым $set. В openapi/MAP — новый справочник и поле kindId.
- Класс задачи — L (сервер+экран+данные), full перед выкладкой; дизайнер принимает анкету.
