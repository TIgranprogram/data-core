## 1. Железные правила (нарушать нельзя)

1. **Один шаг за раз.** Бери ровно одну задачу из списка в разделе 4, делай, проверяй, отмечай в `docs/PROGRESS.md`, только потом следующую.
2. **Ничего не считается готовым, пока ты не запустил проверку и не увидел успех.** Слова «должно работать» запрещены. Покажи вывод команды.
3. **Только Python ≥ 3.12.** Никаких `.bat`/`.cmd`. Зависимости через `uv`.
4. **Windows-правила:** пути только `pathlib.Path`; внешние команды только `subprocess.run([...], ...)` списком аргументов, **без `shell=True`**; все файлы читать и писать с `encoding="utf-8"`; не склеивать пути строками с `\`.
5. **Работаешь только внутри папки `D:\data-core\tests_ai_tiit\nightshift\`.** Код проверяемого сайта читать можно, менять нельзя. В боевой сайт, боевую БД и боевое хранилище не писать никогда и ничем. Секреты (пароли, ключи) не копировать, не печатать, не логировать.
6. **Все настройки — в `config/*.yaml`.** Пороги, лимиты, имена моделей, ссылки на установщики в коде не хардкодить.
7. **Не удалять и не ослаблять тесты, чтобы «позеленело».** Если тест падает — чини код, а не тест. Исключение — тест неверен по ТЗ; тогда запиши в `DECISIONS.md`.
8. **Не раздувай.** Делай минимум, который закрывает пункт ТЗ. Без «на будущее».
9. **Ядро не зависит от GUI.** Вся логика в `orchestrator/`, `suites/`, `ai/`; GUI только вызывает ядро.
10. **Каждый набор тестов — плагин:** папка в `suites/<имя>/` с `suite.yaml`. Ядро ничего не знает про конкретные наборы.
11. Если застрял на одной проблеме больше 3 попыток — остановись, запиши проблему и что пробовал в `docs/BLOCKERS.md`, переходи к следующей независимой задаче.
12. После каждого шага: запусти `uv run pytest nightshift/tests -q` — зелёный результат обязателен перед переходом дальше.

## 2. Что строим (кратко)

Приложение, которое ночью без человека: скачивает копию боевого сайта → поднимает изолированный стенд в Docker → гоняет наборы тестов → локальный ИИ (OpenAI-совместимый агент по адресу `http://localhost:1235/v1`) чинит только мелочи на стенде → всё складывается в папку `handoff/<дата_время>/` для мощного ИИ. Результат — отчёт JSON + HTML. Управление — CLI и GUI. Поставка — один `nightshift.exe`.

Роли: **скрипт руководит, ИИ исполняет, проверяет только компьютер.**

### ЭТАП 1. Каркас, CLI, отчёт, handoff

- **1.1** `pyproject.toml` (Python ≥3.12; зависимости: typer или click, pydantic, pyyaml, jinja2, psutil, pytest, pytest-xdist; остальное добавляй по мере этапов). `uv sync`. Проверка: `uv run python -c "import nightshift"`.
- **1.2** `orchestrator/db.py`: SQLite `data/nightshift.db`, таблицы: `runs`, `stages`, `issues`, `attempts`, `fixes`, `metrics`. Проверка: тест создаёт БД и пишет/читает запись.
- **1.3** `orchestrator/plugins.py`: поиск `suites/*/suite.yaml`; поля: `name, command (список), timeout_sec, priority, depends_on`. Проверка: тест находит набор `demo`.
- **1.4** `suites/demo/`: два тестовых скрипта (один проходит, один падает) для проверки самого приложения.
- **1.5** `orchestrator/runner.py`: запуск набора через `subprocess.run([...], timeout=...)`, перехват stdout/stderr, код выхода, **жёсткий таймаут с убийством дерева процессов**, падение одного набора не останавливает остальные. Проверка: тесты на «успех», «падение», «зависание» (таймаут).

Схема Pydantic: сводка (пройдено/упало/пропущено/новое vs прошлый прогон) + список проблем с полями: `suite, test, run_time, commit_hash, expected, actual, error, stacktrace, log_fragment, file, line, repro, repeatability, resource_metrics, priority, scenario_id, group_id`. Отсортировано по приоритету. Проверка: тест генерирует отчёт по результату `demo` и валидирует JSON схемой.
- **1.7** `orchestrator/handoff.py`: создаёт `handoff/<дата_время>/` со структурой из ТЗ 4.10 (`README_FOR_AI.md, summary.md, summary.json, issues/, fix_history/, needs_big_ai/, metrics/, environment.json`) и zip-архив с лимитом размера (важное первым). Проверка: тест проверяет наличие всех файлов.

Проверка: `uv run nightshift run --suite demo` → код 1, отчёт и handoff созданы.

### ЭТАП 2. Стенд, изоляция, регрессия, карта сценариев

- **2.1** `config/project.yaml`: `project_path`, команды получения кода/БД/файлов (из `DISCOVERY.md`). Доступы читаются из папки проекта, **не копируются в nightshift**.
- **2.2** `stand/docker-compose.yml` + `stand/scripts/`: поднять копию сайта (код, БД, файлы) в контейнерах; команда `nightshift stand refresh`; сброс стенда к чистой копии перед прогоном; `stand up/down` одной командой. Проверка: стенд поднимается с нуля, открывается его главная страница.
- **2.3** `stand/isolation/`: ловушка почты (Mailpit), тестовый режим платежей, заглушки внешних ключей, отключение рассылающих планировщиков, сеть стенда без доступа к боевым системам и интернету. **Тест изоляции** `suites/isolation_check`: пытается обратиться к боевым адресам и попытаться отправить письмо — всё должно быть заблокировано/перехвачено. **Без зелёного теста изоляции прогон не стартует (код выхода 2).**
- **2.4** `orchestrator/scenarios.py` + `nightshift scenarios sync`: сверка `scenarios.yaml` с кодом; новые страницы/формы/API без сценария → в отчёт «не покрыто тестами».
- **2.5** `suites/regression/`: pytest + pytest-xdist на всех ядрах; на каждый поток своя копия БД и свой порт; Playwright для сквозных тестов по сценариям из `scenarios.yaml` (критичные первыми). Проверка: запуск на стенде, параллельность видна в логе, критичные идут первыми.
- **2.6** `suites/static/`: статанализ, уязвимости зависимостей, поиск секретов, покрытие кода (инструменты по `DISCOVERY.md`).
- **2.7** Сравнение конфигураций стенда и боевого сайта → раздел в отчёте.
- **Готово когда:** `nightshift run --suite regression` даёт полный отчёт на стенде; тест изоляции зелёный.

### ЭТАП 3. Расписание, продолжение после сбоя, ресурсы

- **3.1** `orchestrator/resume.py`: каждый этап пишет статус в SQLite; после kill/перезагрузки прогон продолжается с первого незавершённого этапа. Проверка: тест убивает процесс посреди прогона и перезапускает — завершённые этапы не повторяются.
- **3.2** `orchestrator/resources.py`: каждые N секунд метрики CPU/RAM/диск/GPU (psutil, nvidia-ml-py) в таблицу `metrics`; пороги из `limits.yaml`: мало места → автоочистка старых логов/артефактов → остановка тяжёлых этапов; высокая температура → снижение параллелизма/пауза.
- **3.3** `orchestrator/scheduler.py`: создание/удаление задачи в Планировщике заданий Windows (`schtasks` списком аргументов), запускающей `nightshift run --profile night`; работает при закрытом GUI.
- **3.4** `config/profiles.yaml`: профиль `night` по ТЗ 4.5 (порядок, лимит времени каждого этапа, время окончания ночи, остановка долгих тестов за 1 час до конца).
- **3.5** Ротация и автоочистка логов; маскирование секретов в логах и отчётах (тест: «ключ» в выводе заменяется на `***`).
- **Готово когда:** прогон переживает kill; расписание создаётся и удаляется командой.

### ЭТАП 4. Нагрузка, soak, chaos, бэкапы

- **4.1** `suites/backup/`: реально восстановить из бэкапа в тестовое окружение, проверить целостность (счётчики таблиц, контрольные записи). Результат — в отчёт как проверка бэкапа.
- **4.2** `suites/load/` (Locust): наращивание нагрузки до деградации, фиксация узкого места, метрики времени ответа.
- **4.3** `suites/soak/`: умеренная нагрузка часами; детект утечек памяти, роста логов, деградации (сравнение начало/конец).
- **4.4** `suites/chaos/` (Toxiproxy): обрыв сети, медленная БД, заполненный диск, нехватка памяти, падение внешнего сервиса; проверка — нет потери данных, понятные ошибки, самовосстановление.
- **4.5** Базовые замеры производительности: сравнение с прошлыми ночами; замедление > порога (по умолчанию 10 %) = проблема.
- **Готово когда:** каждый набор укладывается в лимит времени и записывает метрики в отчёт.

### ЭТАП 5. Фаззинг, мутации, визуальные, monkey, flaky, bisect

- **5.1** `suites/fuzz/` (Hypothesis + фаззер под стек): случайные и некорректные входы API/форм; найденный сбой упрощается до минимального примера.
- **5.2** `suites/mutation/`: инструмент по стеку; неубитые мутанты → в отчёт как «тест ничего не проверяет».
- **5.3** `suites/visual/` (Playwright): скриншоты vs эталон, несколько браузеров и разрешений, подсветка отличий.
- **5.4** `suites/monkey/`: случайные клики и ввод часами, ловля падений и ошибок консоли.
- **5.5** `suites/flaky/`: многократный перезапуск тестов, пометка нестабильных, повторяемость «N из M».
- **5.6** `orchestrator/bisect.py`: для нового падения автоматический `git bisect` по коммитам за день, виновный коммит в отчёт.
- **5.7** Группировка похожих ошибок, схлопывание дубликатов, отдельный список «новое за ночь».
- **Готово когда:** отчёт содержит тренды, повторяемость и виновный коммит для искусственно внесённого падения.

### ЭТАП 6. Локальный ИИ (внедряй по подэтапам, не всё сразу)

Сначала **6A: только сортировка и диагностика**, затем **6B: исправления**.

- **6.1** `ai/llm_client.py` (вместо ollama_client): клиент **OpenAI-совместимого API**. Адрес локального агента: **`http://localhost:1235/v1`** — запиши в `config/ai.yaml` как `base_url` (не хардкодь). Используй `GET {base_url}/models` для проверки доступности и списка моделей и `POST {base_url}/chat/completions` для запросов (`model`, `messages`, `temperature` низкая, `max_tokens`, по возможности `response_format` для JSON). Ключ API не нужен (если потребуется — поле в конфиге). Модель берётся из `ai.yaml` (если пусто — первая из `/models`). Таймаут, повторы, логирование всех запросов и ответов. Агент недоступен → профиль `no-ai`, не падать. Проверка: тест на заглушке + ручной вызов `GET http://localhost:1235/v1/models` (если агент запущен, покажи ответ).
- **6.2** `ai/schemas.py`: Pydantic-схемы ответов по ролям. Ответ ИИ — **только JSON по схеме**; не прошёл — повторный запрос с указанием, что не так (максимум N повторов).
- **6.3** `ai/roles/` и `ai/prompts/`: четыре роли, **один запрос = одна роль**: *сортировщик* (группировка, дубликаты, краткое описание), *диагност* (вероятная причина по логам), *исправитель* (правка), *рецензент* (проверка на подгонку под тест).
- **6.4** `ai/context.py`: скрипт сам собирает контекст — по стектрейсу и поиску по коду находит нужные функции, добавляет краткую карту проекта (модули и их назначение), укладывается в бюджет контекста; большие задачи дробит. Каждый запрос самодостаточен.
- **6.5** `ai/loop.py` (6A): для каждой проблемы карточка со стадиями «новая → диагностика → (исправление → проверка) → готово / передано мощному ИИ»; состояние в SQLite; продолжение с той же стадии после сбоя.
- **6.6** (6B) Исправитель возвращает пары «найти → заменить»; скрипт применяет их в **отдельной git-ветке/копии**; запускает тесты; провал → новый запрос с итогами прошлых попыток; лимит попыток (по умолчанию 5) и времени; исчерпан → `needs_big_ai`.
- **6.7** Защиты (каждая — с тестом): хеши файлов тестов до/после (изменены → правка отклонена); ИИ не имеет доступа к боевому сайту/БД/паролям; ИИ ничего не запускает; запрещены правки вне разрешённых типов (многомодульные, БД, безопасность, архитектура → только описание в `needs_big_ai`).
- **6.8** Критерии записи в `fix_history` (все обязательны): упавший тест проходит; остальные проходят; тесты не удалены и не ослаблены; производительность не хуже порога; рецензент не нашёл подгонки; повторный полный прогон на чистом стенде зелёный. Запись: проблема и тест, причина, `.patch` и описание, затронутые файлы и сценарии, подтверждение проверок, хеш коммита, дата, число попыток, модель. Файлы: `fix_history.md`, `fix_history.json`, `*.patch`.
- **6.9** `ai/kb.py`: база знаний успешных исправлений; для похожей ошибки скрипт подкладывает прошлое решение как пример.
- **6.10** Все тесты ИИ-цикла — на **заглушке модели** (фейковый клиент возвращает заранее заданные ответы), чтобы тестировать без GPU.
- **Готово когда:** на искусственно внесённой ошибке цикл даёт проверенное исправление в ветке; попытка «ослабить тест» отклоняется; неисправимая задача уходит в `needs_big_ai` с историей попыток.

## 5. Как работать с каждым шагом (шаблон)

1. Назови номер шага.
2. Напиши, какие файлы создашь/изменишь.
3. Сделай изменение.
4. Запусти проверку шага и `uv run pytest nightshift/tests -q`.
5. Покажи вывод. Если красное — исправь код, повтори.
6. Отметь шаг в `PROGRESS.md` (дата, что сделано, результат проверки).
7. Переходи к следующему.

## 6. Чего делать нельзя (типичные ошибки малых моделей)

- Не пиши «готово», не запустив проверку.
- Не выдумывай пути, имена файлов и команды проверяемого сайта — бери из `DISCOVERY.md`; нет данных — спроси или запиши допущение.
- Не переписывай файлы целиком ради мелкой правки — меняй точечно.
- Не добавляй зависимости без необходимости; каждую новую отметь в `DECISIONS.md`.
- Не используй `shell=True`, `os.system`, склейку путей строками, чтение файлов без `encoding="utf-8"`.
- Не храни и не печатай пароли/ключи.
- Не трогай боевые системы; не отключай изоляцию «для скорости».
- Не удаляй тесты и не ослабляй проверки.
- Не пропускай этапы и не меняй их порядок: сначала стенд и регрессия с отчётом, потом остальное, ИИ — последним.
- Не делай несколько шагов подряд без проверки.

## 7. Финальная проверка (когда все этапы закончены)

Пройди чек-лист и для каждого пункта покажи доказательство (команда + вывод):
- [ ] Приложение запускается одной кнопкой; наборы запускаются из интерфейса.
- [ ] Ночной прогон по расписанию работает без человека.
- [ ] После прогона есть `report.json` + `report.html` в описанном формате.
- [ ] История прогонов и история починки доступны в приложении.
- [ ] Папка `handoff/` целиком передаётся ИИ (есть `README_FOR_AI.md`).
- [ ] Тест изоляции зелёный; запись в боевые системы невозможна.
- [ ] Прогон переживает принудительное прерывание.
- [ ] Исправление ИИ без прохождения всех проверок в `fix_history` не попадает.
- [ ] `nightshift.exe` работает на чистой Windows.
Если пункт не выполнен — запиши причину в `BLOCKERS.md` и сообщи владельцу прямо, без приукрашивания.
