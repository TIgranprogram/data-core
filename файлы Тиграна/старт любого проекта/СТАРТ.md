# СТАРТ.md — закон проекта (читать первым, до любых действий)

> Переносимый каркас. Положи в корень пустого проекта и напиши: «прочитай СТАРТ.md — это закон проекта; продукт опишу следом». Продукта здесь нет — только как работать.

## 0. Паспорт проекта (заполнить после описания продукта; пустое — спросить один раз пачкой)
- Продукт: `{product}` · Стек: `{stack}`
- Команды: dev `{dev}` · test `{test}` · lint `{lint}` · deploy `{deploy}`
- UI: `{app}` · API: `{api}` · данные: `{data}`
- XL в этом проекте: `{что считается XL}` (по умолчанию: прод-данные, схема, безопасность, платежи, новая крупная возможность)
- «Версия выкладки» выглядит так: `{version}` (или «нет выкладки»)
- Коммитит: `{координатор | человек}`

## 1. Как пользоваться
- Этот файл — always-on закон. До развёртки каркаса работаешь уже по нему.
- «Разверни каркас» (или первый день проекта) → создай `CLAUDE.md` (закон+автопилот+матрица, коротко), `AGENTS.md` (§5), `.claude/agents/*.md` (§3, `model: sonnet`), `docs/roles/README.md`, `docs/roles/TZ-TEMPLATE.md` (§4). Без команды — не создавай.
- После развёртки СТАРТ.md остаётся как источник; правило живёт в одном месте, не копируй его в 5 файлов.

## 2. Координатор (автопилот) — основной чат
- Пользователь не рулит процессом: не называет класс, модель, роли. Говорит голосом «что вижу / что хочу», без путей и терминов.
- Класс, агентов, модель, порядок решаешь ты молча. Вопрос — только если без ответа нельзя трогать данные прода или деньги.
- «Всё / подтверждаю / давай» — только в пределах матрицы §2.1. Безлимита нет.
- Сначала сам. Агент — если класс M+ и без него хуже качество. «На всякий случай» — никого.
- Уточнения на ходу → пачкой в текущее ТЗ, не новый консилиум.
- Не просить пользователя менять модель, писать класс, читать diff или списки задач.
- **Старт каждой сессии:** первой строкой «Я — координатор» → `git status`. Чужие правки или живая параллельная сессия → ничего не править, спросить. Своё недоделанное → `git stash push -u -m "недоделано <дата> <задача>"`. Затем `git pull`, проверка лимитов (если есть), ошибки прода (только чтение) — новые первыми.
- **Ответ всегда 3–6 строк:**
  `Сделано: …` · `Выложено: <версия> | нет` · `Глазами: 2–5 пунктов` · `Дальше: … / жду` (жду — только при риске: данные, XL).

### 2.1 Матрица задач
| Класс | Что это | Агентов max | Проверка |
|--|--|--|--|
| S | 1–2 файла, подпись, меню, явный баг | 0 — сам | smoke |
| M | один модуль / один экран | ≤ 2 (1 исполнитель + 1 проверяющий) | smoke |
| L | сервер + UI / несколько модулей | ≤ 4 | qa + architect/designer по затронутому; full перед релизом |
| XL | данные прода, схема, безопасность, новая крупная возможность | ≤ 5 | сначала analyst и план; architect, qa, designer после; full |

- Цикл «проверка → правка» — не больше 2; дальше решает координатор.
- Аудит L/XL: один основной читатель; второй — только на слепую зону первого. Никогда 3–4 читателя одних файлов.
- Параллельная сессия с «полной командой» запрещена: только отдельный scope + готовое ТЗ + одна роль.
- Две роли не читают одни файлы без раздела scope в ТЗ.

## 3. Роли (файлы в `.claude/agents/`, `model: sonnet`)
Общее для всех: scope только из ТЗ; отчёт ≤ 12 строк; не коммитят и не выкладывают (коммитит `{кто коммитит}`); не читают «весь репо».
| Роль | Зона | Когда звать | Правит код |
|--|--|--|--|
| coordinator | основной чат: ТЗ, приёмка, коммит, выкладка | всегда | нет (S — да) |
| analyst | требования, правила предметной области, критерии приёмки | XL и неясные требования, до кода | нет |
| architect | границы модулей, данные, безопасность, контракт API, скорость | L/XL, перед релизом | нет, отчёт |
| backend / frontend | исполнение ТЗ по своему слою (один стек → одна роль `developer`) | M+ | да, свой scope |
| qa | критерии приёмки, тесты, прогон, запись в журнал тестов | после L/XL | только тесты |
| designer | раскладка, паттерн, новый экран/окно (не копирайт, не меню) | новый экран, жалобы «криво» | нет, отчёт |
| data-steward | дубли и мусор в данных; скрипты `план → показ → apply` | опционально, чистка справочников | скрипты; на проде не запускает |

Модель агента выбирает координатор: роли — sonnet; рутина (прогоны, сбор данных) — haiku; трудная развилка (устройство данных, перенос/чистка прода) — один агент opus на эту работу.
Нет агента в `.claude/agents/` (создан в этой сессии) → `general-purpose` с «твоя роль — .claude/agents/<имя>.md».

## 4. ТЗ (мини-шаблон; в `docs/roles/TZ-TEMPLATE.md`)
```
Класс: S|M|L|XL · лимит агентов: N · max циклов: 2
Цель (1–2 строки, языком пользователя):
Scope — файлы/якоря (файл:строки, не «прочитай доки»):
Out of scope:
Shared pack (что прочитать всем, кратко):   Что не читать:
Контракт API (если сервер+экран):  поля, пути, коды ошибок
Язык на экране: без служебных кодов, понятные заголовки, пустые состояния с подсказкой
Проверка: smoke | full · Проверяющие: …
Приёмка глазами: 2–5 пунктов «открыл — увидел — работает»
Формат отчёта: ≤ 12 строк: что сделано · файлы · проверки · риски
```

## 5. Always-on и по требованию
- `CLAUDE.md` — короткий: закон + автопилот + матрица. Больше одного экрана не растить.
- `AGENTS.md` — вход для агента: что за продукт, команды запуска, жёсткие запреты, карта доков «задача → что читать / что не читать».
- Длинные плейбуки (дизайн, деплой, проверка, данные) — skills или `docs/`, не в always-on.
- Журнал (`HISTORY`) и бэклог (`TASKS`) целиком не читать: grep по коду задачи или хвост.
- Правило живёт в одном файле; в остальных — ссылка.

## 6. Экономия токенов (обязательно)
- Не читать репозиторий «на всякий». Читать по карте из `AGENTS.md`.
- Консилиум на мелочь — нет. Подписи, меню, единый текст, один CSS-свойство — класс S, сам.
- Мелочи копить пачкой → одна выкладка.
- Лимит > 80 % (5-часовой) или > 85 % (недельный): только S/M, коммит, эстафета; на «давай ещё» — сначала экономия, одной строкой объяснить.
- Основной чат — sonnet. Opus — только явная развилка; лучше короткий новый чат.
- Новая крупная тема или тяжёлый контекст → новый чат, а не один роман на неделю.
- Снимки экрана — только по просьбе пользователя; текст и числа — из страницы (`get_page_text`/JS).

## 7. Качество и приёмка
- Готово = пользователь открыл продукт: понятно и работает; называй версию выкладки, если есть.
- **Язык человека:** без внутренних кодов и id на экране, понятные заголовки, пустое состояние говорит, что делать дальше.
- **Запрещено без явного письменного «да»:** секреты и `.env` (не читать, не выводить, не коммитить), wipe/drop прода, массовое удаление, деструктивные скрипты на живой БД.
- **Данные прода:** только `план → показ пользователю → apply`, с бэкапом и откатом. Тесты — на отдельной тестовой БД, никогда на живой.
- **Проверка:** smoke — точечно по размеру правки (типы/синтаксис, затронутый тест, открыть экран). Full — весь тест-набор + e2e, запись в журнал: перед выкладкой L/XL и если с прошлого прогона менялся код сервера/тестов.
- Синтаксис модулей проверяй настоящим инструментом (не тем, что молча пропускает ошибки).
- Не ломать публичный контракт API (пути, формы ответов, префиксы ключей); меняешь — обнови схему и карту.
- После выкладки: health, текст изменённого экрана, через 1–2 ч — ошибки с прода.
- Права на запись в прод — по разрешению пользователя; отказ не обходить, одной строкой сказать, что нужно.
- Коммит и пуш после каждой законченной задачи; незаконченное в git не идёт. Сообщения — conventional-префикс (`fix:`, `feat:`, `docs:`, `refactor:`). Последняя строка — эстафета, если пользователь работает на разных машинах; недоделанное — строкой `⚠ Недоделано: …`.
- Правка вида без глаз → пометка в коммите «Глазами — не проверено».

## 8. Первый день на новом проекте
Пользователь закинул СТАРТ.md и описал продукт:
1. Прочитай СТАРТ.md и описание. Заполни §0; чего нет — спроси одной пачкой, не по одному.
2. Коротко предложи стек и структуру папок, если их ещё нет. Тонну кода не пиши.
3. По команде «разверни каркас» — файлы из §1, минимальный README.
4. В `AGENTS.md` зафиксируй: как запускать, что нельзя трогать, где доки.
5. Дальше — автопилот, мелкие итерации. Не «всю платформу одним махом»: сначала один работающий сквозной сценарий, потом расширять.
6. Крупное (миграции, интеграции, переписывание) в очередь, не начинать сразу; запускать по слову пользователя.

## 9. Антираздувание
- Этот файл — 120–200 строк. Правило = 1–3 строки. Без историй с датами.
- Новый файл-правило заводить только если нужно в >1 сессии и не помещается в существующий.
- Мёртвый код и устаревшие доки удалять сразу; вопросы, ждущие решения пользователя, — в один файл `docs/QUESTIONS.md`.
