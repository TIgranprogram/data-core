## 2. Логика номеров и надписей (как сделано сейчас)
- **Паспорт №** — сквозной (224, 225…).
- **Гарантийный талон** = `<год><месяц без нуля>-<№ паспорта>`: `20258-224` (август 2025), `202610-548` (октябрь 2026). Совпадает с датой и номером во **всех 326** строках. Нюанс: месяц без ведущего нуля (`20269` и `202610` сортируются неверно).
- **Номер изделия** (серийный) = № паспорта + 2030 (№224→2254) для 238 строк; для № 461 → +2029; для № 463 → +2028. **Дубль: №461, 462, 463 имеют один номер изделия `2491`.**
- **Описание** строится по шаблону: «<Наименование> (в дальнейшем именуемое «Изделие»), изготовленное из <Материалы>…», далее «Установка» (типовая фраза, 82 варианта) и «Назначение» (177 вариантов).
- **Артикул** — внутренний код `N_N` / `N_N_N` (188+56 строк), 16 — просто число, 64 пусты; смысл кода не описан (категория_подкатегория?) — уточнить.

## 4. Как это ляжет на нашу базу
Есть модуль `product-passport` (коллекция `productpassports`, из kppdf): поля `passportNumber`, `productCode`, `warrantyCode`, `date`, `name`, `category`, `article`, `height/length/width/weight`, `description`, `installationSite`, `supplier`, `photo`, `isActive`, `deletedAt`; **`productId` обязателен и уникален** (1 паспорт на изделие); эндпоинты `/passports`, `/products/:id/passport`; своего раздела в приложении и PDF нет.

Сопоставление:
| Лист «Данные» | Куда | Статус |
|--|--|--|
| Паспорт№ | `passportNumber` | ✅ есть |
| Дата | `date` | ✅ есть |
| Гарантийный талон | `warrantyCode` | ✅ есть |
| Номер изделия | `productCode` | ✅ есть (нужна уникальность и счётчик) |
| Артикул | `article` | ✅ (уточнить смысл кода) |
| Наименование, Категория | `name`, `category` | ✅ (категория → из справочника/каталога) |
| Высота, Длина, Ширина, Вес | `height/length/width/weight` | ✅ (мм, кг) |
| Описание | `description` | ✅ (сделать сборку из частей) |
| **Материалы** | — | ❌ нужно поле `materials` |

| **Назначение** | — | ❌ нужно поле `purpose` |

| Поставщик | `supplier` (текст) | ⚠ лучше `supplierOrgId` → наши компании (`isOurCompany`: СпортИнЮг, СпортСтройЮг, СпортСет) |

| Ссылка на PDF | — | ❌ `pdfFileId` / дата последней выдачи |

**Главное расхождение:** `productId` unique — паспорт здесь **экземпляр** (серийный номер, заказ, объект, дата), а изделие — **модель** (≈243 модели на 326 паспортов). Нужно: убрать `unique` у `productId`, сделать его необязательным (`productId` → модель из каталога/«Продукции», если найдена по артикулу/названию), либо вести паспорт независимо от каталога. Миграция уникального индекса на живой базе (kppdf читает те же коллекции!) — только согласованно с kppdf (T21 в TASKS).

## 5. Предложение по разделу «Паспорта» в приложении
- Раздел в меню (рядом с «Заказы»/«Продукция»): список (номер, дата, наименование, категория, заказчик/объект, поставщик, талон), фильтры (год, месяц, категория, поставщик, заказчик, «без фото», «неполные»), поиск, массовый ввод по общему компоненту (МВ), «Требуют заполнения».
- Карточка паспорта: поля, фото по видам (общий вид, габариты, зона, монтаж) — вставка/перетаскивание как в складе, предпросмотр листа, **«Скачать PDF»**, «Копия паспорта» (для той же модели), «Выдан/отправлен» (дата).
- Новый паспорт: выбор модели из каталога (подставляет габариты, вес, материалы, описание, фото) → указать заказчика/объект/дату → номера присваивает **сервер** (счётчик `Паспорт №`, талон по правилу, номер изделия из своего счётчика, уникальные).
- PDF: серверная сборка листа A4 по макету (макета-текста в Google Docs нет — только картинка; нужен образец готового PDF), кириллические шрифты в `backend/pwa/fonts`, фото по видам; «Скачать PDF» одного и пакетом (ZIP) по фильтру.
- Права: смотреть — менеджер и выше; создавать/менять — директор/админ (как деньги/справочники); все изменения — в «Историю изменений».

## 6. Риски
- Паспорта **уже выданы** (бумага/PDF): нельзя молча менять номера, талоны, даты.
- Общая база с kppdf: схема `productpassports` — менять синхронно (T21).
- Фото: основной объём данных (файл 33 МБ) — может оказаться не в выгрузке; без них PDF неполные.
- Макет паспорта не восстановим из таблицы — нужен образец PDF.

**Выводы для модели и PDF**
- Нужна **типовая часть** (разделы 3–7, таблицы 4–6) как редактируемый **шаблон текста** в приложении («Шаблон паспорта», версия, дата) — не в каждом паспорте.
- Нужна **комплектность** (`bom[]`: позиция, обозначение, наименование, кол-во, ед.) — отдельное поле, по умолчанию «Изделие в сборе».
- Реквизиты шапки берутся из **организации-поставщика** (ИНН, КПП, телефон, e-mail, торговая марка, ФИО директора, **печать+подпись** как изображение организации). Печать и подпись — загружаемые изображения организации (места загрузки в карточке организации); PDF скачивается **в двух вариантах: с печатью и подписью и без**.
- Картинки: общий вид (титул), габариты (до 4 видов), зона безопасности, монтаж (2); **общий вид в таблице лежит картинкой в ячейках `Данные!E`** (видно на скриншоте таблицы — это «Фото_ОбщийВид_ID», фактически вставленные изображения), остальные — нет.
- Вывод PDF — **два режима**: (а) постраничный A5 (10 стр.) для просмотра; (б) «в печать» — спуск 2 стр. на лист A4 альбомной для двусторонней печати буклетом (как в образце).
- Шрифт: решение пользователя — наиболее похожий на паспорт (ГОСТ-подобный, свободный, с кириллицей); водяной знак с названием компании.
