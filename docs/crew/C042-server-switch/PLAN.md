# C042-A — ПЛАН

## Целевая схема
Active-passive, ручная кнопка: VPS nginx (dc-switch home|office, уже готов) ведёт на главный; запасной держит копию не старше 15 мин и роль standby. Реплика (replica set) и автомат — не сейчас: 2 узла без третьего голоса (VPS 539 МБ не тянет арбитра), макет дал потерю 30 % записей при обрыве + смерти главного; нужны WireGuard, rs0 у CRM, 2 недели замеров (TZ HA-TWO-SERVERS Э0–Э6).

## Механизм синхронизации (Mongo 4.4, 2 площадки, 1 ядро на VM)
Выбор: уже написанное «Обновить» (kind=refresh: короткая пауза записи, дамп, mongorestore --drop на соседе, фото rsync, код) — по расписанию 15 мин, запуск мостом на самом главном (cron), без домашнего ПК. База около 21 МБ: дамп секунды, нагрузка малая. Потеря при внезапной смерти главного — до 15 мин; при плановом переключении 0 (свежий дамп под readonly до 10 мин).
Почему не oplog-репликация: нет третьего голоса, чужой риск для CRM и 1 ядра; отдельный проект после наблюдений.

## Кнопка «Переключиться» (админка -> Серверы)
Шаги (реализованы в switch-watch.sh): проверки соседа (hostname, HA_SELF, standby, копия, мост) -> фото заранее -> readonly -> дамп -> восстановление на соседе -> сверка 5 коллекций и health -> dc-switch -> этот сервер standby+readonly. Ошибка до смены домена = откат, домен не тронут.
Добавить: версии кода обоих на экране и запрет при расхождении; крупно «сейчас главный: X»; журнал шагов; обратная кнопка там же (есть).
Откат: та же кнопка; nginx — kppdf-proxy.bak-switch-<время> на VPS; три страховочных дампа на соседе.
