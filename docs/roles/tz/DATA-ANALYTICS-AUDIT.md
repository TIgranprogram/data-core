# Аудит данных для аналитики (цены, себестоимость, прогноз) — аналитик, 2026-10-28

Класс XL. Только требования; «как технически» — архитектор. Источники — схемы в `backend/src/modules/*`.

## 1. История цен и поставщиков — решение
**Уже есть почти готовое:** `supplieritems` (supply/supplier-item.schema.ts): `supplierId`, `materialId`, `unit`, `price`/`priceDate`, массив `priceHistory[{price,date,source: excel|request|stock|manual}]`. Это «позиция поставщика» с историей.
**Рекомендация:** не новая коллекция, а одна точка записи факта цены — отдельная плоская коллекция `materialprices` (событие = строка):
`materialId, supplierId, supplierItemId?, price (за ед., без НДС), vatRate, priceWithVat, unit, qty, currency (RUB), date (дата счёта), source (invoice|request|manual|excel), invoiceId?, requestId?, salesOrderId?, createdBy`.
Почему не только `priceHistory` внутри `supplieritems`: массив в документе не агрегируется удобно по году/поставщику/материалу, растёт без предела, нет ссылки на счёт/заявку. Почему не выводить из заявок: в заявке цена — `priceHint`/`lineTotal` (подсказка, правится, нет НДС отдельно), заявки общие с CRM и меняются задним числом — истории правок нет.
`priceHistory` в `supplieritems` оставить (CRM/каталог), дописывать параллельно.
**Когда пишется строка:** счёт переходит в «выставлен» (цена из счёта, деление суммы по строкам уже есть) и повторно при «оплачен», если цена изменилась. Ручная правка менеджером цены/поставщика в заявке до счёта — `source: request`. Правка не удаляет прошлое — новая строка.
**«Последняя цена» материала:** `materials.pricePerUnit` + новые `lastPrice, lastPriceDate, lastSupplierId` (только дополнение схемы) = последняя строка `materialprices` по `date` из источника invoice (иначе request). Обновлять при записи строки, не пересчётом. При создании заявки подставлять `lastSupplierId` и цену; менеджер может сменить.

## 2. Что собирается / чего не хватает
| Сущность | Есть | Не хватает |
|--|--|--|
| Материал (`materials`) | `unit`, `pricePerUnit`, `supplierId` (один), `composition` | дата цены, НДС цены, валюта, последний поставщик; несколько поставщиков — только через `supplieritems` |
| Заявка (`supplyrequests`) | `qty`, `unit`, `priceHint`, `lineTotal`, `supplierId`, `invoiceNo`, `invoiceDate`, `requestDate`, `supplierOrderDate`, `paidAt`, `salesOrderId/LineId`, `orderId`, `costCenter/costObject`, `invoiceId` | цена за ед. без НДС и ставка НДС раздельно; дата получения (факт); история правок полей |
| Счёт (`supplyinvoices`) | `no`, `date`, `amount`, `supplierId`, `payerCompanyId`, `status`, `paidAt`, файлы | `vatRate`/сумма НДС, `currency`, `dueDate` (срок оплаты), частичные оплаты, условия (предоплата %/отсрочка) |
| Поступление (`stockmovements`) | движение, `salesOrderId/LineId`, `productId`, отмена | цена прихода (за ед.), ссылка на `requestId`/`invoiceId` — без этого нет фактической стоимости партии |
| Заказ (`salesorders`) | строки, связи с заявками/резервами | плановая/фактическая себестоимость строки (снимок) — не проверено детально |
| Изделие и состав | `composition` (материалы + вложенные изделия), себестоимость «по последним закупкам» в карточке | трудоёмкость (нормо-часы / виды работ `work-type`) в составе; версия состава на момент заказа |
| Доходы/расходы (`incomes`, finance) | платежи `payments[]`, cashflow, forecast | ссылка расхода на счёт поставщика (`invoiceId`) и на заказ — проверить у архитектора |
| ФОТ (`payroll`) | расчёт (payroll-calc) | привязка часов/сдельщины к заказу или изделию |

## 3. Себестоимость — недостающие связи
1. Приход на склад → цена за ед. + `invoiceId/requestId` (факт закупки партии).
2. Списание в производство → `salesOrderId/LineId` (есть) + цена списания (средняя или по партии — решение пользователя, вопрос 1).
3. Труд: в составе изделия — норма работ (`workTypeId`, часы); в ФОТ — факт по заказу.
4. Снимок состава и цен в строке заказа при запуске (иначе себестоимость «плывёт» при правке состава).
Без 1–2 считаем только плановую себестоимость (по последним ценам) — это уже работает в карточке изделия.

## 4. Платёжный календарь и прогноз
Есть: `paymentTermDays` у контрагента/организации, `paidAt` у счёта, модуль forecast.
Не хватает: `dueDate` в счёте (по умолчанию `date + paymentTermDays` поставщика), условия (предоплата % / постоплата), частичные оплаты счёта (`payments[]` как в incomes), ожидаемая дата поступления денег от клиента по заказу (график оплат заказа).

## 5. Порядок работ
1. **Дешёво и самое полезное:** коллекция `materialprices` + запись строки при «выставлен/оплачен» счёта и правке цены в заявке; `lastPrice/lastSupplierId` в материале; подстановка в новую заявку. Разовая заливка истории из оплаченных заявок и `supplieritems.priceHistory`.
2. Счёт: `vatRate`, `dueDate` (авто из `paymentTermDays`), `currency` — прогноз календаря сразу точнее.
3. Приход на склад: цена за ед. + `invoiceId/requestId`.
4. Труд в составе изделия (вид работ, часы) и снимок себестоимости в строке заказа.
5. Отчёты: рост цен по материалу, закупки у поставщика за год, себестоимость заказа; вход для выводов ИИ.

## Вопросы пользователю (записать в QUESTIONS.md)
1. Цена в истории и себестоимости — без НДС или с НДС? **По умолчанию:** храним обе, считаем без НДС.
2. Списание со склада в себестоимость — по средней цене или по цене конкретной закупки? **По умолчанию:** средняя (проще, стандарт малого предприятия).

Риски: общие с CRM коллекции — только новые поля; `supplieritems` пишет CRM-каталог — не ломать формат `priceHistory`. Mongo 4.4 — без `$setWindowFields` в отчётах.
