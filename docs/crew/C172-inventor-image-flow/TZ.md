# C172 — единый путь рисунков из Inventor

**Зачем:** владелец отправил новые рисунки из Inventor/iLogic, но паспорт №616 показывает прежний чертёж. Поручение: «наведи грамотно порядок с путями рисунков»; уточнение: «логик должен обновить все если я отправляю через инвентор».
**Результат (Ц3):** одна отправка обновляет применимые рисунки и подтверждённые характеристики без повторной ручной загрузки PNG. Прежние файлы и история сохраняются.
**Класс:** L · **Max agents:** 4 · **Reviewers:** architect, qa, designer при UI · **Max review loops:** 2.
**Проверки:** целевые typecheck/unit/e2e, заполненный desktop-сценарий; full перед выпуском. Выкладка и запись на прод этим ТЗ не поручены.

## Глубже
- Сырьё: снимки владельца — новый монтажный чертёж и старые габариты в PDF №616. API недоступен (curl7), статус и изделие №616 ещё не установлены.
- Метод: проследить photoId и kind от экспорта до PDF, установить владельца каждого значения и точку фиксации; проверять повтор, частичный сбой, конкурентную правку и историю.
- Внешний судья: регрессии на разных старых/новых photoId, проверка реального PDF на копии и сохранности предыдущей редакции.
- Планка: одна отправка, ноль ручных переносов файлов; повтор без новых данных не создаёт лишних редакций.

## Серверный контракт (после первичного архитектурного разбора)
- `GET /api/products/:productId/passport-import-context` → `{contextToken:string}`: отпечаток актуальных чисел/версии изделия, трёх целевых связей и версий целевых паспортов. Никаких секретов.
- `POST /api/products/:productId/passport-import` → тело `{contextToken,images:[{kind,photoId}],confirmed:{dimensions?:{length,width,height,unit:'мм'},weightKg?:number,foundationDepth?:number}}`.
- `images` — ровно три уникальных вида overview/dimensions/foundation; локальные живые PNG, содержимое проверяет сервер. `confirmed` — только одобренные числовые поля; отказ от чисел ничего не очищает.
- Ответ `{status:'applied'|'unchanged',updatedKinds:string[],confirmedFields:string[],issued:[{id,number,fromRevision,toRevision}],drafts:string[],skipped:[{id,reason}],warnings:string[]}`. Статус 200. Данные, используемые iLogic, с точными именами закрепить в BACKEND-REPORT.
- После загрузки файлов — **одна транзакция**: CAS контекста, замена только трёх passport-kind, числа изделия, синхронизация паспортов того же productId (не чужих изделий). Session через чтения/пересборку/запись. Числа приводятся к полям паспорта существующим преобразованием единиц.
- Для issued прежние затронутые поля + images/textSnapshot/printSnapshot в revisions; +revision только при реальном изменении; прочие виды/ручные тексты/номер/связи заказа сохраняются. Отдельно учесть legacy без status и presentationVersion.
- annulled/deleted не менять; printFile (прикреплённый готовый PDF) не перерисовывать, явно вернуть skipped+warning. Автоматически удалять printFile запрещено.
- Дедупликация по серверному содержимому PNG, а не случайным photoId: если такой же файл уже используется, сохранить прежний photoId; новый request с теми же байтами/числами не создаёт revision. Повтор запроса после потерянного ответа с уже применёнными данными → unchanged, даже если contextToken устарел. Новых receipt-коллекций/обязательных индексов ради этой задачи не добавлять; достаточно проверки фактического результата и существующего Idempotency-Key при необходимости.
- Ошибка/конфликт целевого паспорта откатывает весь commit; сообщение указывает проблемный паспорт. Не подавлять readiness/сбой пересборки. Ограничение размера набора — явный отказ до изменений, без незаметного limit.
- Загрузки файлов вне транзакции; не удалять файлы при rollback (они могут использоваться в истории). Защитить участвующие файлы от конкурентного удаления существующим протоколом sourceProtected/sourceDeleting.

## Уточнение: закрытый заказ и полный архив
Владелец потребовал: в работе паспорт обновляется редакцией; полностью закрытый и оплаченный заказ хранится неизменно. Исследование — ARCHIVE-RULES.md. Этап closed уже существует, но ещё не является серверным неизменяемым архивом и не проверяет оплату.
- C172 не внедряет всю систему архива. В импорте **консервативно пропускаются все паспорта закрытых договоров** (`order_closed`), даже при недоплате; это временная защита, не признание договора оплаченным.
- Проверка связей и закрытия — внутри транзакции; сериализовать с закрытием/удалением существующим passportGuard. Потерянные/противоречивые связи — отдельный безопасный пропуск с предупреждением. Без заказа — обновить с явной пометкой.
- Полный архив всех документов/операций, проверка оплаты и специальное повторное открытие — отдельный этап с критериями в ARCHIVE-RULES.md и очереди TASKS. Физически переносить записи в отдельную коллекцию не требуется.

## Дополнение после первого ревью
Архитектор обнаружил phantom-вставку: ручная привязка productphotos и создание нового паспорта не писали общий документ изделия, поэтому могли не попасть в snapshot импорта. Backend разрешены точечные дополнительные изменения `modules/product-photo/product-photo.service.ts` и существующих create/issue путей паспорта: целевые passport-записи и импорт должны сериализоваться транзакционной записью общего products guard (без новой схемы/индекса). QA — регрессии state-read → конкурентные attach/create. Конкурентный импорт не должен успешно оставить дубли одного вида либо паспорт на прежних входах.
