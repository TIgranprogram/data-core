## Что уже подходит

`salesorders` — клиентские договоры; `incomes` — их19позиций с количеством, единицей, ценой и связью orderId; производственный заказ — группировка нескольких договоров по productionNo, самостоятельной сущности ProductionOrder нет (`production-orders.ts:1`, controller:13). Сумма обязательств5521400₽ считается один раз по позициям; связанные счета не являются дополнительными доходами. Три пары доказаны источником, КП3131000₽ отдельный, покупатели видимые копии договоров не подписали.

Платёжные даты и частичные суммы для факта существуют в Income.payments. `incomePayments` также трактует legacy paidDate как полную оплату (`income.schema.ts:130`), поэтому заполнять paidDate по дате документа опасно. Текущие источники не разрешают ни одного POSTpayments/статусаpaid. Факт отражается в финансах по исходной позиции/договору; план/цена позиции не равны банковскому поступлению.

## Можно сделать до доработки

Сверить существующие наши компании/контрагентов/договоры и сохранить готовые payload/реестр вне БД. Создание заголовков/позиций текущим API возможно технически, но не решает полную задачу и принудительно создаёт производственные группы; выбор группы45/46 пока неизвестен. Не объявлять такой импорт завершённым и не загружать7PDF бесхозно. Позиционное photoIds может хранить PDF технически, но не даёт тип/приоритет/контрактную принадлежность, а права фото допускают user (`photos.controller.ts:35`); правовой комплект требует проверки доступа и удаления связанных файлов.
