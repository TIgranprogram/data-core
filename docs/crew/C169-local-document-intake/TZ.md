## Конвейер и файлы
1. Статусы: `Inbox` («Входящие») → `Processing` («Разбираются») → `Ready` («Готово») либо `Question` («Сомнительные»).
2. Одна выбранная корневая папка/том; переход — атомарное перемещение оригинала без копий и перезаписи одноимённого файла. Незавершённую загрузку/открытый файл не захватывать.
3. До обработки вычислить SHA-256 исходных байтов (`originalSHA`) и устойчивый UID; UID не зависит от пути/имени/перезапуска. Переименование не создаёт новую операцию; содержимое после захвата неизменно.
4. Журнал хранит UID/SHA, пути и переходы, версии extractor/model/rules, proposal, решения, операции API и доказательства; секреты в журнал не попадают.
5. `Ready` только после свежего API-proof: нужные сущности/строки/суммы/источник/связи сохранены либо доказан существующий дубль с ID и SHA/бизнес-ключом. Успешный ответ модели/HTTP сам по себе недостаточен.
6. Неизвестный тип, конфликт, обязательное недостающее поле или неоднозначный дубль → `Question` с коротким объяснением и следующим действием. Сбой связи → приостановка, а не «Готово».
7. Сбой между записью API, журналом и перемещением разбирается при возобновлении по UID/receipt/read-proof. Нельзя вслепую повторять POST, upload, оплату или переименовывать поверх файла.

## Предметные правила
8. Сначала определить направление/тип: счёт поставщика, договор покупателя, КП, счёт покупателю, акт/связанный документ; неизвестное не превращать в закупку.
9. Использовать существующие сущности: supplyinvoices/заявки для закупок; SalesOrder + Income для договора/строк; CommercialOffer для КП; типизированный комплект документов C164 для клиентских счетов/актов. Новую параллельную таблицу учёта не заводить.
10. Дубль проверять API по SHA и нормализованному бизнес-ключу (наша фирма/контрагент/тип/полный номер/дата/редакция), включая удалённые записи. Совпадение имени файла или номера недостаточно.
11. Изменённая версия счёта — новая редакция с отличиями и связью с прежней, не дубль и не второй расход. Неоднозначность требует review; оригинал/история не заменяются.
12. Договор, КП, счёт и акт связывать по доказанному комплекту; сохранять исходные строки и расхождения. Отдельный документ не создаёт повторный доход/заказ/расход. Связь КП с договором не означает принятия/оплаты.
13. Неизвестное оставлять пустым и создавать manager issue, если контракт допускает черновик. Тогда `Ready` означает «учтено», а отчёт отдельно показывает незакрытые вопросы; блокирующее неизвестное остаётся в `Question`.
14. Даты документа/события исторические; createdAt — время импорта. «Вчера», дата файла и дата обработки не заменяют дату оплаты/приёмки.
15. Счёт/акт не доказывают платёж или складскую приёмку. Автоматический факт допустим только по явному источнику, проверенному правилу и отдельному разрешённому маршруту; иначе пусто/issue. Подтверждение оплаты без даты — только по действующему C165, без фиктивной проводки.
16. Не создавать каталог, производство, подписи, приёмку, долг или прогноз из предположения ИИ; соблюдать draft/unknown и финансовые ограничения C164/C158/C165.

## Локальный ИИ и исполнитель
17. Локальный extractor/OCR извлекает текст/таблицы; ИИ возвращает только валидируемый структурированный proposal: тип, поля, строки, связи, ссылки на страницы/фрагменты, сомнения. Уверенность модели не заменяет доказательство.
18. Текст PDF/имя файла/изображение — недоверенные данные. Инструкции внутри документа не исполнять. У ИИ нет shell, секретов, записи файлов/API или права выбирать произвольный маршрут.
19. Отдельный детерминированный исполнитель проверяет схему, суммы/валюты/НДС/даты, allowlist полей и действий; отклонённый proposal не пишет данные.
20. API — минимальные разрешения для типов импорта; без admin по умолчанию и без прямого Mongo. Токен получает исполнитель, не модель. После настройки разрешённых правил однозначные документы проходят автоматически в рамках поручения владельца; подтверждение каждого счёта или пакета не требовать. Конкретный план и результаты сохраняются в журнале; человек разбирает исключения.
21. Повторная запись защищена стабильным operation UID, hash, CAS/version и серверными receipts. На конфликт/неизвестный исход — reconcile/read-proof, затем конкретное решение; без blind retry. Частичный комплект остаётся draft до полной сверки.

## Исключения и улучшение правил
22. Один отчёт пакета: «учтено», «уже было», «нужна проверка», «остановлено»; по исключению — источник, отличие/причина и допустимое решение. Выбрать несколько однотипных решений можно пакетом, конфликтующие — отдельно.
23. После решения повторно обрабатывать только выбранные исключения/незавершённые шаги; завершённые не отправлять в ИИ/API заново. Изменение proposal требует новой проверки плана.
24. Не обучать веса автоматически. Хранить версионированные исправленные правила и короткие примеры/RAG только с одобренным решением и ссылкой на источник; необсуждённый proposal не становится знанием.
25. Новая версия правил сначала проходит короткий регресс на реальных примерах; доступен откат. Ранее импортированные факты автоматически не переписывать. Данные наружу не отправлять; внешний ИИ — отдельное решение, действующее C092 не расширяется.

## Пульт и этапы
26. Будущий отдельный раздел «Разбор документов»: «Папка», «Разобрать», «Отчёт», «Возобновить». Показывать «Обработано 7 из 12», текущий файл и понятную причину остановки; SHA/HTTP/JSON — только в подробностях.
27. Повторное нажатие не запускает второй обработчик. Недоступная модель/API даёт понятное состояние и возможность продолжить, а не скрытый перезапуск runtime.
28. MVP: один пользователь/ПК и папка; ручной запуск; ограниченные типы C157/C164; извлечение → proposal → API-проверка → согласованный импорт → proof → перемещение; пакет исключений и восстановление после сбоя обязательны.
29. Расширение: новые форматы/сканы/типы, фоновое наблюдение, накопленные примеры и разрешённая автоматизация понятных пакетов. Без очереди микросервисов, второго учёта и автоматического обучения весов.
30. Вероятные готовые блоки: исполнители/UID-журналы C157, typed legal/CAS/receipts C164, существующие upload/DTO/API, локальные профили и OCR, каталог/отчёт пульта. Перед повторным использованием проверить контракт и побочные действия; не копировать разовые helpers вслепую.
31. Скорость: не повторять чтение платежей/отчётов после каждой позиции. Справочники и проверку дублей получать адресно на пакет, результат документа сверять перед денежным фактом и после него. При необходимости предусмотреть серверную пакетную запись документа с единым UID и результатом по строкам, сохранив старый API. Прогресс показывать сразу; завершённое не разбирать повторно. Измерять время извлечения, ИИ и API отдельно, чтобы видеть настоящее узкое место.

## Проверяемый чек-лист будущей приёмки
- [ ] Если тот же файл переименован/запущен повторно, то API-сущности, платежи и загрузки не дублируются; журнал показывает существующий результат.
- [ ] Если номер совпал, а содержимое/редакция отличаются, то показано сравнение; новая версия не теряется как дубль и не создаёт второй расход.
- [ ] Если комплект содержит договор/КП/счёт/акт, то источники связаны с правильными существующими сущностями без повторных денег и ложных состояний.
- [ ] Если поле неизвестно, то оно пустое с issue либо файл в «Сомнительных»; даты/оплаты/приёмка не выдуманы.
- [ ] Если API ещё не доказал результат или обнаружен удалённый дубль, то файл не попадает в «Готово».
- [ ] Если процесс упал до/после API commit, upload или перемещения, то «Возобновить» восстанавливает единственный результат и оригинал без слепых повторов.
- [ ] Если PDF содержит команду/инструкцию, то она остаётся данными; модель не получает права её выполнить.
- [ ] Если менеджер решил 3 из 5 исключений, то повтор касается этих 3; оставшиеся 2 и завершённые файлы сохранены без изменений.
- [ ] Если правила обновлены, то короткий регресс (дубль/версия/комплект/unknown/сбой/враждебный текст) проходит; откат возвращает предыдущие правила.
- [ ] Если пользователь работает в пульте на компьютере, то путь от папки до отчёта понятен без команд и технических кодов; доказательства приёмки сохранены в crew.
