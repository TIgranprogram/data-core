# C161. План приёмки

## Данные для Chrome

На изолированном 3102 отдельный клон 1066 через `POST /api/showcase/6ae1269ae36900370537a2f3/clone` после разрешения координатора. API копирует физические характеристики и настройки, а паспортные связи рисунков хранятся отдельно. Для клона добавить недостающие `overview`, `dimensions`, `holes` через `POST /api/products/<cloneId>/photos` с точными `{photoId,purpose:"passport",kind}` из родительского GET. Использовать живые оригиналы, уже доступные на копии. До UI сверить отдельный id и артикул, отсутствие собственных настроек C161 и экземпляров, известную свою фирму для выпуска. [Клонирование](../../../backend/src/modules/showcase/showcase.service.ts#L427) · [Рисунки](../../../backend/pwa/sections/product-files.js#L13)

Используем три действующие строки `passportParts` из таблицы ниже. Фраза вычисляется из их словарных форм. Номер нового паспорта фиксируется из ответа выпуска. Контрольные хеши старых выпусков №611 и №612 сверяются до и после.

### Точные данные существующего стенда

`POST /api/showcase/6ae1269ae36900370537a2f3/clone` принимает пустое тело и сам назначает новое имя и артикул. После отдельного разрешения выполнить точечный `PATCH /api/showcase/<cloneId>` с телом `{"name":"QA C161 — Хипс"}`. Записывать только ID, возвращённый клонированием. Перед созданием проверить отсутствие точного имени, после него сверить отдельные ID и SKU, ноль экземпляров и пустое собственное описание. Если операция прервётся после клонирования, продолжить по уже возвращённому ID, повторный клон не создавать.

После GET списка рисунков клона привязать только отсутствующие пары. Для каждого `POST /api/products/<cloneId>/photos` тело состоит из указанного `photoId`, `kind` и `purpose: "passport"`.

| `kind` | `photoId` | Размер подтверждённого PNG |
| --- | --- | ---: |
| `overview` | `6af2bdb1750f7e34dbcc402f` | 65 643 |
| `dimensions` | `6af2be70750f7e34dbcc423c` | 51 192 |
| `holes` | `6af2bef8750f7e34dbcc4374` | 29 406 |

Это ID исходных фото, которые API возвращает в `photoId.id`. GET исходных ссылок вернул PNG с контрольными суммами C155. Фирма для отдельного выпуска QA — `6ad52bec863df73f344ea489` из выпуска №611. Номер нового документа определит ответ выпуска.

Фикстура подтверждена после пересборки стенда. `6aff2a4c2d9e948b326337fc`, артикул `1037`, «QA C161 — Хипс». До сценария есть унаследованная словарная фраза, собственное описание отсутствует, готовность положительная, число экземпляров равно нулю.

После основного приёмочного прогона `C161_VISUAL_ONLY=1` открывает только этот шаблон и сверяет уже выданный №613 (`6aff2b122d9e948b326339c6`). В этом режиме прокси не принимает разрешений на запись. Для обеих тем снять пустой выбор с подсказкой, затем предзаполненную ручную форму. Режим `C161_VISUAL_ONLY=manual` снимает ручную форму прямо из сохранённого выбора. Отдельной проверкой воспроизводит очистку, пустое сохранение и повторный выбор с диагностикой по каждому шагу. Оба дополнительных прогона сравнивают хеши шаблона и доступного снимка №613 после отмены. Результаты фаз хранятся отдельно.

| Часть | ID | Родительный падеж |
| --- | --- | --- |
| Каркас | `6af81f883389de160b2c97d9` | каркаса |
| Ручка | `6adceeeb3ca001b9b3b0e575` | ручки |
| Ногоступ | `6ae32682a3f6de10abf0365b` | ногоступа |

Ожидаемая фраза «Изделие состоит из каркаса, ручки и ногоступа.» Прочитанные на стенде хеши контрольных полей выпущенных паспортов совпали с прежними. №611 `0fe843d976947965cae9c2634042d2b0b88677add015d19043e8664b07402a62`. №612 `98200456603e8e7ff00becf21390477cac581647eb4395911fabe474bce7b98b`. Снимки до обновления кода хранятся в `tools/logs/c161-qa/`. Клон и связи по этому плану создаются только после отдельного разрешения координатора.

На обновлённом QA подготовлен единственный клон `6aff2a4c2d9e948b326337fc`, артикул `1037`, «QA C161 — Хипс». GET подтвердил ноль паспортов, три исходных PNG с неизменными SHA и готовый начальный шаблон со словарным описанием. Собственное `defaults.simpleDescription` отсутствует, поэтому начальный CAS ожидает `null`. Сравнение исходного 1066 и контрольных полей выпусков 611/612 до и после подготовки совпало. Локальные подтверждения находятся в `tools/logs/c161-qa/fixture-summary.json` и `tools/logs/c161-qa/openapi.json`. OpenAPI обновлённого QA документирует `mode: "parts"`, ручной режим и форму `expected`.

## Проверки

| Критерий | Доказательство |
|---|---|
| Грамматика и порядок | Целевые unit и e2e. 1/2/3 части, повторение id, перестановка, незаполненный падеж, сокращения, пустая выборка, недоступная ссылка. В Chrome действительная тройка через видимый список «Добавить часть», предпросмотр в «Предпросмотр краткого описания». |
| Сохранение и ручной режим | В Chrome точечные CAS PATCH `/showcase/<cloneId>/passport-template?variant=short`: начальный `null` → `{mode:'parts',partIds}` → ручное значение с этими же id → автоматическое значение. После каждого ответа сверить `defaults`, источник и текст. Закрыть и открыть после первого сохранения. Отмена выполняется до выдачи разрешений на запись. Состояние 409 и сохранение ввода проверяются локально. |
| Образец, выпуск и печать | Один POST образца `{productId,presentationVersion:1,variant:'short',mode:'pages',pack:'passport'}`. Проверить PDF по серверным байтам и отсутствие нового документа. Подтвердить выбранную фирму, разрешив один POST создания нового экземпляра по UUID и один POST issue только по возвращённому id. Один GET PDF этого id, совпадают фраза и присвоенный номер. Снимки интерфейса в обеих темах. |
| Совместимость и заморозка | Новый C161 e2e на `datacore-test`: прежний ручной формат и PUT/bulk, сохранённые ссылки автоописания, новый short на тех же данных, старый full/legacy, заморозка выпуска и печати после изменения названия части. Два прежних выпуска на стенде только GET с `readOnly=1`. |
| Общие ворота | После фиксации кода: `tsc --noEmit`, lint изменённых серверных файлов, весь Jest unit, весь e2e только на Docker MongoDB 4.4 и имени `datacore-test`, PWA imports/Node/guards и дизайн. Записать числа, exit-коды и ограничения в TEST-LOG. |
