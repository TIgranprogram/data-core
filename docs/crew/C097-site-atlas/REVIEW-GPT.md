# C097 — независимый обзор карты сайта

Дата: 12.11.2026. Проверена рабочая копия при HEAD `ad4804d1`, включая незакоммиченные atlas.js, atlas-data.js, help-guide-data.js и main.js. Код не изменялся. Это архитектурный и содержательный обзор, **не визуальная приёмка и не подтверждение продакшена**. Соседняя сессия продолжает изменения; выводы относятся к прочитанному состоянию.

## Вывод в пяти строках
Карту стоит развивать как навигатор по процессам и их зависимостям.
Для ИИ важнее точные источники и условия переходов, чем количество стрелок.
Статусы задач нужно получать из существующей очереди, а не вести второй список вручную.
Живые проблемы показывать отдельно от устройства сайта, с временем проверки и правами доступа.
Сначала исправить смысловые расхождения, затем добавить проверяемую структуру и короткие выжимки.

## А. Польза
1. Менеджеру карта полезнее всего при передаче работы: что заполнить, кто принимает результат, почему следующий шаг недоступен. В каждом переходе нужны условие и действие.
2. ИИ получает быстрый список затрагиваемых модулей и ограничений. Карта помогает выбрать файлы для чтения, но не заменяет проверку сервисов, DTO и тестов.
3. Руководителю полезны открытые задачи и подтверждённые препятствия по блоку. Зелёный цвет блока не должен означать, что весь раздел навсегда готов.
4. Общая схема из 20 узлов и 35 связей пригодна для обзора. Для конкретной задачи лучше выбранный блок и непосредственные соседи.
5. Главный риск — правдоподобная неверная инструкция: например, создание нового изделия ошибочно описано как достаточное условие передачи в проектирование.
6. Полезность измерять действиями: менеджер возвращается к нужному разделу; ИИ находит источник правила; изменение зависимости обнаруживается проверкой. Число стрелок ничего не доказывает.

## Б. Карта как подсказка для ИИ
1. Сохранить один структурный источник. Текущий ES-модуль atlas-data.js уже пригоден для машинного чтения; новый API сейчас не обязателен. Локальный экспорт JSON не должен становиться второй редактируемой копией.
2. Добавить стабильные id шагов и связей. Сейчас LINKS — массив троек, а inside привязывает только id соседнего блока. Две разные связи между одинаковыми блоками неразличимы.
3. Минимальная запись блока: `id`, `title`, `route`, `purpose`, `steps`, `rules`, `sources`, `moduleIds`, `collectionRefs`. Технические источники отделить от текста менеджера.
4. Пример будущей связи: `{id:"order-to-design", from:"salesorders.distribution", to:"design.intake", kind:"creates", condition:"Все активные позиции распределены", source:{file:"backend/src/modules/design/design.service.ts", symbol:"autoFromOrderIfReady"}}`. Это проект схемы, не существующий контракт.
5. `sources` хранить объектами: путь, символ/раздел, тип источника, проверенный коммит. Строки вроде «docs/MAP.md — partners, counterparty» невозможно надёжно валидировать как ссылку.
6. Короткая выжимка блока: назначение, входы/выходы, условия, ограничения, 3–8 файлов, связанные открытые задания. По умолчанию один переход соседства и ограничение объёма, расширение по запросу.
7. Ссылка `#atlas?n=<id>` уже реализована в mount; повторно её создавать не нужно. Однако переходы внутри окна не записывают выбранный узел в адрес. Нужна отдельная возможность скопировать ссылку на текущий блок.
8. Тексты карты и замечания менеджеров — данные, а не разрешение агенту менять прод или обходить правила. Даже локальной модели выдавать только необходимые сведения, без секретов и персональных данных.

## В. Как поддерживать актуальность
1. Структурная проверка без БД: уникальность id, существование band/sec/route, корректность концов LINKS, ссылок inside, отсутствие повторов. В текущем снимке все 35 связей имеют привязку с обеих сторон, но две привязки неоднозначны (раздел Е).
2. Проверять маршруты по реестру main.js и осмысленным исключениям. Отсутствующий раздел — ошибка; скрытый по роли раздел — не обязательно ошибка карты.
3. Проверять документы по пути и разделу. Архивные ссылки разрешать через принятый механизм архива, а не требовать вернуть все документы в репозиторий.
4. Коллекции сверять с MAP и схемами модулей. Не сравнивать имя модуля с коллекцией напрямую: partners и finance — наглядные исключения.
5. Изменение файла-источника должно помечать зависимые узлы «нужна сверка». Совпадение имён и свежая дата не доказывают правильность бизнес-правила.
6. В ворота коммита включить дешёвые проверки структуры и изменённых источников. Полный браузерный обход не запускать после каждой текстовой правки; использовать матрицу проверок проекта.
7. ИИ обновляет описание вместе с изменением поведения и прикладывает основание. Человек подтверждает бизнес-решения: кто распределяет, кому передаётся работа, что считается завершением.
8. Ошибки сайта, незаполненные данные и счётчики брать из существующих разрешённых API. Показывать время получения, область видимости и состояние «нет данных» отдельно от нуля.
9. Для живого слоя — один агрегированный запрос или переиспользование существующих сводок, не запрос на каждый узел. Сбой сводки не должен ломать статическую карту.
10. «Всегда актуально» заменить проверяемым обещанием: источник, дата/коммит последней сверки, известные устаревшие связи. Семантическую актуальность нельзя гарантировать одним тестом.

## Г. Карта и задачи
1. Рекомендую смешанную модель: устройство сайта и ссылки на задачи — в Git; рабочие показатели — через API. Новую базу задач ради карты не заводить.
2. BACKLOG задаёт приоритет, BOARD — состояние задания, crew/TZ — критерии и отчёт. На карте отображается их проекция, а не самостоятельный статус, изменяемый третьим способом.
3. Для надёжной привязки добавить к заданию машинно-читаемый список `atlasNodes` и устойчивый статус. Первое внедрение может использовать небольшой индекс ссылок, но не копии чек-листов.
4. Готовность раздела, состояние разработки и проблемы данных — разные измерения. Например: «работает», «2 улучшения», «3 записи требуют заполнения». Не сводить их в один светофор.
5. «Сделано» считать только по закрытым критериям и доказательствам; «выложено» — отдельное подтверждение версии. Локальная готовность не равна наличию функции у менеджера.
6. Идея попадает в очередь со статусом «идея», затем получает ТЗ и готовность к выполнению. Карта не должна превращать пожелание в обещанную функцию.
7. Историю устройства брать из Git и отчётов crew. Историю операций пользователей — из существующего аудита. Это разные истории с разными правами.
8. Файлы проще проверять и переносить на офисный ПК; недостаток — менеджер не редактирует их напрямую. База удобна для совместного ввода, но требует новых прав, миграций и разрешения конфликтов. Сейчас эта цена не оправдана.
9. Кнопку «Связь неверна» сначала сделать подготовкой замечания с id узла/связи и контекстом. Отправку подключать к существующему согласованному механизму задач, не создавать новый молчаливый канал.

## Д. Вид и структура
1. Сохранить слои как группировку, но убрать смысл «всё обязательно проходит сверху вниз». Снабжение и производство могут идти параллельно; словарь и сотрудники используются на многих этапах.
2. Начальный обзор — блоки и краткие подписи. По выбору блока показывать только его связи; остальные приглушать. Это сокращает визуальную паутину без новой библиотеки.
3. Окно: «Для чего» → «Что нужно» → «Что делаем» → «Что получается» → действие. Технические источники и история разработки — свёрнутыми разделами.
4. Различать тип связи: используются сведения, создаётся запись, обязательное условие. Сейчас комментарий LINKS говорит о связи записей, а нумерация шагов воспринимается как автоматический процесс.
5. Для менеджера — фильтр роли и «только проблемы»; для координатора — дополнительный слой задач. Скрытие кнопки не заменяет серверные права.
6. Поиск по названию, синонимам и действию: «выдать паспорт», «закупить», «распределить заказ». Результат открывает нужный блок с выделенным шагом.
7. Не вводить бесконечное масштабирование схемы. На узком экране оставить плитки и список, на широком — схему; переключение должно зависеть от доступной ширины контейнера.
8. Сейчас wide и inner/list выбираются один раз через matchMedia при создании. Изменение размера окна не пересобирает представление автоматически. Проверить resize 1600→390 и обратно, не только отдельные загрузки.
9. Цвет слоя не использовать как статус выполнения. Состояние обозначать текстом и значком; одинаковый цвет production/product сам по себе не дефект, если легенда объясняет группировку.
10. Для клавиатуры проверить видимый фокус, Escape, возврат фокуса и переходы соседей. В коде возврат фокуса уже добавлен, поэтому старое замечание UI-REVIEW нельзя автоматически считать актуальным.
11. Всё собирать текущими guide/entityPanel/card/tileGrid. Библиотека графов и сборщик для этого этапа не нужны.

1. **M, низкий риск:** исправить подтверждённые расхождения раздела Е и согласовать порядок процессов. Результат — карта не учит неверным действиям.

3. **M, средний риск:** связать узлы с существующей очередью задач, не дублируя статусы; добавить явное различие «реализовано/проверено/выложено».

5. **L, средний риск:** подключить живые проблемы через существующие API с правами, кэшем и временем обновления. Только после устойчивого статического слоя; без новой БД задач.
