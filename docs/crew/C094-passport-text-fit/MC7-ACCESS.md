# Стенд для МЦ-7

Проверка принадлежности выполнена чтением списка контейнеров и пути монтирования `/app/pwa`.

| Контур | Проект Docker | API / Mongo | Рабочее дерево |
|---|---|---|---|
| МЦ-7 | dc-bf4e527a619f5e6f21c58d48 | 3102 / 27118 | data-core |
| C088 | dc-bd4533224a88fbc430c1e995 | 3112 / 27128 | data-core-c088 |

Оба QA-контура слушают loopback. Основной стек 3001 / 27018 в проверках не используется. Указатель текущего стенда C088 и его контейнеры не менялись. Для МЦ-7 используется существующая отдельная копия проекта data-core.

После фиксации кода штатное обновление — `tools/dc.cmd stand refresh` из data-core. Проверка — `deploy/synology/api.sh stand` в login Git Bash. Этот режим закреплён за `localhost:3102`. Браузерный прогон — через `stand BROWSER` в отдельном headless-контексте. Для выпуска используются только созданные тестовые записи QA. Тесты e2e должны явно использовать отдельную тестовую БД, не БД QA с копией данных. До фиксации кода обновление не запускалось.

QA обновлён штатным refresh. Без эскалации Docker inventory недоступен. С разрешённым запуском Docker завершил сборку и запустил контейнер. Оболочка Node завершилась с Windows libuv assertion после старта контейнера. Работа подтверждена live API и браузерными операциями.

Созданы отдельные изделие BLG, заказ на два изделия, позиция заказа, плательщик и поставщик. Шаблон получил габариты, массу, настройки и три ссылки на настоящие рисунки указателя 3905. Спецификация материалов нового изделия оставлена пустой для проверки переноса из состава. ID находятся в игнорируемом `tools/logs/c094-mc7-fixtures.json`. Первый запрос создания поставщика вернул 400 из-за неверного значения kind. Повтор со значением supplier прошёл, уже созданные записи переиспользованы. Первый UI-прогон сохранил заявку, выставил и оплатил счёт и принял материал. Сценарий остановился на неверном селекторе складской карточки. Следующий прогон продолжит с сохранённых ID.

Штатный экспорт OpenAPI из QA подтвердил 502 маршрута. Результат совпадает с текущим `docs/openapi.json`. Новые вложенные поля спецификации материалов не попадают в Swagger из TypeScript-типов без явной схемы.

На шаге складской связи реальный PATCH складской позиции вернул 200, а GET материала не содержал passportSpec. Причина найдена в интерфейсе: сборщик формы уже разбирает JSON поля widget, после чего savePassportSpec повторно вызывает JSON.parse для объекта. Запрос сохранения паспортных полей поэтому не отправляется. Проверка приостановлена на существующих ID до исправления.

Повторный UI-прогон подтвердил сохранение складской связи отдельным PATCH, выдачу 4 м, приём предложения 2 м на изделие, перенос материала в техописание и скачивание PDF. Размеры PDF предпросмотра — 114 653 байта, техописания — 9 523 байта. Оба стандартных обхода QA прошли: qa-smoke 29 экранов без сбоев, screen-walk 18 экранов и 24 панели без находок. Матрица истории карточек прошла на 375 и 1920 px в светлой и тёмной темах.

Контроль сайта до выкладки: v1.730, UI a9b3860b, backend f888b571. Сняты health, готовность 3905 и снимки №500, №522, №597. Doctor выявил две существующие группы ошибок версии a9b3860b: ложное GarbageText для обычного текста о креплении подвесов (14:52:14 UTC, 4 случая, products, core/errors.js:114) и один временный отказ операции записи (14:33:21 UTC, products, core/api.js:155/314). Служебные ошибки оставлены в журнале. Это исходный уровень до выкладки МЦ-7.

Выпуск без заказа выполнен через интерфейс на собственном тестовом изделии. GET подтвердил issued и паспортную формулировку в снимке. Скачан валидный выпущенный PDF размером 108 915 байт. Попытка выбрать заказ из воронки возвращала панель выбора категории, выпуск по этому пути не подтверждён. Матрица складской карточки и материалов прошла функциональные проверки в четырёх комбинациях, но в каждой зарегистрировала GarbageText для `[object HTMLSpanElement]`. Источник разбирается отдельно. Сайт не менялся.
