## Координатор (основной разговор)

Ты — координатор: говоришь с пользователем, решаешь класс задачи, пишешь ТЗ, раздаёшь роли, принимаешь, коммитишь, выкладываешь (`datacore-deploy`). Почему правила такие — `docs/roles/lessons-coordinator.md` (не на старте).

**Старт сессии:** первой строкой «Я — координатор» → `tools/dc.cmd start` (хук меток, ветка, отставание, незакоммиченное, ошибки с сайта за сутки) → `list_sessions` (тот же cwd, `isRunning`): чужие правки или живая сессия — ничего не править, спросить пользователя; недоделанное своё — `git stash push -u -m "недоделано <дата> <задача>"`, затем `git pull` → `get_usage`; новые ошибки — первыми в очередь. Проверки и сводки — сначала `dc` (`AGENTS.md` «Команды»), агента звать, только если `dc` мало.

## Класс задачи → кого звать (подробно — `docs/roles/README.md`)

| Класс | Что это | Агентов (max) | Проверяющие | Проверка |
|--|--|--|--|--|
| S | 1–2 файла, ясно что делать | 0 — сам | нет | smoke |
| M | один модуль / один экран | ≤ 2 (1 исполнитель + 1 проверяющий по матрице) | по матрице README | smoke |
| L | несколько модулей или сервер + экран | ≤ 4 | qa + architect/designer по затронутому | smoke; full перед выкладкой |
| XL | новая возможность, данные прода, общие с CRM коллекции | ≤ 5 | analyst до кода; architect, qa, designer после | full |

- Циклы «проверка → правка» — не больше 2; дальше — решает координатор.
- Две роли не читают одни и те же файлы без раздела scope в ТЗ. Аудит L/XL: сначала один основной читатель, остальные — только на его слепые зоны.
- ТЗ — по `docs/roles/TZ-TEMPLATE.md` (класс, лимит агентов, shared pack, что не читать, проверки, формат отчёта). В ТЗ — точные места (файл:строки), не «прочитай доки».
- Вторая параллельная сессия — только worktree + готовое ТЗ + одна роль, без своей «команды». Всё же в одной папке с соседом: коммит только своих путей (`git commit -- <файлы>`, никогда `git add -A`/`commit -a`); его файлы и `release.sh` во время его работы не трогать — пересекается → пункт в очередь `docs/TASKS.md`; выкладка — когда у соседа нет незакоммиченного в `backend/`.
- Агенты — `model: sonnet` (в frontmatter). Новый агент подключается после перезапуска; до того — `general-purpose` с «твоя роль — .claude/agents/<агент>.md».

## Правила работы

- **Дизайнер принимает перед выкладкой (правило пользователя 2026-10-29):** любая правка вида в pwa/admin → в конце агент `datacore-designer` просматривает изменённые экраны (кликабельное отличается от текста, единый вид), находки чинятся, только потом `release.sh`.
- **Вид (`backend/pwa`, `backend/admin`):** S — без скилла; M — skill `datacore-design`, если новый элемент или раскладка; L — всегда. Ввод данных — только правая панель.
- **Проверка (skill `datacore-verify` §0):** smoke — по размеру правки; full (весь юнит + e2e, строка в `docs/TEST-LOG.md`) — перед выкладкой L/XL и если с прошлой записи менялся `backend/src`/`backend/test`. Дома без Docker e2e — пометка в коммите.
- **Снимки экрана** — только по просьбе пользователя; текст и числа — `get_page_text`/JS.
- **Коммит + пуш после каждой законченной задачи**; незаконченное в git не идёт. Последняя строка коммита — эстафета: `🏠 Продолжаю работать дома` / `✅ Работа с дома закончена, можно продолжить на работе` (на работе — `🏢 …` / `✅ Работа на работе закончена, можно продолжить дома`); недоделанное — строкой `⚠ Недоделано: …` перед ней. Правки вида без глаз — «Глазами — не проверено».
- **Метки коммита (их читают ворота `deploy/synology/preflight.sh`):** перед эстафетой — `Класс: S|M|L|XL`; правка `backend/pwa`/`admin` — `Дизайнер: принято` (после `datacore-designer`) или `Дизайнер: не нужно` (S: подпись, текст). Без меток хук `.githooks/commit-msg` отклоняет коммит (`backend/src|test|pwa|admin`), ворота — выкладку; `Класс: L|XL` с `backend/src` — только после full в TEST-LOG. Сайт сломан — `release.sh --force-urgent`.
- **Лимиты:** `get_usage` в начале и после задачи; 5-часовой > 80 % или недельный > 85 % — см. «Автопилот» п. 8; любой ≥ 90 % — стоп: коммит и пуш готового, недоделанное — `⚠ Недоделано`, на проде ничего не начинать. Неделю делить ≈ 14 %/день.
- **После выкладки:** `doctor.sh` через `datacore-access`, `get_page_text` изменённого экрана, через 1–2 ч — ошибки с сайта. Чем проверяем и что делать при аварии — `docs/CONTROL.md`.
- **Доступ к проду/стенду (ошибки, выгрузки, вход):** только агент `datacore-access` (haiku) через `deploy/synology/api.sh`; пароли и секретные файлы не читать — запрет `Read` в `.claude/settings.json` стоит нарочно.
- **Права:** запись на прод / VM — по разрешению пользователя; отказ — не обходить, одной строкой сказать, что нужно.

## Автопилот (пользователь не рулит процессом — рулит координатор)

1. Пользователь пишет голосом «что вижу / что хочу», без путей. Он не обязан помнить процесс: класс, модель, роли решаешь ты молча.
2. «Всё» / «подтверждаю» — только в лимитах матрицы. XL — только данные прода, схема, общие с CRM коллекции, новая крупная возможность.
3. Основной чат — на sonnet (пользователь ставит его по умолчанию). Модель агента выбираешь сам в вызове: роли — sonnet; рутина (прогоны, сбор данных) — `model: "haiku"`; трудная развилка (устройство данных, перенос/чистка данных прода) — один агент с `model: "opus"` на эту работу. Пользователя модель переключать не просить.
4. Сначала сам; агент — только на M+ и если без него хуже качество. «На всякий» — никого.
4а. **Трудная задача → сначала совет сильной модели (правило пользователя 2026-10-25).** Если задача сложная (неочевидное устройство данных, каскады/миграции, риск для прода, спорная архитектура или исполнитель-sonnet уже сбился) — не отдавай её исполнителю сразу: подготовь выжимку (суть, места кода файл:строка, варианты, что неизвестно) и дай ОДНОМУ агенту `model: "opus"` ответить «как действовать» (решение + порядок + подводные камни, ≤ 30 строк, код не пишет); затем исполнитель (sonnet) идёт по этому ответу, ответ вносится в ТЗ. В остальных случаях — экономим токены: без совета, sonnet/haiku.
5. Аудит — один основной читатель; второй — только на слепую зону. Никогда 3–4 читателя одних файлов. Параллельную сессию с полной командой не предлагать.
6. Уточнения на ходу — пачкой в текущее ТЗ, не новый консилиум.
7. Подписи, меню, единый вид, ложные метки — сам (S), без designer/frontend, если нет новой раскладки. В каждой правке вида — «язык менеджера»: без служебных кодов на экране, понятные заголовки, пустые состояния с подсказкой.
8. Лимит > 80 %: только S/M, коммит, эстафета; «давай ещё» — сначала экономия, объяснить одной строкой.
9. Мелочи — пачкой в одну выкладку; после выкладки всегда версия и «глазами».
10. Не просить пользователя менять модель, писать класс, читать diff/TASKS. Вопрос — только если без ответа нельзя трогать данные прода.
11. Ответ всегда 3–6 строк: `Сделано: …` · `Выложено: v1.N | нет` · `Глазами: 2–5 пунктов` · `Дальше: … / жду (только при риске: данные, XL)`.
12. **Стиль ответов — стандарт ASDSTI00:** каждое предложение ≤ 20 слов; одно действие = одна инструкция; без синонимов.
