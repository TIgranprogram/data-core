# C166. Владелец каталога заявок моста

20.11.2026. Прошли 53 из 53 локальных проверок. Среди них шесть сценариев на настоящем ядре Linux. Изменения подготовлены для выпуска координатором.

## Причина и исправление

Завершённая заявка `e72ab449cdcd` осталась в рабочем каталоге. Контейнер создал файл как root с режимом 0644. Каталог тоже принадлежал root и имел режим 1777. Sticky-бит означал, что пользователь cron с UID 1000 мог записать новый файл, но не мог убрать этот чужой файл. Очередь сохраняла старую заявку, последующие задания истекали без начала выполнения. Разовую производственную коррекцию выполнил координатор отдельно, до этой доработки.

Установщик `SRV-ERP/setup-switch.sh` выполняет проверку на обоих узлах до настройки ключей и VPS. Он получает числовые UID и первичную GID на самом сервере под пользователем, которому устанавливается crontab. Под существующим замком моста он приводит только каталог очереди к этому владельцу и режиму 1777. Для заранее созданного Docker каталога 0755 без файла замка права подготавливаются перед созданием замка. При необходимости повышенных прав установщик использует точечный `sudo -n` и выводит причину отказа. Символьная ссылка и попытка повторной установки из чужой учётной записи при работающем мосте отклоняются.

При выпуске и обновлении запасного проверка выполняется под захваченным cron-flock, если у текущего пользователя обнаружена активная запись запуска моста. Проверка ничего не переназначает. Каждый запуск самого моста сверяет владельца и режим до записи heartbeat и до чтения заявки. При несоответствии мост завершает работу с ошибкой, фиксируя в диагностике текущие и ожидаемые значения. Ошибка снятия уже обработанной заявки также возвращает ненулевой код. Механизм защиты от повторной обработки через last-id сохранён.

### Команда Linux-теста из корня рабочей копии в Git Bash

```bash
set -o pipefail
export MSYS_NO_PATHCONV=1
tar -cf - deploy/ha/switch/release-artifact.sh deploy/ha/switch/switch-watch.sh tools/test/ha-owner.sh |
  docker run --rm -i --pull never --network none --read-only \
    --cap-drop ALL --cap-add CHOWN --cap-add SETUID --cap-add SETGID --cap-add DAC_OVERRIDE \
    --security-opt no-new-privileges --tmpfs /tmp:rw,exec,nosuid,nodev \
    --tmpfs /data/db --tmpfs /data/configdb --workdir /tmp --entrypoint /bin/bash mongo:4.4 \
    -c "tar --no-same-owner --no-same-permissions -xf - && bash tools/test/ha-owner.sh"
```

Использован имеющийся локальный образ `mongo:4.4` с точкой входа Bash. Временные файлы размещены в tmpfs, каталоги хоста не монтировались. Поведение Linux при смене UID/GID, установке sticky-бита, блокировке и удалении проверено реально. Команду sudo в фикстуре принимает узкая подстановка, сверяющая аргументы и сигнализирующая родительскому процессу о единственном разрешённом chown в его tmpfs. Конфигурация sudoers рабочих серверов этой проверкой не охватывается.
