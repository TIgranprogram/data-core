# C241 — выбор установки и применимость редакций

Вердикт: **можно по политике ниже**, класс L. Основание — новое явное требование владельца, не переделка стандарта ПС-1.0. ПС-04/05/06/07/09/10 сохраняются; закрытие раздела паспортов этим изменением не объявляется.

## Политика существующих экземпляров

**Выбор в Inventor задаёт установку шаблона изделия, но не меняет установку ранее созданных паспортов.** Три рисунка одной отправки изображают один подтверждённый способ. Совпадения только класса foundation/mounting недостаточно: анкеры, свободная установка и другие способы могут иметь разные схемы при одинаковом третьем kind.

| Экземпляр | Действие импорта |
|---|---|
| Действующий draft/issued с точным installationTypeId выбранного способа | Обновить только три целевых рисунка/подтверждённые применимые числа по прежним правилам; issued — новой редакцией с прежним номером |
| Свой installationTypeId отличается, даже если совпадает thirdImportKind | Пропустить **весь экземпляр**, reason installation_mismatch; не менять ни схему, ни числа/тексты/номер |
| ID отсутствует, удалён или неизвестен | Пропустить весь экземпляр с ясной причиной; не угадывать установку по виду/рисунку/старому default |
| Аннулирован, готовый PDF, выбран вложенный паспорт, удалённая/чужая позиция/договор, closed/activeArchiveVersion | Сохранить прежние skip-границы; ничего не менять, включая служебные версии/историю |

Материализованный ID паспорта считается его снимком независимо от того, когда-то подставился из изделия или был выбран вручную: текущая схема не хранит доказанный признак наследования. Равенство прежнему default не доказывает разрешение сменить экземпляр. Для будущих новых экземпляров используется новый default. Нет отдельного автоматического переноса старых паспортов между способами.

Старый клиент без нового поля сохраняет выбор изделия и прежний контракт POST; при этом небезопасная подстановка схемы чужого способа существующим паспортам прекращается с явным skipped/warning по ПС-04/05. Не ослаблять защиту ради сохранения ошибочного поведения.

## Аддитивный API и атомарность

1. GET context расширить `{contextToken, installationTypeId:currentEffectiveId|null, installations:[{id,name,code,thirdImportKind,depthApplicable}]}`. Варианты только живые, известные installationProfile, с применимым третьим листом; предвыбранный ID — существующий effective root legacy→defaults, не первый в списке. Включение справочника в digest уже есть.
2. Optional `confirmed.installationTypeId`: валидный MongoId, **undefined — прежний выбор, null/пустой/неизвестный/удалённый — отказ без изменений**. Права WORK/AppSection/ключей не расширять. Wire image kind по-прежнему foundation; сервер нормализует третий kind по выбранному профилю.
3. При явном выборе записать `passportDefaults.installationTypeId`; если legacy корневой installationTypeId уже существует — синхронизировать его тем же ID **в этой же транзакции**, иначе он перекроет выбор. Не удалять историческое поле/не мигрировать остальные изделия. Отсутствующий root не создавать без нужды.
4. Внутри существующего session.withTransaction: state+token→валидация выбора/PNG→расчёт изменений изделия и применимых экземпляров→claims заказов/позиций/изделия→все записи/редакции. Никакого отдельного PATCH установки перед импортом. Ошибка любого применимого паспорта откатывает весь commit. Upload PNG сам по себе не равен успешной привязке.
5. Для anchors third=mounting, concrete=foundation. Глубина разрешена только depthApplicable; неприменимую foundationDepth не записывать/не стирать, вернуть предупреждение. При смене профиля убрать из **актуальных** productlinks прежний взаимоисключающий импортный foundation/mounting, не удаляя файл/историю; не затрагивать holes/embedded_layout и нецелевые картинки. Для экземпляров сохранять прежние captions/order и остальные изображения.
6. Точный контекст/CAS, file protection, claimWritableOrders/claimPassportLine, дедупликация SHA и no-op сохраняются. Старый token допускается лишь для прежнего доказанного полностью unchanged-повтора; изменённый ввод/контекст→409. Изменение установки само является изменением, даже при тех же PNG, и входит в проверку контекста/confirmedFields.
7. Для issued сохранять прежние installationTypeId, images/textSnapshot/printSnapshot и все изменяемые поля в revisions; номер неизменен. Не пересобирать skipped/исторические PDF. Legacy при отдельной согласованной редакции сохраняет прежний формат/источники; чтение не мигрирует его (ПС-10).

## Проверки перед приёмкой

- Матрица anchor/concrete/другой supported/unknown/deleted/null/отсутствующий выбор; legacy root конфликтует сdefaults; послеcommit effectiveID равен подтверждённому; словарь поменялся послеcontext→409.
- Существующие паспорта: exactID draft/issued, другойID того жеkind, другойkind, отсутствующийID, материализованный прежнийdefault, readyPDF/attachment/annulled/closed/archived. Для mismatched/skipped сравнить полный снимок/номер/историю до-после.
- Rollback на втором паспорте; конкурентная правка выбора/словаря/изделия/позиции, архивирование; двойной commit/потерянный ответ/no-op без редакции. Файлы/aliases защищены от удаления, прежняя редакция печатается прежними источниками.
- Два разных PNG anchor/concrete и реальный PDF проверяют назначение третьего рисунка и отсутствие Г у anchors. Числа/свои тексты/обложка/нецелевые рисунки сохранны. Старый клиент безполя проходит прежние сценарии.
- Адресные unit/e2e + полный необходимый backend verify на итоговой дельте; реальный Inventor отдельно: API/текстовый тест VB не объявлять исполнением Inventor. Использовать существующий пункт Пульта обновления правила, не создавать дубль.

Код, данные и ПС-стандарт при планировании не менялись. Новая политика смены установки готовых экземпляров потребовала бы отдельного явного требования владельца, в C241 её нет.

## Обнаруженный стык чтения: старый default не должен мигрировать экземпляр

Дополнительно разрешён адресный scope `ProductPassportService.fromProductDiff/getPresentation/syncDraft` и эффективных managed-image источников: текущий productPatch накладывается на draft при чтении, а syncDraft может сохранить результат. Поэтому одного import.skip недостаточно — следующий GET способен переопределить concrete экземпляра новым anchor изделия.

Материализованный installationTypeId экземпляра не менять на новый default ни при GET, ни при syncDraft/подготовке выпуска. При exactID mismatch не применять product-diff к этому экземпляру по принятой политике «skip всего экземпляра»; не подмешивать новый installationMethod/foundationDepth/установочный текст или managed-схему изделия, даже если thirdImportKind совпадает. Нецелевое наследование других экземпляров/создание новых паспортов не переписывать. Эффективные картинки старого экземпляра должны оставаться его собственными/прежними доказанными источниками, а не новыми продуктными схемами чужого способа.

Регрессия: старый draft concrete + новая anchor установка изделия, затем два обычныхGET и чтениеPDF/DB. Сравнить прежнийID, изображения, размеры/массу, текст/источники, историю/номер — skipped экземпляр остаётся неизменным. Повторить для другогоID того жеthirdkind и неизвестногоID, а также issued/legacy/closed. Старое e2e-ожидание автосмены установки заменить лишь с явным основанием ПС-04/05/10 и новой сильной проверкой сохранности; не удалять контроль и не объявлять его flaky. Это исправление обнаруженного обхода утверждённой политики, не новая модель наследования.

## Уточнение существующего неизвестного способа — только применимый контекст

Замораживание existing экземпляра с missing/unknown/deleted способом применяется **только когда способ установки действительно участвует в его действующем контексте**. Использовать прежнюю предметную применимость (в частности существующее требование установки в missingFieldsV2), а не вводить новую обязательность для всех категорий. Обычная немонтажная категория без installationTypeId сохраняет прежнее наследование productdiff; отрицательный контроль обязателен.

Различение existing read и new create — явная неперсистентная опция вызова: наличие `_id` недостаточно, create генерирует его заранее. Не добавлять поле наследования в БД и не выводить existing из случайной формы объекта. Valid собственный способ при mismatch остаётся известным и сохранным; unknown применимый не достраивается первым справочником. После freeze проверить точные caller paths/context и DB/PDF/2GET, не расширяя аудит всех категорий.
