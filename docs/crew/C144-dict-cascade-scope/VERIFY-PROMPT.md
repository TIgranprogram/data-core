# Промпт для проверки C144 (скопировать целиком)

Ты — проверяющий data-core (архитектор + взгляд менеджера). Код сам не переписывай — только отчёт с находками и вердиктом.

## Контекст
Задача **C144**: в справочниках «Паспорта» должно быть видно **каскад по типам паспорта** — на основании чего предлагают части / материалы / покрытия / элементы / тексты; порядок «что за чем»; в паспорте/книжке та же логика. Директор без кодов TRN/WRK понимает, кому что предложат, и где дыра.

ТЗ: `docs/crew/C144-dict-cascade-scope/TZ.md`  
Аудиты (если уже есть): `AUDIT.md`, `SHOULD.md` в той же папке.

## Что уже задумано / в работе (проверь факт, не намерение)
1. Список справочника: колонка **«Кому предлагают»** — метки типов словами («Для всех типов» / «Тренажёр»…), не сырые коды; у частей пустые категории ≠ «для всех» (короткий список).
2. Фильтр списка по типу паспорта: «как в выпадающем списке изделия с этим типом».
3. В таблице материалов книжки/карточки: покрытия и части с понятным основанием (подписи / группы «Для этого типа» / «Другие»).
4. Семантика пустого `categories` согласована в UI и подсказках:
   - материалы/покрытия/элементы/монтаж: пусто = для всех;
   - части: пусто = не в коротком списке при выбранном типе.
5. Форма записи справочника: чипы типов + понятный hint «кого затронет».

Файлы смотреть (не целиком репо):  
`backend/pwa/sections/dicts-sort.js`, `dicts.js`, `backend/pwa/ui/materials-spec.js`, `backend/pwa/ui/kit/pick.js` (`tagPick`), `backend/pwa/ui/cat-chips.js`, `backend/src/modules/dicts/dicts.defs.ts` (hints categories), книжка `book-side-edit.js` / `common.js` `dictOpts`.

## Как проверять
1. Прочитай ТЗ и этот промпт. Сверь код с критериями ниже (Grep + Read, файл:строка).
2. На стенде `http://localhost:3102/app/` (если доступен):  
   - Справочники → Паспорта → Материалы и покрытия / Части изделия — колонка «Кому предлагают», фильтр по типу.  
   - Изделие с типом паспорта → книжка → «Части у материалов» / покрытие: список совпадает с фильтром справочника для того же типа.
3. Не пиши «сверьте сами» — каждая находка: файл:строка → что не так → как исправить (P0/P1/P2).
4. Код не меняй. Секреты и прод не трогай.

## Критерии приёмки (PASS / FAIL по каждому)
- [ ] В списке материалов/частей/элементов видна колонка основания предложения (словами).
- [ ] Пустая привязка у **части** визуально не равна «для всех».
- [ ] Пустая привязка у **материала/покрытия** = «для всех типов».
- [ ] Есть способ увидеть список «как у изделия типа X» (фильтр или эквивалент).
- [ ] В книжке/форме материалов фильтр по типу паспорта изделия согласован со справочником.
- [ ] На экране менеджера нет опоры на сырые коды TRN/WRK как единственную подпись.
- [ ] Нет регрессии: `tagPick.setScope`, `materials-spec.own/groupOf`, контракт API не ломались.

## Формат отчёта
Сохрани **один файл**:

`docs/crew/C144-dict-cascade-scope/VERIFY-REPORT.md`

Структура:
1. Вердикт: **PASS / PARTIAL / FAIL**
2. Таблица критериев: критерий · PASS/FAIL · доказательство (файл:строка или стенд)
3. Находки P0 / P1 / P2 (что → где → как чинить)
4. Что не проверял (стенд недоступен, нет данных…)
5. Итог одной фразой для координатора

В чат — ≤ 12 строк: вердикт · топ-3 · путь к VERIFY-REPORT.md.
