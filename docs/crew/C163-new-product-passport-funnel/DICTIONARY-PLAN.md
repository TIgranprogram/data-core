## 4. Уместность частей при критериях

Существующая объяснимая связь: `productFacetValues.id` → `passportPhrases.facetValueIds` + `kindIds` → `leaf.partIds`. У `passportParts` в текущем контракте есть categories и падежи; отдельного поля разрешений cardio/bodyweight/weightstack/levers нет. У facet values есть elementIds (функциональные элементы), они не равны паспортным частям. Заполнять их id из passportParts нельзя.

В снимке уже есть точные наборы: contact двух платформ → Каркас/Ручка/Ногоступ; contact гребной тяги → Несущая рама/Рычаг/Ручка/Упор для ног. Они ограничены конкретными kind+contact, а не всей категорией TRN. Новый contact Вело добавит третий подтверждённый набор. По ним UI может показывать обоснованные рекомендованные части, сохраняя ручной доступ к полному списку и ранее выбранные id.

| Выбранный контекст | Что можно обосновать | Чего данных пока не хватает |

| Кардио | Для contact Вело — набор §2; только слово «кардио» не задаёт конструкцию | Подтипы степпера, эллипса и т. п.; автоматически добавлять педали любому кардио нельзя |

### 7.1. Проверен способ прочитать владельцев через готовые API

Точный read-only маршрут администратора: `GET /api/admin/collections/:name/docs?page=1&limit=100&deleted=exclude&q=...`, где name=`products` или `productpassports`; доступ admin/user:admin. Проверены `collections-admin.controller.ts` docs и `collection-docs.ts` parseDocsQuery/buildDocsFilter/sanitizeValue, а также клиент `backend/admin/admin.js` (~843). Параметры только page, limit, deleted, q; произвольного Mongo-фильтра/проекции нет. q из 24 hex ищет **_id самого документа**, а не id в его вложенных ссылках. Иной q ищет только name/title/label/username/email/article/sku/key/slug/code/inn/displayName/fullName. Запрос products/docs?q=<partId> поэтому не годится для reverse-ref audit: пустой ответ не означает отсутствия владельцев.

«Найти в данных…» в `pwa/sections/dicts-ops.js` вызывает `GET /api/dicts/:key/candidates`: ищет ещё не заведённые текстовые значения для импорта, не владельцев id. В `dicts.controller.ts` нет маршрута для внутренних related(), а `dicts.service.ts get()` related не возвращает. `/products` имеет только документированные фильтры списка и bulk по id владельцев, partId-фильтра нет. Готового **точечного** запроса по products.materialsSpec.rows.partIds / passportDefaults.simpleDescription.partIds и draftPassport refs не найдено в проверенных контрактах.

Технически доступен отдельный более широкий readonly-пакет: постраничные `products/docs` и `productpassports/docs` без q (limit≤100) → локальная фильтрация двух partId → список id/sku/name/status/путей найденных ссылок → точечный GET raw docs?q=<ownerId> при необходимости. Это не запускалось без поручения координатора. Санитизатор режет массивы после 100 элементов, строки после 2000 символов, вложенность после глубины 8; локальный фильтр обязан отмечать такой документ как неполный, а не считать отсутствие id доказанным. Новые маршруты/код ради аудита не создавались. При сохранении текущего tiny scope merge остаётся условным планом.
