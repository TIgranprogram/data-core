# Склад по-новому — требования пользователя и план (2026-10-23)

> Требования записаны со слов пользователя (разговор 2026-10-23). Это общий документ задачи: по нему координатор режет ТЗ `SK-1…SK-8` (ниже чек-листы), аналитик уточняет логику, архитектор решает «как хранить». Принцип пользователя: **одна база всё объединяет** — новых таблиц не плодить, где можно — представление существующих (заявки ↔ счета ↔ склад ↔ заказы ↔ продукция).

## Требования (словами пользователя, сжато)

**Фильтры и поиск («хлебные крошки» М4, М6, М8, «Болт мебельный»…)**
- Нравится. Число после значения убрать («М6 19» путает). Значение с нулём не показывать.
- В свёрнутом виде не мозолить глаза: большой заметный значок поиска; нажал — можно вводить текст, и раскрываются фильтры.
- Фильтры — как в интернет-магазине: панель слева (на телефоне — выезжающая), галочки; группы (категория, тип, резьба…) — выпадающие, по умолчанию свёрнуты; короткие — раскрыты.

**Кто работает:** кладовщик. У человека может быть **несколько ролей** (кладовщик + инженер…) — видит разделы и поля всех своих ролей.

**Склад — одна страница:** главные действия «Принять», «Выдать», «Забронировать» (+ «ещё»: списать, пересчёт); остатки ниже; движения — история (последние + «вся история»). Набросок координатора — в разговоре 2026-10-23, принят как основа.

**Принять:** в основном по заявке (через приложение); бывает «купили без заявки, есть оплаченный счёт» — тоже принимаем. Будет раздел **«Бухгалтерия»** со счетами (позже — договоры): счета связаны с заявками; **одна база — это представление** заявок/счетов, а не новые таблицы.

**Выдать:**
- под **позицию заказа**: заказ № → позиции 1, 2, 3… (обозначение вида «№ заказа-№ позиции», например `552-2`); при выборе кладовщик видит **название позиции и картинку изделия**, а не цифры; выбор — выпадающие списки с поиском;
- **сотруднику** (расходники) — без заказа;
- «под что» указывать не всегда: «просто выдано» сотруднику или на заказ;
- если выдано под позицию, привязанную к изделию «Продукции», — **состав изделия копится**: «6 болтов, 12 гаек…» → со временем у изделия полный состав и себестоимость (цены — из заявок/счетов). Изделия бывают стандартные и индивидуальные (под проект); стремимся к стандартным.

**Забронировать:**
- под заказ клиента (выбор заказа и позиции из списка; если указано в спецификации — подставляется само);
- бронь можно править (изменилось при проектировании);
- **«Выдать по брони»** — одной кнопкой выдать забронированное под заказ; бронь снимается сама;
- инженер загружает **спецификацию** (Excel по шаблону / пачкой) → позиции бронируются под заказ автоматически.

**Пересчёт и списание:** на карточке позиции — «Пересчитать»: ввёл фактическое количество → корректировка (было 9, по факту 10/12). Остаток всегда актуальный; следит менеджер. Списание (брак и пр.) — «Списать» с причиной.

# Аналитика SK-2 (аналитик, 2026-10-24)

> Опора: `stock/schemas/stock-movement.schema.ts`, `reservation.schema.ts`, `stock/dto.ts`, `stock.controller.ts` (маршруты `batch`, `reserve-list`, `reservations/issue`, `movements/:id/cancel`), `incomes` (`lineNo`, `orderNo`, `productId`, `photoIds`), `CompositionLine` (`lineType`, `refId`, `quantity`). Как хранить новое — решает архитектор (SK-3). Вопросы пользователю — `docs/QUESTIONS.md`, раздел «Склад по-новому» (СК-1…СК-9).

## 0. Что уже есть в данных (многого делать не надо)

- Движение `stockmovements` уже умеет: `type` (in/out/adjust/reserve/unreserve/count), `salesOrderId`, `salesOrderLineId` (= позиция заказа в `incomes`), `reservationId`, `issuedToPersonId`, `issuedTo` (текст), `documentRef`, `notes`, `batchId`, `clientUid`, `qtyBefore/qtyAfter`, `cancelOf`. Это почти всё для SK-5.
- `StockBatchDto` (приход/списание/пересчёт пачкой) уже принимает заказ, позицию, сотрудника и текст «кому». `StockMoveDto` (одна позиция) принимает сотрудника и текст, но **не принимает** заказ и позицию.
- `reservations`: есть `salesOrderId`, `groupName`, `batchId`, `issuedQty`, статусы active/released/fulfilled/cancelled; **нет ссылки на позицию заказа** (есть только `orderItemIndex` из старой логики комплектов CRM, смысл другой). Нужно необязательное поле «позиция заказа» (архитектору).
- «Выдать по брони» (`reservations/issue`) и «Бронь списком» (`reserve-list`) на сервере есть.
- Импорт Excel: в приложении есть чтение xlsx (`core/xlsx-read.js`) и вставка списком (`ui/bulk.js`), но **спецификации и шаблона нет**.

## 1. Единая запись «под что / кому» (общая для выдачи и брони)

Выбор «Кому / под что» — одно из трёх:
1. **Позиция заказа** — заказ № → позиция №. Пишется `salesOrderId` + `salesOrderLineId`.
2. **Сотрудник** (расходники, без заказа) — `issuedToPersonId`. Текст `issuedTo` — только если получатель не из списка (бригада, объект).
3. **Просто выдано** — ссылок нет; комментарий в `notes` (необязательно).

Допустимо и позиция заказа, и сотрудник сразу (сотрудник забрал материал под заказ). В состав изделия такая выдача идёт по заказу (п. 4).

## 2. Ссылка на позицию заказа: «заказ-позиция» (`552-2`)

- Хранится **не текстом**, а ссылкой `salesOrderLineId` (+ `salesOrderId`). Обозначение «552-2» всегда вычисляется на показе: `incomes.orderNo` + «-» + `incomes.lineNo`. Сменили номер заказа — обозначение не разойдётся.
- Показ: «552-2 · название позиции · картинка». Название — изделие (`productId`) или текст позиции; картинка — фото позиции (`photoIds`), иначе фото изделия, иначе заглушка. Цифры без названия не показывать.
- Выбор: два выпадающих списка с поиском: заказ (по № и клиенту) → позиция (по № и названию, с картинкой). Ввод «552-2» в поиск сразу находит позицию. Позиции грузятся при выборе заказа, не при открытии экрана.
- В списке только открытые заказы (не отгруженные и не аннулированные); «показать все» — галочкой.
- В истории движения и карточке заказа: «Выдано под 552-2: материал × N».
- Только заказ без позиции («на весь заказ») допустим: заполнен один `salesOrderId`.

## 3. Сценарии

### 3.1 Принять
Два входа, результат один — движение `in` (склад, зона, количество, цена `cost`, `documentRef`).
- **По заявке** (основной): заявка → «Принять» → позиции заявки с «заказано / уже принято / принимаем сейчас». Пишется `stockmovements` (`in`, `documentRef` = номер заявки или счёта, цена из заявки); в заявке растёт принятое количество и статус (частично / полностью).
- **Без заявки, есть оплаченный счёт**: «Принять» → «Без заявки» → счёт (номер, поставщик — пока текстом в `documentRef`), позиции склада (поиск), количество, цена из счёта. Нет такой позиции склада — создаёт кладовщик в этом же окне (категория и ед. изм. — из справочников). Ссылкой на счёт связь станет после «Бухгалтерии» (SK-3).
- Приём «по весу» и пачкой («несколько позиций») — как сейчас.
- Ошибки: количество ≤ 0, нет склада — запрет; повторное нажатие — защита `clientUid`.

### 3.2 Выдать
«Выдать» → «Кому / под что» (п. 1) → позиции (поиск; рядом остаток и «свободно» = остаток минус чужая бронь) → количество → «Выдать».
- Пишется `stockmovements`: `type=out`, `salesOrderId/LineId` и/или `issuedToPersonId`/`issuedTo`, `qtyBefore/After`, `notes`.
- Больше свободного, но есть остаток в чужой брони — предупреждение и подтверждение («берёте из брони заказа 553»); больше остатка — запрет.
- Если по выбранной позиции заказа есть бронь на этот материал — предложить «Выдать по брони» (3.4).
- «Отменить» — обратное движение (`movements/:id/cancel`).

### 3.3 Забронировать
«Забронировать» → заказ и позиция (списки; из спецификации подставляется сама) → позиции склада, количество.
- Пишется `reservations` (active, `qty`, `salesOrderId`, новая ссылка на позицию, `groupName` = «552-2 название») и движение `reserve`.
- Больше свободного — запрет, показать сколько свободно.
- Правка брони: число, позиция заказа. Уменьшение = `unreserve` на разницу, увеличение = `reserve`; всё в истории.
- «Висящие» брони (заказ отгружен или аннулирован) подсвечиваются в «Остатках», снимает человек (вопрос СК-6).

### 3.4 Выдать по брони
Заказ (или позиция) → список броней с количествами → «Выдать по брони» (подтверждение, строки можно убрать или уменьшить число).
- На каждую строку: `out` с `reservationId`, `salesOrderId/LineId` из брони; в брони растёт `issuedQty`; выдано всё — `status=fulfilled`; частично — `active` на остаток.
- «Кому» (сотрудник) — необязательно.
- Выдача из брони не требует «свободного»: бронь и есть право.

### 3.5 Спецификация → бронь — п. 5.

### 3.6 Пересчёт
Карточка позиции → «Пересчитать» → фактическое количество → подсказка «было N, станет M (разница ±K)» → «Записать». `type=count`, корректировку считает сервер; остаток изменился, пока вводили, — 409 «обновите и повторите» (`expected`). Факт ниже брони — запрет без подтверждения (`force`), в тексте — какие заказы в брони.

### 3.7 Списать
Карточка позиции или «ещё» → «Списать» → количество + **причина из справочника** (брак, потеря, порча, прочее — СК-7) + комментарий. Это `out` без заказа и сотрудника, причина в `notes`/поле причины. В состав изделий не попадает. Больше остатка — запрет.

## 4. Накопление состава изделия из выдач (SK-7)

Цель: после выдач под позицию заказа у изделия копится состав («6 болтов, 12 гаек…») и считается себестоимость.

**Когда предлагается.** После выдачи (3.2, 3.4), если: есть `salesOrderLineId`; у позиции есть изделие (`productId`); выдан материал. Выдача только сотруднику, списание, брак, пересчёт — не участвуют.

**С подтверждением человека, не автоматически** (СК-1). В конце выдачи плашка: «Добавить в состав изделия <название>: болт М8 × 6, гайка × 12» — «Добавить» / «Не добавлять» / «Позже». Причина: материал могли выдать на ремонт или с запасом, и молчаливая запись испортит себестоимость. «Позже» — в карточке изделия остаётся блок «Предложено из выдач».

**Расчёт** (СК-2). В состав идёт количество **на одно изделие** = нетто выдано под позицию (выдачи минус возвраты; отменённые не считаются) ÷ количество изделий в позиции (`incomes.qty`). Дробное — до сотых, с пометкой «округлено».

**Повторные выдачи.** Не прибавлять «ещё 6», а пересчитывать от суммы всех выдач под позицию: было 6, доплатили 2 → «6 → 8 на позицию». Повторное подтверждение не удвоит число. Если строка состава уже есть (введена вручную) и отличается — «в составе 6, по выдачам 8: заменить / оставить».

**Возврат** (СК-4). Приход `in` с той же позицией заказа и пометкой «возврат»; вычитается из нетто.

**Стандартное и индивидуальное изделие** (СК-3).
- Стандартное (много одинаковых): состав — эталон; из выдач предлагаем «Дополнить состав» с показом разницы, сами ничего не удаляем.
- Индивидуальное (под проект, одна позиция): состав растёт свободно, предложения принимаются целиком.
- Признака в изделии пока нет; до ответа ведём себя как для стандартного.

**Несколько позиций с одним изделием.** Если «на одно изделие» разное — показать расхождение, выбрать, какое принять; среднее не считать.

**Себестоимость.** Состав × последняя цена закупки из заявок и счетов (как в БЗ-5); у материалов без цены — «не всё с ценой». Цену выдачи как источник не берём.

**Куда пишется.** `products.composition` (`lineType='material'`, `refId` = позиция склада, `quantity` на одно изделие, `sourcePosition` = «552-2»). Новой таблицы не нужно.

## 5. Спецификация из Excel (SK-6)

**Где.** Инженер: «Забронировать» → «Из спецификации» → файл → просмотр → «Забронировать».

**Шаблон (скачивается из приложения, один лист).**

| Колонка | Обязательна | Пояснение |
|--|--|--|
| Заказ | да, если не выбран в окне | номер заказа (`552`); можно слитно «552-2» |
| Позиция | нет | номер позиции (`2`) |
| Код | нет | код/артикул позиции склада |
| Наименование | да | как на складе: «Болт мебельный М6×40» |
| Кол-во | да | число > 0 |
| Ед. | нет | сверяется с единицей позиции склада |
| Примечание | нет | идёт в `notes` брони |

Заказ и позиция — либо в файле построчно, либо одним выбором в окне на весь файл; если и там и там — побеждает файл, расхождение показывается.

**Сопоставление строки с позицией склада** (по порядку, до первого успеха):
1. по коду/артикулу (точно);
2. по наименованию без учёта регистра, пробелов, «×/х/x», запятых;
3. иначе «не сопоставлено»: автоматом не угадываем и **не создаём** новую позицию.
Нашлось несколько — «неоднозначно», выбор вручную в просмотре.

**Просмотр до записи (обязателен).** Таблица: строка файла → позиция склада → заказ-позиция → нужно / свободно. Статусы: «готово», «не хватает N (свободно M)», «не сопоставлено», «неоднозначно», «заказ или позиция не найдены», «другая единица». Сопоставление можно поправить выпадающим списком; строку можно пропустить. Ставятся «готово» строки; «не хватает» — только отдельной кнопкой «сколько свободно» (СК-9). Запоминание ручных сопоставлений — не в первой версии (СК-5).

**Итог.** «Забронировано X, не попало Y» + файл-отчёт с причинами по строкам (в том же шаблоне, чтобы исправить и загрузить снова). Во время разбора и записи — индикатор.

**Повторная загрузка заказа.** Не удваивает: «по заказу 552 уже есть брони из спецификации от <дата>: заменить / добавить / отмена». «Заменить» = снять прежние брони той загрузки (`batchId`), поставить новые; всё в истории.

**Техника** (формат, лимит 500 строк как в пачках, где разбирать файл) — архитектор; чтение xlsx в приложении уже есть.

## 6. Критерии приёмки

### SK-3 (решение архитектора) — что должно получиться
- [ ] У пользователя можно задать несколько ролей; видны разделы и поля всех его ролей; снял роль — разделы пропали.
- [ ] Старые пользователи и ключи `kppd_` работают без перенастройки; CRM не ломается.
- [ ] Движение и бронь хранят ссылку на позицию заказа и сотрудника; старые записи читаются без ошибок.
- [ ] Выбор «Кому / под что» в одном месте API, без дубля логики между выдачей, бронью и пачкой.

### SK-4 (Склад — одна страница)
- [ ] Три главные кнопки «Принять / Выдать / Забронировать» и «ещё» (Списать, Пересчитать); все открывают правую панель, не окно.
- [ ] В «Остатках» у позиции видны остаток, в брони, свободно; остаток = в брони + свободно.
- [ ] «Заканчивается» и «в брони» — сверху списка (или фильтром).
- [ ] История: последние 5 + «вся история»; в карточке позиции — её история и те же кнопки.
- [ ] Старые адреса вкладок «Движения» и «Операции» открывают новую страницу (не 404).
- [ ] «Несколько позиций» внутри «Принять» и «Выдать»: 10 строк проводятся одной операцией; отмена пачки откатывает всё.
- [ ] Варианты списков грузятся по нажатию кнопки; страница открывается без заметной задержки.

### SK-5 (выдача под позицию и сотруднику)
- [ ] Выдача под «552-2»: выбор заказа → позиции; в списке видны название и картинка, не только цифры; поиск «552-2» находит позицию.
- [ ] В истории и карточке заказа: «Выдано под 552-2: материал × N».
- [ ] Выдача сотруднику без заказа сохраняется с сотрудником; без выбора «кому» («просто выдано») проходит.
- [ ] Больше остатка выдать нельзя (понятная ошибка); из чужой брони — только с подтверждением, заказ-владелец назван.
- [ ] Остаток после выдачи = до − выдано; «Отменить» возвращает остаток.
- [ ] Повторное нажатие или повтор из очереди не создаёт дубль.
- [ ] Старые движения без позиции показываются как раньше.

### SK-6 (бронь, выдать по брони, спецификация)
- [ ] Бронь ставится на заказ и позицию из списков; больше свободного нельзя, пишется сколько свободно.
- [ ] Бронь можно изменить (число, позиция); в истории видны действия; «в брони» и «свободно» пересчитываются.
- [ ] «Выдать по брони»: список с количествами, подтверждение; после — остаток уменьшен, бронь «выполнена» (всё) или осталась на остаток (часть); повторное нажатие ничего не делает.
- [ ] Спецификация: шаблон скачивается; просмотр до записи; сопоставленные строки бронируются, остальные — в отчёте с причиной.
- [ ] Неизвестная позиция склада не создаёт новую позицию сама.
- [ ] Неоднозначное название даёт выбор, а не берёт первое.
- [ ] Повторная загрузка заказа спрашивает «заменить / добавить / отмена»; «заменить» не оставляет двойной брони.
- [ ] Пустой файл, чужой формат, >500 строк, нечисловое количество — понятная ошибка, ничего не записано.
- [ ] На загрузке виден индикатор.

### SK-7 (состав изделия из выдач)
- [ ] Выдача под позицию с изделием показывает «Добавить в состав»; выдача сотруднику, списание, пересчёт и позиция без изделия — нет.
- [ ] «Добавить» вносит в состав количество на одно изделие = нетто выдано ÷ количество в позиции; повторное подтверждение не удваивает.
- [ ] Доплата (6 → 8) предлагает «было 6, станет 8», а не «+8».
- [ ] Возврат под ту же позицию уменьшает расчёт; отменённая выдача не учитывается.
- [ ] Строка состава уже есть и отличается — показана разница и вопрос; сами ничего не удаляем.
- [ ] «Не добавлять» ничего не пишет; «Позже» оставляет предложение в карточке изделия.
- [ ] Себестоимость считается по последним ценам закупки; у материалов без цены сказано «не всё с ценой».

### SK-9 (пересчёт и списание) — для полноты
- [ ] «Пересчитать»: до записи видно «было N, станет M»; факт ниже брони — предупреждение с заказами; остаток изменился параллельно — «обновите и повторите».
- [ ] «Списать»: нельзя без причины и количества; больше остатка — запрет; в состав изделия не попадает.

## 7. Нужно от архитектора (SK-3)
- Необязательное поле «позиция заказа» в `reservations` (общая с CRM); принимать `salesOrderId`/`salesOrderLineId` и причину в `StockMoveDto` (сейчас только в пачке).
- Где хранить причину списания (поле или `notes` + справочник).
- Признак «стандартное / индивидуальное» у изделия — если пользователь решит различать (СК-3).
- Источник картинки позиции заказа для списка (без тяжёлых запросов).
- Возврат: приход с пометкой или отдельный вид (СК-4).
- Где разбирать файл спецификации; привязка `batchId` к загрузке для «заменить».
- Ссылка на счёт вместо текста `documentRef` — после «Бухгалтерии».

## 8. Решение архитектора SK-3 (2026-10-24, принято координатором)

**Главное:** новых коллекций нет; все новые поля — необязательные, без enum; формат ответов `{items,total,page,limit}` не меняется; после каждого шага — openapi + MAP.

| Тема | Решение |
|--|--|
| Кому / под что (SK-5) | `stockmovements` уже хранит `salesOrderId`, `salesOrderLineId`, `issuedToPersonId`, `issuedTo` — схему не менять. `StockMoveDto` + `salesOrderId?`, `salesOrderLineId?` (@IsMongoId). Одна функция `stock/stock-target.ts` `resolveTarget()` (заказ существует и не в корзине; позиция принадлежит заказу; заказ по позиции берёт сервер; сотрудник существует) — в move, batch, выдаче по брони, брони списком. |
| Причина списания (СК-7) | `stockmovements.reason?: string` — название из справочника «Причины списания» (dicts: брак, потеря, порча, прочее). Списание без заказа/сотрудника без причины → 400 «Укажите причину списания»; неизвестная → 400. В `notes` не класть. |
| Возврат (СК-4) | `stockmovements.isReturn?: boolean` — только у `in` и только с `salesOrderLineId` (иначе 400). `type` (общий с CRM) не трогать. Нетто под позицию = Σout − Σin(isReturn), без отменённых (`cancelledAt`, `cancelOf`). |
| Бронь под позицию (SK-6) | `reservations.salesOrderLineId?: ObjectId`; индекс `{salesOrderId:1}` sparse → после выкладки `scripts/ensure-indexes.js`. `orderItemIndex` (CRM) не трогать. В копии схем kppdf не вносить — записать в `UNIFY-SUPPLY-WAREHOUSE.md` «поля только data-core». |
| Картинка позиции | `GET /api/salesorders/:id/lines-lookup` → `[{id, orderNo, lineNo, title, productId, photoId, qty}]`, photoId: фото позиции → фото изделия → null; без цен; грузить при выборе заказа. «552-2» — считается на показе. |
| Спецификация Excel (SK-6) | Файл разбирается на клиенте (`xlsx-read.js`), на сервер — JSON-строки. `POST /api/stock/spec/preview` (ничего не пишет, ≤500 строк) и `/spec/apply` (брони с общим `batchId`, `groupName` «Спецификация <дата>»; «заменить» = снять брони прежней загрузки; повтор — `clientUid`). Сопоставление — одна серверная функция на `article-clean.ts`, один запрос `$in`, без N+1. Новых полей нет. |
| Состав из выдач (SK-7) | `GET /api/stock/composition-suggest?salesOrderLineId=` (нетто ÷ qty, разница с составом, цена последней закупки; деньги — только canSeeMoney) + `POST` «принять» через существующий сервис состава. Предложение не хранится — считается заново. |
| Стандартное/индивидуальное (СК-3) | Не вводить, заглушек не оставлять. |
| Видимость разделов (SK-8, минимум — сейчас) | `roles.appSections?: string[]` по константе `common/app-sections.ts`; пусто = как сейчас (по иерархии роли). `/auth` отдаёт `sections`, приложение строит меню по ним. Это только видимость — права остаются на маршрутах (@Roles, permissions, MoneyMask). «Две роли у человека» — пока новой ролью-сочетанием в «Ролях». |
| Несколько ролей (SK-8b, позже) | `users.extraRoles?: string[]` (не admin, ≤5), `role` не трогать; объединение через `userRoles()` в `roles-hierarchy.ts` во всех ~10 проверках; `kppd_`-ключ тоже. Отдельное ТЗ с тестами guard'ов — после SK-4…SK-7. |
| Бухгалтерия → Счета | Представление заявок (`invoiceNo`, `paid` уже есть), фильтры `hasInvoice`, `paid` — после SK-8. |

**Риски:** ValidationPipe — каждое новое поле сразу в DTO; `stock-movements.service.ts` (413 строк) — новое выносить в `stock-target.ts`, `stock-spec.service.ts`, `stock-composition.service.ts`; цены — только деньговым ролям.

**Нарезка и порядок.** Две цепочки идут одновременно, внутри цепочки — строго по порядку (общие файлы):

- frontend (`backend/pwa`, `backend/admin`): **4b** одна страница «Склад» с панелью действий (после 4a) → **5b** выбор «Кому / под что» с картинкой (после 5a) → **6b** брони и спецификация (после 6a) → **9** «Пересчитать / Списать» → **7b** блок «Предложено из выдач» → **8** меню по разделам, галочки ролей.
- SK-1 (фильтры) — параллельно, если не тот же файл, что 4b.
