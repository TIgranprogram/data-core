- Предпросмотр переносов показывает только реально изменяемые связи. Корни/листья с REVIEW остаются в старой ветке; спорные возвраты/подотчёт/дивиденды не меняют type. Если нужны разные входящие/исходящие статьи, подготовить отдельное решение, сохранив идентичность старых фактов.
- Для смены родителя payroll новый seed должен опираться на code, а не название родительской группы. Все ридеры/выборы/агрегации рекурсивные; сначала выпуск кода, затем перенос данных.
- До/после: сумма поступлений, сумма выплат, число платежей и allocation, даты, наши компании и articleId фактов совпадают; измениться могут только пути/групповые подытоги. ФОТпроверить отдельно на отсутствие дублирующих начислений/выплат.

- Нет разрешения из этого файла исполнять прод-миграцию. Нужны проверка на копии, свежая сверка, бэкап и конкретное разрешение применения.

## Что не решается перестановкой статей

- Пустую статью у оплаченного allocation исправлять отдельной классификацией с audit (CONTRACT§4), не falseсторно/повторной оплатой.
- Не выбирать company/project/costCenter по имени листа. Старые слова «офис/цех/площадка» сохраняются для узнаваемости, но измерения задаются связями исходного документа/явной корректировкой.
- Два «Представительских расхода»/два «Иные затраты»/два «Скипидар…» в разных ветках не объединяются по совпадению названия. Нужны usage/источники/выбор владельца.
- Доходную классификацию не выдумывать по названию заказчика/изделия. Настройка начальных подсказок допустима по явному lineType/service с подтверждением, но не массовое изменение оплаченных фактов без аудита.
