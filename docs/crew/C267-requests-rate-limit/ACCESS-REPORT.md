# C266 — read-only диагностика HTTP 429

Проверено 24.11.2026, около 14:45–14:46 МСК. Только штатные GET через `deploy/synology/api.sh`; нагрузка не создавалась, код/БД/прод не менялись.

- Прод `/app/version.json`: `v=d9c0c0d3`, `n=1053`, `b=a9897e4a`, дата приложения `2026-11-24T13:10:35+03:00`.
- Прод `/api/health`: `ok`; Mongo, память, диск, бэкап — `up`. Последний бэкап `2026-11-24T05:46:08`, возраст по API — 6 ч.
- `/api/client-errors/top?hours=1`: одна группа HTTP 429, **2 записи**, **1 пользователь**, `requests`, `GET /supply/requests`, `kind=background`, версия `d9c0c0d3`. Последнее событие `2026-11-24T11:44:03.111Z` = **14:44:03 МСК**. Контекст содержит повторные переходы и «Повторить»; это след действий, а не доказательство причины.
- За 24 ч в доступном top: **21 запись 429, 13 групп**; requests — 2, products — 11, salesorders — 7, desk — 1. У каждой группы users=1; это не доказывает одного пользователя для всех групп. Старые ошибки словарей паспортов и production-orders приходились также на предыдущие версии, до текущего выпуска C266.
- Один спокойный GET прода `/api/supply/requests?limit=1&page=1` успешно вернул пагинацию: `total=355`, `page=1`, `limit=1`, одна строка. Значения строк не выводились и не сохранялись. На момент проверки постоянной недоступности списка нет.
- Группированный журнал — не полный access-log: он ограничен top100 и собственной частотой приёма ошибок. Он не позволяет восстановить точную частоту запросов, конкретное окно лимита, заголовок Retry-After, долю пользователей или источник IP. IP, JWT и секреты не запрашивались/не печатались. Доступного штатного API сырого HTTP access-log в этой проверке нет.
- Локальный код, ориентир для разработчика: `app.module.ts` задаёт short=10/1000 мс и long=100/60000 мс. `ThrottlerBehindAuthGuard` строит tracker по роли и сетевому адресу; таблица getLimitForRole сама по себе ещё не доказывает фактическое применение этих значений. Настройки и фактическое окно на проде не изменялись и не проверялись чтением env.
- Стенд проверить **не удалось**: штатный `api.sh stand` завершился до входа, защита owned-стенда сообщает недоступный Docker Desktop Linux engine. Это **SKIP, не отсутствие 429**. Docker не запускал, защиту не обходил, нагрузку не создавал.

Санитизированная выборка групп 429 за 24 ч: `tools/logs/c266-429-errors.json` (без значений записей заявок, IP и токенов).

## Повтор после запуска Docker Desktop (C267)

По поручению координатора сделан один повтор `api.sh stand GET /api/health/ready`: Docker inventory уже доступен, но owned-защита сообщает **«backend собственного стенда не запущен»**, exit 3. До API запрос не дошёл. Стенд не запускал, restore/refresh не делал; старый C266 BROWSER не запускался. Ожидается новый проверенный сценарий C267.

## Baseline до исправления C267

После того как координатор запустил только существующие owned-контейнеры, health ready → `ok`, Mongo `up`. Проверенный им `c267-board-429-before.mjs` выполнен штатно через `api.sh stand BROWSER`, exit 0. Синтетические 429 и отчёты о них перехвачены внутри браузера; данные не менялись.

- Общий список и шесть колонок начали GET практически одновременно: 486–489 мс от старта сценария.
- `requested`: синтетический 429 на 505 мс; автоматический повтор на 1610 мс; второй 429 на 1611 мс. Указанный в перехвате `Retry-After-long: 3` не выдержан.
- Финал: одна ошибочная колонка (`failed=1`), **кнопок повторения нет** (`retryButtons=0`); видимый текст: «Не загрузилось / Слишком много запросов — подождите минуту».
- Остальные шесть ответов — 200; ошибок JavaScript нет. Снимок и тайминги сохранены сценарием в `evidence/`.

## Первый финальный прогон C267

Проверенный координатором `tools/logs/c267-board-429.mjs` выполнен через `api.sh stand BROWSER`, exit 1. **25 PASS, 2 FAIL, ошибок JavaScript 0**. Deadline light/dark, повторный 429 и ручной повтор, отсутствие заголовка, соседняя отложенная колонка и SPA-уход (`destroy`) прошли. Оба FAIL относились к смене поиска (`cancel`): «устаревший повтор не отправлен», «новый экран не испорчен». Зафиксированы запросы requested с пустым q на 0, 97 и 3103 мс. Подробности — `evidence/after.json`, сохранены 10 PNG. Сценарий и рабочий код агентом доступа не менялись; координатор уведомлён.

## Уточнение и повтор смены поиска

Координатор обнаружил и исправил дефект самого сценария: он проверял параметр `q`, а фактический API использует `search`, поэтому ложно подменял 429 также для нового поиска. Runtime frontend не менялся. Проверенный исправленный сценарий повторно выполнен только для `C267_CASES=cancel`: **3 PASS, FAIL 0, ошибок JavaScript 0, exit 0**. Новый результат — `evidence/after-cancel.json`; исходный `after.json` сохранён как история первого прогона. Утверждение первой краткой сводки о провале SPA-ухода было ошибочным: `destroy` уже был PASS.
