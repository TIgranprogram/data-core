# C244 — фото строки сопоставленного изделия

Решение: исправлять только read-only photo projection. Подтверждённая причина — common/photos.ts читает products.photoIds, тогда как3413 имеет productphotos purpose=passport/kind=overview; showcase уже разрешает этот источник. Ни income.photos, ни product.photoIds автоматически не заполнять.

1. Scope backend: `common/photos.ts` и небольшой общий resolver в `common/` (при необходимости), `modules/showcase/showcase-photos.ts` как совместимый adapter к вынесенной существующей логике, адресные specs. Common не импортирует showcase: обратное направление создаёт неверную границу/цикл. Перенести общий resolver вниз, не дублировать выборoverview в разныхмодулях.
2. Приоритет строки: пригодное собственное фото income (включая оригиналКП) → явно заданные каталожные products.photoIds → актуальный живой productphotos passport/overview → существующий совместимый legacy passportoverview fallback → null/штатныйplaceholder. Сохранить порядок existing explicitphotos, sortOrder/createdAt/_id overview и дату/id legacy. mainPhotoId не вводить как новый источник без подтверждения существующего контракта.
3. Все fallback-кандидаты привязаны строго текущему line.productId; несовпадающий productId/чужие kind dimensions/mounting/purpose исключены. Некорректные ObjectId/битые/deleted связи, original/variants и unsafeURL отбрасывать; следующий пригодныйoverview допустим. Использовать имеющиеся safeUploadPath/live-проверки resolver, не ослаблять ради результата. Product selection с deletedAt:null; собственные фото строки сохраняют приоритет независимо от изделия.
4. По странице — batch products/productphotos/legacyphotos/variants по уникальным ID, постоянное число запросов, без template/PDF/effectiveImages и GETdetail накаждуюстроку. Нет новыхcache/индексов/очистки данных. Пустойнабор пропускает запросы. Фильтр родителя/ролей/видимости остаётся у caller до вызоваhelper; resolver не добавляет чужиестроки в ответ.
5. Публичный контракт прежний: loadLinePhotos Map<lineId,{url,thumb}|null>, `salesorders.lines[].photo`, productiondetail и существующие callers общегоhelper наследуют fallback; новых endpoint/DTO/permissions нет. Production list намеренно возвращает coverPhoto:null поC017 и не вызываетhelper — этот performance-контракт внеC244 и сохраняется. Existing showcase photoSource/explicit photos массив сохраняются. Не расширять задачу на frontend редактор/паспорт/привязки.
6. Прочитать только затронутые callers: salesorders get/list, production get, shipments и stockreservations используют общийhelper; сохранить их source/parent/closed/archive guards. Salesorders.get/production.get уже показывают currentlines/photo и для closed; fallback здесь динамический и не является frozenисторией. Archive GETversion/filedownload читает сохранённые lines/chunks/SHA — не менять archiveFacts/prepareFiles/bundle/photoIds/PDF/issued attachments. Отдельный linesLookup (`GET /salesorders/:id/lines-lookup`, выборпри выдаче, `{photoId,photoThumb}`) **вне C244scope**, его прежний explicit-only контракт сохранить; не расширять задачу на этот другой consumer/UI.
7. Backendtests: фактическийcase own[]+catalogue[]+живойoverview→photo; incomeown вышеcatalogue/overview; explicitcatalogue вышеoverview; deleted/unsafe/invalid/otherproduct/otherkind не попадают; следующийvalidкандидат; сменаproductA→B не оставляетA; empty/noimage→null; несколькострок/общийproduct batch безN+1; adaptershowcase прежнийphotoSource/формат; callerclosed/archive беззаписей. Независимыйreview exactdiff послеfreeze.
8. QA/дизайнер: desktop заказ22-26,3413 видимаяминиатюра и переходизпродукции; ownКП приоритет, другаяпозиция/нетфото; productiondetail совместим, productionlistcover прежнийnull. Наprodтолько GET черезaccess; публикация послеотдельногоразрешения координатора. Изображения/данные проверяющий не меняет.
