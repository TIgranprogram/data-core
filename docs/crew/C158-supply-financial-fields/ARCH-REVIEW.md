### P1 — обязательный CAS при omitted version (условие PASS)

`supply-invoice-payments.service.ts:137,140,147–159`: canonical/defaults вычислены по first до транзакции, а fresh-version пока проверяется только при присланном dto.version. Между first и transaction либо при повторе callback возможна смена currency/payer: без version платёж сохраняет старые defaults, но currency нового документа. CAS в synchronize защищает fresh-версию внутри транзакции, но не связывает её с first, по которому построен canonical.

Координатор принял конкретную защиту: `expectedVersion = dto.version ?? Number(first.version || 0)`; внутри callback после prior-key replay проверять fresh.version против expectedVersion, включая retry callback. Тогда canonical не используется с другой версией, а состоявшийся replay по ключу остаётся разрешённым до CAS. Условие закрытия: точечный diff + forced-change/barrier тест между first и transaction, без присланной version, и прежние concurrent same-key/overpay/replay тесты. Рабочий код в этом review не исправлялся.

## Первый проход — сохранённые исходные находки

## P1 — валютное обязательство исчезает из денежных экранов

`backend/src/modules/finance/finance.service.ts:95`, `:125`, `:183`, `:281`.

Сценарий: выставить USD840 без документного курса/подтверждённой RUB-оценки; открыть календарь и прогноз. До первого платежа заявка имеет `priceHint=0` и отсекается запросом. После частичной фактической оплаты появляется ledger-маркер, однако `balanceDue=null` отсекается условием на строке125. Возвращаемые `{ops,invoices,awaiting}` не содержат отдельного списка таких обязательств. В результате незакрытые USD440 после оплаты USD400 остаются только в карточке счёта, а деньги показывают отсутствие ожидаемого долга. Это нарушает CONTRACT §2/§6.5: нужен список «Нужен пересчёт», без вымышленной рублёвой суммы и влияния на остаток.

Дополнительно `:129` не переносит в pending признаки `balanceEstimated`, currency/sourceBalance: известная валютная оценка показывается как обычная сумма рублей без оговорки об оценке.

Исправить: выбирать открытые валютные обязательства независимо от наличия ledger и положительного `priceHint`; отдавать отдельный список неизвестных RUB-оценок и сохранять валюту/исходный остаток/признак оценки у известных. Протянуть данные в календарь и прогноз. Проверить четыре случая: до первого платежа; после частичного платежа без оценки; после частичного платежа с оценкой; полностью погашенный счёт. Первые два должны оставаться видимыми, но не входить в рублёвые суммы; последний должен исчезать из ожидаемых.

## P1 — частичный склад раскрывает полный старый paymentSnapshot

`backend/src/modules/supply/supply-invoice-payments.service.ts:49–53`; `backend/src/modules/supply/invoice-financials.ts:58`; `backend/src/modules/supply/supply-invoice.service.ts:282`.

Сценарий: нетронутый legacy paid-счёт со snapshot150руб, из них видимая складскому пользователю строка50руб, скрытая100руб. `present(partial=true)` заменяет amount на50, но оставляет paymentSnapshot.amount150. `paymentTotals()` для legacy возвращает paidAmount150. Локальное исполнение реальной функции на scoped-входе подтвердило `{visibleAmount:50,paidAmount:150,sourcePaidAmount:50}`. Таким образом новый агрегат раскрывает полный итог чужой части счёта.

GETcard также возвращает `...inv`, где остаются полные `paymentSnapshot` и `paymentAdjustments`; новый MoneyMask скрывает их лишь у пользователя вообще без доступа к деньгам, но не у имеющего money-доступ с ограничением склада. Эти структуры требуют отдельного scope-преобразования, иначе скрытые строки и суммы доступны прямо из JSON.

Исправить: для partial отдельно вычислять legacy totals по видимым snapshot allocations и исключать/редактировать полные snapshot/adjustments. Проверить GETcard и GETlist, оба с money-capable scoped пользователем и legacy snapshot; нельзя ограничиваться новым ledger-счётом. Суммы50 должны совпадать, скрытая100/полный150 и ID скрытых строк отсутствовать.

## P2 — денежные запросы читают всю историю ledger

`backend/src/modules/finance/finance.service.ts:111–123`, `:281`.

Каждый `ops()` читает полные документы всех ledger-счетов, всех их заявок и всех active-платежей без ограничения компанией, периодом и проекции. Затем на каждый счёт повторяет `ledgerRequests.filter` и `ledgerFacts.filter`: CPU O(I×(R+P)), память O(I+R+P). Прогноз дополнительно вызывает полный `ops()` ради pending; вычисление начального остатка может вызвать его ещё раз. Глобальная исключаемость legacy действительно нужна, но для неё достаточно идентификаторов/маркеров; полные факты вне диапазона нужны лишь в сгруппированных итогах остатка, а не как документы в памяти Node.

Исправить: отделить глобальный набор invoiceId от выборки активных операций по `{payerCompanyId,date}` и от выборки открытых обязательств выбранной компании. Суммы платежей группировать в Mongo4.4; использовать Map по invoiceId для группирования строк. Прогнозу не вычислять посторонние доходы/ФОТ/факты ради pending. Проверить план индексов и число прочитанных документов на большой истории; время запроса измерить на наполненном стенде. Заявлять превышение300мс без замера нельзя: здесь доказан неограниченный рост работы, замера стенда в этом проходе нет.

## P2 — список счетов включает историю платежей и вложения

`backend/src/modules/supply/supply-invoice.service.ts:238–243`; `backend/src/modules/supply/supply-invoice-payments.service.ts:36–41`, `:54–55`.

Список читает все факты каждого счёта страницы и метаданные всех их подтверждений; `present()` включает до100 полных платежей на каждый элемент. Ограничение `slice(0,100)` применяется уже после чтения всей истории. Страница100счетов может получить10000 платежей с allocations/notes/files, хотя её строки используют только агрегаты. Это не новый SQL/Mongo N+1: чтение пакетное; проблема в размере чтения и ответа, растущем с историей.

Исправить: отдельное представление списка без `payments`/proof-files, только агрегаты и счётчик; историю и подтверждения читать по действию/пагинации карточки. Контроль: размер JSON списка не зависит от числа исторических платежей; число запросов остаётся постоянным.

## P2 — повтор платежа зависит от изменённых реквизитов счёта

`backend/src/modules/supply/supply-invoice-payments.service.ts:109–122`.

Сценарий: отправить RUB-платёж без необязательных payerCompanyId/sourceAmount; сторнировать его; разрешённым PATCH изменить компанию счёта; повторить исходное тело с исходным clientUid. `canonical(first,dto)` подставит новую компанию, requestHash изменится, поиск repeat вернёт409 вместо согласованного200. При смене валюты на USD предварительная canonical-валидация выдаст400 «Укажите сумму погашения в валюте документа» ещё до поиска сохранённого платежа. Повтор исходного намерения не должен повторно исполняться или зависеть от изменившихся после него defaults.

Исправить: хранить стабильный hash нормализованного присланного намерения отдельно от разрешённых на момент создания defaults; найти существующий ключ до проверок бизнес-состояния текущего счёта и сравнить с сохранённым намерением. Проверить replay после сторно+смены плательщика и после сторно+смены валюты, а также409 для реально изменённого тела. Находка передана backend; интеграционное воспроизведение требуется в его e2e. Попытка прямого импорта сервиса через ts-node не исполнила сценарий из-за зависимых schema/declaration startup-ошибок; это не результат e2e.
