# C151 — аудит источников изображений

Статус: чтение кода; причина конкретного случая 3218 требует readonly-фактов prod (статус, productId, photoId). Код не менялся.

## Фактическая цепочка Inventor

- passport-images.iLogicVb:519–525: читает /products/:id/photos?purpose=passport и запоминает только overview/dimensions/foundation. Прочие виды и purpose не участвуют. :530–539 загружает все три PNG прежде изменения связей; :540–545 повторно сверяет старые связи на конкурентную правку.
- :548–578 привязывает три новых изображения и пишет согласованные габариты/глубину; ошибка приводит к отмене уже добавленных новых связей. :580–583 удаляет прежние связи после успешной привязки всех трёх новых. ProductPhotoService.remove:73–75 выполняет soft-delete связи, физический файл остаётся.
- ProductPhotoService.upsert:26–45 создаёт новую связь, не имеет самостоятельной семантики replace по kind. Следовательно корректность замены определяется последовательностью attach/delete в используемой версии правила. Отправка старой локальной копией без delete — отдельная гипотеза, версию пользовательского файла пока не читали.
- :390 правило открывает #products?bookFor=productId. book-entry.js:17 передаёт только productId общему openBookForProduct, без специального контекста импорта.

## Почему обновлённое изделие может открыть старое изображение

- open-book.js:13–20 ищет до 20 паспортов по -updatedAt, предпочитает draft; если draft нет, выбирает issued. Открывается существующий паспорт, новый черновик создаётся только если паспортов вообще нет (:30–36).
- ProductPassportService.productImageRows:840–841 читает живые productphotos только purpose=passport, сортирует sortOrder/createdAt. Витринные фото сюда не подмешиваются.
- effectiveImages:848–851 для issued/annulled возвращает только собственные images[] снимка. Для draft с изделием mergeProductImages использует новые productphotos по kind вместо собственных старых видов (passport-product-images.ts:22–26). freezeImages:855–859 фиксирует эффективные изображения при выпуске, с guard status=draft.
- common.js:120 и book-images.js:16 показывают effectiveImages прежде own images. Поэтому при успешной замене productphotos черновик должен показать актуальный рисунок; issued сохранит прежний снимок. Это корректное сохранение выпуска, но общий вход после импорта не объясняет выбор исторического экземпляра.
- Гипотеза для случая 3218: после выпуска и при отсутствии draft ссылка Inventor выбрала issued. Подтверждать только сравнением prod status/own/effective/productphotos. Из одного кода статус 3218 неизвестен.

## Почему ручная загрузка добавляет старый и новый

book-images.js:39 содержит [...all,{kind,photoId}] и сохраняет весь images[] через PATCH (:22). Это строго добавление, а подпись обещает «Добавить ещё или заменить». У inherited-вида кнопка скрывается (:38–39); у issued рисунки собственные, поэтому upload доступен и добавляет второй overview. Удаление старого — отдельная кнопка (:32–34). Дефект подписи/действия установлен кодом независимо от версии Inventor.

## Отдельный разрыв миниатюры списка

passport-queries.ts:113–124 attachThumbs выбирает первый overview только из d.images. Не обращается к effectiveImages/productphotos даже у draft. Поэтому список способен показать старую/пустую миниатюру, когда GET карточки и draft PDF показывают новый рисунок из изделия. Это отдельный подтверждённый разрыв источников, а не доказательство причины открытой книжки 3218. attachThumbs вызывается после page slice (:66), возможное исправление должно загружать productphotos пачкой для draft страницы и сохранять issued-thumbnail по снимку.

## Минимальный контракт для решения координатора

1. Если prod подтвердит issued-контекст: вход после успешного импорта явно открыть актуальную работу изделия (переиспользовать draft либо предложить новый экземпляр/редакцию), сохранить исторический issued. Не менять effectiveImages issued на live-product.
2. Ручная загрузка: разделить «Заменить этот вид» и «Добавить ещё»; замена только после успешной загрузки, без физического удаления файлов и с сохранением прочих видов. Это frontend-контракт, backend PATCH уже принимает полный images[].
3. Миниатюра draft списка должна соответствовать effectiveImages; issued остаётся собственным снимком.
4. Проверка на копии: два набора PNG A→B, B без A в live links; ошибка upload/attach в середине сохраняет A; прочие kinds/purpose сохранны; существующий issued показывает A, явно открытая актуальная draft-работа показывает B.

Открытые факты: версия локального Inventor-правила пользователя; реальные old/new photoId и live/deleted productphotos; статус/выбор паспорта 3218. До данных и контракта исправления код не менять.
