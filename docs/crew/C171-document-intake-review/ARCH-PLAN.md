# C171 — архитектурный план до реализации

Основа: `7ce3eac1`, 21.11.2026. Совет по указанным клиентским файлам C169; серверная реализация ещё не проверялась. Код не менялся.

1. Разделить команды `analyze`, `review/save`, `prepare-send`, `send`, `reconcile`. `run/resume/retry` Пульта не должны вызывать прежнюю автоматическую запись. CLI C169 сохранить отдельным явно названным режимом либо перевести безопасно; не менять семантику скрытно.
2. Анализ использует локальный read-only адаптер API: только GET справочников/дубликатов. Сохранять SHA256, страницы, raw-кандидат, версию извлекателя/правил/модели и причины ДО `validateProposal`: сейчас `index.mjs:94–107` теряет спорные доказательства.
3. Не переименовывать старое `ready` в «Готово к отправке»: C169 `ready` означает уже подтверждённую запись. Ввести независимый `reviewState` и версию формата журнала; старые complete/receipt только сверять. Миграция не должна повторно отправлять завершённое.
4. Черновик: batchId, arrivalId, sourceSha256, revision, immutable candidate/evidence, operator patches, normalized payload, ruleVersion, target, actor. Каждая правка с expectedRevision; CAS под общим файловым lock, новая revision, повторная проверка всех полей. После начала отправки payload заморожен, менять можно только новой операцией после сверки старой.
5. Версия черновика должна проверяться доверенным сервером: локальный сервер Пульта владеет ревизией для UI/XLSX, DataCore проверяет идентичность подтверждённого payload и версии отправки. Для защиты от изменений справочников между сверкой и записью нужен DataCore preflight/send с серверным токеном или persisted draft revision/CAS, связанным с actor/target/source/payload. Одной проверки UI недостаточно.
6. `prepare-send` строит подтверждение с контуром, списком arrivalId/revision/hash; `send` принимает именно этот снимок. Повторяет права, однозначные ИНН/роли/плательщика, дубликаты/корзину, суммы/НДС. Не использует закэшированный `doc.parties` без нового разрешения ИНН.
7. Сохранить стабильный C169 UID от SHA256 и квитанции; batchId описывает поступление, не заменяет идемпотентность документа. Изменение revision не создаёт новый UID исходника. Первый успешный send фиксирует fingerprint; повтор с другим payload отклоняется, повтор с тем же восстанавливает квитанцию.
8. Отказ до записи не должен загружать PDF. Сейчас `api.mjs:453–459` загружает файл раньше POST счёта: отказ POST оставляет файл. Предусмотреть серверный preflight перед загрузкой и send с повторным guard; для строгой гарантии без загруженного PDF при любом отказе — единый multipart commit со staging вне опубликованного файлового архива и очисткой при отказе. Финальная видимость карточки/оригинала только после успешного commit. Файловый rename и Mongo-транзакция требуют явного журнала восстановления; не обещать общую атомарность.
9. Состояние «Загружено» только после receipt, обратного чтения полей/строк/связей/статуса и проверки байтов PDF (`api.mjs:401–427`). При обрыве повторяет reconciliation, не create. Документный отказ продолжает пачку; AUTH/MODEL_UNAVAILABLE/API_UNAVAILABLE приостанавливают. Ошибка исходника/ответа модели — на сверку, без остановки всех документов.
10. UI PDF читает только original по validated arrivalId через сервер Пульта; произвольные пути/URL запрещены. Ввод через allowlist полей и стабильные rowId; quote/page неизменяемы без проверки против сохранённых страниц. Исправление человеком не должно изображать машинное доказательство: хранить авторство и основание отдельно.
11. XLSX — дополнительный транспорт тех же patches: batchId/revision/arrivalId/rowId обязательны. Отклонять формулы, внешние ссылки, неизвестные/повторные строки и stale revisions; строки документа экспортировать как текст. Предпросмотр diff, затем CAS и тот же валидатор; никакого send при импорте XLSX.
12. Журнал исключений — отдельная служебная сущность с role/owner scope и идемпотентным ключом batchId+arrivalId+revision+code. Сайт получает причину/метаданные, без исходного PDF и полного текста; локальная outbox повторяет доставку. Ссылки не раскрывают локальные пути другому пользователю.
13. Подготовка ПК — отдельный resumable state machine: проверка → утверждённый компонент → download bytes/hash → install → реальный schema probe. Профили версионировать с точными digest/размером/движком; не выдавать непроверенный профиль за принятый. Не выполнять инструкции модели/документа, не передавать модели токены.
14. Поэтапно: A локальные черновики+очередь+проверки без POST; B серверные CAS/preflight/send и исключения; C Пульт/PDF/XLSX/setup; D общий пилот/чистый Windows/full. Счета выпускаются только после A–D; договоры/OCR/внешняя модель отдельно.
15. Обязательные негативные тесты: zero POST при анализе; спорный raw сохранён; stale UI/XLSX/confirm; справочник изменился после preflight; двойной click; kill после upload/commit; одинаковый SHA в двух пачках; битый средний PDF; старый ready C169. Новый Windows и эталон 30 счетов нельзя заменять unit-тестами.

Вердикт: реализацию начинать с A и серверного контракта B; выпуск пока не принят. `review-scope --done` не ставился: это адресный совет до кода, не ревью изменения. API/прод/стенд не вызывались; циклы не гонялись, код не менялся.

## Минимальный серверный этап без нового Nest-модуля

Разместить в существующем `supply` и отдельной служебной коллекции черновиков; не добавлять поля черновика в общую CRM-схему счёта. Прочитаны адресно controller/service C169 по дополнительному запросу координатора.

- **Инфраструктурный WIP A:** локальный сервер Пульта держит `batchId + arrivalId + sourceSha256 + revision + payloadHash` под файловым lock. `analyze`/`review` не имеют write-адаптера DataCore. Никакой новый send не включается, серверная приёмка не заявляется. Это безопасный законченный подэтап, не выполнение всего C171.
- **B1 `POST /supply/invoices/intake/review`:** `draftId, expectedRevision, sourceSha256, sourceSize, facts, evidenceSummary`. Доверенный сервер нормализует DTO, проверяет права/scope, ИНН и текущие организации, состав/НДС, известные дубликаты; CAS сохраняет новую revision/payloadHash и result. Источник PDF не загружается. Первое создание допускается только с expectedRevision=0; повторы одного requestId возвращают прежний результат. Отказ — метаданные исключения, не бизнес-запись.
- **B2 `POST /supply/invoices/intake/prepare`:** принимает точные draftId/revision/payloadHash; возвращает короткоживущий ticket с actor, scopeHash, contourId, rulesVersion, SHA256, revision, payloadHash и сроком. По желанию ticket — HMAC от claims существующим серверным signing-key с отдельным purpose. Секрет не передаётся Пульту. Сервер проверяет latest draft revision; изменение черновика инвалидирует старое подтверждение.
- **B3 `POST /supply/invoices/intake/commit`:** multipart ticket + PDF; сначала проверить claims/latestRevision, права, MIME/размер/хеш потока. Принимать bytes только в закрытый quarantine вне `/uploads`; обычный `PhotoDoc` и квитанцию C169 пока не создавать. Повторный GET квитанции до любой новой записи. Дальше transaction с общим identity lock C169, CAS `validated → committing`, повторные справочники/дубликаты и создание одной бизнес-записи/строк/PhotoDoc/receipt. FileId резервируется сервером. При отказе карантин удаляется, бизнес-транзакция откатывается.
- **B4 восстановление файловой публикации:** файловая система и Mongo не атомарны. Перед commit сохранить durable staging intent; готовые файлы публиковать в конечный путь с fsync/atomic rename; записи с pending-file не показывать обычным клиентам. Явно протестировать crash до/после rename и до/после Mongo commit. Возобновление по тому же uid завершает журнал, не создаёт второй файл. Если это слишком большой рефакторинг, B3 остаётся закрытым до реализации, старый upload-first не выдаётся за соответствие строгому отказу C171.
- **B5 `GET /supply/invoices/intake/review/:draftId` и существующий `GET /supply/invoices/intake/:uid`:** первый восстанавливает только разрешённый черновик и latest revision; второй восстанавливает результат send. Результат `uploaded` после полной обратной сверки C169, включая bytes.
- **XLSX/UI:** оба отправляют patches в локальный CAS, затем серверный B1 CAS; серверная revision из B1 включена в prepare/commit. Пропавший/устаревший draft не отправляется. Локальные пути не уходят на сайт.

**Почему одного signed ticket мало:** ticket доказывает «эта версия когда-то проверялась», но не «это текущая версия». Даже полная повторная валидация при import не выявляет, что оператор уже исправил черновик. Для latest-version CAS нужен сохранённый серверный revision/state либо явно иной согласованный контракт; ticket сам по себе одноразовость тоже не даёт. Идемпотентный UID защищает от второй карточки, но не от записи первой по старому подтверждению.

**Предел проверки PDF:** запрет «не отправлять исходный PDF при отказе» выполним буквально для отказов preflight. Сервер не может определить ошибку SHA/MIME самого PDF до получения bytes. Для конкурентных отказов commit quarantine предотвращает сохранение/публикацию оригинала; это точное техническое толкование следует отметить в REPORT, не обещать отсутствие сетевой передачи при любом отказе.
