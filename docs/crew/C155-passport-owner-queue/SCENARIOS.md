# П155-1 — живой прогон исходного состояния

Только изолированный стенд на копии реальных данных. Любой прод-адрес запрещён. Операции с заказом/платежами/складом не выполнять; тестовые записи ограничены паспортами/шаблоном копии.

Вход и секреты принадлежат datacore-access. QA пишет сценарий без секретов; access запускает его с уже полученным входом. Отчёты не содержат токенов и персональных реквизитов.

## Сценарии

1. Открыть карточку изделия1066 штатным поиском. Зафиксировать паспортные кнопки и их состояния.
2. «Править шаблон паспорта»: проверить заголовок, фактический объект, появление выбора фирмы, создание/выбор draft/issued. Ничего не выпускать ради самого редактирования.
3. В книжке проверить реальную очередь «Сначала», необязательные «срочно», правую таблицу материалов, наличие выбранного short/full.
4. Проверить доступный просмотр/скачивание/печать образца. Снять паспортные ID/статусы/номер до и после, чтобы обнаружить побочный выпуск или расход номера.
5. Нажать «Выпустить» на неполном1066 и зафиксировать точные блокеры. Не добавлять фиктивные материалы ради прохождения. Успех неподготовленного документа не требуется.
6. Проверить отдельный standalone-выпуск на готовом реальном изделии копии, если такой экземпляр доступен: выбранная организация, отсутствие заказа, однократный номер, повторное скачивание. При невозможности указать точную причину и SKIP.
7. Через карточку заказа открыть паспорт конкретной позиции. Сопоставить ID позиции/изделия/паспорта, проверить правку/просмотр/печать и возврат. Две позиции одного изделия проверять, если есть подходящая фикстура; иначе отметить отсутствие.
8. Светлая/тёмная темы на компьютере: доступность действий, дубли, ввод и ошибки. Не менять глобальные настройки пользователя, только локальный браузерный профиль стенда.

## Доказательства

Один краткий QA-REPORT.md с PASS/FAIL/SKIP по каждому действию и действительным URL/датой копии/версией кода. Скриншоты — evidence/qa-*.png, обезличенные сетевые факты — evidence/qa-results.json. Полученные PDF при наличии — в evidence, без личных реквизитов в именах файлов.

Скриншот владельца — evidence/owner-1066.png. Он не заменяет свежую проверку текущей версии.

## Разделение

QA: подготовить `scenario.test.mjs` в этой папке по FRONTEND-AUDIT, используя существующий Playwright из проекта. Не читать серверную зону и секреты. URL/токен получать через environment, жёстко разрешить только 127.0.0.1/localhost на порту подготовленного QA. Не логировать auth/тела запросов с токенами. Скрипт диагностический, не команда пульта для пользователя.

Access: проверить изоляцию и версию, выполнить сценарий; ключи/пароли не передавать координатору. Отдельно записать ограничения live Inventor и физической печати.

Координатор: визуально оценить итоговые снимки и синтезировать аудит/очередь исправлений. Текущие дефекты не превращать в PASS оттого, что программные проверки зелёные.
