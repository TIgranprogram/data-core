# C050 — совет перед кодом (architect/opus, 2026-11-08)

**1. Мультироли — нет; одна своя роль.** «Рабочий» = baseRole `user` + `['my-tasks']`; «Мастер» = baseRole `manager` + `work`, `my-tasks`, «Деньги» выкл. Нужна смесь — директор создаёт роль-комбинацию галочками (это уже есть). `extraRoles` трогает не 3 функции: в `backend/src` 72 прямых сравнения `user.role`, клиент берёт одну роль (`pwa/core/api.js:32-57`), `PermissionsGuard` смотрит `{name: user.role}` (`permissions.guard.ts:92-99`). Польза для 50 человек та же, риск ниже на порядок. `users` не трогаем совсем.
**2. Если мультироли всё же понадобятся (позже):** одна функция `rolesOf(user)` в `common/roles-hierarchy.ts`, все проверки только через неё. Список ролей кладёт `JwtStrategy.validate` в `req.user`, в JWT ничего не писать. Стратегия и так читает пользователя на каждом запросе (`jwt.strategy.ts:41`), поэтому снятие роли действует сразу, а не «со следующего входа».
**3. `persons.userId`** (`persons` — `kind: core`, не CRM): ObjectId; уникальный частичный индекс `{userId:1}`, `partialFilterExpression: {userId: {$type: 'objectId'}}` (Mongo 4.4 это умеет) — в схему и `ensure-indexes.js`. Пишет только admin/director через карточку сотрудника (сохранение `dicts` persons, `dicts.defs.ts:552+`). Проверять: пользователь есть, не удалён; занят → 409 «вход уже у <ФИО>». Увольнение или удаление сотрудника → `$unset userId` (иначе индекс держит вход). Шаги с `assigneeId` остаются как история. `/my-tasks` находит человека запросом `persons.findOne({userId, deletedAt: null})` по индексу, без кэша.
**4. Порядок и подводные камни.**
- Э1a: `persons.userId` + индекс + поле в карточке; сид двух ролей по `name` идемпотентно: создать, если роли нет; правки директора не перезаписывать.
- Э1b: `GET /my-tasks` → `@Roles('user')` + `@AppSection('my-tasks')`. В ответе только явный белый список полей (projection), на `MoneyMask` не полагаться. Без `limit` по всем планам нельзя: брать `steps.assigneeId` (индекс есть, `order-line-plan.schema.ts:30`) + только запущенные планы.
- Действия: одна атомарная запись с фильтром `{_id, steps: {$elemMatch: {_id: sid, assigneeId: myPerson}}}` и позиционным `steps.$.…`. Совпадений 0 → 403/404. Не писать `steps.${index}`, как в `work-schedule.service.ts:146` (гонка с правкой плана). Идемпотентность — `startedAt: {$exists: false}` в фильтре.
- 🔴 Не делать `$inc: {rev}` на действиях рабочего. Иначе каждое «Начал» даёт мастеру 409 в Ганте (`work-schedule.service.ts:160,193`) и при сохранении плана (`order-line-plan.service.ts:190`).
- 🔴 Сохранение плана переписывает `steps[]` через `normalizeRows`. Он переносит только `startedAt/finishedAt` (`common/work-route-rows.ts:121`). Новые `status/reason/deferUntil/reportedAt/By` добавить туда же, иначе менеджер молча сотрёт «Отложено/Проблема». Юнит на это — обязателен.
- 🔴 Права рабочего шире одного экрана. 19 контроллеров с `@Roles('user')` без `@AppSection` (dicts, user, photos, messages, today, audit…) открыты роли на base `user`. e2e под токеном «Рабочего» обходит их список: всё лишнее → 403, нужное (notifications, units) — явно разрешено. Отдельно проверить, что список `persons` не отдаёт телефоны и ставки всех.
- e2e: чужой шаг → 403; рекурсивный поиск ключей `MONEY_FIELDS` + `factHours/hours` по всему JSON; повтор start/finish → одна строка `workhours`.
- Клиент: обобщить `onlyStockMobile` (`api.js:57`) в `onlySection(id)`, копию рядом не заводить. У «Мастера» `session.role` = `manager`, поэтому `canEdit` = true (`api.js:35`): кнопки правки проверить в разделе «В работе».

Вычеркнуть:** `users.extraRoles` и критерий «две роли объединены»; «со следующего входа» (действует сразу); фото к «Проблеме» (→ C051 или потом); авто-уведомление «всем мастерам» заменить счётчиком в «Сегодня» (уведомление — одной строкой, если просто); штриховку в Ганте (Э4) — отдельным M после приёмки Э3.
