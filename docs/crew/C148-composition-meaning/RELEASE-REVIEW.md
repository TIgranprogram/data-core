# C148 — серверная проверка перед выпуском

**Вердикт после проверки порта C095: до выпуска защитить богатые modules[].** Прежние три P1 закрыты, но новое уточнение владельца выявило риск потери существующих name/dims/qty/photoId при первом issue. Подробности — AUDIT.md §7. Непроверенные бизнес-сценарии не объявляются PASS.

## Первоначальные P1 backend (закрыты, финальная перепроверка выполнена)

1. **Предпросмотр и новый выпуск расходятся по старым модулям.** `passport-pdf-v2-layout.ts:38` прячет legacy modules[] только у draft с compositionSheet. Первый выпуск `passport-issue.ts:57` меняет статус на issued, не фиксируя выбранную модель отображения и не очищая дубль. Такой документ перед выпуском показывает одно дерево, после выпуска опять оба списка. Нужен явный frozen-признак версии представления при первом выпуске нового документа либо исключение legacy modules из этого первого выпуска при известном дереве. Старые issued не менять. Тестировать реальный переход draft → issue → повторный PDF, а не два независимых mocked статуса.
2. **Сервер может выдать собственное несохраняемое предложение.** `composition-expand.ts:140`, `materials-text.ts:148–151,161–163` объединяют все пути одного сырья/материала, но `material-source-refs.ts:13` отвергает больше 100 источников в строке. Допустимый BOM из 101 разных деталей с одним сырьём даёт sourceRefs=101 и 400 при parseMaterialsSpec. Лично воспроизведено без БД на реальных функциях через ts-node. Согласовать bound producer/consumer: разбивать предложенные строки или дать явный контролируемый overflow с сохранением источников; не усекать молча. Дубли и повтор принятия должны оставаться идемпотентными.

## Что сделано безопасно

- sourceRefs аддитивны и необязательны; старые строки остаются без них. Парсер ограничивает список, глубину, виды, ObjectId и длину текстов; произвольные ключи отбрасываются (`material-source-refs.ts:11–28`). В печати источник — сохранённое название/обозначение, без склонения по догадке (`tech-sheet-rows.ts:46–48`).
- Полный путь проходит parse → present → StoredSpec и паспортный DTO (`materials-table.ts:56–64,83`; `create-product-passport.dto.ts:59`). Update DTO наследует Create через PartialType. Схема паспорта хранит этот объект целиком. Showcase PATCH использует Record и ручной parse, скрытого вложенного DTO с whitelist, который выбрасывал бы sourceRefs, не найдено.
- `techsheet-gaps.ts:11–18` исключил partIds из готовности и очереди. Пустые строки и отсутствие materialId всё ещё дают пробел материалов. Это соответствует необязательному словесному названию части.
- Метаданные — снимок происхождения, не новый FK, не источник прав доступа и не команда переименования физической позиции. Копирование сохраняет историческое происхождение, производственный BOM не переписывается.
- Разные детали с одинаковым названием разделяются по refId/path/lineId, вложенные изделия для таблицы родителя не разворачиваются, подбор материала по имени остаётся только предложением. Коллекции и маршруты не заменены.

## Readiness и границы обещания

Readiness по сохранённой materialsSpec совместим с безопасным явным принятием: BOM не должен угадывать материал или перезаписывать ручной текст. Но такой readiness означает **«в принятой таблице заполнены материалы»**, а не «весь текущий BOM покрыт материалами». После добавления в BOM неизвестного сырья прежняя таблица может оставаться готовой; unmatchedSources появится лишь при новом запросе предложения.

Поэтому нельзя объявлять автоматическую проверку полноты текущего BOM выполненной. Для текущего scope достаточно явно показывать актуальность/расхождения и неизвестные источники в предложении, сохранять их при принятии остальных строк и не называть такую ситуацию полной синхронизацией. Если требуется блокировать выпуск по непокрытому BOM, это отдельное правило проверки покрытия и отдельная согласованная граница обязательности; одного удаления parts из очереди недостаточно. Frontend и сценарий частичного принятия ещё проверить.

Закрытия и корректные пути frontend:

## Финальная перепроверка исправлений

- `passport-issue.ts:55–56` атомарно фиксирует modules:[] вместе с первым issued при непустом printable tree. Существующие issued возвращаются до записи. Тест вызывает реальный PassportIssue и затем раскладку PDF, проверяет новый выпуск/legacy/reissue.
- `materials-text.ts:183–192` разбивает sourceRefs на группы100, не сливая их обратно. `showcase-materials.ts:49–50` вызывает тот же parseMaterialsSpec до успешного ответа. Границы строк/пути/ручных значений остаются явными ошибками, усечения нет.
- `passport-from-product.ts:64–70` сохраняет ручное name и marker при повторной синхронизации. `product-passport.service.ts:311–322` защищает отличающееся имя при создании, не замораживая обычное каталожное имя.
- `passport-pdf.service.ts:247` больше не читает incomes для подмены имени. Single и batch получают сохранённые имена и textSnapshot; old issued без marker также остаются неизменными. Тест перехватывает фактический input обоих рендеров и проверяет отсутствие create/issue/запроса incomes. Генерация PDF-байтов в этом тесте подменена, фактическая вёрстка принимается отдельно.
