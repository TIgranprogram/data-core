# Полный аудит `tests_ai_tiit`, `md.md` и вариантов превращения в рабочий плагин для `data-core`

**Дата аудита:** 05.11.2026  
**Проект:** `D:\invSportiN\Сайт\01_Проекты_CRM\data-core`  
**Проверенная область:** `tests_ai_tiit\`, файл `md.md`, подпроект `nightshift\`, ключевые документы и архитектурные правила `data-core`.  
**Цель:** понять, что реально создано, что не работает или не завершено, что совместимо с проектом, и какой вариант плагина даст практическую пользу без дублирования пульта и риска для данных.

---

## 1. Итоговое заключение

В папке лежат **два разных замысла**, которые сейчас ошибочно воспринимаются как один проект.

1. `md.md` описывает **PLM AI Copilot**: интеллектуальный слой с tool calling, серверной оркестрацией, детерминированными проверками, аналитикой и будущими предложениями клиентам.
2. Остальные документы и код `nightshift\` описывают **отдельный QA-harness «Ночная смена»**: безопасный запуск тестов `data-core` на изолированном Docker-стенде, формирование отчета и handoff.

Эти направления связаны, но не должны становиться одним приложением.

### Моя главная оценка

`nightshift` уже можно считать **полезным рабочим каркасом QA-инфраструктуры**, однако это **не готовый AI-плагин**, не полноценное автономное приложение и не реализация всех требований ТЗ. По текущим документам тема отдельного окна и новых кнопок для Nightshift закрыта: проверки запускаются из существующего пульта.

Самый правильный путь:

- сохранить `nightshift` как **внутренний безопасный исполнитель тестов**;
- подключить его к существующему `pult` только через одну управляемую команду и существующий release-gate;
- не строить второй GUI и второй оркестратор поверх `data-core`;
- вынести идеи `md.md` в отдельный будущий **Data Core AI Copilot / AI Control Plane**, который работает через REST API и зарегистрированные серверные инструменты;
- сначала сделать 3–5 реальных read-only инструментов для анализа `data-core`, а не пытаться сразу строить универсального автономного агента.

**Реалистичный статус:**

- как QA-harness: **рабочая принятая основа, примерно 60–70% нужного минимального QA-контура**;
- как полноценная «Ночная смена» по исходному ТЗ: **не завершено, примерно 25–35%**;
- как AI Copilot из `md.md`: **архитектурная концепция, реализация почти отсутствует**;
- как безопасный плагин для текущего проекта: **создать можно, но это должен быть адаптер к существующему пульту, а не второе приложение**.

### 2.3. Фактические наборы тестов

Реально подключены:

- `harness` — тесты самого Nightshift;
- `static` — проверки data-core, заявленные как typecheck/ESLint/PWA imports/backend unit;
- `backend_unit` — запуск backend unit-проверок;
- `isolation_check` — проверки изоляции стенда;
- `regression` — текущий read-only regression-проход внутри стенда;
- `demo` — учебный набор с намеренным падением;
- `backup`, `load`, `soak`, `chaos`, `fuzz`, `mutation`, `visual`, `monkey`, `flaky` — **не реализованы** и явно помечены `implemented: false`.

По `BLOCKERS.md`, `PROGRESS.md` и `README.md` два night-профиля были приняты: `harness`, `static`, `backend_unit`, `isolation_check`, `regression` прошли успешно. Одновременно там прямо указано, что это не означает готовность всех обещанных наборов.

## 3. Сверка `md.md` с реальным `data-core`

## 3.1. Что в `md.md` совпадает с архитектурой проекта

### Разделение детерминированного и интеллектуального уровней

Это полностью соответствует `data-core`.

Правильная мысль из `md.md`: SQL, фильтрация, сравнение, проверка обязательных полей и расчет агрегатов должны выполняться кодом и базой данных. ИИ должен объяснять результаты, классифицировать проблему и предлагать следующий шаг.

Для `data-core` это особенно важно, потому что:

- MongoDB является постоянным ядром данных;
- API — единственная нормальная точка доступа внешних клиентов;
- у API уже есть JWT, машинные ключи `kppd_`, права, роли, rate-limit и аудит;
- данные нельзя отдавать модели целиком;
- часть коллекций общая с CRM и финансово значима.

### Единый набор серверных инструментов для кнопки и ИИ

Идея использовать одни и те же серверные функции для кнопки человека и вызова ИИ очень сильная.

Например, одна функция:

```text
get_product_structure()
```

может быть вызвана:

- человеком из панели;
- MCP-коннектором;
- AI-агентом через function calling;
- ночным анализом;
- внешним скриптом через API.

Это лучше, чем писать отдельный код для каждой точки входа.

### Предварительная обработка данных

Идея pre-computation полностью соответствует проекту. Агрегаты, поиск по индексам, проверка связей и сравнение версий должны происходить на сервере. Модели нужно передавать только компактный результат:

```json
{
  "entity": "product",
  "id": "...",
  "checks": 12,
  "errors": 2,
  "warnings": 4,
  "risk": "medium"
}
```

Это снизит стоимость, уменьшит утечки данных и сделает выводы воспроизводимыми.

### Semantic layer

`data-core` уже имеет основу semantic layer:

- `docs/openapi.json`;
- `docs/CONNECT.md`;
- `/api/meta/schema`;
- `/api/meta/openapi.json`;
- `/api/meta/guide`;
- реестр коллекций;
- машинные ключи с ограниченным scope;
- единые ответы списков `{items,total,page,limit}`.

Поэтому `md.md` не нужно реализовывать как отдельную базу или отдельный backend. Правильнее достроить слой описания операций поверх существующего API.

## 3.2. Где `md.md` не совпадает с текущим проектом

### PLM — не текущая главная предметная область

`md.md` написан языком PLM: BOM, изделия, ревизии, ECO, CAD, ERP, предложения клиенту. В `data-core` сейчас приоритет другой:

- рабочее место;
- снабжение;
- склад;
- заказы;
- заявки;
- контрагенты;
- продукция;
- паспорта;
- общие коллекции с CRM.

Поэтому нельзя начинать с универсального PLM Copilot. Сначала нужно адаптировать терминологию к реальным коллекциям и действиям `data-core`.

### Предлагаемые функции пока не существуют как единый tool registry

Функции вроде `compare_revisions()`, `find_open_changes()` и `calculate_implementation_scope()` являются названиями идей. В текущем коде нет общего реестра таких инструментов, JSON Schema для параметров, разрешений, версий и журнала вызовов.

### Нельзя давать ИИ прямой доступ к MongoDB

В `md.md` есть формулировка «PLM-база». Для нашего проекта это не означает доступ агента к MongoDB. По правилам `data-core` внешние клиенты ходят через API и ключ. Будущий Copilot должен использовать:

```text
AI → tool registry → data-core REST API → MongoDB
```

а не:

```text
AI → MongoDB
```

### «Самообучение» нужно заменить на контролируемое улучшение

Хорошо, что `md.md` не предлагает менять веса модели бесконтрольно. Но в рабочей реализации нужно еще жестче разделить:

- неизменяемый журнал действий;
- подтвержденные примеры;
- версии промтов;
- версии правил;
- черновики предложений;
- решения, одобренные человеком.

Иначе база знаний начнет накапливать ошибочные выводы.

## 4. Сверка Nightshift с реальным data-core

## 4.1. Что сделано правильно

### Безопасная изоляция Docker

В `stand/docker-compose.yml` предусмотрены хорошие защитные решения:

- отдельный случайный project `nsqa-<32 hex>`;
- отдельные контейнеры;
- отдельная MongoDB;
- отдельная база с суффиксом `-night`;
- внутренняя Docker-сеть `internal: true`;
- отсутствие опубликованных портов;
- запрет `docker.sock` и `.env` mounts;
- synthetic secrets;
- ownership labels;
- запрет работы с чужим project;
- `down` без `-v`, чтобы остановка не удаляла volume.

Это сильная часть проекта и хорошая база для production-like QA.

### Отказ от production fallback

Это принципиально правильно. Без явного `--project` тестовый API-контур блокируется. Без явного backup `stand refresh` не должен выполнять восстановление.

### Плагинная структура suites

В `orchestrator/plugins.py` ядро ищет `suites/*/suite.yaml`. Это хороший механизм расширения:

```yaml
name: my_suite
command: [python, -m, my_suite.run]
timeout_sec: 300
priority: important
needs_stand: true
```

Новый набор можно добавить папкой, не переписывая основной runner.

### Безопасный runner

Runner использует список аргументов, `shell=True` не используется, вывод кодируется UTF-8, есть таймаут, на Windows убивается дерево процессов через `taskkill /T /F`.

### Разделение ошибок

Есть различие между:

- ошибкой приложения;
- ошибкой runner;
- timeout;
- blocked;
- not implemented;
- ожидаемым падением demo.

Это лучше обычного «зеленый/красный» и полезно для будущего AI-анализа.

### Redaction

В проекте реализована маскировка на границах сохранения отчетов, логов, handoff и Docker-ошибок. Это важнее красивого интерфейса: ошибки не должны уносить секреты в архив для ИИ.

## 4.2. Главные ограничения текущего Nightshift

### Это не полноценная «ночная смена» из исходного ТЗ

По собственным документам не входят в текущую готовность:

- нагрузочные тесты;
- soak;
- chaos;
- fuzz;
- mutation;
- visual;
- monkey;
- flaky;
- backup-suite;
- полноценный локальный AI-цикл;
- GUI;
- полноценное расписание;
- работающий resume всей ночи;
- автоматическое исправление кода.

Их нельзя считать готовыми только потому, что папки и `suite.yaml` существуют.

### AI-цикл является заглушкой

`ai/loop.py` содержит фактически минимальную заготовку:

```python
class AILoop:
    def process(self, issue):
        return {"status": "done"}
```

`llm_client.py` умеет отправить простой запрос к OpenAI-совместимому API, но вокруг него нет полноценного цикла:

- роли сортировщика, диагноста, исправителя и рецензента;
- Pydantic-схемы результата;
- проверки JSON и повторного запроса;
- patch apply;
- отдельной ветки;
- хешей тестов;
- проверки, что тесты не ослаблены;
- лимита попыток;
- воспроизведения на чистом стенде;
- записи подтвержденного решения в fix history.

Следовательно, локальный ИИ сейчас **не исправляет код**.

### Отчет пока намного проще ТЗ

`report.py` формирует JSON и HTML, но HTML — фактически `<pre>` с JSON. Отсутствуют или не полностью реализованы:

- Jinja2-шаблон с понятной сводкой;
- отдельные тесты вместо одного большого набора;
- надежное сравнение с прошлым прогоном;
- тренды деградации;
- приоритеты проблем;
- file:line;
- повторяемость `N из M`;
- resource metrics;
- группировка дублей;
- автоматический bisect;
- полноценный config diff.

### Handoff — технический контейнер, а не полноценная передача ИИ

`handoff.py` создает структуру и ZIP, это полезно. Но `README_FOR_AI.md` сейчас состоит из двух строк, а содержимое недостаточно объясняет:

- какой commit проверялся;
- какие suites реально выполнялись;
- какие результаты являются blocked;
- какие данные были замаскированы;
- как воспроизвести проблему;
- какие действия запрещены;
- что нужно проверять перед переносом патча.

### SQLite пока не является журналом прогонов

`db.py` создает таблицы, но `cli.py` не строит полноценный lifecycle записи run/stage/issue/attempt/fix/metrics. Наличие схемы не равно наличию истории.

### Resume не подключен к основному прогону

`resume.py` умеет записать стадию и найти следующую, но основной CLI не организует весь прогон через эти записи. После перезагрузки нет доказательства, что ночной workflow продолжится с нужного места.

### Scheduler слишком минимален

`scheduler.py` умеет создать или удалить ежедневную задачу `schtasks`, но нет:

- отдельной CLI-команды управления расписанием;
- проверки существующего задания;
- безопасного quoting сложной команды;
- хранения профиля и project;
- восстановления после перезагрузки;
- проверки логов Task Scheduler.

### Packaging потенциально неполный

В `pyproject.toml` указано:

```toml
[tool.setuptools]
packages = ["orchestrator"]
```

При этом проект содержит `ai` и другие подпакеты. Для запуска из исходной папки это не всегда мешает, но для `uv build`, PyInstaller или переносимого `nightshift.exe` может привести к неполному пакету. Это нужно проверить отдельной сборкой.

### Карта сценариев еще черновая

`scenarios.yaml` содержит 15 сценариев со статусом `draft`. Это хороший старт, но пока:

- сценарии не утверждены владельцем;
- покрытие не доказано тестами;
- не все реальные потоки рабочего места перечислены;
- карта не является полноценным контрактом для e2e;
- `scenarios sync` не превращает автоматически найденные изменения в рабочие тесты.

### Discovery содержит устаревшие и спорные места

`ГЛАВНЫЙ_ОРКЕСТРАТОР.md` прямо предупреждает, что часть снимка состояния устарела. В `DISCOVERY.md` встречаются старые сведения о контейнерах и путях. Для рабочего плагина discovery нужно обновлять автоматически и хранить дату, commit и источник каждого факта.

## 5. Важное расхождение в документации

В документах есть одновременно две линии:

1. `README.md`, `BLOCKERS.md`, `PROGRESS.md` сообщают, что T22 закрыт и пять suites приняты.
2. `ГЛАВНЫЙ_ОРКЕСТРАТОР.md` содержит подробный исторический раздел, который перечисляет прежние ложные зеленые места: static-заглушку, regression только самого harness, неполный стенд и простой handoff.

Это не обязательно противоречие во времени, но для будущего агента опасно. Нужно явно маркировать документы:

- `CURRENT` — актуальное состояние;
- `HISTORY` — исторический снимок;
- `SUPERSEDED` — требования отменены;
- `NOT_IMPLEMENTED` — функция не реализована.

Иначе ИИ может прочитать старое утверждение и объявить несуществующую проверку готовой.

## 6. Оценка совместимости с правилами data-core

| Область | Совместимость | Комментарий |
|---|---:|---|
| Запрет записи в production | Высокая | В стенде есть ownership и synthetic environment |
| Mongo 4.4 / rs0 | Высокая | Используется подходящая версия и replica set |
| API-only принцип | Средняя | QA-стенд может обращаться к Mongo внутри стенда, но AI-плагин должен использовать API |
| Общие CRM-коллекции | Риск | Нужны отдельные QA-копии и запрет удаления общих данных |
| Пульт как единственная пользовательская точка | Высокая после решения T22 | Не делать второй GUI |
| Контракт API | Высокая | Ночные проверки должны использовать публичные API и реальные схемы |
| Аудит действий | Пока средняя | Nightshift имеет собственные логи, но нет единого журнала действий AI-инструментов |
| Права и ключи | Средняя | Нужен отдельный read-only ключ со scope по приложению |
| Бэкапы и restore | Средняя | Refresh поддержан, но backup-suite не является готовой ночной проверкой |
| Безопасность секретов | Высокая в стенде | Нужно проверять упаковку и экспорт handoff отдельно |
| Поддержка PWA/admin | Средняя | Есть import/static проверки, полноценная UI-регрессия не включена |
| Единый дизайн и правила проекта | Высокая | Если не создавать второй GUI |

## 7. Что реально можно создать из этого

## Вариант A — рекомендуемый: QA-плагин Nightshift для существующего пульта

Это самый безопасный и полезный вариант.

### Целевая схема

```text
pult
  ↓ кнопка «Проверки выпуска» / «Night QA»
  ↓
tools/dc.cmd или отдельный безопасный launcher
  ↓
nightshift CLI
  ↓
Docker QA-контур
  ↓
report.json + report.html + handoff
  ↓
pult показывает краткий итог
```

### Что получает владелец

- одна кнопка в уже существующем пульте;
- явный профиль `local` или `night`;
- запрет запуска без ownership и project;
- отчет по пяти принятым suite;
- понятный статус: passed / app_failure / blocked / timeout / runner_error;
- ссылка на папку отчета;
- отсутствие второго окна и второго меню;

2. Добавить проверку версии и расположения проекта.

5. Стабилизировать `report.json` как версионируемый контракт.
6. Добавить в пульт только одну кнопку запуска и одну кнопку открытия последнего отчета.
7. Передать в отчет commit, измененные области и список реально выполненных suites.
8. Добавить автоматическую пометку `not_implemented`, чтобы незапущенные suites не выглядели зелеными.

## 8. Предлагаемая архитектура будущего AI-плагина

### 8.1. Реестр инструментов

Каждый инструмент должен иметь декларацию:

```yaml
name: find_incomplete_records
version: 1
description: Найти записи с отсутствующими обязательными полями
access: read
scope: [supply, stock, products]
confirmation: never
input_schema: schemas/find_incomplete_records.input.json
output_schema: schemas/find_incomplete_records.output.json
handler: api
max_rows: 200
```

Обязательные поля:

- имя и версия;
- описание для человека и модели;
- JSON Schema входа и выхода;
- требуемый scope ключа;
- разрешенные коллекции;
- лимит объема;
- необходимость подтверждения;
- маскирование чувствительных полей;
- запись в аудит.

### 8.2. Разделение режимов

| Режим | Разрешения |
|---|---|
| `observe` | только чтение и агрегаты |
| `analyze` | чтение плюс вычисление риска |
| `draft` | формирование черновика изменения или предложения |
| `confirm` | выполнение конкретной операции после подтверждения человека |
| `admin` | только ручной административный режим, не для автономного ИИ |

Первая версия должна включать только `observe` и `analyze`.

### 8.3. Формат результата

ИИ не должен получать произвольный HTML или длинные логи. Нужен стабильный объект:

```json
{
  "tool": "find_incomplete_records",
  "tool_version": 1,
  "generated_at": "2026-11-05T00:00:00Z",
  "data_scope": {
    "organization_id": "...",
    "collections": ["supplyrequests"]
  },
  "summary": {
    "total_checked": 120,
    "issues": 7,
    "risk": "medium"
  },
  "items": [
    {
      "id": "...",
      "field": "warehouseId",
      "reason": "required field is empty",
      "severity": "important"
    }
  ],
  "next_actions": ["Проверить заявки без склада"],
  "redactions": []
}
```

### 8.4. Аудит вызова

Для каждого вызова нужно сохранять:

- пользователя или API key id;
- имя инструмента и версию;
- параметры после маскирования;
- время;
- количество прочитанных записей;
- результат и код ошибки;
- модель и версию промта, если участвовала модель;
- факт подтверждения человеком.

Это должно быть отдельным типом аудита, а не только локальным файлом Nightshift.

## Этап 1. Довести Nightshift до надежного минимального QA-плагина

## Этап 4. Безопасный локальный AI-анализ, без исправления кода

**Критерий:** AI не может изменить файл и не может объявить проблему исправленной.

## 11. Основные риски

### Риск 1. Второй control plane

Если сделать отдельное приложение с собственными кнопками, появятся два места для запуска проверок: pult и Nightshift GUI. Команды разойдутся, а результаты будут разными.

**Мера:** только CLI-ядро, запуск из pult.

### Риск 2. Ложный зеленый результат

Папка и suite существуют, но команда может быть stub или проверять только сам harness.

**Мера:** в отчете хранить команду, commit, stdout/stderr, число тестов, exit code и `executed=true`; not implemented не считать pass.

### Риск 3. Случайное касание production

Особенно опасны fallback-пути, Docker context, общие volumes и неправильный `MONGO_URI`.

**Мера:** ownership labels, synthetic env, запрет remote Docker context, mandatory project, отдельный тест отсутствия production адресов.

### Риск 4. Утечка секретов через handoff

Даже при redaction могут утечь значения через stderr, environment, Docker inspect или архив.

**Мера:** redaction до каждого persistence boundary, тест с синтетическими секретами, allowlist полей environment.json.

### Риск 5. Автоматическое исправление тестами

ИИ может сделать тест зеленым, ослабив тест или изменив expected.

**Мера:** хеши тестов, запрет записи в tests, отдельная ветка, полный повторный прогон, ручное подтверждение.

### Риск 6. Смешение PLM-терминов и реальных сущностей

AI Copilot может начать выдавать красивую PLM-аналитику, не соответствующую полям `data-core`.

**Мера:** сначала реальные схемы, OpenAPI и read-only инструменты, затем промты.

### Риск 7. Устаревшая документация

Сейчас часть документов прямо помечена как история, но это видно не везде.

**Мера:** единый CURRENT.md или раздел статуса с датой проверки и командой-подтверждением.

## 13. Финальная оценка

`tests_ai_tiit` — не бесполезная папка и не готовый плагин. Это ценный прототип с уже реализованной безопасной частью: изолированный стенд, ownership, базовый runner, suite discovery, классификация ошибок, redaction, отчеты и handoff.

Главная проблема не в том, что «ничего не работает». Главная проблема в том, что в папке смешаны:

- исходная идея автономного приложения;
- принятый ограниченный QA-harness;
- будущий AI Copilot;
- исторические инструкции;
- еще не реализованные обещания ТЗ.

Если объединить всё в одно приложение, получится тяжелая и рискованная система с дублирующимся пультом, неясными границами доступа и ложными гарантиями.

Если разделить направления, получится сильная архитектура:

```text
data-core API
  ├── существующие клиенты и pult
  ├── Nightshift QA CLI → Docker QA-стенд → отчеты
  └── будущий AI Copilot → tool registry → API → аналитика
```

**Мой окончательный совет:** создать из текущей папки не «универсальный AI-плагин», а два связанных, но независимых продукта:

1. **Nightshift QA adapter** — безопасный плагин для проверок через существующий пульт.
2. **Data Core AI Copilot** — отдельный read-only аналитический слой по идеям `md.md`, который использует API и зарегистрированные инструменты.

Такой путь соответствует текущей архитектуре `data-core`, не нарушает правило единственного API-писателя, не создает второй control plane и дает возможность постепенно перейти от красивой концепции к реально полезным функциям.
