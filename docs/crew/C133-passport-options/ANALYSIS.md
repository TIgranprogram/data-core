# C133 — варианты настроек паспорта 3601

Дополнение после анализа: фактические варианты и данные 3601 проверены агентом доступа только GET, см. `DATA-CHECK.md`. Отсутствие «2», посторонняя лестница в местах и несвязанный список бетон/стеклопластик подтверждены. Ниже сохранена исходная граница статического анализа; живую сверку читать вместе с указанным отчётом.

Статус: анализ кода выполнен 16.11.2026. Код, справочники и данные не менялись. Тесты и выпуск C132 не затронуты. Ни раскрытый список на проде, ни запись изделия 3601 в этой проверке не получены: фактический состав вариантов должен подтвердить access.

## 1. «Мест»: почему нет 2 и как добавить

Факт кода: это не числовое поле, а признак `blg.seats`. `passport-applicability.ts:48` допускает его для типа seating; столы относятся к seating по группе (`:41`). `passport-gaps.ts:161–175` получает значения из `loadFacets`, выбирает дочерние записи признака и отдаёт все их варианты. В этом окне нет фильтра по количеству изделий: не путать с поисковой воронкой `funnel/pick-steps.js`.

Источник вариантов — `dict_values`: `productFacets` → `productFacetValues.parentId` (`passport-funnel.ts:11–15`). `fill/control.js:244–256` показывает обычный select и сохраняет ID в `products.facetValueIds`; добавить значение рядом нельзя. Исторический проект наполнения `docs/crew/C028-passport-funnel/facets-seed.json:85–92` содержит диапазоны «до 5», «25 и более», а не все целые числа. Это объясняет исходную модель классификатора, но не доказывает сегодняшний список прода и причину отсутствия конкретной записи «2».

Предложение: точное «Количество мест для сидения» — положительное целое свойство изделия, доступное при seating. Не подменять его `maxUsers`: это ограничение одновременных пользователей, которое для BLG по умолчанию не применяется (`passport-applicability.ts:14–26`). Диапазонный признак может остаться для отбора каталога, но не выдавать диапазон за точную вместимость. Точное место хранения и совместимость фильтров — задача архитектора. Старые диапазоны автоматически в числа не переводить. До такой доработки значение можно завести в существующем справочнике «Значения признаков» с родителем `blg.seats`; это временная возможность модели, а не выполненная правка данных.

## 2. «Перила, спинка»: откуда и свои варианты

Факт кода: `blg.rail` также применим к seating и питается теми же двумя справочниками; название вопроса и названия ответов приходят из БД. Исторический seed объединял перила и спинку в одном признаке (`facets-seed.json:98–102`). Реальные варианты и выбор изделия 3601 пока неизвестны.

Справочник уже позволяет создавать свои значения: `backend/src/modules/dicts/dicts.product-facets.ts:82–119`; обязательны название, родитель-признак и уникальный код. В окне паспорта нет перехода к такому созданию. Для конкретного стола вопрос может быть двусмыслен: спинка стула и перила трибуны — разные свойства. Предложение: ясная подпись по контексту и перечисления конструкции; независимые свойства не сводить в один ответ. Разделение существующих вариантов — только после проверки их использования, без удаления привязок.

Готовый образец добавления с возвратом: `fill/control.js:110–158`, `addElement`: `ctx.pause()`, редактор справочника, «Сохранить и вернуться», обновление списка и возобновление формы. Применить тот же сценарий к значениям признаков, заранее указав родителя; технический код не должен становиться вопросом менеджеру. Создавать новые записи только при имеющемся праве редактирования справочников.

## 3. «Материал»: связь с техописанием

Факт: признак `blg.material` — ещё один независимый select. `facetApplies` не ограничивает неизвестные коды по типу; `productGaps` не проверяет `step`, поэтому даже признак с `step:false` попадает в незаполненные вопросы. В историческом seed он предназначался для ухода за материалом (`facets-seed.json:104`), а не для подробного состава. Выбор такого значения в текущем `controlGap` записывает лишь `facetValueIds`, а не состав изделия.

Подробные материалы уже связаны с техописанием:

- `fill/control.js:208–210`: отдельные «Материалы» → «Заполнить материалы» → техописание; `fill/index.js:67` вызывает `openTechSheet(prod)`.
- `backend/pwa/sections/tech-sheet.js:102–104,126–128`: редактирует и сохраняет `products.materialsSpec`. Поле `materialsText` передаётся виджету как исходный текст.
- `backend/src/common/catalog/materials-table.ts:10–14`: строки `materialsSpec` ссылаются на существующий `passportMaterials`, части — на `passportParts`. Это не складской справочник `materials` и не значения фасета.
- `passport-from-product.ts:38–42`: состав изделия → `materialsSpec` паспорта, `materialsText` → `materials`, умолчания `materialIds` берутся отдельно. Пустое значение источника не затирает историческое.
- `passport-compose-parts.ts:79–103`: описание предпочитает строки состава (`passportText`, иначе название материала); старые `materialIds` дают `madeOf`, свободный `materials` служит запасным источником. `passport-v2-text.ts:139–140`: явно ручное описание сохраняет приоритет.

Следовательно, связь техописания с описанием паспорта есть, но два похожих вопроса скрывают разный смысл. Автоматическое соответствие `blg.material` ↔ `materialsSpec` этими путями не обеспечивается. Более того, `passport-v2-text.ts:119–143` строит признаки ухода и таблицы ТО из `materialIds`: совпадение красивого описания с правилами ухода нельзя считать доказанным только по заполненному составу.

Предложение: один видимый блок «Материалы изделия» из существующего состава, с переходом в техописание и добавлением через существующий справочник материалов. Для текстов ухода использовать согласованную классификацию материалов этого же состава. Противоречие старого фасета составу показать явно; неизвестный материал не угадывать по названию. Не создавать ещё один независимый справочник. Отдельно проверить возврат и обновление открытого паспорта после сохранения техописания: в просмотренном вызове `openTechSheet(prod)` callback обновления нет, визуальное поведение не проверено.

## 4. Проверяемая приёмка будущего решения

1. Если менеджер задаёт 2 места, то сохраняется точное целое 2, и при повторном открытии видно 2. Ноль, отрицательное и дробь не принимаются; пустое не превращается в ноль. Старое «до 5» не превращается в 5 автоматически.
2. Если изделие не относится к seating, то вопросы мест и спинки/перил не появляются; смена типа не удаляет старые сведения молча.
3. Если нужной конструкции нет, то «Добавить вариант» открывает существующий справочник с указанным родителем, возвращает в тот же паспорт и выбирает созданное значение. Незавершённый ввод, остальные ответы и прокрутка сохраняются. Отмена не создаёт записи; повтор после ошибки не создаёт дубль.
4. Если сохранён состав в техописании, то открытый шаблон обновляет материалы и автоматическое описание без повторного ввода. Ручное описание сохраняется; пользователь видит его ручной источник.
5. Если состав содержит несколько материалов, то все они представлены в описании и подходящих правилах ухода; старый одиночный фасет не заставляет выбрать один из нескольких материалов.
6. Если состав и старые признаки противоречат, то противоречие объяснено до записи/выпуска. Уже выпущенный снимок автоматически не меняется.
7. Если пользователю нельзя редактировать справочники, то форма не предлагает недоступное создание и объясняет дальнейшее действие.
