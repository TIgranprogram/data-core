# C133 — совет «как действовать» (opus, 16.11.2026)

1. Мест. Хранить точное число как поле паспорта того же рода, что maxUsers/ageFrom: ключ `seatsCount` в USER_FIELDS-подобном списке (`passport-applicability.ts:13`), путь gap `kind:'field'` (`passport-gaps.ts:185–198`). Место записи — там же, где сейчас пишутся поля паспорта изделия (`passportDefaults` в data-core-схеме `product-passport.schema.ts`), НЕ новое корневое поле `products`: схема products общая с CRM; доп. вложенное поле CRM не ломает, корневое — лишняя сущность в чужом контракте. Если поля паспорта пишутся в корень products — исполнитель backend сначала проверяет и пишет в ту же структуру, без нового пути API.
2. Применимость: `seatsCount` только при type seating (как blg.seats `:48`). Валидация: целое ≥ 1, пустое = не задано (не 0). В pwa — `<input type=number min=1 step=1>` в fill/control.js рядом с остальными field-вопросами.
3. `blg.seats` не удалять: остаётся для каталога/воронки. В окне «Настройки паспорта» скрыть его, если задан `seatsCount` (иначе показывать с подписью «Мест (диапазон для каталога)»). «Подъём (лестница) трибуны» — чужой вариант: записать в docs/DATA-FIX-USER.md (перенести под признак трибун / свой признак) — правит пользователь, код не трогает. Диапазоны в числа не переводить.
4. Перила/спинка: кнопка «+ Добавить вариант» у каждого facet-select по образцу addElement (`fill/control.js:110–158`): ctx.pause() → редактор dict productFacetValues с заранее заданным parentId и автокодом (код генерирует сервер/редактор, менеджер его не видит) → «Сохранить и вернуться» → перезагрузка options → автовыбор нового id → resume. Кнопка видна только при праве записи справочников (то же право, что у `dicts.product-facets.ts:82–119`; на сервере оно уже проверяется — фронт лишь прячет). Признак сейчас не делить: только подпись по контексту (стол/скамья → «Спинка», трибуна → «Перила») на фронте/в label gap; разделение — пункт в DATA-FIX-USER после проверки привязок.
5. Материал: в passport-gaps не отдавать `blg.material`, если `materialsSpec` непуст (фасет остаётся для каталога). Вместо вопроса — блок «Материалы из техописания»: список строк materialsSpec (имена), кнопка «Изменить в техописании» → `openTechSheet(prod, { onSaved })`; onSaved перечитывает изделие и gaps и перерисовывает окно. Добавить необязательный callback в tech-sheet.js (`:126–128` после успешного save) — обратно совместимо. Новый справочник не создавать. Заодно: gaps не должен выдавать признаки со `step:false` (баг из ANALYSIS §3) — отдельной строкой, с тестом.
6. Исполнители и порядок:
   a) backend (sonnet): seatsCount в применимости/gaps/сохранении + DTO (учесть forbidNonWhitelisted — добавить поле в существующий DTO, иначе 400); скрытие blg.material при materialsSpec; скрытие blg.seats при seatsCount; фильтр step:false; seatsCount в текст паспорта только если шаблон его использует (не менять выпущенные снимки). openapi перегенерировать, MAP обновить.
   b) frontend (sonnet), после (a): поле числа, «Добавить вариант», блок материалов + onSaved, контекстная подпись спинки/перил. Затем designer (снимки окна 3601).
   c) qa: юнит + e2e затронутого, full перед выкладкой (L).
7. Подводные камни: CRM читает products — не переименовывать/не удалять поля; pause/resume должен сохранить несохранённые ответы; двойной клик «Сохранить» не плодит дубль (код уникален → 409 → взять существующий); кэш `loadFacets`/cached — сбросить после создания значения; Mongo 4.4.
8. Тесты: gaps — seating показывает seatsCount, не-seating нет; 0/-1/1.5 → 400, пусто не пишет 0; materialsSpec есть → нет blg.material; step:false не попадает; DTO принимает seatsCount; e2e: создание значения фасета с parentId и появление в options; без права справочников → 403. Приёмка — пункты 1–7 ANALYSIS §4 на 3601.
