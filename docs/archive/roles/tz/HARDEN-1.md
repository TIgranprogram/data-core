## Обязательно (потеря денег или склада)

1. `incomes.service.ts` `derive()`: форма позиции (`pwa/sections/orders.js:291`) всегда шлёт `paidDate`. Сейчас это обнуляет `payments`, и аванс превращается в «оплачено целиком». Правило: при правке записи с платежами неизменённый `paidDate` игнорируется; изменённый — 400 «Дату меняйте в платеже». `payments: []` остаётся отменой оплаты. Создание и записи без платежей работают как раньше.
2. `incomes.service.ts` `addPayment`, `removePayment`: запись платежей с условием на прежнее состояние (прежний `paidAmount` и число платежей), иначе 409 «Оплату уже изменили, обновите карточку». В `POST /incomes/:id/payments` необязательный `clientUid`: повтор возвращает запись без второго платежа. В `DELETE /incomes/:id/payments/:index` необязательный параметр `amount`: не совпало с платежом по этому номеру — 409.
3. `supply-invoice.service.ts:345`: оплата счёта не меняет `status` заявок со статусом `received`; `paid`, `paidAt` им ставятся. То же для `supply.service.ts:456` (правка статуса не откатывает «Получено» без явного отмены прихода). `receiveRaw` (:493): полностью принятая заявка — отказ, а не второй приход. Частичный приём продолжает работать. `:518–520`: при найденном `clientUid` заявку не менять.
4. `stock-movements.service.ts` :220, :255, :436–450: отмена движения сначала атомарно занимает запись условием `cancelledAt: null`, все изменения в одной транзакции. Двойная отмена не возвращает остаток дважды.
5. `stock-movements.service.ts` :43, :138, `stock-reservations.service.ts:153`: проверка `clientUid` повторяется внутри транзакции первой строкой. Если индекс `clientUid` можно сделать уникальным разреженным без риска для имеющихся данных, не делай: запиши это в отчёт как решение.
