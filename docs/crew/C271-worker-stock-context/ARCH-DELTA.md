# C271 — контракт перед подключением рабочих сеток

Вердикт: после исправления двух блокеров. Опора `6a13c176`, адресная реализация `a6b3f770` уже в v2.66. Ниже изменения для следующей дельты C271. Решение по области общей части и якорь карты фиксирует координатор.

## Ожидания

`supply.service.ts:227–244` отдаёт исходные поля заявки, `invoiceAmount` и `invoiceNote`. Маскирование проверяет перечень ключей, поэтому новый UI подключается к `GET /api/stock/items/:id/requests?page=1&limit=20` в существующем `SupplyStockRequestController`. Дефект действующего общего списка передать владельцу supply отдельно.

- Раздел stock, текущий StockScope, роли admin/director/manager/user. Сначала `stock.activeItem(id, scope)`: 400 для неверного ObjectId, 403 для чужого материала, 404 для отсутствующего или архивного. `stockViews` остаётся настройкой отображения. Использовать существующий DTO пагинации 1…100 с запретом лишних параметров.
- В Mongo точные `materialId`, `deletedAt: null`, статусы requested/in_progress/ordered. Историческое `ordered + paid=true` выдавать как `paid`. Сортировка `requestDate DESC, _id DESC`, count и страница по одному фильтру. Ответ `{items,total,page,limit}`. GET доступен при отключённом флаге записи C262.
- Поля элемента: `id, num, materialId, qty, unit, status, statusLabel, supplierName, invoiceId, invoiceNo, invoiceDeliveryDate`. ID — строки, qty — текущий остаток, unit — единица заявки. Отсутствующие номер/подписи/ссылки/дата — null. Срок только из `supplyinvoices.deliveryDate`. Использовать существующее форматирование статуса и прямую проекцию на уровне Mongo. Обогащение по ссылкам только со страницы, пакетно, с фильтром удаления и узкой проекцией имени поставщика и срока. Общие `list/present` собирают лишние данные.

## Повтор и аудит

`idempotency.interceptor.ts:109–120` может вернуть сохранённый ответ перед owner action. Для POST C271 нужен opt-out через metadata метода и ранний переход к `next.handle()` до поиска ключа. Готовой metadata в текущем interceptor нет. Координатору расширить TZ только на этот opt-out в common/idempotency и его адресный тест. HTTP `Idempotency-Key` на данном POST игнорируется. UI сохраняет один `clientUid` до известного исхода, используя текущий core API. Этот абзац заменяет требование стабилизировать HTTP-заголовок в TZ и ARCHITECTURE.

Сохранить deterministic ID и fingerprint owner action. Каждый повтор проходит DTO, guard, проверку текущего материала, scope и флага C262, возвращает текущий остаток. Конфликт намерения остаётся 409. Если позже редактирован materialId самой заявки, перед возвратом сверить его с адресным материалом и отклонить несовпадение 409, чтобы повтор не вернул сведения другой позиции.

`supply-stock-request.controller.ts:20` помечает каждый успешный replay созданием. Убрать `@AuditAction` только с этого POST и вызвать существующий AuditService из узкой C271-ветки штатного create после успешной вставки. Сохранить action/entity/id, безопасный snapshot и данные автора запроса. Гонка и повтор не записывают второе событие. Ошибка аудита обрабатывается в принятом best-effort режиме.

## Проверки

- Native stock-only scoped manager и наблюдатель: точные поля ответа GET, >100 открытых, оплаченная ordered, частичный приход, разные unit, отсутствие даты, исключение закрытых/удалённых и чужого материала. Засеять финансовые поля и примечание счёта для отрицательной проверки.
- В e2e повторить один и тот же HTTP key и body после уменьшения qty, выключения C262 и архива материала. Ожидать текущий остаток, 409 и 404 соответственно. Другой qty с тем же UUID даёт 409. Одновременная отправка — одна заявка и одно событие аудита. Проверить, что opt-out касается только аннотированного метода.
- Прежняя адресная проверка по REVIEW-DELTA: HTTP/Mongo 5/5, unit 502/502, tsc и ESLint 0. Независимый `audit-cycles`: 0 взаимных пар, 0 новых длинных циклов. 11 мс на страницу броней по локальному HTTP-журналу, ожидания и экран предстоит замерить. Общая дельта architect с `267bc1c` вне этой проверки, отметку `--done` не ставить.
