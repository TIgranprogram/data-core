# ТЗ T27 — Оплаченный счёт: правки до первой приёмки и сохранение факта оплаты

> Статус 2026-11-03: пользователь подтвердил вариант B — оплаченный счёт редактируется до первой приёмки; первый приём фиксирует финансовые данные всего счёта. Реализация и изолированные regression E2E завершены. Фактический контракт описан ниже; production E2E не запускался.

**Класс:** L · **Приоритет:** P1 · **Проверки:** unit + изолированные e2e на тестовой БД; никаких production e2e.

## Фактические расхождения

- `lockReason()` блокирует финансовые правки только при наличии принятой строки; статус paid сам по себе не блокирует (`backend/src/modules/supply/supply-invoice.service.ts:57-67`). `updateLine` и `addRequests` поэтому допускают изменения paid счёта до первой приёмки; после операции пересчитываются `amount` и история цены (`:382-416, :545-579`).
- Удаление строки, напротив, безусловно запрещено при `status === 'paid'` (`backend/src/modules/supply/supply-invoice.service.ts:582-597`); PWA также скрывает кнопку удаления для paid (`backend/pwa/sections/invoices-tab.js:209-225`).
- Merge двух счетов запрещён, если любой из них paid (`backend/src/modules/supply/supply-invoice.service.ts:440-449`).
- Сохранённый `paymentSnapshot` фиксирует сумму, состав строк, компанию и время платежа. `paymentAdjustments` учитывает последующие add/edit отдельно; FinanceService читает snapshot как банковский факт и исключает связанные legacy-заявки из cashflow.

## Требования

1. Сохранить выбранную границу пользователя: до первой приёмки менеджер должен иметь последовательное и понятное правило редактирования; после первой принятой строки сумма/позиции заблокированы, кроме согласованных реквизитов счёта.
2. Инвентаризировать, что `status=paid`, `amount`, `paidAt` и `materialprices` означают для фактических денежных отчётов. Установить, где хранится реальная перечисленная сумма, если она отличается от текущей суммы строк.
3. Определить корректное поведение для изменения цены/количества, добавления, удаления позиции и merge до первой приёмки. Не менять статус «оплачен» и сумму так, чтобы отчёт выдавал исправленный invoice amount за новый банковский платёж.
4. Если разница суммы означает переплату/доплату, ввести явную корректировку/сверку с автором, временем, причиной и ссылкой на исходный invoice; не переписывать молча существующий денежный факт. Если безопасно поддержать remove/merge нельзя, оставлять действие запрещённым с ясным объяснением и задокументировать исключение из общего правила.
5. Сохранить историю каждой отдельной закупки по material/request/invoice/supplier/qty/line amount. Не дедуплицировать закупки одного материала и не удалять записи истории при изменении каталога.
6. Рассматривать атомарность первой приёмки отдельно по T24: операции правки paid invoice также не должны обходить receipt boundary через гонку.
7. Не менять схемы общих CRM-коллекций, не трогать `/opt/kppdf*`, ничего не удалять из Mongo. E2E — только на изолированной тестовой БД.

## Зафиксированное правило прав

| Состояние | Финансовые правки и добавление | Удаление строки / merge | Метаданные |
|---|---|---|---|
| Черновик до приёмки | Разрешены по обычным правилам | Удаление — до приёмки; merge — явный по существующему API | `fileIds`, `contractId`, `no`, `date` |
| Выставлен, не принят | Разрешены до первой приёмки | Paid-only restrictions не применяются; явный merge | Те же поля |
| Оплачен, не принят | Line edit/add разрешены с обязательной причиной; исходный платёж не изменяется | Удаление paid строки и merge paid счетов остаются запрещены | Те же поля |
| Есть хотя бы одна принятая строка | Сумма и состав заблокированы | Запрещены | Только `fileIds`, `contractId`, `no`, `date` |

Paid line edit/add записывает `paymentAdjustments` с актором/временем/причиной/дельтой и отдельный источник `invoice_adjustment`; исторический `invoice_paid` и `paymentSnapshot` не перезаписываются.

## Критерии приёмки

- [x] Таблица прав для paid/not-received, received-any-line, issued/not-paid соответствует выбранному правилу.
- [x] E2E подтверждает прежние `paymentSnapshot.amount`/`paidAt` после paid edit/add; каждое изменение получает журнал и отдельную историю цены.
- [x] Merge paid-счетов и удаление paid строки остаются запрещены; исключение описано выше и отражено в API/PWA.
- [x] После первой приёмки финансовые поля заблокированы; разрешены только `fileIds`, `contractId`, `no`, `date`.
- [x] Изолированный finance E2E проверяет summary/cashflow без дублирования банковского расхода и цену одного материала в двух отдельных счетах вместе с двумя `invoice_adjustment` событиями; общие CRM-схемы не менялись.
- [x] Unit/E2E, документация и TEST-LOG синхронизированы; production E2E не запускался.
