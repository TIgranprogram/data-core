# ТЗ C144 — каскад типов паспорта в справочниках

**Зачем (словами пользователя):** в справочнике видно каскадные связи по категориям и порядок «что после чего»; интуитивно понятно, при каких типах паспорта какие выпадающие списки собираются; быстро добавить нехватающие главные категории; эта же привязка грамотно в паспорте/книжке.

**Зачем — глаголом:** директор за 1 минуту видит «для BLG / воркаута» какие части, материалы, покрытия и тексты предлагаются, и где дыра.

## Глубже
- **Результат:** в «Справочниках → Паспорта» видно основание предложения (типы паспорта словами, не коды); в таблице материалов/покрытий/частей понятно, почему список такой; дыры по типу заметны.
- **Сырьё:** живые `passportMaterials` / `passportParts` / `passportElements` / фразы; изделие с типом паспорта на стенде :3102; скрин «Части у материалов» (все покрытия сразу).
- **Метод:** карта «тип паспорта → что фильтруется»; эталон меток как в `cat-chips` / `.pt-cats`.
- **Судья:** отчёт аудита; стенд — список справочника + панель материалов; design-lint 0.
- **Планка:** 0 сырых кодов TRN/WRK на экране менеджера; колонка «Кому предлагают» всегда видна у материалов/частей/элементов.

**Класс:** L · **Max agents:** 4 · **Reviewers:** architect ☐ designer ☐ qa ☐ · **Max review loops:** 2 · **Проверки:** smoke  
**Язык менеджера:** да · **Приёмка:** стенд :3102 справочник + книжка материалов

## Shared pack
- Поле `categories` (пусто / коды типов): **материалы и покрытия** — пусто = для всех типов; **части** — пусто = не в коротком списке при выбранном типе (только «Показать все»). Не ломать контракт API.
- Не менять схемы Mongo общих с CRM коллекций без явного «да».
