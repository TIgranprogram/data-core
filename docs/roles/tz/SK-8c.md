# ТЗ SK-8c — свои роли: «Новая роль» с «права как у», название роли, роли сотрудника из «Ролей»

**Зачем (словами пользователя, 2026-10-24):** «в админке создаю роль, подкрепляю галочками нужные разделы, потом роль подкрепляю к сотруднику». Пример: «Кладовщик» — права как у менеджера, разделы «Склад», «Заявки»; «Инженер» — тоже как менеджер, но другие разделы. Переименовать роль (название) — можно, код — нет.

**Роли:** backend ☐ (сервер + админка) · frontend ☐ (pwa, 2 строки — делает координатор после SK-8b) · qa ☐ · архитектор ☐ (проверка итога: права)

## Решение координатора (как делать)
- Встроенные роли (`user`, `manager`, `accountant`, `director`, `admin`) — без изменений; иерархия `common/roles-hierarchy.ts` остаётся.
- Своя роль = документ `roles` с `name` (код, создаёт сервер: `r-` + короткий случайный, неизменяемый), `label` (название, правится), **`baseRole`** — одна из `user|manager|accountant|director` (не admin), `appSections`.
- **Права своей роли = права её `baseRole`** (+ иерархия ниже). Реализация: в `roles-hierarchy.ts` кэш «код своей роли → baseRole» (в памяти процесса; заполняется при старте из `roles`, обновляется при создании/правке/удалении роли в `RoleService`). `effectiveRoles('r-xxx')` → `['r-xxx', baseRole, ...ROLE_INHERITS[baseRole]]`. Все проверки прав (guard'ы, MoneyMask, `MONEY_ROLES`, места с `.role ===`/`effectiveRoles` — их ~25 в `src`, найти grep'ом) должны идти через `effectiveRoles` / функцию «базовая роль», а не сравнивать `user.role` напрямую с встроенными (кроме `=== 'admin'` — своя роль никогда не admin).
- `kppd_`-ключи: если у ключа есть роль — то же правило.
- `users.role` принимает встроенную роль **или** код существующей активной своей роли (DTO создания/правки пользователя: `@IsIn` встроенных заменить проверкой в сервисе; текст ошибки по-русски).
- Ответ входа и `/auth/me`: добавить `baseRole` (для встроенной — она сама; для своей — её baseRole) и `roleLabel`. Приложение будет брать права по `baseRole`.
- `name` и `baseRole` у встроенных ролей менять нельзя (400); `label` — можно у всех. Удалить свою роль, пока она назначена хоть одному пользователю, — 409 «роль назначена N сотрудникам».
- CRM kppdf читает `users.role`: сотрудник со своей ролью в CRM прав менеджера не получит — это допустимо (CRM заморожена), записать в отчёт.

## Что сделать (backend)
1. `role.schema.ts` / DTO: `baseRole` (IsIn 4 значения), `label`; создание — `name` генерирует сервер; правка — запрет менять `name`, `baseRole` у встроенных.
2. Кэш baseRole + `effectiveRoles`; пройти все проверки прав (список в отчёт: файл → как было → как стало).
3. Пользователи: допуск своей роли; `GET /api/roles` уже есть — убедиться, что админка может взять список для выпадающего.
4. `/auth`: `baseRole`, `roleLabel`.
5. Админка: вкладка «Роли» — кнопка «Новая роль» (название, «Права как у» — выпадающий список, галочки разделов) по скиллу `datacore-design` (ввод — в раскрывающейся строке, как уже сделано; окно допустимо, только если полей ≤3 — название + права как у + галочки: решай по DESIGN); правка названия у любой роли; удаление своей роли (с подтверждением). Форма сотрудника (`#f-role` в `admin/index.html`, фильтр `#user-role-filter`) — список из `GET /api/roles` (встроенные + свои, с названиями), а не зашитые варианты.
6. Юнит: своя роль с baseRole=manager проходит `@Roles('admin','manager')`, не видит денег; baseRole=accountant — видит деньги; неизвестная роль у пользователя — 400; удаление назначенной роли — 409; кэш обновляется после правки.
7. `docs/MAP.md`, `docs/data-model.md`, `docs/ARCHITECTURE.md` (раздел RBAC — одна-две строки про свои роли), `docs/openapi.json` (как в SK-8a, вручную, если нет Docker).
