# C172 — очередь стабильности до пополнения лимита

21.11.2026. Только триаж; код/прод/данные/настройки не менялись. Источники: BACKLOG, CONTROL, открытые TASKS и BOARD из чистого release-worktree; для приоритета локального ИИ — только C171/IMPLEMENTATION.md и ARCH-PLAN.md из основной D:-копии. 17% — остаток со слов владельца, не оценка часов. Из актуального baseline известно только health OK: исторические ошибки не объявляются действующими.

## Решение

Закончить разрешённый C172 без примеси C171. Затем **стабильный локальный ИИ для счетов — первый пользовательский приоритет**: вернуть основной пульт на принятый main и проверить существующий выпущенный C169. Большие серверные CAS/карантин/архив сейчас не начинать. Если после этого хватает ресурса на целый отдельный цикл исправление→проверка→приёмка→выпуск, брать максимум один доказанный локальный блокер C169; прочие улучшения ниже. Сохранить стабильную работу ценнее незавершённой новой пачки.

## Локальный ИИ: что готово и минимальная следующая ступень

**C169 можно использовать сейчас:** выпущенный MVP текстовых PDF договоров/КП/RUB-счетов поставщиков, локальная Gemma, оригиналы, проверки, выбранные исключения, длинная сессия и идемпотентные квитанции. Это уже принятая возможность (BACKLOG/CONTROL C169), её не следует заново реализовывать. Перед использованием основной пульт должен запускать принятый main. Проверка MVP имеет приоритет над AIT-3 и любыми UI-мелочами.

**C171 WIP сейчас умеет:** preflight Windows/места/PDF/реального ответа модели/readonly прав; отдельную очередь счетов с hash/страницами/evidence/локальными версиями, паузой; библиотечный reviseDraft под lock; просмотр полей/строк/цитат. `checked` — только «Проверено локально». **Отправки нет**, редактирования UI нет, серверный CAS отсутствует, PDF рядом и XLSX ещё впереди. Маркер папки C171 намеренно запрещает C169 run/resume/retry — нельзя убрать его, чтобы «доделать загрузку» старым upload-first.

**Минимальный новый кусок по желаемому сценарию** «разбор → preview → подтверждение → сохранение без дублей» — один текстовый RUB-счёт, одна изолированная среда, одна ревизия подтверждения; без XLSX/OCR/пачки/договоров/установщика/новой модели. Но для реального сохранения C171 обязательны B1 серверный revision/CAS/review, B2 prepare ticket на точные actor/target/hash/revision, B3 quarantine+повторная валидация+единая транзакция, B4 crash-safe файловая публикация/восстановление, B5 readback/receipt; затем минимальный UI подтверждения, повторы/обрывы/stale/права/оригинал и независимая приёмка. Только B1 без send можно закончить отдельно, но пользы «загрузить счёт» он ещё не даёт. Одним подписанным ticket или существующей идемпотентностью CAS заменить нельзя.

**Оценка при 17%:** полного нового C171 не обещать и не выпускать под видом готового. Реально закончить операционную стабилизацию пульта + проверку имеющегося C169 и один локальный доказанный дефект, если проверки оставляют ресурс. После пополнения — отдельное разрешённое ТЗ на минимальный end-to-end C171 с B1–B5; ≥30 вручную сверенных счетов/чистый Windows/full остаются условиями полного C171. Источник: C171 IMPLEMENTATION §§«Следующие подэтапы», «Границы»; ARCH-PLAN §§1–18 и B1–B5.
