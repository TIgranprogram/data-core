## Кнопки и проверка подключений

1. **Рабочий сайт.** Переиспользовать `link-srv-synology` из `pult/catalog.mjs:238–239` с фиксированным `https://kppdf-crm.ru/db/app/`. `buildRun` уже обрабатывает `run.open` (`pult/dispatch.mjs:84–108`), пульт открывает его системным браузером (`pult/server.mjs:282–304`). Для сведения о версии доступен публичный `/db/app/version.json`. По `deploy/synology/release.sh:88–97` поле `v` — последний коммит PWA, `b` — последний серверный коммит, `n` — номер PWA. Сравнивать `v` с локальным коммитом по `backend/pwa`, `b` — по соответствующему набору серверных путей. `dc status` сейчас сравнивает `v` с общим HEAD (`tools/dc.mjs:277–295`), поэтому для этих двух сведений его сравнение не подходит.
2. **Разработка.** Добавить видимую кнопку в `COMMANDS` раздела `day` рядом с рабочим сайтом, `risk: 'local'`, `needs: ['docker']`. Тонкая оркестрация использует `standInfo().run` для выбора между `standUp(ctx)` и `standRefresh(ctx)`, затем `standOwned()` и проверку `ready` по порту паспорта. Открывать `/app/` после подтверждения готовности. Текущий `run.open` завершает обработку до создания задания, поэтому запуск с открытием должен быть одной командой или продолжением только после её успеха. `pult/process.mjs:16` отвечает за остановку дерева процессов. Сейчас `runCommand` блокирует повторы по ID кнопки (`pult/server.mjs:305–310`), а ИИ-тестировщик также может вызвать `up`/`refresh`/`renew` (`tools/ai-tester/run.mjs:213–263`). Три команды управления одним ручным стендом должны разделять защиту от параллельного обновления.
3. **Подключения.** Добавить видимую кнопку `risk: 'read'` в том же разделе. Проверять по отдельности здоровье и версию рабочего сайта, локальный Docker и принадлежащий этому checkout стенд, наличие локальной копии и связь с GitHub. Существующий `local-checks --ready-only` проверяет наличие Git и Docker (`tools/local-checks.mjs:52–65`), `deploy-link` выполняет отдельную диагностику маршрута до VM (`pult/catalog.mjs:87–88`). `dc status` читает здоровье через `api.sh prod GET /api/health` (`tools/dc.mjs:115–121,277–295`). Доступ к production API по правилам репозитория остаётся у `datacore-access`. Если публичная статическая версия доступна, этого достаточно для отдельного результата «рабочий сайт отвечает». `readStatus()` по таймеру оставляет production-поля нейтральными (`pult/server.mjs:63–106`) и проверяет только наличие запущенного контейнера по меткам, `standOwned()` с guard и loopback `ready` дают более точную ручную проверку.

Для данных разработки вывести именованный архив из `standInfo()` и дату восстановления. Путь к резервным копиям согласовать с существующим загрузчиком: `night.mjs:21` использует `DC_BACKUPS` и Windows-путь, `pult/server.mjs:64` использует `DATACORE_BACKUPS` и тот же Windows-путь, `deploy/backup-pull/pull-backup.sh:12` на Linux использует `DC_BACKUPS` или `~/datacore-backups`. Надёжной метки текущей сборки backend у `night` нет. Минимум для вывода — текущие ветка, HEAD и признак правок на диске плюс время успешной сборки. Для подтверждения версии запущенного backend сохранять отпечаток входов сборки или SHA и признак изменений только после успешной сборки и `ready`, связав их с ID образа/контейнера. PWA берётся прямо с диска, поэтому его состояние и версия backend показываются отдельно. Метаданные держать в локальном паспорте запуска.

## Git и проверка пульта

- `tools/dc.mjs:360–379` уже делает `git fetch`, показывает ветку, ahead/behind и незакоммиченные файлы. Там же меняется `core.hooksPath` и запрашиваются ошибки production, поэтому для ручной проверки связи удобнее выделить Git-пробу. Для проверки доступности подойдёт `git ls-remote --exit-code origin HEAD` с таймаутом. Свежие сведения для ahead/behind даёт `git fetch` с явным результатом, после него `git rev-list --left-right --count HEAD...@{u}`.
- Кнопки `git-pull` и `git-push` уже есть (`pult/catalog.mjs:228–231`). Автоподтягивание ограничено чистым checkout без локального опережения, активной команды и чаще одного раза в 10 минут (`pult/server.mjs:434–439`). Эстафета хранится в последней строке коммита по `CLAUDE.md:35–36`, для вывода можно прочитать последний коммит локально. Порядок завершения — `CLAUDE.md:58`. Кнопки режимов и проверки соединений используют чтение статуса Git.
- После изменения `pult/catalog.mjs` выполнить `node pult/gen-docs.mjs`. Проверки каталога, сервера и подсказок уже входят в `dc check` (`tools/dc.mjs:269–273`). `pult/audit.mjs:22–45` сверяет скрипты, подкоманды и кнопки. Правила видимости на `pult/ui/app.js:47–50`. Три повседневные кнопки в `day` должны быть без `hidden`/`extra`.
