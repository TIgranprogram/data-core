# C096 Э4 — новое изделие из паспорта

Класс L, продолжение текущей задачи. Приоритет — достоверность связей и сохранение ввода. Прод и исходные записи QA не менять.

## Задача исполнителя frontend

Рабочие пути: `backend/pwa/sections/passports/funnel/new-product.js`, `funnel/index.js`, `passports/product-block.js`, `form-state.js`, при необходимости `products/data.js` и `products/form-fields.js`; тесты рядом. Ты не один в репозитории, чужие изменения не откатывать.

Существуют две цепочки: маленькая форма в воронке → passportFill (все применимые пробелы); полная форма изделия через createProductFor с возвратом в старую форму паспорта. Использовать существующий passportFill, CANON/PATTERNS и kit, не создавать универсальный CRUD.

1. Проверь и обеспечь целостный путь: выбранная категория/группа/подтверждённые признаки → новое изделие → применимые сведения → возврат к паспорту. Общие данные сохраняются в изделии и passportDefaults, номер/дата/заказ экземпляра не становятся умолчаниями изделия.
2. Уместные варианты и похожие изделия — только явный выбор. Не переносить свойства случайного изделия. При смене группы не присваивать признаки предыдущей группы; несовместимую категорию/ручные значения объяснять, не стирать молча.
3. Реальные найденные риски: new-product выполняет POST→assignSku→setFacets→GET без защиты повторной отправки/частичного успеха; повтор после сбоя создаёт дубль. Полный products.form.create также POST→savePd, повтор может создать второе изделие. Исправить повтор так, чтобы продолжалась созданная запись; не скрывать частичный успех.
4. createProductFor в product-block сохраняет лишь семь полей stash и использует навигацию; проверить сохранение всего введённого черновика и возврат без потерь. Смена изделия: снять старые автоматические значения, ручные сохранить с явной проверкой несовместимости; ничего старого не выдавать как данные нового изделия.
5. Создание должно приводить к открытому заполнению относящихся к типу/категории полей. Если это уже делает passportFill сразу после создания, сохранить этот путь и проверить; не плодить вторую форму с теми же вопросами.
6. Подтверждено при уточнении scope: `fill/index.js:onCategory` сразу очищает `textChoices/textOverrides`, вне очереди сохранений. При непустых значениях необходимо явное решение пользователя; отмена возвращает прежнее состояние. Смена категории сериализуется с текущими сохранениями. Сброс собственной категории должен действительно снимать её (`resetPdCategory` уже есть), а не возвращать прежнюю через `savePd`.
7. Переход/закрытие воронки ждёт сохранения текущего ввода. Запоздалый ответ от ранее выбранного изделия не подставляет его поля поверх нового выбора. Scope `fill/index.js` расширен только для этих переходов и категории.

## Приёмка

Новое изделие, похожее/дубликат, нет категории/обязательного поля, несовместимая категория, смена изделия, сбой после успешного POST и повтор, повторное открытие, сохранение черновика при возврате. Старый issued автоматически не меняется. Нужны unit/DOM проверки значимых веток и живая проверка новым QA-клоном через access. Полный отчёт E4-REPORT.md: что уже было, реальные пробелы, изменения, ограничения; компактное сообщение координатору. Сначала сообщить найденное и план границ, затем реализовать.
