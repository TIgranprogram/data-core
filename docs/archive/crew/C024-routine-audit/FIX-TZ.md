## РТ-1. «Заменить фото» в задаче проектирования (REPORT № 1)

- Класс: S. Исполнитель: `datacore-frontend` (1). Экран без изменений сервера; «Отменить» — через существующие вызовы.
- Цель одной фразой: заменить чертёжное фото в задаче одним действием вместо «убрать + загрузить + удалить».
- Как сейчас → как будет: сейчас «×» убирает фото с подтверждением, потом новое грузится отдельно, старый файл удаляется; 67 таких циклов за 30 дней. Будет: на фото кнопка «Заменить» — сразу открывается выбор файла (перетащить и Ctrl+V тоже), новое встаёт на место старого, в тосте — «Отменить».
- Файлы: `backend/pwa/ui/design-stickers.js:81-103` (блок «Фото», кнопка «×»), `backend/pwa/ui/kit/photos.js:20-55` (общая зона загрузки), `backend/src/modules/design/design.controller.ts:63-72` (прикрепить/убрать фото — не менять).
- Критерии приёмки:
  1. У каждого фото задачи (право записи) в меню «⋯» есть «Заменить»; выбор файла открывается сразу.
  2. После выбора новое фото на месте старого; старого в задаче нет; порядок остальных фото не меняется.
  3. Тост «Отменить» возвращает старое фото (как при одиночных действиях).
  4. «×» (убрать без замены) и добавление нового фото работают как раньше.
  5. Журнал задачи содержит те же записи, что при ручной замене (убрано + добавлено).
- Что проверить тестом: юнит `photosBlock` — замена пишет пару «убрано/добавлено», «Отменить» возвращает; регресс «×» и добавления.
- Риски: низкие — задачи проектирования и их фото читает только data-core (CRM kppdf их не использует).

## РТ-2. Сопоставление: уверенные связи — сами, очередь — с клавиатуры (REPORT № 2)

- Класс: M. Исполнитель: `datacore-backend` (1) + `datacore-frontend` (1).
- Цель одной фразой: позиции договора связываются с изделиями без клика по каждой строке.
- Как сейчас → как будет: сейчас каждая строка очереди подтверждается кнопкой (49 раз за 30 дней, серии до 46). Будет: (а) сервер при появлении несопоставленной позиции сам подтверждает совпадение ≥ 90% (те же правила «уверенно»), в журнале — пометка «сопоставлено автоматически»; (б) в очереди Enter = «Подтвердить» и переход к следующей строке, «Не изделие» — без мыши.
- Файлы: `backend/src/modules/matching/matching-rules.ts:71` (порог уверенности), `backend/src/modules/matching/matching.service.ts:30-49,113-117` (подсказки/подтверждение), `backend/pwa/sections/matching-queue.js:77-97,119` (очередь, кнопки, массовое «уверенные»).
- Критерии приёмки:
  1. Новая позиция с совпадением ≥ 90% сразу «сопоставлена», в журнале — «автоматически».
  2. В очереди такие строки видны с меткой «авто — проверить» и фильтром; связь отменяется как обычно.
  3. Совпадение ниже порога — строка в очереди как раньше, вручную.
  4. Enter подтверждает лучшую подсказку и переходит к следующей строке; Esc — выход из строки.
  5. Счётчик «Несопоставленные» у списка заказов не считает автосвязанные.
- Что проверить тестом: юнит порога и автоподтверждения; e2e — создание позиции с точным названием изделия (связалась, журнал с пометкой), отмена связи, позиция без похожих (осталась в очереди).
- Риски: средние — неверная «уверенная» связь уведёт проектирование и паспорта не туда. Удержание: пометка в очереди, лёгкая отмена, журнал, порог не ниже текущего 0.9, автосвязь только у новых позиций (старые не трогать).

## РТ-3. «Заказать всё ниже минимума» одним окном (REPORT № 3)

- Класс: S/M. Исполнитель: `datacore-frontend` (1); сервер не меняется.
- Цель одной фразой: закупить все позиции с остатком ниже минимума из одного окна с готовыми цифрами.
- Как сейчас → как будет: сейчас фильтр «Ниже минимума» советует открыть каждую позицию и нажать «Заказать» (29 заявок за 30 дней). Будет: на этом фильтре кнопка «Заказать все (N)» — таблица: позиция, «добрать до минимума», поставщик и цена из прошлых закупок, галочки; «Создать заявки» — по одной заявке на позицию через тот же вызов, что и быстрый «Заказать».
- Файлы: `backend/pwa/sections/stock.js:175-191` (фильтр «Ниже минимума» и подсказка), `:280` (действие «Заказать»), `backend/pwa/sections/item-orders.js:73-120` (умолчания количества, поставщика, цены; предупреждение о заказанном — переиспользовать).
- Критерии приёмки:
  1. Кнопка появляется только на фильтрах «Ниже минимума» и «Требуют внимания»; число N совпадает со счётчиком фильтра.
  2. Количество по умолчанию — «добрать до минимума»; поставщик и сумма — из прошлых закупок позиции.
  3. У позиции с открытой заявкой — предупреждение и галочка снята.
  4. «Создать» создаёт заявки со связью с позицией склада; они появляются в «Заявках» со статусом «Заказать».
  5. Тост «Отменить» убирает все созданные заявки сразу.
- Что проверить тестом: юнит расчёта «добрать до минимума» (остаток, минимум, уже заказано); e2e — создание трёх заявок пачкой через POST /supply/requests.
- Риски: средние — заявки в общей с CRM коллекции: писать только существующим эндпоинтом, без прямых записей; задвоение закрывает предупреждение о заказанном.

## РТ-4. Доска проектирования: раздача задач пачкой (REPORT № 4)

- Класс: S. Исполнитель: `datacore-frontend` (1); механизм чекбоксов на доске уже есть в kit.
- Цель одной фразой: назначить исполнителя и взять в работу несколько задач одним окном.
- Как сейчас → как будет: сейчас карточки переносятся по одной, и на каждом переносе в «В работе» спрашивается исполнитель (371 изменение задач за 30 дней, серии до 73). Будет: в колонках «Очередь»/«В работе» чекбоксы на карточках → «Взять в работу (N)» — одно окно исполнителя на всех; в «Приостановлено»/«Отменено» — одна причина на всех.
- Файлы: `backend/pwa/sections/design.js:67-82` (перенос, окно исполнителя), `:236-247` (колонки доски), `backend/pwa/ui/kit/board.js:70-90` (готовый механизм «Выбрано N»), образец — `backend/pwa/sections/requests.js:373`.
- Критерии приёмки:
  1. В «Очереди» и «В работе» можно отметить несколько карточек; полоса «Выбрано N · действие» как у доски заявок.
  2. «Взять в работу (N)» спрашивает исполнителя один раз; без исполнителя — отказ без изменений.
  3. Перенос в паузу/отмену пачкой спрашивает одну причину; она пишется каждой задаче.
  4. Каждая задача в журнале — как при одиночном переносе; «Отменить» в тосте возвращает все.
  5. Доска на 375 px не сломана (чекбоксы не мешают перетаскиванию).
- Что проверить тестом: юнит переноса (статус, исполнитель, причина); e2e — перенос трёх задач пачкой и откат.
- Риски: низкие — задачи проектирования читает только data-core; правила причин и исполнителя не меняются.

## РТ-5. Позиции договора списком — вставка из Excel (REPORT № 5)

- Класс: S. Исполнитель: `datacore-frontend` (1); разбор таблицы уже написан для импорта заказа.
- Цель одной фразой: добавить в договор много позиций одной вставкой, а не по одной строке.
- Как сейчас → как будет: сейчас позиции добавляются по одной через форму; разбор таблицы из Excel работает только при создании нового заказа. Будет: в карточке договора на вкладке «Позиции» кнопка «Вставить списком…» — вставить из Excel (№, наименование, ед., кол-во, цена) → предпросмотр со строками и ошибками → «Добавить».
- Файлы: `backend/pwa/sections/salesorders-import.js:18-50` (разбор строк таблицы — переиспользовать), `backend/pwa/sections/salesorders.js:306` (вкладка «Позиции», место кнопки), создание позиций — существующий вызов строки договора.
- Критерии приёмки:
  1. Кнопка видна с правами изменения позиций (правила этапа — как у обычного добавления).
  2. Понимает вставку из Excel: столбцы через Tab и «;», запятая в числах; пустые строки пропускаются.
  3. Предпросмотр показывает все строки; строки с ошибками (нет названия, не число в количестве) подсвечены и не добавляются.
  4. «Добавить» создаёт только отмеченные строки; список позиций и суммы договора обновляются.
  5. Отказ (Esc) ничего не создаёт.
- Что проверить тестом: юнит разбора строк (переиспользованный парсер); e2e — вставка трёх строк создаёт три позиции, строка с ошибкой не создаётся.
- Риски: низкие — позиции договора принадлежат data-core; цены не пересчитываются, пишутся как введены.
