# C019 — аудит «Смотреть как роль» (админ)

**Дата:** 2026-11-04 · **Класс:** M (после уточнения) · **Статус:** PASS — режим «только просмотр», упрощённый клиентский View as · **Код не менялся**

Параллельный чат (услуги) не трогали.

## Зачем (словами пользователя)

Администратор в «Мой профиль» выбирает любую роль из списка. Приложение показывает меню, кнопки и ответы сервера **как у этой роли**. Не выходя из приложения, снова открывает профиль и меняет роль. У не-админа такого пункта нет. Цель — смотреть сайт глазами других ролей.

## Вердикт

**Можно**, только с серверным `viewRole` в JWT. Правка только меню в браузере **недостаточна**: API всё равно отдаёт админские данные (деньги, закрытые разделы, `@Roles`). Менять `users.role` в базе **нельзя**: это уже не просмотр, а смена учётки.

## Как устроено сейчас (точки)

| Слой | Место | Сейчас |
|--|--|--|
| Профиль UI | `backend/pwa/sections/profile.js` | имя, телефон, аватар, вид экрана; роли нет |
| Сессия клиента | `backend/pwa/core/api.js:19–51` | `role` = `baseRole\|\|role`; `sees` / `canEdit` / `canMoney` / `isAdmin` |
| Меню | `backend/pwa/main.js` `shell()` + `sees()` | пересборка после `/auth/me` |
| JWT access | `auth.service.ts` `signAccess` ~283–297 | `sub, username, role, version, orgId` — **без** viewAs |
| Hydrate | `jwt.strategy.ts:40–58` | `req.user.role` **из БД**, не из claim токена |
| Права | `RolesGuard` → `effectiveRoles(req.user.role)` | |
| Деньги | `canSeeMoney` / MoneyMask | `isOwner` и `admin` всегда видят суммы |
| Разделы | `app-sections.ts` `openSectionsFor` | `admin` / `isOwner` → без ограничений |
| Список ролей | `GET /api/roles` | `@Roles('admin','manager')` |

## Решение пользователя (2026-11-04)

Нужен **только просмотр** (меню, доступы, кноки), чтобы проверить настройку роли — **не** действовать от её имени. Перелогин нежелателен. Если проще — сделать проще.

## Рекомендуемый вариант (упрощённый)

**Клиентский View as (класс M, без правок JWT):** в «Мой профиль» select роли → наложить на сессию `sections` / `canMoney` / `baseRole` / `roleLabel` из `GET /roles`; полоса «только просмотр»; любые не-GET в `api()` режутся на клиенте. Роль в БД и токен не меняются — поэтому select всегда доступен админу.

Обычная практика у программистов: тестовые учётки на роль **или** «View as» в продукте. Для проверки галочек роли клиентского просмотра достаточно.

## Отвергнуто / отложено

- **Действовать как роль (запись под её правами)** — не нужно.
- **Тестовый логин под каждой ролью** — то, от чего уходим.
- **JWT `viewRole` + серверная маска** — точнее для зон склада и 403 разделов; **волна 2**, если простой режим мало.
- **PATCH `users.role` в базе** — нельзя.

## Риски упрощённого варианта

1. В Network по-прежнему могут прийти суммы (сервер думает, что вы админ) — в UI скрываем; для глаз админа ок.
2. Зоны склада / серверный запрет раздела — **не** проверяются; в UI не обещать.
3. Блокировка записи только в `api()` — обойти из консоли может тот же админ; для инструмента проверки ролей приемлемо.
4. Ссылка «Администрирование» скрывается за счёт эффективного `session.role` после наложения.
