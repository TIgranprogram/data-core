# Единая локальная проверка

## Сохранность uploads при обновлении изолированного стенда (12.11.2026)

В `tools/night/compose.yml` добавлен собственный именованный том `<project>_uploads` с метками запуска.
Owner-проверка принимает прежние три тома и новый четвёртый, но запрещает чужие метки, bind uploads и подключение uploads к другому сервису.
Прод compose, живые базы и тома не менялись. Уже исчезнувшие до исправления файлы этим исправлением не восстанавливаются.

Процедура для существующего owned stand выполняется штатным `standRefresh` (`dc stand refresh`), только когда тестировщик закончил работу.
До запуска агент сверяет выбранный паспорт `current-stand.json`, project и порт с требуемым стендом: нельзя случайно обновить соседний 3102 вместо QA.
В ходе реализации ни 3102, ни отдельный активный QA 56535 не перезапускались.

1. Проверяется ownership всех ресурсов. Останавливается только backend по immutable ID; Mongo не пересоздаётся.
2. Существующий `/app/uploads` копируется в `tools/.night/stands/<run-id>/uploads-<id>/` на ПК. Рядом сохраняется SHA-256-манифест.
3. Только после успешного копирования и сохранения журнала backend пересоздаётся **остановленным**, с собственным uploads-томом.
4. Файлы возвращаются в том; отдельная контрольная копия сверяется с манифестом. Backend запускается только после совпадения.
5. При повторе после сбоя используется сохранённый журнал (`saved` → `verified`). Последующие refresh сохраняют именованный том без повторной миграции.

Копия, контрольная копия и тома автоматически не удаляются. При ошибке Docker cp, изменённой копии, ссылке/специальном файле или несовпадении содержимого — остановка с ошибкой.
Если legacy `/app/uploads` отсутствует, копирование также отказывает до пересоздания: сначала отдельно подтвердить отсутствие нужных файлов, не обходить защиту.
Существующий uploads-том без журнала у legacy backend не перезаписывается; требуется разбор координатором.
Проверено: `node --test tools/night-uploads.test.mjs tools/night.test.mjs` — 26/26 PASS; fake Docker, временные каталоги, без обращения к стендам.
Реальная проверка на отдельном QA-контуре выполнена: контейнер заменён, PNG и SHA256 сохранены. Доказательства — `../C086-passports-owner-review/QA-FINAL.md` и `QA-EVIDENCE.json`.

## Дома днём, на работе ночью: подготовка агентом

Проверено по `pult/catalog.mjs`, `tools/ai-tester/run.mjs`, `lib.mjs`, `watchdog.vbs`, `tools/night-stand.mjs` (12.11.2026).
Это порядок использования существующих инструментов; долгий прогон на втором ПК ещё не проверен.

1. Агент обновляет чистый checkout с GitHub, проверяет чужие процессы и незакоммиченные изменения. Секреты другого ПК не копирует.
2. Запускает «Готов ли компьютер к проверкам», устанавливает отсутствующие зависимости штатным способом и кнопкой «Установить проверки дизайна».
3. Выполняет «Все локальные проверки» один раз. Устраняет FAIL; фиксирует SKIP, не повторяет успешные этапы без изменений.
4. Для длительного UI-прогона проверяет Docker Desktop, Edge/Chrome и локальную LM Studio. Использует «Установить ИИ на этом ПК», затем «Проверить готовность» в разделе ИИ-тестировщика.
5. До подключения модели проверяет, что адрес LM Studio — loopback этого ПК, выбранная модель загружена и поддерживает инструменты. В отличие от vision-review, длительный runner не запрещает внешний baseUrl программно: это обязательная проверка агента.
6. Проверяет наличие свежей `datacore-*.tgz` в `D:\datacore-backups` либо папке `DC_BACKUPS`. Без копии длительный запуск не готов. Для получения копии предусмотрена «Скачать копию базы на этот ПК»; доступ/учётные данные — через ответственного агента доступа, без вывода секретов.
7. Подтверждает изоляцию стенда night: паспорт `tools/.night/current-stand.json`, собственные контейнеры/БД, адрес `http://localhost:3102`. Один localhost не доказывает изоляцию. Вход и проверки доступа поручает datacore-access; сам пароли не читает. Не подставляет :3000/:3001/:3002 или рабочую БД.
8. Запускает существующую кнопку «Запустить ИИ-тестировщика» сначала на 15 минут. Проверяет `run.log`, выполнение заданий и уборку тестовых записей; зелёная проверка готовности без работающего стенда недостаточна.
9. После успешной пробы выбирает 8/12/24 часа той же кнопкой. Дома — дневное окно, на работе — ночное. Новый runner, ежедневное расписание или бесконечный цикл не нужны.

Длительный инструмент повторяет UI-задания модели с тестовыми записями на копии. Он **не повторяет Jest/e2e непрерывно**.
Полный тестовый проход с e2e — отдельная существующая кнопка «Тесты кода: все (перед большой выкладкой)» после проверки изоляции.
C088 остаётся одноразовым прогоном без БД; не обещает 24 часа UI/e2e и не заменяет визуальную приёмку.

### Остановка и утренний разбор

- Долгий runner уже регистрирует Windows-задачу `DataCore AI tester watchdog`: вход в систему и каждые 10 минут. Это восстановление текущего запуска до выбранного срока, не новый ежедневный запуск. Регистрация требует работающего Планировщика; предупреждение об отказе нельзя скрывать.
- При трёх ошибках модели или сбое браузера текущий проход заканчивается, но сторож может возобновить его до срока. Для окончательной остановки использовать «Остановить ИИ-тестировщика» и проверить завершение; не считать отдельный сбой окончательным остановом.
- Истечение срока или кнопка остановки завершают цикл и запускают уборку. При подозрении на неверный стенд, внешний адрес модели, повторяющиеся ошибки или рост тестового мусора агент останавливает прогон и разбирает причину.
- Отчёт: `tools/logs/ai-tester/<дата>/REPORT.md`; доказательства — `run.log`, `steps.log`, `shots/`. Дата папки задаётся при старте процесса; ночной отчёт искать также за предыдущий день. Повторный запуск в один день дописывает отчёт.
- Агент сверяет завершённые задания, подтверждённые ошибки и гипотезы модели, остатки тестовых записей. После обрыва использует штатную уборку только на подтверждённом стенде.
- После фактического разбора отмечает отчёт `--reviewed <дата>` существующего runner. Сводку и пути доказательств сохраняет в crew; подробные журналы не пересказывает облаку.
- Журналы не синхронизируются Git. Агент на другом ПК не увидит их автоматически: разбирать на ПК запуска либо передавать проверенную краткую сводку без секретов. Закрытие пульта допустимо; выключенный ПК не выполняет тесты.

В пульте: **Тесты кода и экранов → Все локальные проверки**. Запуск ручной, расписание не создаётся.
Перед первым запуском доступна кнопка **Готов ли компьютер к проверкам**.
**Итог локальной проверки** показывает статус и путь к последнему отчёту без повторного тестирования.

Один прогон последовательно проверяет окружение, типы, юнит, импорты PWA/admin, design-lint, циклы модулей, пульт и инструменты проверки вида.
Копии этих проверок через `dc check` внутри прогона нет. Браузер проверяет HTML-фикстуру: подписи, геометрию и axe.
Это проверка инструментов, а не текущих экранов приложения.

Журналы: `tools/logs/local-checks/<запуск>/REPORT.md`, `summary.json` и отдельный `.log` каждого выполняемого этапа.
Отчёт сохраняется после каждого этапа. Незавершённый отчёт имеет статус RUNNING; указатель last обновляется только после завершения.
Вывод каждого процесса ограничен последними 2 МБ. Максимум: юнит 15 минут, типы/пульт/инструменты 3 минуты, модель 5 минут, остальные этапы 1 минута.
Блокировка исключает два одновременных запуска оркестратора; исчезнувший процесс освобождает блокировку при следующем запуске.

Статусы: PASS — этап выполнен, FAIL — ошибка или таймаут, SKIP — этап недоступен/не выполнен полностью.
Общий итог: FAIL при любой ошибке, иначе PARTIAL при любом пропуске, иначе PASS.
Коды выхода: 0 PASS, 1 FAIL, 2 PARTIAL или сбой оркестратора. При частичном отчёте нельзя заявлять полную проверку.
Пропуск Docker не мешает тестам без БД. При отсутствии зависимостей этап пропускается явно, установки автоматически не запускаются.

## Для координатора

На другом рабочем ПК Git переносит код и кнопки, но не установленные зависимости, журналы или настройки LM Studio.
Нужны Node.js, Git, зависимости backend и tools/design-checks, установленный Edge (или DESIGN_BROWSER).
Проверка готовности ничего не устанавливает. Docker для прогона без БД необязателен; отсутствие даст SKIP.
Локальная модель нужна только при явно переданных снимках; используются настройки этого ПК, обязательного облака нет.
Журнал первого запуска появится только после проверки на этом ПК; кнопка последнего итога до этого сообщает ошибку отсутствующего отчёта.

Для заданных изображений: `node tools/local-checks.mjs --baseline <принятый.png> --current <новый.png> --vision-input <снимок-или-папка>`.
Параметры необязательны. Модель использует существующие настройки и кэш `vision-review`; только loopback, максимум 3 изображения.
Результат модели — гипотезы; PASS этого этапа означает выполненный анализ, не отсутствие дефектов. Различие PNG означает необходимость просмотра.
Старые снимки не подбираются автоматически. Эталон автоматически не утверждается. Без изображений эти этапы SKIP.

Обход реального сайта, e2e с БД и приёмка человеком отмечены SKIP с причинами.
Стенд и база автоматически не запускаются: изоляция БД и доступ требуют отдельного подтверждённого процесса проекта.
Новый запуск не читает .env, не входит в API сайта, не отправляет данные в облако и не изменяет расписания.
