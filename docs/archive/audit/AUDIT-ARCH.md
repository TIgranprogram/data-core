## 0. Главный вывод

1. Данные и сервер к жалобе почти не причастны: тяжёлые списки уже кэшируются по версиям данных (`DataVersionService.cached`: склад, заказы, итоги заявок), N+1 в просмотренном нет (`supply.service.ts:128 present` — 5–7 пакетных запросов на страницу).
2. Узкое место — **старт оболочки**: DOMContentLoaded 2,4 с при нулевой сети (всё из SW) [изм]. Разбор кода — доли секунды, значит ~1,3 с уходят на ожидание, а не на работу. Вероятная причина — `sw.js` ждёт `version.json` по туннелю перед ответом (§1.2). Это гипотеза: подтвердить 15-минутным замером (§1.1).
3. Статический граф от `main.js` — 48 файлов, 324 КБ, глубина 4 [изм, скриптом по import/export]. Остальное из «54» тянут `import()` и modulepreload. Экран входа грузит почти всё приложение (list, form, card, board, чат, колокольчик) раньше, чем человек увидит поле «Логин».
4. Лишнего кода немного (§3). Переписывать архитектуру или менять фреймворк не нужно.

## 1. Загрузка приложения

### 1.1 Что видно (факты)
- `index.html` уже содержит `modulepreload` для 38 модулей (генератор `backend/scripts/pwa-preload.mjs`) [изм]. Граф — 4 уровня, а не «лесенка» из 20.
- План С5 (`docs/ARCH-PLAN.md:44`) решил: «время уходит на задержку туннеля». Новый замер противоречит: transfer 0, а модули всё равно ~1,27 с. Значит, ждёт кто-то между страницей и кэшем: SW или главный поток.
- Одинаковое время (1270–1290 мс) у независимых модулей — признак общего ожидания одного события, а не последовательных загрузок.

**Замер, отличающий SW от главного потока (консоль прода, код не правим):**
`performance.getEntriesByType("resource").filter(r=>r.name.endsWith(".js")).map(r=>[r.name.split("/").slice(-2).join("/"), Math.round(r.workerStart-r.startTime), Math.round(r.fetchStart-r.workerStart), Math.round(r.responseStart-r.fetchStart)])`
- большое `startTime→workerStart` — SW долго стартует или занят; большое `workerStart→fetchStart` — ожидание внутри обработчика (гипотеза `await ver`); всё малое при большом `duration` — занят главный поток (разбор 740 КБ и выполнение `main.js`).
Повторить при холодном SW (вкладку закрыть, подождать ~1 мин) и при тёплом.

### 1.2 `sw.js` — почему вероятно виноват он
- `sw.js:97–102`: каждый запрос модуля делает `await (ver ??= syncVersion())`. `syncVersion` (`:31`) — `fetch("version.json", {cache:"no-store"})` через туннель (~1 с). После пробуждения SW переменная `ver` пуста: каждое открытие начинается с сетевого запроса, хотя кэш уже локально.
- `sw.js:80–94`: страница (`navigate`) отдаётся **только после** сети: `await ver` и `await net`. Кэшированный `index.html` не используется, старт не быстрее одного круга до сервера.
- `sw.js:41–43`: при смене версии удаляется весь кэш оболочки — после каждой выкладки заново тянутся все файлы, даже если изменился один. Выкладок много (v1.340).
- `Cache-Control: no-cache` (`main.ts:134,147`) для работы с SW безвреден; без SW (первый заход) каждый файл — отдельная сверка ETag.

## 2. Данные экранов

Цель (предложение, не договорённость): DCL входа < 1,2 с, список «Заказы» < 2,5 с при тёплом кэше.
