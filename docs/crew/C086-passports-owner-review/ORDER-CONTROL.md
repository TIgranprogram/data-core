## Дополнение: план обычных заменяемых рисунков (не выполнен)

Координатор сообщил последующее разрешение пользователя сохранить временные примеры рисунков обычными изображениями изделия для замены завтра. **В этой проверке прод по-прежнему только читался; POST/PUT/DELETE не выполнялись.** Перед исполнением координатор должен закрепить конкретную разрешённую запись в ТЗ.

Повторный GET `/api/products/6adaff432a8dad6034b14603/photos?purpose=passport` нашёл ровно одну связь: `6ae6caffcd8ad39a38939545`, kind=`overview`, photoId=`6ad8d491371b65d090d8c88c`. Её и витринное фото сохранить. Связей dimensions/foundation пока нет.

Точный план для исполнителя после разрешения:

1. Подготовить два PNG с видимой надписью «ВРЕМЕННЫЙ ПРИМЕР — НЕ ДЛЯ МОНТАЖА», без выдуманных инженерных параметров фундамента. Размеры изделия использовать из текущего каталога, с указанием, что они требуют сверки с рабочим чертежом.
2. Повторно прочитать связи purpose=passport: если нужный вид появился после проверки, не удалять и не перекрывать его автоматически.
3. Для каждого PNG: `bash deploy/synology/api.sh prod POST /api/photos/upload?purpose=passport --form 'file=@/d/.../имя.png'`. Скрипт поддерживает multipart; путь файла абсолютный, поскольку сам скрипт меняет каталог. Сохранить только ID ответа и связь с исходным файлом, не токены.
4. Затем POST `/api/products/6adaff432a8dad6034b14603/photos` с JSON `{"photoId":"<ID нового PNG>","purpose":"passport","kind":"dimensions","caption":"Временный пример — заменить рабочим чертежом"}` и аналогично `kind:"foundation"` для схемы фундамента. JSON-файлы передавать api.sh абсолютными путями. **kind=install отсутствует в enum и даст 400**; `mounting` — самостоятельный допустимый вид монтажа, но текущую потребность в `foundation` не закрывает.
5. Не изменять passportDefaults, номера, старый паспорт №500 или другие фото. Зафиксировать ID двух новых ProductPhoto-связей; повтор запроса attach не идемпотентен и создаёт новую связь, поэтому сначала сверять GET.
6. Проверить GET связей и GET плана заказа. Появление ready означает только полноту полей по программе, не техническую пригодность временного примера. Выпуск/клиентскую печать не запускать.

Обычная замена в UI (`product-files.js:attachProductFile`) сначала загружает/привязывает новую картинку, потом мягко удаляет **только старую связь конкретного слота**. Сам файл остаётся для уже выпущенных паспортов. При ошибке удаления обе связи остаются; это требует ручной проверки. При первоначальном добавлении в пустые слоты DELETE вообще не нужен. Откат добавления — удалить только две записанные новые связи; старую overview не трогать.

### Права и предел обещания «менеджер завтра заменит»

По текущему коду upload и attach/PATCH/DELETE фото доступны `admin, manager` (директор наследует права менеджера через RolesGuard; владелец проходит role gates). `PUT /api/showcase/:id/passport-defaults` и `POST /api/passports/preview` — `admin,director`/владелец. PUT defaults **заменяет весь нормализованный объект**, а не частичный merge; для рисунков он не нужен.

Форма `passports/fill/index.js` передаёт слотам `canEdit = session.canEdit && canEditTexts()`, а `common.js:canEdit` разрешает только admin/director/isOwner. Поэтому **обычному менеджеру нельзя обещать замену именно в этой форме**, несмотря на разрешённый API фото. Без изменения кода нужен директор/администратор/владелец для замены через этот экран; права конкретного аккаунта не проверялись и не менялись.
