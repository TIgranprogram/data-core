# C169 — архитектура загрузчика на одном ПК

1. Выбранный корень содержит Inbox, Processing, Question, Ready и закрытую служебную папку. Обрабатывать только обычные файлы внутри корня, исключить ссылки, junction и временные файлы. Папки переходов должны находиться на одном томе.
2. Один обработчик держит блокировку корня от начала сканирования до записи отчёта. Повторная кнопка показывает текущий прогресс. При восстановлении проверять владельца блокировки, возраст файла сам по себе не доказывает остановку.
3. Завершённое поступление подтверждает атомарная публикация закрытого файла производителем либо проверка эксклюзивного доступа к файлу на Windows. Пока файл занят или меняется, он остаётся во входящих. Две одинаковые проверки размера не доказывают закрытие.
4. Для каждой физической копии создать отдельный случайный ID поступления. До перемещения записать исходное имя и место назначения. Перемещать оригинал через rename в эксклюзивно созданный каталог этого поступления; занятый путь сверять по журналу. Так сохраняются и одноимённые файлы, и байтовые дубли.
5. Из захваченных байтов получить SHA-256. Идентификатор документа вывести из SHA, ключ шага — из идентификатора документа, назначения и стабильного имени действия/строки. Корень, путь, партия, модель и время в эти ключи не входят. Привязать обработку к настроенному контуру API и сверять его при возобновлении.
6. В служебной папке хранить на поступление снимок состояния с номером версии. Запись во временный файл, flush, закрытие и атомарная замена. Сохранять переходы, SHA, версии разбора, proposal, план с хешем, решения, receipt и результат сверки. Заголовки авторизации и сырые HTTP-ошибки в журнал не переносить.
7. В журнале до действия закрепить намерение и его параметры. После сбоя проверить оба пути и SHA, для сетевого действия — серверный результат по UID. При противоречии остановить конкретное поступление. Подтверждённое перемещение или действие записать как выполненное. Завершённый разбор переиспользовать по SHA.
8. Локальный extractor отдаёт текст с привязкой к странице/ячейке. Модель получает только данные, возвращает JSON по закрытой схеме с цитатами. Исполнитель проверяет принадлежность цитат источнику, направление, обязательные реквизиты, валюту, даты, суммы и строки, затем строит план из разрешённых действий. API, токен, пути и команды задаёт приложение.
9. До записи запросить кандидатов по SHA и полному предметному ключу, включая удалённые. Неоднозначность, удалённая запись или другая редакция требуют решения с показом отличий. Счёт или акт сами по себе не разрешают платёж, получение товара или создание заказа.
10. Использовать предметные API, если для каждого шага подтверждены уникальность UID, сверка хеша и доступный после перезапуска результат. Для частично сохранённого комплекта хранить черновик и продолжать с первого недоказанного шага. Повтор того же UID с другим планом — конфликт; после исправления сначала сверить прежние эффекты.
11. При пробеле в API добавить узкую серверную операцию импорта с чтением результата по UID. Сервер ограничивает типы/поля/роли, связывает receipt и предметную запись одной транзакцией, хранит UID с уникальным индексом и проверяет hash/CAS. Для файлов нужны отдельная адресуемая стадия, проверенный сервером SHA и повторное использование тех же байтов/ID после сбоя записи метаданных.
12. Перед Ready прочитать актуальные данные через API и сверить IDs, живое состояние, SHA вложения, связи, ожидаемые строки и суммы с планом. Для дубля предъявить ID и совпадающий источник/ключ. Записать доказательство до последнего перемещения; при потере связи показать паузу. Черновик с разрешёнными открытыми вопросами пометить в отчёте.
13. В пульте путь «Папка → Разобрать → Отчёт» показывает текущий файл, счётчик, четыре итога и причины. «Возобновить» продолжает остановленные шаги, решение менеджера запускает только выбранные исключения. Ключи и адресные доказательства доступны в подробностях.
14. Приёмка на временной папке и тестовом API: параллельный старт, занятый файл, одинаковые имена и SHA, удалённый дубль, смена контура, обрыв после upload/commit/rename, перезапуск и изменённый план. Сравнить число оригиналов, API-записей и вложений; каждый Ready должен иметь читаемое доказательство.

Основания — C169/TZ.md, строки 21–28, 41–60, и C164/CONTRACT.md, строки 40, 53–59, 83–85. Какие маршруты уже выполняют условия пунктов 10–11, устанавливает проверка реализации контрактов.
