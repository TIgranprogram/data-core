# C155. Контракт шаблона изделия и выпуска паспорта

Контракт для П155-2–9, 19.11.2026. Основание — SHOULD.md, серверная и интерфейсная проверки. Имена ниже обязательны для обеих сторон. Все пути начинаются с `/api`. Образец строится из сохранённых сведений изделия. Каждый экземпляр имеет отдельный `passportId`.

## Данные и совместимость

| Где | Поле | Семантика |
|---|---|---|
| `products.passportDefaults` | `simpleDescription?: {text: string, partIds: ObjectId[]}` | Собственная краткая фраза имеет приоритет. Ссылки на действующие `passportParts` необязательны, порядок сохраняется. В JSON id передаются строками. Если своего текста нет, сервер ищет применимый словарный вариант. |
| `productpassports` | `presentationVersion?: 1`, `variant?: 'short' \| 'full'` | Пара полей нового генерируемого экземпляра. Без Mongoose default на старых записях. Сервер выставляет оба поля вместе. Параметр версии в запросе выбирает известный контракт, запись версии в Mongo выполняет сервер. |
| `productpassports.textSnapshot` | `description` и имеющиеся разделы, правила, ТО, метки компоновки | Для нового short в `description` фиксируется утверждённый текст. Для нового full используется существующий подробный сборщик. Исходные таблицы/модули изделия продолжают хранить все данные. Подписи и текст выпуска сохраняются по значениям на момент выдачи. |

**Выбор версии.** Новая книжка, включая заявку после iLogic, явно передаёт `presentationVersion:1` для check, preview, плана заказа и команд создания. На новом маршруте шаблона версия 1 подразумевается. Для версии 1 начальный вариант — short, полный выбирается прямо в текущей книжке. В существующих API вызов без версии, у которого ещё нет целевого экземпляра, сохраняет прежнюю семантику. У сохранённого экземпляра его собственные поля определяют версию. Вариант черновика версии 1 может быть явно изменён через существующий PATCH экземпляра с пересчётом готовности и снимка. Изменение переключателя шаблона или плана не изменяет существующий экземпляр.

**Старые данные — уточнение владельца 19.11.** Работа C155 относится к созданию новых паспортов. Отсутствие `presentationVersion` выбирает прежнюю ветку даже при `status` отсутствующем или историческом. Старые паспорта и черновики не мигрируют и не переводятся в v1, их контент/снимок/номер/привязки/файлы не переписываются новым потоком. В новом интерфейсе для них только просмотр/печать с понятной отметкой старого образца. Попытка PATCH legacy→v1/variant возвращает409. Если старая позиция уже имеет legacy, новый поток показывает его, не создаёт дубль и не аннулирует ради нового формата. Старые API прежних клиентов, готовые файлы и маршрут совместимости CRM сохраняются; ручные изменения старых документов этой задачей не выполняются. Новое создание standalone того же изделия — отдельный новый экземпляр, не переделка прежнего.

## Шаблон и частичное сохранение

Новый вход архивной карточки использует `GET /passports/:id?readOnly=1`, печать из неё — `GET /passports/:id/pdf?readOnly=1`. Параметр также принимают `GET /passports/order/:orderId/pdf` и `GET /passports/zip`. Этот режим открывает сохранённые данные, собирает отсутствующий текст прежней формы в памяти и оставляет запись и отметку скачивания без изменений. Вызов без параметра сохраняет поведение прежних клиентов.

**GET `/showcase/:id/passport-template?variant=short|full`** — новый запрос `PassportTemplateQueryDto`. Возвращает 200 для живого изделия, в том числе без категории. Права — `@Roles('admin','director','manager')`, `@AppSection('products','passports')`, как у изменения паспортных настроек. Чтение не создаёт черновик и не синхронизирует сохранённые экземпляры. Формат результата:

```ts
{
  mode: 'template', productId: string, presentationVersion: 1, variant: 'short' | 'full',
  product: { name: string, article: string | null, dimensions: object | null, weightKg: number | null },
  defaults: object,                   // собственные сохранённые настройки, {} при отсутствии
  document: object,                   // полная разрешённая проекция previewDoc для renderer книжки, без id/_id/номера/фирмы/заказа
  passportCategory: string | null,    // действующий тип после наследования
  effectiveImages: Array<{kind: string, photoId: string, url: string | null, caption?: string}>,
  standardImages: Array<{kind: string, photoId: string, url: string | null}>,
  textSnapshot: object | null,        // результат сборки в памяти, как для предложения страниц в previewDoc
  readiness: Readiness
  simpleDescriptionSource: {kind: 'own'|'dictionary', id?: string, rootId?: string, partIds: string[]} | null,
  simpleDescriptionSuggestions: Array<{id: string, rootId: string, name: string, text: string, partIds: string[]}>
}
```

Нет категории — `textSnapshot:null` и адресный блокер `category`. Отсутствующий подтверждённый short-текст отображается в образце как незаполненный, сохранённый технический текст допускается показать только как предложение для принятия. Независимый `GET /passports/template` продолжает обслуживать общий шаблон категории. Список или «последний паспорт» изделия для открытия книжки продукта не используется.

`document` содержит разрешённые поля готовой in-memory проекции: реальные габариты/массу, унаследованные параметры категории, textSnapshot и effectiveImages. Он не создаёт Mongo-сущность и не имеет passportId. Frontend использует его для существующего renderer, а `defaults` — только как прежние собственные значения PATCH; правила наследования на клиенте не дублируются. Общий контекст книжки `mode:'template'` запрещает обращения к `/passports/:id` для сохранения этого объекта.

`simpleDescriptionSuggestions` перечисляет готовые конечные варианты живых корней назначения `simple-description`. Приоритет — собственная фраза, явно выбранный применимый вариант, однозначный вариант по виду, признакам или групповому контексту, затем дефолтный или единственный подходящий. У выбранного словарного источника `id` — вариант, `rootId` — раздел, `partIds` — его части. При равных вариантах сервер возвращает `choice:<rootId>`; когда применимых фраз нет — `simpleDescription`. Для выбора в существующей воронке `GET /passports/funnel?productId=…&category=…&presentationVersion=1&variant=short` включает применимое дерево кратких фраз. `defaults.simpleDescription` содержит только собственную фразу.

**UI-ссылки:** новое iLogic/карточка открывают `#products?templateFor=<productId>`. Старый `bookFor=<productId>` поддерживается как совместимый вход в шаблон, без создания экземпляра. Прямой вход конкретного паспорта по его id сохраняется. «Выпустить» из шаблона отдельно выбирает фирму/контекст, создаёт экземпляр и продолжает только по возвращённому id.

**PATCH `/showcase/:id/passport-template?variant=…`** — новый `PatchPassportTemplateDto`. Тело `{changes, expected}`: два объекта с одинаковым непустым набором редактируемых ключей. `expected` содержит прежние **собственные** значения из `defaults` для этих ключей, отсутствие — `null`. Вложенные карты `textChoices` и `textOverrides` сравниваются и изменяются только по переданным id корней. `simpleDescription` — одно атомарно редактируемое значение. Пример принятия описания:

```json
{
  "expected": { "simpleDescription": null },
  "changes": { "simpleDescription": { "text": "Основные части — каркас, рукоятки и педали.", "partIds": [] } }
}
```

Типы и разрешённые ключи `changes` — редактируемые параметры из `showcase/passport-defaults.ts` (`passportCategory`, `kindId`, элементы, материалы, монтаж, соединения, ручные тексты, модули, числовые поля, места, выборы и переопределения текстов) плюс `simpleDescription`. Пустая строка в новом описании при записи — 400, снятие собственного значения явно передаётся как `null`. Оба объекта проверяются по закрытому списку, ссылки частей — ObjectId в нужном живом словаре, дубли исключаются с сохранением порядка. При смене типа уже подтверждённые значения остаются доступны для проверки применимости. Неизвестный ключ, имя Mongo-оператора, неверный id или значение — 400 с полем. Недоступное изделие — 404.

Точные ключи: `passportCategory`, `kindId`, `elements`, `materialIds`, `installationTypeId`, `isKit`, `joints`, `manualText`, `modules`, `ageFrom`, `ageTo`, `heightMin`, `heightMax`, `weightMax`, `maxUsers`, `fallHeight`, `siteLength`, `siteWidth`, `serviceLifeYears`, `warrantyMonths`, `foundationDepth`, `seatsCount`, `textChoices`, `textOverrides`, `simpleDescription`, `manualDescription`, `manualPurpose`, `manualInstall`. Массивы принимают `[]` как своё пустое значение. `manualDescription` → `description`, `manualPurpose` → `purpose`, `manualInstall` → `installationMethod` в проекции. Это собственные строки шаблона с приоритетом над общими полями изделия в версии 1. В short описание берётся из `simpleDescription`. `manualText` по-прежнему хранит флаги общих текстовых полей изделия.

В `textChoices` значение корня — id конечного варианта, в `textOverrides` — строго `{text}` либо `{off:true}`. Для снятия передайте `null` в переданном корне. Например, два изменения независимы:

```json
{
  "expected": { "textOverrides": { "64abc0123456789012345678": null } },
  "changes": { "textOverrides": { "64abc0123456789012345678": { "text": "Устанавливать на подготовленное основание." } } }
}
```

Сохранение одной операцией Mongo под фильтром `_id`, `deletedAt:null` и прежних значений затронутых полей. Нормализация различает отсутствие, пустой список, null и явное снятие, сравнивает BSON-типы как при записи. Явный `passportDefaults:null` у старого изделия инициализируется под отдельным условием, без потери параллельных изменений. Назначаются/снимаются только разрешённые пути. Из двух редакторов независимые поля сохраняются оба, второе изменение одного поля возвращает 409 и позволяет перечитать книжку. Для ответа на успех используется тот же JSON, что у GET, с актуальной готовностью. Права и аудит — как у имеющегося `PUT /showcase/:id/passport-defaults`.

Старый PUT заменяет свой прежний набор настроек. При отсутствии нового поля он обязан сохранить `simpleDescription`, включая случай пустого старого PUT и конкурентной записи через новый PATCH. Защиту реализовать в существующем методе под проверкой прежнего значения или точечными изменениями старых ключей. Через новый PATCH разрешено явное снятие краткого описания. Массовое изменение настроек не должно потерять новый блок. Проверить круговой проход старого клиента, которому поле незнакомо.

**Общие поля изделия.** Размеры, масса и паспортные рисунки сохраняются существующими маршрутами редактирования изделия/фото с их действующими правами. `PATCH /showcase/:id` уже обслуживает ручной ввод и iLogic. Сохраняются только реально изменённые данные, отсутствующая при повторном импорте масса пропускается. В шаблонном PATCH нет произвольных полей продукта. Такое разделение сохраняет права на каталог, подтверждение смены импортируемых данных и один источник физических характеристик. Каждое действие сообщает об успехе только после ответа своего API.

## Готовность, книжка и PDF

```ts
type Readiness = {
  ready: boolean,
  missing: Array<{key: string, label: string, hint: string}>,
  recommendations: Array<{key: string, label: string, hint: string}>,
  defaulted: Array<{key: string, label: string}>,
  requiredImages: string[],
  imageSlots: string[]
}
```

Для версии 1 `ready` равен `missing.length === 0`. Единое вычисление принимает действующий тип, изделие и его контекст выбора фраз, данные конкретного экземпляра при наличии, версию, вариант, режим template/instance. Вычисление смотрит фактически используемые изображения (включая стандартные схемы) и проверяет читаемость, как при выпуске. Сохранённые/автоматически разрешённые варианты не попадают в очередь. Обязательный выбор, ошибка источника или повреждённый обязательный рисунок видны адресно. Ошибку сборки нельзя превращать в `ready:true`. Список рекомендаций не меняет готовность. При открытии шаблона достаточно `readiness` в одном ответе, второй запрос техописания/общей очереди не нужен.

| Вход | Контракт версии 1 |
|---|---|
| `POST /passports/check` | Добавочные `presentationVersion`, `variant`, `mode`. Для шаблона нужен `productId`. Для сохранённого экземпляра добавить `passportId`: брать экземпляр по нему, отвергать противоречащие id и учитывать его собственные поля. Для старых форм допускать их действующие параметры. Ответ сохраняет верхнеуровневые `mode, missing, defaulted, requiredImages, imageSlots` и добавляет `ready,recommendations,variant,presentationVersion`. Статус и номер не меняются. |
| `GET /showcase/:id/passport-gaps`, `GET /passports/:id` | В новом режиме выдают те же блокеры, сохраняют старые ключи, отдают дополнительно `readiness`. Переключение варианта в книжке изделия перечитывает шаблон. Готовность выпущенного относится к снимку, автоматический пересчёт по текущему изделию для исторической печати не нужен. |
| `POST /passports/preview` | Расширить существующий `PassportPreviewDto` одним необязательным `presentationVersion:1`. Новая книжка шлёт `{productId,presentationVersion:1,variant,mode:'pages',pack:'passport'}`. Ответ — действующий PDF с меткой черновика, без фирменного номера, создания экземпляра, изменения счётчика и отметки выдачи. `mode:'print'` — явная печать буклетом. Недостающие поля обозначаются в образце. Без категории сохраняется содержательный 400. |
| `POST /passports/:id/issue` | Принимает существующий пустой запрос. Для версии 1 определяет variant по сохранённому черновику. Если клиент передаёт ожидаемый `variant` или `presentationVersion`, они должны совпасть, иначе 409 с предложением перечитать книжку. Готовность исходных данных и принадлежность перепроверяются в существующем транзакционном выпуске. При блокерах — 400 с `{message,missing}`, без расхода номера. Повтор для того же уже выпущенного id возвращает тот же экземпляр. |
| `GET /passports/:id/pdf` и PDF заказа | Черновик версии 1 использует сохранённый variant. Выданный — проекцию и вариант именно его редакции. Переданное старым клиентом `?variant` не меняет представление нового выданного экземпляра. Общий PDF может содержать одновременно short и full. Для legacy действуют прежние правила варианта запроса. Сохраняются существующие `mode, bw, stamp, seal, sign`, готовые вложенные PDF и обработка пропущенных/ошибочных позиций. |

**Short.** Обязателен определённый краткий текст из собственной настройки или действующего словаря. Отсутствие производственного дерева, материала, марки, сечения, покрытия, таблицы материалов, каталоговых признаков и выборов только для подробного описания само по себе не добавляет блокер. Подтверждённые назначение и тип могут удовлетворить назначение без повторного выбора «Элементов». Элементы/соединения, применимые нормативные данные, монтаж и ограничения учитываются, если от них действительно зависит обязательная инструкция данного типа. В шаблоне не требуются фирма, дата выдачи или заказ. В образце, книжке и выдаче используется одинаковый разрешённый текст. Состав/ручные модули не включаются в краткий раздел конструкции; реальная комплектность поставки и применимые инструкции печатаются. `pack=tech|combined` остаётся самостоятельным явным выбором.

**Полный.** Проверять и печатать по текущим подробным правилам full, с богатым описанием, материалами, модулями и действующими правилами категории. Новое `simpleDescription` не заменяет `products.description`, флаги `manualText` или богатые строки. Текст, сведения и рисунки шаблона можно использовать для обоих вариантов, но готовность каждого рассчитывается отдельно.

**Неизменность.** В транзакции версии 1 фиксируются `variant`, версия, разрешённый текст, применимые поля и выбранные ссылки на фактически использованные рисунки, включая стандартные, в существующем снимке/экземпляре. Для новой версии зафиксировать использованные входы печати из изменяемых справочников и реквизиты оформления у экземпляра: переименование частей, смена фирмы в заказе, замена схемы, правка изделия и повторный iLogic не должны изменить ранее выданный паспорт. Ссылки на использованные файлы относятся к прежним файлам, которые сохраняются при замене. При репринте выбирать зафиксированные источники, без замены не найденного файла новым по виду. Явная редакция обновляет данные через существующую историю. Проверяются тексты, изображения, номера и принадлежность. Сравнение байтов PDF не является обязательным способом проверки, поскольку служебные метаданные нового рендера могут отличаться.

## Создание и принадлежность

- **Самостоятельный.** На действие «Выпустить паспорт» клиент выбирает действующую свою организацию (можно заранее показать единственную). `POST /passports` с `{presentationVersion:1,variant,productId,supplierOrgId,creationKey}` создаёт самостоятельный черновик. `creationKey` — UUID одного нажатия, прежний ключ сохраняется при техническом повторе до получения id. После создания UI продолжает строго по возвращённому `id`. Возможна отдельная осознанная новая выдача той же модели с новым ключом. В новом самостоятельном запросе связи заказа отсутствуют и номер клиентом не задаётся. Ответ — существующий объект паспорта плюс variant/версия. Отбор из списка последних паспортов не используется.
- **Позиция.** `POST /passports` с `{presentationVersion:1,variant,incomeId,salesOrderId,productId}` открывает/создаёт живой черновик именно этой позиции. Сервер находит действующую позицию, её действующий заказ и изделие, сверяет все три id. Чужой, отсутствующий или отменённый источник даёт содержательную ошибку. При наличии живого экземпляра соответствующей позиции возвращается его id и фактический статус, включая issued. Конфликт между запрошенным вариантом и существующим черновиком показывается клиенту; изменение возможно только явным PATCH. Старый черновик предлагается открыть в прежнем режиме или явно перевести. Две позиции одного изделия получают разные id.
- **Фирма.** Действующая наша `salesorders.companyId` определяет `supplierOrgId` позиционного экземпляра. Противоречие с явным id/фирмой сохранённого черновика — 409 до номера. Если у заказа фирмы нет, принять выбранную действующую нашу из существующей панели; единственная наша допустима как умолчание. Если `companyId` задан, но фирма удалена/чужая, показать источник конфликта, без подстановки другой. Существующий черновик с пустым поставщиком получает разрешённую фирму до проверки и выдачи. В шаблон изделия фирма из позиции не переносится. Для каждого нового выпуска проверять `organizations._id`, `deletedAt:null`, `isOurCompany:true`. В standalone нет источника для заказа и покупателя. При выпуске позиции повторно проверяются её статус, связи, фирма и единственность живого паспорта, в том числе после изменения заказа.
- **План заказа.** Расширить `GET /passports/order/:orderId/plan` и `OrderIssueDto` необязательной версией. Параметр панели определяет вариант для новых позиций. У имеющейся позиции учитываются её конкретный паспорт и фирма, даже если в том же заказе повторяется изделие. Форма `lines`, `issued`, `skipped` и счётчики сохраняются. Выбор чужого `incomeId` не выпускает документ. Согласовать одиночный и пакетный выпуск на одном результате проверки.
- **Повтор/гонка.** Использовать один дополнительный технический строковый ключ в существующей `productpassports` с уникальным разреженным индексом. Для standalone — `single/<actorId>/<creationKey>`, для живой позиции — `line/<incomeId>`, сервер строит его сам. Запрос с тем же ключом обязан вернуть ранее созданный объект при совпадении исходной принадлежности и варианта; несовпадающие данные дают 409. Проверка и повторное чтение при дубле индекса обязательны. У позиционного ключа освободить занятость при аннулировании/удалении и проверять при восстановлении; прежние номер и история сохраняются. У исторических записей без ключа перед присвоением использовать текущий поиск по `incomeId`, не выбирать произвольно при нескольких живых строках. Общие пути создания/восстановления позиционных экземпляров в этом API соблюдают тот же инвариант. Фоновое переписывание имеющихся документов не требуется. Имя технического поля — `creationScopeKey`, индекс — `creationScopeKey_1`, отсутствующее поле совсем пропускается. Прописать индекс в действующем `ensure-indexes.js`, проверить наличие до включения нового сценария. Только заголовок `Idempotency-Key` недостаточен для параллельных первых запросов: текущий middleware сохраняет ответ после успешной записи.

## Справочники, права и контроль

`passportParts` — словарь названий частей и грамматических форм. Ссылки `passportDefaults.simpleDescription.partIds` и `passportPhrases.partIds` учитываются при проверке использования, удалении и объединении. Ручной текст и снимки выпущенных паспортов сохраняются. `passportPhrases` хранит назначение `simple-description`, ссылки `kindIds` на виды ветки и `partIds` на части конечной фразы. `{parts}` подставляет грамматические формы `genPlural`/ `genSingular` в порядке ссылок. Ветки используют действующий тип, вид, группы и сохранённые признаки. Эти корни предназначены для short-воронки. Материалы, нагрузка, масса, глубина и скрытый крепёж берутся из подтверждённых источников. Общий словарь пополняется с действующими правами справочника.

Новые GET/PATCH шаблона и существующие preview/check, доступные из продукта, должны учитывать оба раздела приложения (`products`, `passports`) при сохранении явного списка ролей. Операции экземпляра и заказа сохраняют текущие `@Roles` и ограничения разделов. Все новые DTO совместимы с глобальным `forbidNonWhitelisted`: явно описать вложенные объекты, параметры, enum и преобразование числовой версии query. Старому маршруту с произвольными реальными полями формы не подставлять узкий DTO, отвергающий прежние ключи. Не расширять права на общий каталог или справочники через PATCH шаблона. Обновить маршруты в MAP и снимок OpenAPI.
