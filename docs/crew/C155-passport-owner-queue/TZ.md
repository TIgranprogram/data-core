# C155 — паспорта: очередь замечаний владельца

Дата: 19.11.2026. Статус: сбор замечаний и последовательная приёмка.

**Зачем:** владелец проходит паспорта и сообщает, что изменить; координатор ведёт очередь, исполнение и доказательства.
**Результат:** пользователь создаёт, заполняет, сохраняет, повторно открывает, выпускает и печатает паспорт без потери данных.
**Класс:** определяется для каждого пункта отдельно. Одновременно максимум три субагента и координатор.
**Приёмка:** компьютерный интерфейс; мобильные замечания записываются на будущее.

## Порядок работы

1. Каждое замечание получает номер П155-N, описание текущего и нужного поведения, критерий приёмки.
2. Перед реализацией координатор указывает зависимости, точные файлы, класс, исполнителя и проверки.
3. Сначала сохранность данных и блокирующие ошибки, затем удобство и оформление. Срочность владельца имеет приоритет.
4. Независимые пункты выполняются параллельно; пересекающиеся файлы принадлежат одному исполнителю.
5. Каждый исполнитель получает только свой пункт и необходимые файлы. Чужие изменения не откатывает.
6. Повторные замечания дополняют существующий пункт; сделанное C148/C151/C152 повторно не реализуется.
7. Закрытие пункта требует проверки результата и записи доказательств. Для интерфейса обязательна приёмка по UI-ACCEPTANCE.

### Контракт до кода (П155-2)

- Явные режимы интерфейса: шаблон изделия / конкретный экземпляр / образец. Шаблон идентифицируется productId; экземпляр — passportId; заказ требует совпадения incomeId+salesOrderId+productId.
- Для нового экземпляра вариант и версия представления сохраняются аддитивно; check, gaps, issue, PDF, план используют один контекст. Legacy без нового признака не переинтерпретируется молча.
- Образец использует существующий preview без создания документа и расхода номера. Утверждённое решение для сценария владельца: посмотреть/печатать без номера, «Выпустить» выдаёт номер. Произвольный номер при каждом скачивании не добавляется.
- Самостоятельный выпуск требует существующую нашу организацию; заказ использует свою фирму и фактическую позицию. Сервер отвергает противоречащие связи.
- Новый краткий текст — добавочная настройка изделия; полный materialsSpec, description и остальные passportDefaults не стираются. Сохранять только изменённые поля с проверкой прежнего значения по существующей защите.
- Точные имена новых полей и DTO, способы PATCH/PUT и форма ответов фиксируются в CONTRACT.md до запуска исполнителей2–6; публичные старые маршруты/ответы сохраняются. Новый модуль/таблица под те же слова не создаётся.

### Параллельность и приёмка

Сейчас выполнены только исследования. Во время реализации один backend-исполнитель последовательно владеет общими service/issue/schema; frontend может работать параллельно после фиксации CONTRACT.md. iLogic отделяется только после согласования целевого входа. QA получает только критерии и нужные состояния; дизайнер — готовые заполненные входы и снимки, без повторного аудита сервера. Полные повторные прогоны — по datacore-verify, а не после каждой подписи.

## Экономия и роли

- Простые пункты координатор делает сам; субагенты получают самостоятельные задачи с ограниченными файлами.
- Рутинные задачи получает подходящая доступная быстрая модель; сложные решения и риски данных — более сильная.
- Выбор ограничен реально доступными моделями; недоступные Sonnet/Haiku/Opus не заявляются использованными.
- Проверяющие подключаются по классу и области изменения; один аудит не дублируется разными моделями.
- Полные отчёты и доказательства остаются в crew, в чат — краткий результат.

## Проверки и границы

- Перед изменением раздела: dc atlas, CANON, соответствующий PRODUCT; дополнительные документы — по задаче.
- После кода: datacore-verify; после интерфейса — datacore-design при применимости и UI-ACCEPTANCE.
- Перед выпуском: требуемые full/e2e и приёмка актуальной общей версии.
- Доступ к проду и стенду — только datacore-access. Запись данных прода требует отдельного разрешения.
- Постановка очереди не является поручением немедленно выкладывать изменения.
