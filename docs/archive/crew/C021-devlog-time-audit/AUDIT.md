# Аудит: «Ведение проекта» — учёт времени

Дата: 2026-11-04. Источник: код `devlog-calc.ts` / `devlog.service.ts` / `admin.js` + чтение прода (GET, без записи).

## Как собираются данные

1. При выкладке `release.sh` гоняет `scripts/devlog-import.js` → `POST /devlog/import`.
2. В базу идут коммиты git (hash, дата, subject, пути, footer эстафеты).
3. Сервер пересчитывает **сессии** (`rebuild` → `buildSessions`).
4. Ошибки — из `clienterrors` (без stack). Документы — из архива. Задачи — из импорта пунктов.

Секреты (`kppd_…`, password) маскируются. Ручные поля сессий при пересчёте не затираются.

## Как считаются часы

Правило в `devlog-calc.ts`:

- Коммиты с разрывом **меньше 2 часов** → одна сессия.
- Часы сессии = **(время последнего − первого коммита) + 0,5 ч**.
- Один коммит без соседей = **0,5 ч**.
- Место (дом/работа) — по большинству меток `🏠` / `🏢` в footer коммита.
- По разделам: часы сессии делятся **поровну** на её коммиты, потом суммируются по `area` / `prefix`.
- Галочка «с ручной правкой» подставляет `manualHours`, если вы ввели свои часы в таблице.

Это **оценка по коммитам**, не табель. На экране уже написано: погрешность ±30–40 %.

## Правильно ли?

**Логика кода согласована с решением Д-1** (QUESTIONS: оценка + ручная правка). Тесты в `devlog.spec.ts` покрывают разрыв 2 ч и +0,5.

Что **занижает** часы:

- День без коммитов (чтение, разбор, созвон) = 0.
- Долгая работа с **одним** коммитом в конце = всего 0,5 ч.
- Эстафета «работа закончена» без `🏠`/`🏢` → место пустое (на проде у многих сессий «—»).

Что **завышает** или искажает:

- Много мелких коммитов подряд растягивает сессию от первого до последнего (+0,5).
- Ночные коммиты (напр. 02:24) попадают в «день» по дате коммита, не по календарю «рабочего дня».
- Раздел «docs» большой — доля часов по area пропорциональна числу коммитов в сессии, не реальному времени на docs.

Вывод: для ответа «сколько примерно ушло на проект» — **годится**. Для зарплаты / точного табеля — **нет**; тогда нужны ваши часы в колонке «Ваши часы».
