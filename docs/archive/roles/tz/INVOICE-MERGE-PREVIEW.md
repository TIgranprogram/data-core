# ТЗ T25 — PWA: предпросмотр явного объединения счетов

> Основание: read-only аудит 2026-11-03. Backend уже предоставляет отдельный GET merge-preview; эта задача — только безопасная подача сценария в PWA.

**Зачем (словами пользователя):** при одинаковом номере менеджер должен осознанно выбрать существующий счёт и увидеть, какие позиции будут добавлены, до того как нажать объединение.

**Класс:** M · **Max agents:** 2 · **Reviewers:** qa ☑ architect ☐ designer ☑ · **Max review loops:** 2 · **Проверки:** smoke.
**Язык менеджера:** да — короткий список позиций, целевой номер/поставщик, понятный итог и явные кнопки «Добавить»/«Отмена» · **Приёмка:** посмотреть сценарий в карточке заявки на ширинах 390 и 1280 px.

## Shared pack

- Дубль номера не склеивается автоматически: PATCH/create отвечает 409 с `existingInvoiceId`; пользователь сам решает, добавить ли позиции в существующий счёт либо оставить отдельный с причиной.
- Backend contract: `GET /supply/invoices/:id/merge-preview?targetId=<id>` — read-only preview; подтверждение — `POST /supply/invoices/:id/merge` с выбранной стратегией (`append`, `mergeSameRequest`, `replaceLines`). Пользоваться точной схемой ответа текущего контроллера/сервиса; не менять контракт без отдельного решения.
- `append` — добавить заявки, не удалять/не заменять существующие строки. Никакого автоматического `POST /merge` при получении 409.
- Paid/received ограничения остаются backend-authoritative; UI обязан показывать отказ API и не обходить его.

## Что сделать

1. В PWA после 409 показать существующий счёт как выбор с номером, поставщиком и статусом; не отправлять merge-запрос автоматически.
2. До подтверждения запросить `GET merge-preview`; показать источник, целевой счёт и точный список перемещаемых/пропускаемых/заменяемых строк согласно фактическому DTO ответа.
3. Кнопка подтверждения делает ровно один явный `POST /merge` выбранной стратегией; «Отмена» не изменяет данные. Повтор после сетевой ошибки не должен повторно отправить POST без нового действия пользователя.
4. Оставить действующий путь «сохранить отдельный счёт с duplicateReason» доступным.
5. Проверить существующие общие modal/drawer примитивы и токены; не добавлять CSS-класс/паттерн без дизайн-ревью.

## Критерии приёмки (проверяет QA и дизайнер)

- [ ] Получение 409 само по себе не вызывает `POST /merge`.
- [ ] Пользователь видит preview и может отменить без изменений; подтверждение отправляет ровно выбранную стратегию и targetId.
- [ ] Сетевые/API ошибки показывают понятный retry, повторный запрос не мутирует данные до повторного подтверждения.
- [ ] Existing `duplicateReason` path и одиночное создание счёта остаются доступными; нет автосклейки.
- [ ] Smoke: PWA imports/syntax + соответствующие tests; ручной просмотр 390/1280 px; никакого e2e на production.

## Нельзя

- Автоматически объединять счета по номеру.
- Выполнять merge до показа preview и явного подтверждения.
- Ослаблять правила paid/received или менять backend contract.
