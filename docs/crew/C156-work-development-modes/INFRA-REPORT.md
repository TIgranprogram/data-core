# C156. Работа, разработка и проверка подключений

В разделе «Сайт» пульта доступны «Открыть рабочее приложение», «Запустить разработку» и «Проверить подключения». Рабочая кнопка использует фиксированный `https://kppdf-crm.ru/db/app/` через штатное открытие ссылки. Пульт открывает ссылки системным браузером на Windows, Linux и macOS. Генерируемая справка обновлена.

`node tools/work-modes.mjs start` проверяет локальный Docker и паспорт копии с портами 3102/27118. Существующую копию обновляет штатный `refresh` из текущей папки. Проверка владения требует существующих Mongo, backend и шлюза. Сохраняются Mongo и uploads. Если запуска ещё нет, штатный `up` проверяет порты, пустой Docker project и локальный архив перед созданием новой копии. Общее исключительное владение защищает операции ручного запуска, пересборки, замены и остановки. После сборки CLI проверяет локальный API и точное совпадение метаданных запущенного приложения. При сбое выводит локальную ошибку. Для проверки без запуска браузера поддерживается `start --no-open`.

`tools/night/compose.yml` подключает `development.json` из игнорируемой Git папки конкретного запуска как bind только для чтения. Дата снимка берётся из имени архива, время восстановления — из паспорта, время сборки записывается после готовности backend. Неизвестные даты остаются `null`. В метаданные входят фиксированный loopback-origin, сведения о снимке и Git-версия на момент сборки. Перед открытием CLI читает `/app/development.json` на loopback без кэша и переходов и сверяет весь JSON с ожидаемыми метаданными этого запуска.

`node tools/work-modes.mjs check` отдельно проверяет публичный `version.json` сайта и готовность рабочего API через `GET /db/api/health/ready` на том же адресе без авторизации, кэша и перенаправлений. Если API недоступен при доступном `version.json`, результат проверки — код 1. Команда читает локальные статусы Docker и копии, Git-ветку, изменения и последнее локальное состояние tracking. Связь с origin проверяет `git ls-remote`. Коммиты сайта сравниваются отдельно с историей PWA и серверных файлов по путям выпуска. Расхождение версий и наличие правок сами по себе не меняют код результата. Источник копии в запущенном стенде и последний локальный архив показаны отдельно. Путь к архивам согласован между пультом и запуском (`DC_BACKUPS`, `DATACORE_BACKUPS`, штатная папка ОС).

Пульт разрешает автоматическое подтягивание Git после успешной проверки локального Docker, только если по списку контейнеров отсутствуют запущенные обычный, legacy и owned backend. Это действует и при отсутствии локального указателя стенда. Неопределённый результат проверки приостанавливает автоподтягивание. Ручные Git-кнопки работают по прежним правилам.

## Проверка

- 122 теста инструментов и пульта прошли, включая 11 тестов C156. Тесты HTTP-сервера пульта использовали временные loopback-порты с разрешённым доступом. Проверены отказ при production URI и чужих томах, сохранение прежнего Mongo/uploads при refresh, замок ручных операций, отсутствие открытия при сбое ready или метаданных, read-only диагностика и отрицательные сценарии авто-pull.
- На заглушках `version.json` с HTTP 200 и рабочим API с HTTP 503 проверка возвращает код 1. Состояние запущенной разработки в этом случае выводится отдельно.
- Пункт «Все локальные проверки» включает `tools/work-modes.test.mjs` и `tools/night-uploads.test.mjs`. Генерация справки и `git diff --check` прошли.
- Координатор запустил `start --no-open` поверх существующего 3102 и проверил подключения. После усиления проверки отдельный HTTP GET подтвердил совпадение фактически выдаваемого `development.json` с ожидаемым файлом того же запуска. Дополнительная пересборка для этой проверки не понадобилась.
- Физический второй компьютер с Ubuntu в этом задании не использовался. Автоматические тесты покрывают допустимые форматы Windows-канала и Unix-сокета Docker.
