# ТЗ CONTROL-CENTER — «Разбор», ночные прогоны, дашборд, команда `dc`

> Основа: аудит `docs/audit/AUDIT-CONTROL-CENTER.md`, совет архитектора (opus) 2026-10-30. Поведение Mongo 4.4 проверять на стенде.
> Два сервера — отдельное ТЗ `docs/roles/tz/HA-TWO-SERVERS.md`.

**Зачем (словами пользователя):** «полный список вопросов, которые решает человек», «не должно быть висячих вопросов», «запустил одной командой, дальше всё автоматически», «по датам фильтровать и видеть, каким был сайт год назад».

**Класс:** XL · **Max agents:** 5 на этап · **Reviewers:** qa ☑ architect ☑ designer ☑ · **Max review loops:** 2 · **Проверки:** full
**Язык менеджера:** да — без служебных кодов, в каждом вопросе «что случилось + что сделать + совет».

## Решения координатора (приняты, менять только с причиной)
1. Кнопка на проде вызывает только готовое действие из реестра сервера, после предпросмотра. Скрипты с веб-процесса не запускаются.
2. Правая панель в админке разрешена. `DESIGN.md:289` и `PRODUCT.md:68,71` обновить вместе с первым экраном.
3. Хранение: дневные точки 400 дней, месячные — всегда; логи прогонов 90 дней, провалы 1 год.
4. ИИ-скрипты ставят вопросы только с ПК, отдельным ключом с правом «добавить вопрос». На VM — скрипты без ИИ.
5. Тяжёлый прогон — на домашнем ПК. Рабочий ПК — после проверки: Docker, Edge, копия бэкапа.
6. Ночные прогоны на серверах включаются после того, как отладятся на ПК. Сначала — только ПК.
7. Видеокарта и локальная модель в прогонах не нужны (память `no-local-llm`).

## Shared pack

### Коллекции (без soft-delete и плагина аудита, как `clienterrors`; запись метрик — через raw driver)
| Коллекция | Назначение | Срок |
|--|--|--|
| `app_control_questions` | вопросы | всегда |
| `app_control_events` | журнал: кто, что, до/после | всегда, строк мало |
| `app_control_undo` | снимки «до» для отката | TTL 90 дней |
| `app_control_jobs` | заявки хост-бегуну (этап 5) | TTL 90 дней |
| `app_control_runs` | прогоны: шаги, коды, мс, коммит, `node` | TTL 90 дней; провалы — `keepUntil` 1 год |
| `app_control_daily` | `_id` = дата, `m:{key:число}`, `schemaV`; `null` ≠ 0 | 400 дней |
| `app_control_monthly` | `_id` = месяц; min/max/avg/last/n | всегда |

### Вопрос: поля
`key, active, type, source{kind,name,runId}, severity, subject{kind,ids}, what, need, advice, options[{code,label,actionId,params,risk}], evidenceHash, seen{first,last,count}, status, dueAt, snoozeUntil, decision{by,at,option,comment}, exec{state,opId,leaseUntil,attempts,error,undoId}, closeReason`.

- `key = sha1(type + subject.kind + отсортированные ids + версия правила)`.
- Уникальный частичный индекс `{key:1}` при `active:true`. `$in` в частичном индексе 4.4 нельзя, поэтому нужен флаг `active`.
- Повтор вопроса — только `count++` и `seen.last`.
- «Не проблема» запоминает `evidenceHash`. Вопрос вернётся, только если изменились данные.

### Реестры в коде
- Тип: `{type, recheck(), options, roles, dueDays}`. Без `recheck` тип не регистрируется.
- Действие: `{id, paramsSchema, roles, risk, preview(), execute(params, opId), undo?}`.
- Кнопка шлёт только `questionId + optionCode`. Параметры сервер берёт из своей записи, не от клиента.
- ИИ выбирает только разрешённый `actionId`. Его текст выводится через `textContent`.

### Жизненный цикл
`open → preview → executing → done`. Другие исходы: `failed`, `waiting_agent`, `snoozed`, `dismissed`, `resolved_auto`, `expired`.

**Правила «нет висячих»:**
1. У каждого вопроса есть «Не проблема» и «Отложить до даты» (не больше 2 раз).
2. `recheck` идёт ночью и перед исполнением. Проблемы нет — `resolved_auto`.
3. Срок вышел — важность выше, вопрос наверху. Сам истекает только `source=ai` без данных, 30 дней.
4. Сбой действия: статус `failed`, понятный текст, запись в журнал. Повтор только руками.
5. `executing` с истёкшим `leaseUntil` → `recheck` → `done` или `failed`. `opId` защищает от двойного исполнения.
6. Нажать нечего: текстовый ответ или `waiting_agent` с таймером 7 дней; не сделано — возврат человеку.

**Предпросмотр.** Сервер считает «что изменится» и хеш плана. При исполнении план строится заново. Хеш другой — показать заново.

**Откат.** Снимок затронутых документов. `undo` отказывает, если их меняли после действия. Необратимое подписано красным.

**Лимиты.** `POST /control/questions`: 20 новых в сутки на источник, 200 открытых всего. Сверх лимита — один сводный вопрос. Похожие — групповой вопрос.

### Команда `dc`
`tools/dc.mjs` без зависимостей: `dc start | check | errors | data | stand | night | status | logs | stop`.
- Итог короткий; полный лог — в файл. Запись на прод и выкладка не входят в `dc`.
- Вход на прод — через `deploy/synology/api.sh`; пароль не выводится.
- Ночной прогон — отдельный git worktree на `origin/main`; рабочая папка не трогается.
- Свой compose-проект `dcnight`, порты 3102 и 27118, БД с именем `*-night`. Жёсткая проверка: никогда `datacore`.
- Lock-файл `{host,pid,start}` с проверкой протухания. Второй экземпляр не запускается.
- `setup.cmd` запускается один раз от администратора: Docker, задания планировщика Windows, проверка компьютера.

### Ночь на VM (после отладки на ПК)
- cron хоста шагами, `nice/ionice`, каждый шаг ≤ 5 мин. VM: 1 ядро, 5,8 ГБ.
- Не стартовать 02:50–03:40 и 04:20–05:00: бэкап и копии вне дома.
- Шаг обращается к API служебным ключом. Логин лимитирован 20/ч. Доступ ключа к `/health/*` проверить в этапе 1.

### Показатели (37; каталог — в коде)
- **Доступность:** % аптайма, минуты простоя, рестарты backend, версия, выкладки/откаты.
- **Скорость:** p50/p95 API, запросов > 1 с, p95 экрана PWA.
- **Ошибки:** всего, новых сигнатур, unhandled, 5xx.
- **Данные:** итог fill-audit, топ-группа, нарушения integrity, дубли контрагентов и справочников, файлы без ссылки, ссылки без файла.
- **Бизнес:** открытые и просроченные заявки, активные заказы, движения склада, активные пользователи, выпущенные паспорта, просроченные платежи.
- **Хранение:** % диска, размер БД, uploads, бэкапов, `auditlogs`, окно oplog.
- **Копии:** возраст локальной, возраст вне дома, дней с учебного восстановления и его итог.
- **Код:** тесты, провалы, длительность, e2e, экраны qa-smoke, eslint + design-lint, файлы > 400 строк, уязвимости high.
- **Контроль:** открытые вопросы, медианный возраст, просроченные, сбои кнопок.
- **Два сервера (после HA):** доступность, ответ, диск, CPU/RAM, макс. лаг, переключения, откаты записей, недоехавшие фото, бэкапы, качество канала. Экран сравнения — рядом, по каждому узлу.

Снимок дня — в 23:30, пока TTL `clienterrors` не стёр исходник. `disk_usage_history` влить в daily. Экран читает только `daily/monthly`. Свёртка идемпотентна; день стирается после проверки месяца. Объём ≈ 2 КБ/день.

## Критерии приёмки
- [ ] Одна команда на чистом ПК поднимает всё; повторный запуск ничего не ломает.
- [ ] Прогон не трогает `datacore`, рабочую папку и порты 3001/3002.
- [ ] Любой вопрос можно закрыть с экрана. Ни один исход не оставляет вопрос без кнопки.
- [ ] Повтор проблемы не создаёт второй вопрос. Двойное нажатие не исполняет действие дважды.
- [ ] Страницы сайта не медленнее базовой линии: новые записи не идут на каждый запрос.
- [ ] Данные за прошлые месяцы показываются после чистки дневных точек.
